# src/modules/payments/

## Purpose

The payments module owns the full lifecycle of an order's money: creating provider payment intents, confirming charges, processing webhooks and disputes, issuing and settling refunds, and supporting offline (bank-transfer) payments. It is a supporting subdomain in the *shop* group, sitting behind a provider port so that no concrete PSP code is baked into the codebase.

## Key parts

- **Domain layer (`domain/`)** — Pure, framework-free business rules. `lifecycle.ts` defines the status-set membership guards that double as concurrency predicates in the repository; `disputes.ts` encodes the invariants of buyer-initiated disputes (chargeback ≠ refund); `transfer-reference.ts` mints/validates ISO 11649 bank-transfer references; `display-status.ts` maps internal status to the Shopify-facing financial label.
- **Provider port (`providers/`)** — `index.ts` is the single interface every real PSP must implement; `registry.ts` is the process-wide registration point so test doubles can substitute at preload; `errors.ts` isolates the throwables an adapter may raise without creating a circular import.
- **Controllers (`controllers/`)** — One thin HTTP handler per endpoint (intent, confirm, sync, webhook, refund create/settle/cancel, search, attention, methods, order-scoped reads/writes). All business logic lives in the service layer; controllers parse, delegate, and shape the response.
- **Service & settlement layer** — Orchestrates the provider-confirmed choreography (`settlement.ts` referenced throughout), the read-model presenter, and the "attention" sweep that surfaces stale refunds, uncommitted stock, and pending order refunds.
- **Model & config** — `model.ts` is the Mongoose schema (one document per order, embedded refund/dispute sub-docs); `config.ts` centralises every deployment-tuned value (bank details, offered methods, signing secrets, grace windows) in a single `defineConfig` instance.
- **Contracts & manifests** — `openapi.yaml` (public REST API), `asyncapi.webhooks.yaml` (the seven `payment.*` webhook channels, merged by the contract bundler), `authorization.yaml` (fine-grained action/subject rules and named rule-sets), `module.yaml` / `module.ts` (kernel mount manifest: routes, jobs, listeners, rate-limit budgets, personal-data hooks).
- **Cross-cutting declarations** — `events.ts` (domain-event payload types via module augmentation), `analytics.ts` (type-safe event names), `audit.ts` (decision vs. settlement audit strings), `metrics.ts` (Prometheus counters), `emails.ts` (five customer-facing email templates), `jobs.ts` (abandoned-attempt reaper, effect-retry sweep).
- **Presentation & routing** — `presenter.ts` is the single transform from `PaymentDocument` → wire contract (payer view vs. staff view); `order-routes.ts` mounts the two order-scoped payment endpoints as a sub-router.

## How it connects

- **`src/modules/orders/`** — The payment document is 1:1 with an order (unique index on `orderId`). Order-scoped routes (`GET/POST /orders/:id/payments`) are mounted via `order-routes.ts`. The attention sweep checks whether an order still owes its refund, and dispute rules constrain what can be done to the payment while a chargeback is open.
- **`src/modules/inventory/`** — The "attention" payload surfaces payments that still owe their stock commit, tying payment settlement back to inventory release.
- **`src/modules/invoicing/`** — Refund and dispute handling intersects with credit-note generation; the disputes domain explicitly notes that a chargeback "never issues a credit note," leaving that to the invoicing module.
- **`src/modules/returns/`** — Refunds in this module are the monetary counterpart to a return initiated elsewhere; admin-initiated refunds operate on the payment without altering the order status, keeping the two subdomains decoupled.
- **`src/modules/cart/` / `src/modules/products/`** — Payment intent creation depends on the cart's line items and products for amount freezing; the public `GET /payments/methods` endpoint lets a guest discover checkout options before any account or cart state exists.
- **`src/modules/account/` / `src/modules/users/`** — Authorization rules in `authorization.yaml` bind actions to subjects at tenant scope; personal-data lifecycle hooks declared in `module.ts` integrate with the account module's export surface.
- **`src/infrastructure/`** — The audit map, analytics port, and mailer adapter all live here. The payments module registers its audit strings, event names, and email templates into those shared ports without importing concrete implementations.
- **`src/modules/shop-tasks/`** — The two scheduled jobs (abandoned-attempt reaper, effect-retry sweep) declared in `jobs.ts` are executed by the shared job runner.

## Where to start

1. **`domain/lifecycle.ts`** — Read this first to understand the six-plus payment/refund states and the membership guards that control every legal transition. Every other file in the module (repository writes, webhook handlers, refund endpoints) ultimately calls into these sets, so grasping them makes the rest of the code read naturally.
2. **`providers/index.ts`** — Next, read the provider port to see the complete contract a PSP must satisfy (create intent, confirm, capture, refund, fetch status, verify webhook). Because the boilerplate ships zero real provider code, this file is the cleanest single place to understand *what* the module expects of the outside world before diving into any specific adapter.

## Files
- `src/modules/payments/analytics.ts` — Declares the analytics event names for the payments module and registers them with the analytics port's `AnalyticsEventMap` via TypeScript module augmentation. Importing this file gives any caller type-safe event names (a typo fails at compile time) without pulling in a published copy.
- `src/modules/payments/asyncapi.webhooks.yaml` — AsyncAPI **fragment** (not a standalone document) that declares the seven `payment.*` webhook channels, their send operations, and the message/payload schemas the payments module publishes. It is merged into the top-level `webhooks/asyncapi.yaml` by the contract bundler and is only visible in `GET /webhooks/events` while the payments module is registered.
- `src/modules/payments/audit.ts` — Declares the audit-action strings emitted by the payments module and registers them in the infrastructure audit map via TypeScript declaration merging. It is the single source of truth for every payment-related audit event, separating "decision" events (refund requested) from "settlement" events (refund settled, refund canceled) and marking admin-only actions with an `admin.` prefix.
- `src/modules/payments/authorization.yaml` — Declares the fine-grained authorization rules and named rule-sets for the payments module. Each rule binds an action (`read`, `display`, `create`) to a subject (`Payment`, `Refund`) at tenant scope, and the `sets` block groups individual rules into reusable permissions that an identity or role can be granted.
- `src/modules/payments/config.ts` — Centralised, per-call configuration for the payments module. Declares every deployment-tuned value related to money — bank-transfer account details, the set of offered payment methods, webhook signing secrets, and the grace windows that drive background effect sweeps — in a single `defineConfig` instance so no other file transcribes its own fallback copy.
- `src/modules/payments/controllers/get-order-payments.ts` — Handler for `GET /orders/:id/payments`. Returns the payment records (intents and their statuses) for a given order so the order-page payment panel can rehydrate on load. An order with no payment started returns `{ items: [] }`; a 404 is returned only when the caller cannot see the order (authorization failure), not when the order simply has no payments.
- `src/modules/payments/controllers/get-payment-attention.ts` — Thin Express controller that handles `GET /payments/attention`. It delegates entirely to `paymentService.listAttention()` and forwards the result (or error) to the HTTP response. The "attention" payload surfaces items still needing human action: stale and hand-owed refunds, payments owing their stock commit, and orders owing their refund.
- `src/modules/payments/controllers/get-payment-methods.ts` — Express handler for `GET /payments/methods`. It returns the shop's available payment methods in a standard success envelope. The endpoint is intentionally public (no auth) so that a guest can discover checkout options before creating an account.
- `src/modules/payments/controllers/get-payment.ts` — HTTP handler for `GET /payments/:id`. Resolves a single payment by its ID and returns it as a JSON response. It exists as the destination target for the `Location` header set after a successful `POST /payments` and for operator-refund redirects that send a client back to read the payment they just interacted with.
- `src/modules/payments/controllers/get-payments.ts` — Single controller that serves both `GET /payments` and `POST /payments/search` (the staff payments list). It defines a query-string-aware Zod schema on top of the generated API body schema and delegates the actual lookup to `paymentService.listPayments`, using the shared `createSearchController` factory to wire up parsing, validation, and response shaping in one place.
- `src/modules/payments/controllers/get-refund.ts` — Handler for `GET /payments/:id/refunds/:refundId`. Returns a single refund record addressed through its parent payment (the read counterpart to `POST /payments/:id/refunds`). Delegates all data access to the payment service and translates the result into an HTTP response.
- `src/modules/payments/controllers/get-refunds.ts` — HTTP controller for `GET /payments/refunds`. It validates query-string parameters (pagination + optional filters) and delegates to `paymentService.listRefunds`, returning one row per refund for the Refunds tab in the UI.
- `src/modules/payments/controllers/post-order-payment.ts` — HTTP handler for `POST /orders/:id/payments`. Records an offline payment (money that never passed through the card provider) against an existing order. The permission gate (`create:Payment`, admin-only) is enforced at the route level, not here.
- `src/modules/payments/controllers/post-payment-confirm.ts` — Handles `POST /payments/:id/confirm` — the step where the browser hands over the tokenised payment method and the service fires the actual charge events. It normalises three distinct outcomes (succeeded, declined, in-flight) into appropriate HTTP responses and records a Prometheus counter for each.
- `src/modules/payments/controllers/post-payment-refund-cancel.ts` — Controller handler for `POST /payments/:id/refunds/:refundId/cancel`. It lets staff void a refund before it can be paid out. The handler extracts route IDs and the request body, delegates the cancellation to the payment service, and returns the voided refund object.
- `src/modules/payments/controllers/post-payment-refund-settle.ts` — Express controller for `POST /payments/:id/refunds/:refundId/settle`. It lets an operator confirm that a refund's funds have been returned outside the application, then responds with the settled refund object. The handler validates both path IDs, delegates to the payment service, and formats the success or error response.
- `src/modules/payments/controllers/post-payment-refund.ts` — Handler for `POST /payments/:id/refunds`. Processes a standalone (admin-initiated) full or partial refund on a payment without altering the associated order's status. Returns **201** with the new `Refund` record and a `Location` header identifying it.
- `src/modules/payments/controllers/post-payment-sync.ts` — Controller handler for `POST /payments/:id/sync`. When the browser signals it has finished a provider-side flow (3-D Secure challenge, wallet sheet), this endpoint re-reads the provider's own payment record and applies it, making the happy path *feel* synchronous to the user while the webhook remains the authoritative settlement mechanism. The operation is idempotent: a payment that is already settled responds without contacting the provider again.
- `src/modules/payments/controllers/post-payment-webhook.ts` — Handles `POST /payments/webhook/:provider`. It receives payment-status callbacks from external providers, verifies the signature (delegated to the provider adapter), and hands the parsed event to the payment service for a single idempotent apply. It deliberately uses no session authentication; the raw-body signature is the sole credential.
- `src/modules/payments/controllers/post-payment.ts` — Thin HTTP controller for `POST /payments`. It validates the request body, delegates intent creation to the payment service, and returns the provider's `clientSecret` to the client. Business logic (ownership checks, `pending` gate, amount freezing) lives entirely in the service; no audit or analytics events fire here because a payment intent is a preparatory step, not a business event—those are emitted on confirm.
- `src/modules/payments/domain/display-status.ts` — Derives the Shopify `displayFinancialStatus` label for a payment from its stored status and refund records, and provides the inverse: a Mongo query that selects payments by that label. The label function and the filter are written side-by-side in this file because they must stay in agreement — the integration suite verifies every label both ways.
- `src/modules/payments/domain/disputes.ts` — Pure domain rules that determine what a shop may still do with a payment while a buyer-initiated dispute (inquiry or chargeback) stands. The file performs no I/O and produces no side effects; it only classifies dispute state and computes the monetary ceiling the bank has already taken. A key semantic distinction it enforces: a chargeback is **not** a refund — it lowers `charged`, never `refunded`, and never issues a credit note.
- `src/modules/payments/domain/index.ts` — Barrel file for the payments domain layer. It re-exports every public symbol from four sibling modules (`lifecycle`, `disputes`, `transfer-reference`, `display-status`) so consumers import from a single path. The domain layer is deliberately framework-free (no Express, Mongoose, or tier dependencies)—enforced by lint rules—and exists as a folder because the status vocabulary (6+ states) exceeds the project's threshold for a scattered-constant approach.
- `src/modules/payments/domain/lifecycle.ts` — Defines the status sets and guard predicates that control which payment and refund transitions are legal. Every exported array is read both as a membership test and as the `$in` operand of the conditional writes in `repository.ts` (`updateStatusIfIn` / `upsertConfirmable`), so the sets *are* the concurrency guard. There is no explicit from→to graph: all transitions funnel through `settlePayment`, which decides the landing status; these sets only answer "may I still move this payment/refund."
- `src/modules/payments/domain/transfer-reference.ts` — Implements ISO 11649 "RF" creditor-reference generation and validation for `bank_transfer` payments. A deterministic reference is minted from the order's ObjectId when the transfer opens; admins later paste the reference back from their bank's website, and this module verifies the Mod-97 check digits before any lookup proceeds.
- `src/modules/payments/emails.ts` — Pure email-builder functions for the five customer-facing messages the payments module sends: payment received, refund issued, refund undeliverable, bank-transfer instructions, and transfer deadline expired. Each function takes a locale plus domain data and returns a fully translated `EmailContent` object whose `template` field the mailer adapter interpolates — the same "language is an argument, output is finished text" convention as `@modules/orders/emails` and `@modules/account/emails`.
- `src/modules/payments/events.ts` — Declares the payments module's domain event payload types by augmenting the kernel's `DomainEventMap` (TypeScript module augmentation in `@kernel/events`), and exports a string constant for each event name. It is the single source of truth for what data each payment event carries, decoupled from where and how the events are emitted.
- `src/modules/payments/globals.d.ts` — Augments Express's `Request` interface with a payments-specific flag (`paymentConfirmDeclined`) via TypeScript declaration merging. It exists here — rather than in infrastructure's global `globals.d.ts` — because the architecture rule (`docs/theory/layers.md`) forbids that file from naming a module, so module-local augmentations live in the owning module.
- `src/modules/payments/index.ts` — Public barrel (barrel export) for the payments module. It is the **only** import surface that sibling modules are permitted to use, enforcing the strategic-DDD rule documented in `docs/theory/strategic-ddd.md` §5. Internals such as `paymentRepository` and the model's runtime stay hidden; all writes are routed through the provider-confirmed choreography in `services/settlement.ts` rather than exposed as direct document writes.
- `src/modules/payments/jobs.ts` — Declares the two scheduled jobs owned by the `payments` module: the abandoned-attempt reaper and the effect-retry sweep. Each entry is a `JobDeclaration` that binds a pre-generated job descriptor (from `jobs.generated`) to the concrete service function(s) that perform the work.
- `src/modules/payments/metrics.ts` — Defines the two Prometheus counters owned by the payments domain: one for confirmation-attempt outcomes and one for settlement mismatches. Counters live here (in the module) rather than in `infrastructure` so the domain owns its own metrics; the module overview endpoint reads them without importing this file directly.
- `src/modules/payments/model.ts` — Defines the Mongoose schema and TypeScript document interfaces for the payment collection — one document per order (enforced by a unique index on `orderId`). It is the single source of truth for the payment's shape: status lifecycle, embedded refund and dispute sub-documents, and the serialization/typing contracts that every other file in the module reads from or writes to.
- `src/modules/payments/module.ts` — The payments module's manifest entry. It declares everything the kernel needs to mount, subscribe, and expose the payments domain: HTTP routes, background jobs, public webhook event mappings, rate-limit budgets, personal-data lifecycle hooks, and domain-event listeners. It exists so the app tier can discover the module generically via the registry rather than importing each piece individually.
- `src/modules/payments/module.yaml` — Module declaration for the **payments** supporting subdomain (group: *shop*). It registers the module's cross-module dependencies, its rate-limit budgets, and its scheduled background jobs, so the runtime can wire up payment handling ("an order's money, behind a provider port") without hard-coding those concerns into handler code.
- `src/modules/payments/openapi.yaml` — OpenAPI 3.1.0 contract for the **payments** module. It declares the module's public API surface (endpoints, schemas, error codes, and personal-data export shape) so the runtime bundler can register routes, validate requests, and generate client SDKs from a single source of truth.
- `src/modules/payments/order-routes.ts` — Express router that wires the two payment routes living under an order path (`GET /orders/:id/payments` and `POST /orders/:id/payments`). It exists so that payment operations scoped to a specific order can be mounted as a sub-router by the payments module, keeping URL hierarchy (Solidus-style nested resource) separate from the module's top-level payment routes.
- `src/modules/payments/presenter.ts` — Single transformation point from the stored `PaymentDocument` to the `Payment` wire contract. Every write endpoint (confirm, offline, refund, sync, intent) returns the result of `presentPayment` alone; `services/view.ts` layers `actions` on top for reads. Encodes the two-audience split: the default payer view and a staff view that re-exposes provider IDs and refund failure reasons the serializer always strips.
- `src/modules/payments/providers/errors.ts` — Defines the error types that payment provider implementations can throw. Split out of `providers/index.ts` so that an adapter (real or fake) can import and throw these errors without pulling in the port interface file, which itself imports the config and the registry the implementation is registered in — avoiding a circular dependency.
- `src/modules/payments/providers/index.ts` — This file is the **payment provider port** — the single interface a real PSP (Stripe, Adyen, …) must implement, plus every supporting type the rest of the payments module consumes. It exists so that no concrete provider is shipped: the boilerplate contains zero card-payment code, and a live project plugs in by adding one adapter file and one `registerPaymentProvider` call. The file is the canonical place to see *what a provider must answer*, without reading any specific adapter.
- `src/modules/payments/providers/registry.ts` — Provides a single, process-wide registry of payment provider implementations. It exists as an isolated module (importing only the registry helper and a type) so that test doubles can register themselves at preload without pulling in the full provider stack (config, orders, etc.) that `./index` would otherwise load.
- `src/modules/payments/providers/webhook-signature.ts` — Implements the shared HMAC-SHA256 signature scheme for PSP webhook deliveries. It provides both the **verify** half (production: check an inbound header against the raw body) and the **sign** half (tests and demo: mint a valid header so a delivery can be exercised end-to-end). Lives in its own file because the two halves are consumed in different places and because a real provider's native verifier (e.g. `stripe.webhooks.constructEvent`) replaces the verify half while this file stays as the canonical reference for the required discipline.
- `src/modules/payments/rate-limits.ts` — Declares and exports the five rate-limit budgets that protect the payments module's HTTP surface — the unauthenticated webhook route, the authenticated confirm/intent/sync routes — and wires a conditional human-challenge gate on top of the two decline budgets. Each budget is plain `RateLimitBudget` data (sourced from `rate-limits.generated`) converted to an Express middleware via the shared `buildRateLimiter` factory.
- `src/modules/payments/repository.ts` — Repository layer for the Payments domain. Wraps `paymentModel` (Mongoose) into a `Repository` built via the shared factory, and adds the specific guarded writes and lookups that payment flows actually need: intent/offline upserts keyed on `orderId`, dispute recording, refund-row searches, and a paginated staff list. The `unique` index on `orderId` makes "one payment per order" a database invariant, so upserts are a single `findOneAndUpdate` with no preceding read.
- `src/modules/payments/routes.ts` — Defines the Express router and route table for all payment operations (intent creation, confirmation, sync, webhook, refund lifecycle, and read-back). It centralises the security layering — authentication, permission checks, fresh-session enforcement, rate limiting, and idempotency — in one place so that individual controllers stay focused on domain logic.
- `src/modules/payments/services/announce.ts` — Moves a payment to `declined` and emits a `PAYMENT_FAILED` event in a single transactional unit, so a decline that commits is always announced and one that loses a race is never. This is the announce side of the payment lifecycle; `PAYMENT_SUCCEEDED` is handled separately by `settlement.ts`.
- `src/modules/payments/services/deadline.ts` — Provides the single service-level lookup for a refund's legal processing deadline. `tasks` calls it to date the work item it opens; when the law imposes no deadline (or the record is missing) it resolves to `undefined`, letting the caller choose its own timing.
- `src/modules/payments/services/disputes.ts` — Handles provider-side dispute reports arriving via webhook delivery. It stores the dispute state on the payment, appends staff-timeline rows to the order, and announces a domain event — all within a single Mongoose transaction. A dispute here is explicitly **not** a refund: it never modifies `amountRefunded`, order status, or credit notes.
- `src/modules/payments/services/effects.ts` — Provides two scheduled sweep operations that finish work a settlement left outstanding: retrying refunds the provider refused or never answered, and reconciling payments whose provider decided without delivering a webhook. Both sweeps share a sequential, batch-capped skeleton and return a count of items actually settled.
- `src/modules/payments/services/errors.ts` — Central collection of standardized HTTP error responses (409 / 404) and one domain error class for the payments service layer. It is a deliberate leaf module — no persistence or cross-module imports beyond infrastructure — so every file under `services/` can pull an error constant without introducing new dependency edges.
- `src/modules/payments/services/external-refunds.ts` — Handles refunds created outside the application (i.e., in the payment provider's own dashboard). When a refund event arrives, this module fetches the provider's refund list, distinguishes refunds already tracked locally from unknown ones, carries provider state onto existing records, and **imports** unknown succeeded refunds as settled records so that credit notes, buyer emails, and order stamps fire exactly as they would for an in-app refund.
- `src/modules/payments/services/index.ts` — Barrel file that assembles every payment-flow function from the sibling modules (`intent`, `settlement`, `refunds`, `effects`, `offline`, `transfer`, `notify`, `scope`, `view`, `retention`, `list`, `stats`, `deadline`) into a single `paymentService` handle. It exists so callers import one name instead of reaching into a dozen sub-files, and so the module's public surface is explicitly curated — internal choreography functions are deliberately left out.
- `src/modules/payments/services/intent.ts` — Entry point into the payments module's money-moving flow: creates (or refreshes) a payment intent at the provider for a given order, and provides the cancel counterpart. Every call that opens, resumes, or closes a provider-side intent flows through this file.
- `src/modules/payments/services/list.ts` — Staff-facing read endpoints for the Payments page: a paginated payment list, a paginated refund list, and a "needs-attention" feed. All three return `display:Payment`-shaped rows (each carries provider IDs). The file exists so the UI never touches the repository or domain logic directly — it composes pagination, order enrichment, canonical-reference parsing, and attention classification in one place.
- `src/modules/payments/services/notify.ts` — Buyer-facing email notifications for the payments module. Defines five mail functions that fire on payment lifecycle events (succeeded, refunded, refund undeliverable) or are called inline for bank-transfer specifics (instructions, expired). The core guarantee: a failed mail never undoes a money movement — every listener logs and swallows errors.
- `src/modules/payments/services/offline.ts` — Records a payment that arrived outside the card provider (cash, bank transfer, phone-order payment) and settles it through the same `settlePayment` path every card payment uses — order moves `pending → paid`, stock commits, and the standard events fire. It exists so that non-card money flows through identical domain logic rather than a parallel settlement branch.
- `src/modules/payments/services/refund-settlement.ts` — Shared settlement logic for refund records that reaches a terminal state: either the provider confirms the refund (status → `succeeded`, order stamped, `payment.refunded` outbox row committed) or the provider refuses it (status → `failed`, attempt counted). Split out of `refunds.ts` so that the provider-side sync flow (`./refund-sync.ts`) and the operator-driven send flow (`./refunds.ts`) can both call these functions without importing each other.
- `src/modules/payments/services/refund-sync.ts` — Bridges the provider's side of a refund to the local record. When a refund is still `pending`, a sweep re-reads the provider for a final status; when a webhook lists a refund (`external-refunds.ts`), the provider's report is applied here. The provider's own status is the sole authority — the delivery body itself changes nothing.
- `src/modules/payments/services/refunds.ts` — Implements the two entry points for returning money on a payment — the operator action `refundPayment` and the automatic `refundForOrder` (triggered by `order.canceled`) — both delegating to a shared `performRefund`. This file owns the full refund lifecycle: opening the record, calling the PSP, and settling the outcome. No other file in the payments module is permitted to move money out.
- `src/modules/payments/services/retention.ts` — Handles the post-movement lifecycle of payment records: detaching a user's ID during account erasure, producing an account's own payment data for export, and sweeping (deleting) abandoned payment attempts that never succeeded. It does not create, charge, or settle payments — it manages what happens to the row after the money event.
- `src/modules/payments/services/scope.ts` — Defines the four row-scope predicates every other payment service calls before reading or writing the `Payment` collection. It centralises the distinction between *read* scope (role-driven, may span all records) and *payer/buyer* scope (strictly the caller's own records), so that money-moving operations never inherit a broad `display:*` grant.
- `src/modules/payments/services/settlement.ts` — The single reconciliation point for all payment settlement. Whether the signal arrives via a browser-driven confirm/sync poll or a provider webhook, both paths funnel into this module so that money is settled exactly once. It detects provider-reported mismatches, performs the atomic `succeeded` write plus order state transition, and opens the refund path when the order can no longer accept the payment.
- `src/modules/payments/services/stats.ts` — Computes the payments "mix" for reporting: how much money came in, grouped by payment method, provider, and currency. It wraps the raw repository aggregation into a clean, typed result suitable for display or further processing.
- `src/modules/payments/services/transfer.ts` — Handles the payment-creation step for bank-transfer orders. When an order is placed with `paymentMethod: 'bank_transfer'`, this module opens a `requires_action` payment row (carrying the reference, deadline, and instructions) and mails the transfer instructions to the buyer. It exists so that the transfer payment is tied to the order lifecycle (`order.created`) rather than being created lazily at settlement time.
- `src/modules/payments/services/view.ts` — Read-only (GET) views for payments: fetch a payment by order, by id, or its refunds, and attach the `actions` block that tells the caller which follow-up mutations (pay, sync, refund, settleByHand, cancelRefund) are available to them. The `actions` shape intentionally mirrors the one `orders` publishes on `OrderActions`.
