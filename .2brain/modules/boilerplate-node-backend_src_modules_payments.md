# src/modules/payments/

## Purpose

The payments module owns the full payment lifecycle for the shop: creating provider-backed payment intents, confirming and settling them, issuing and settling refunds, tracking disputes, minting bank-transfer references, and surfacing payment status to both buyers and staff. It exposes an HTTP API, emits domain events, runs scheduled background jobs, and defines the provider-adapter port that a live PSP plugs into.

## Key parts

- **Domain layer (`domain/`)** — Pure, framework-free rules: payment/refund status transitions and concurrency guards (`lifecycle.ts`), dispute predicates (`disputes.ts`), display-label computation and its inverse query (`display-status.ts`), and ISO 11649 bank-transfer reference minting (`transfer-reference.ts`). Re-exported through `domain/index.ts`.
- **Data & model** — `model.ts` defines the single Mongoose document (one per order) that stores the provider payment lifecycle, embedded refunds, and disputes. `presenter.ts` shapes that document into the wire contract returned by every endpoint.
- **Controllers (`controllers/`)** — Thin HTTP handlers for the public and staff APIs: intent creation/confirm/sync, refund create/settle/cancel, webhook receipt, order-nested offline payments, staff list/search, and the attention dashboard.
- **Provider port (`providers/`)** — `providers/index.ts` declares the contract every PSP adapter must satisfy; `providers/registry.ts` lets a concrete adapter (or test double) register itself; `providers/webhook-signature.ts` provides the shared HMAC verify/sign pair; `providers/errors.ts` isolates the error types to avoid circular imports.
- **Module wiring & config** — `module.ts` is the single registration point (routes, event subscriptions, jobs, rate limits, GDPR hooks, demo scenario). `config.ts` centralises deployment-tunable values. `index.ts` is the only import surface other modules may use.
- **Cross-cutting declarations** — `events.ts` (domain-event names), `analytics.ts` (analytics event names), `audit.ts` (audit action strings), `metrics.ts` (Prometheus counters), `emails.ts` (i18n email bodies).
- **Background jobs** — `jobs.ts` + `jobs.generated.ts` wire scheduled work (abandoned-attempt reaping, effect sweeping) to service functions.
- **Contract & limits** — `openapi.yaml` (OpenAPI 3.1 spec) and `rate-limits.generated.ts` (typed rate-limit budgets derived from `module.yaml`).

## How it connects

- **`src/modules/orders/`** — Payments are 1-to-1 with orders (unique index on `orderId`). The order-nested routes (`order-routes.ts`, `post-order-payment.ts`) let an admin record an offline payment against an existing order, and the order service emits the `order.created` event that triggers bank-transfer reference minting.
- **`src/modules/inventory/`** — The "pending stock commits" surfaced by `get-payment-attention.ts` indicate inventory holds that resolve only after a payment settles. `config.ts` deliberately mirrors the inventory module's per-call-read config pattern.
- **`src/modules/notifications/`** — `emails.ts` produces the `EmailContent` objects (payment received, refund issued, transfer instructions, etc.) that the notifications module delivers.
- **`src/modules/account/`** — The OpenAPI spec contributes a slice to the account data export (GDPR personal-data hooks registered in `module.ts`). The metrics pattern here follows `modules/account/metrics.ts`.
- **`src/modules/returns/`** — Refund creation and settlement in this module are the financial counterpart to the return workflow; the attention endpoint tracks refunds pending stock commit.
- **`src/modules/users/`** — Tokenised payment-method references are tied to a user's account for repeat checkout; the `get-payment-methods` endpoint is public so guests can see options pre-signup.
- **`src/infrastructure/http/`** — Controllers are Express route handlers; `globals.d.ts` augments the shared `Request` type with a payments-specific flag per the project's layering rules.
- **`scenarios/`** — Test doubles (the fake provider) and the admin demo scenario (referenced in `module.ts`) live here and register through `providers/registry.ts` before the app boots.

## Where to start

1. **`domain/lifecycle.ts`** — Read this first: it defines which statuses each operation may start from and encodes the refund-settlement decision rules. Every guard in the repository and every status transition in the service layer traces back to these arrays, so understanding them makes the rest of the module predictable.
2. **`module.ts`** — The single registration point shows how routes, events, jobs, rate limits, and the provider port come together. Skimming it gives a complete map of what the module exposes to the application tier without reading every controller.

## Files
- `src/modules/payments/analytics.ts` — Declares the canonical analytics event names for the payments domain and registers them with the analytics port's `AnalyticsEventMap` via TypeScript module augmentation, so that any `emit` of a payments event is type-checked against this list. Controllers import this file directly (mirroring the pattern `./audit.ts` uses for audit actions) rather than a published copy.
- `src/modules/payments/audit.ts` — Centralises every audit action string the payments module can emit, registers its security-relevant events with the observability layer, and augments the shared `AuditActionMap` type so the rest of the codebase can reference these actions by name. It exists so that payment-related audit and security events have a single source of truth rather than scattered string literals.
- `src/modules/payments/config.ts` — Centralises every deployment-tunable payment value (bank-transfer account details, provider selection, webhook secrets, grace windows) behind a single `defineConfig` call, and exposes typed accessor functions so that consumers read the value at call-site rather than transcribing their own fallback. Follows the same per-call-read pattern as `@modules/inventory`'s config.
- `src/modules/payments/controllers/get-order-payments.ts` — HTTP handler for `GET /orders/:id/payments`. Serves the payment panel on the order page so that a mid-flow reload recovers the payment intent and its current status rather than forcing the caller to start over. Returns an empty `items` array for orders with no payment activity; reserves 404 for orders the caller genuinely cannot see.
- `src/modules/payments/controllers/get-payment-attention.ts` — Express route handler for `GET /payments/attention`. It surfaces a summary of items requiring manual attention (stale refunds, hand-owed refunds, pending stock commits, pending order refunds) by delegating entirely to the payment service and shaping the HTTP response.
- `src/modules/payments/controllers/get-payment-methods.ts` — Express controller that answers `GET /payments/methods` with the list of payment methods configured for the shop. It exists so the frontend can discover available checkout options dynamically instead of hard-coding them. The endpoint is intentionally public—guests should be able to see what payment options exist before signing up.
- `src/modules/payments/controllers/get-payment.ts` — Controller handler for `GET /payments/:id`. Retrieves a single payment by its id and returns it to the caller. It is the destination that a `Location` header points to after a successful `POST /payments`, and the read-back target an operator-refund response sends a client back to.
- `src/modules/payments/controllers/get-payments.ts` — Defines the controller for `GET /payments` and `POST /payments/search` (the staff payments list). Both routes are served by a single controller instance produced through the shared search-controller factory, with a query-string-aware schema that coerces text inputs to their proper types.
- `src/modules/payments/controllers/get-refund.ts` — Handler for `GET /payments/:id/refunds/:refundId`. It resolves a single refund record that is always addressed through its parent payment (the same target a `Location` header points to after creating a refund via `POST /payments/:id/refunds`). The controller performs ID validation, delegates the fetch to the payments service, and shapes the HTTP response.
- `src/modules/payments/controllers/get-refunds.ts` — HTTP controller for `GET /payments/refunds`. Exposes a paginated, filterable list of one row per refund across all payments, serving the Refunds tab in the UI. It validates query-string parameters and delegates to the payment service.
- `src/modules/payments/controllers/post-order-payment.ts` — HTTP controller for `POST /orders/:id/payments`. Lets an admin record an offline payment — money the card provider never saw — against an existing order. Thin adapter: extracts the order ID, validates the body, delegates to `paymentService.recordOfflinePayment`, and shapes the HTTP response.
- `src/modules/payments/controllers/post-payment-confirm.ts` — HTTP handler for `POST /payments/:id/confirm` — the step where the browser hands over the tokenised payment method reference and the payment is actually attempted. It maps the service result to three HTTP outcomes (succeeded, in-flight, declined) and fires the associated metrics and audit context.
- `src/modules/payments/controllers/post-payment-refund-cancel.ts` — Controller for `POST /payments/:id/refunds/:refundId/cancel`. Lets staff void a refund before it is paid. It validates path params and the request body, delegates to the payment service, and returns the now-voided refund. Business rules (refusing already-closed refunds or ones that may have moved money) live in the service layer, not here.
- `src/modules/payments/controllers/post-payment-refund-settle.ts` — HTTP handler for `POST /payments/:id/refunds/:refundId/settle`. An operator uses it to confirm that a refund's funds actually left the application. The controller extracts the two route IDs, delegates to the payment service, and returns the settled refund object on success.
- `src/modules/payments/controllers/post-payment-refund.ts` — Handles `POST /payments/:id/refunds`: creates a (full or partial) refund on an existing payment without altering the parent order's status. Returns **201 Created** with the new `Refund` record and a `Location` header. This is the operator's standalone refund action; "cancel and refund" is left to the client issuing this call *and* a separate order-cancel call.
- `src/modules/payments/controllers/post-payment-sync.ts` — HTTP handler for `POST /payments/:id/sync`. When the browser finishes a provider-side step (3-D Secure challenge, wallet sheet), this endpoint re-reads the provider's own record and applies it, making the happy path feel synchronous to the user while the webhook remains the source of truth. Already-settled payments short-circuit without re-querying the provider (idempotent).
- `src/modules/payments/controllers/post-payment-webhook.ts` — Single HTTP handler for `POST /payments/webhook/:provider`. Receives provider-originated payment event deliveries, verifies the request via the provider's own signature (no session auth), and delegates the parsed event to the payment service. It exists to be the one place where the "browser's word" is replaced by a cryptographically signed raw body as the sole authority for what happened to a payment.
- `src/modules/payments/controllers/post-payment.ts` — Thin HTTP handler for `POST /payments`. It validates the request body, delegates to `paymentService.createIntent`, and returns the payment intent. Deliberately contains no business logic, auditing, or analytics — an intent is preparation, not a business event; those concerns fire at confirm time.
- `src/modules/payments/domain/display-status.ts` — Computes the human-facing display label for a payment (Shopify's `displayFinancialStatus`) from its stored status and refund records, and provides the inverse MongoDB query for each label. The two must agree: the integration suite verifies every label in both directions.
- `src/modules/payments/domain/disputes.ts` — Pure domain rules for card-payment disputes. It encodes the distinction between an *inquiry* (no money moves) and a *chargeback* (bank reclaims funds, opens an evidence window), and answers the question "what may the shop still do with this payment while a dispute stands?" — specifically around refund blocking and partial-loss accounting. No I/O, no side effects.
- `src/modules/payments/domain/index.ts` — Barrel file that re-exports every public symbol of the payments **domain layer** — pure status vocabulary, dispute predicates, bank-transfer reference helpers, and display-label logic — so callers can import from a single path (`payments/domain`) without reaching into individual sub-modules. The header doc block states the contract: no Express, Mongoose, or framework-tier imports are permitted here (enforced by lint).
- `src/modules/payments/domain/lifecycle.ts` — Defines which payment and refund statuses each domain operation is allowed to act from, and encodes the refund-settlement decision rules (reversal, finality, overshoot, hand-settlement eligibility). Every status array here doubles as the `$in` predicate for the conditional writes in `repository.ts`, making the array itself the concurrency guard rather than an adjacent check.
- `src/modules/payments/domain/transfer-reference.ts` — Mints and validates the ISO 11649 "RF" creditor reference attached to a `bank_transfer` payment. The reference is derived deterministically from the order's ObjectId so a redelivered `order.created` event can never produce a second code, and ISO 7064 MOD 97-10 check digits ensure a mistyped code is rejected rather than matching the wrong order. The arithmetic is hand-rolled because `ibantools` (the repo's IBAN/BIC library) has no ISO 11649 support.
- `src/modules/payments/emails.ts` — Builds the five email bodies the payments module sends (payment received, refund issued, refund undeliverable, transfer instructions, transfer expired). Each function resolves all i18n strings into finished text at call time — language is an argument, output is done — and returns an `EmailContent` object whose template only performs simple interpolation later. This keeps translation logic out of the mailer adapter and out of the HTML templates.
- `src/modules/payments/events.ts` — Declares the domain events emitted by the payments module by augmenting the kernel's `DomainEventMap` interface (the same pattern as `modules/orders/events.ts`). Also exports a string constant for each event name so other code can reference them without hard-coding the string.
- `src/modules/payments/globals.d.ts` — Augments Express's `Request` interface with a payments-specific boolean flag via declaration merging. It exists as a separate file (rather than living in infrastructure's `src/globals.d.ts`) because the project's layering rules (`docs/theory/layers.md`) forbid infrastructure's global types file from naming a module, so payments-local fields live here.
- `src/modules/payments/index.ts` — Public barrel for the Payments module. It is the **only** import surface exposed to sibling modules (enforced by the strategic-DDD rule in `docs/theory/strategic-ddd.md` §5). It re-exports services, domain logic, events, and emails by value, and re-exports the model as **types only**, keeping the model's runtime internal to the module.
- `src/modules/payments/jobs.generated.ts` — Auto-generated data file that declares the scheduled jobs for the payments module as plain metadata (name, cron schedule, summary). It exists so that job definitions live in a single YAML source (`module.yaml`) and can be regenerated mechanically, keeping the "what" (scheduling) separate from the "how" (execution logic in `jobs.ts`).
- `src/modules/payments/jobs.ts` — Declares the two scheduled jobs the `payments` module owns—abandoned-attempt reaping and effect sweeping—as a readonly array of `JobDeclaration` objects. It wires generated schedule metadata to the actual service functions that do the work, so the kernel can discover and run them.
- `src/modules/payments/metrics.ts` — Defines the Prometheus counters for the payments domain: one for confirmation outcomes and one for settlement-amount mismatches. Metrics live here (in the module) rather than in `infrastructure` so the domain owns its observability vocabulary; the overview endpoint reads them without importing this file (see `modules/account/metrics.ts` for the pattern).
- `src/modules/payments/model.ts` — Defines the Mongoose schema, TypeScript document interface, and embedded sub-document types for the payment record. One document per order (enforced by a unique index on `orderId`), it persists the provider-facing payment lifecycle, all refund attempts, and all buyer-bank disputes. It is the single source of truth that `repository.ts` queries and `services/*` mutate.
- `src/modules/payments/module.ts` — The module manifest (default export) for the payments domain. It is the single registration point where the payments module wires itself into the application: HTTP routes, domain-event subscriptions, webhook-visible public events, personal-data (GDPR) hooks, rate limits, config slices, background jobs, and an admin demo scenario. Everything the app tier needs to "mount" payments is declared here.
- `src/modules/payments/openapi.yaml` — OpenAPI 3.1.0 contract for the payments module. Declares the module's operations (payment methods, payment lifecycle, staff list/search), its custom error-code vocabulary, and the slice it contributes to the account data export. Serves as the single source of truth for both server implementation and client SDK generation.
- `src/modules/payments/order-routes.ts` — Express router that exposes the two payment operations nested under an order's URL (`/orders/:id/payments`). It exists to keep the URL hierarchy order-first (matching the Solidus convention) while the domain logic and authorization keys remain in the payments module.
- `src/modules/payments/presenter.ts` — Transforms a stored `PaymentDocument` into the wire `Payment` contract that every write endpoint returns. It also produces an optional staff view that adds provider identifiers (`providerRef`, `providerRefundRef`) and refund `failureReason` fields stripped from the payer-facing shape. `services/view.ts`'s `withActions` layers `actions` on top of this for read endpoints that need them.
- `src/modules/payments/providers/errors.ts` — Defines the two error classes that a payment provider adapter (real or fake) throws when it refuses a cancel or a refund. It is split out of `providers/index.ts` so that an implementation can import only these error types without pulling in the port interface, the config, or the registry that the adapter itself is registered in — avoiding a circular import.
- `src/modules/payments/providers/index.ts` — This file defines the **payment provider port** — the contract every real PSP adapter must satisfy. It exists as a single, stable seam so that the rest of the codebase (controllers, settlement, sweep) never names a specific provider. No provider is shipped in the boilerplate; a live project plugs one in by writing one adapter file and one `registerPaymentProvider` call. The `fake` double used in dev/demo/tests lives under `scenarios/support/doubles/` and is registered before the app boots.
- `src/modules/payments/providers/registry.ts` — Standalone registry for payment provider implementations. It exists as its own module (importing only the registry helper and a *type* from `./index`) so that test doubles can register themselves at preload without pulling in the full provider barrel—config, orders, and all transitive dependencies.
- `src/modules/payments/providers/webhook-signature.ts` — Shared HMAC-SHA256 signing and verification for PSP webhook deliveries. The signature is over `<timestamp>.<raw body>`, compared in constant time, and rejected if the timestamp is outside a 5-minute window. This file exists because the **verify** side is called by production providers while the **sign** side is needed by the demo and the test harnesses, and because a real PSP's own verifier (e.g. `stripe.webhooks.constructEvent`) only replaces the verify half — this stays as the reference implementation for what it must do.
- `src/modules/payments/rate-limits.generated.ts` — Generated data table that declares the rate-limit budgets (namespaces, defaults, windows, and descriptive bounds) for every payments endpoint. It exists as a build artifact so that the single source of truth remains the YAML definition in `module.yaml`, and so consumers get a typed, importable object without parsing YAML at runtime.
- `src/modules/payments/rate-limits.ts` — Defines the payments module's rate-limit budgets (webhook, confirm attempts, confirm declines per account and per address block, intent/sync) and builds each into an Express middleware via the shared `buildRateLimiter` factory. It also composes a challenge gate that escalates to a human challenge when an account or its address block has already burned into the decline budget.
- `src/modules/payments/repository.ts` — Data-access layer for the Payments collection. It combines the generic CRUD factory (`createRepository`) with the bespoke reads and guarded writes that the payments service actually performs: intent/offline upserts, status transitions, refund sweeps, dispute recording, and the provider-facing lookups. The file exists to keep every Mongoose query, projection, and aggregation in one place so that service code only expresses intent.
- `src/modules/payments/routes.ts` — Express router that wires every payment HTTP endpoint to its controller and enforces the cross-cutting concerns (authentication, authorization, rate limiting, idempotency, cache-control) at the router level before any controller runs. It exists as a single, ordered declaration of routes so that public endpoints stay above the auth wall and sensitive money-movement routes carry the strongest guards.
- `src/modules/payments/services/announce.ts` — Provides the single entry point for recording a declined payment. It atomically writes the `declined` status, appends the order timeline row, and enqueues a `PAYMENT_FAILED` outbox event in one transaction, so a decline either fully lands (status + timeline + event) or does not at all. This is the counterpart to `settlement.ts`, which owns the `PAYMENT_SUCCEEDED` announcement.
- `src/modules/payments/services/deadline.ts` — Computes the due instant for a refund on a payment — the legal deadline when one is set, otherwise the "needs-attention" cutoff derived from the refund's creation time. Consumed by the `tickets` flow to date the work item it opens.
- `src/modules/payments/services/disputes.ts` — Applies a dispute report carried by a provider webhook delivery onto its payment. It records the dispute state on the payment, appends staff timeline rows, and announces a `payment.dispute_opened` or `payment.dispute_updated` domain event — all within a single database transaction. A dispute is explicitly **not** a refund: it never mutates `amountRefunded`, order status, or credit notes.
- `src/modules/payments/services/effects.ts` — Two scheduled sweep operations that finish what a settlement left undone: retrying refunds the provider refused or never acknowledged, and reconciling payments whose provider decided without delivering a webhook. Both sweeps are sequential, batch-capped, and idempotent, mirroring the sweep shape in `orders/services/cancel.ts`.
- `src/modules/payments/services/errors.ts` — Centralized factory functions and one internal error class for every "this payment action cannot proceed" response in the payments service layer. It is deliberately a **leaf module** (no persistence or cross-service imports) so any file under `services/` can reach it without creating dependency edges among the services themselves.
- `src/modules/payments/services/external-refunds.ts` — Handles refunds created directly in the payment provider's dashboard (outside the application). When a refund event fires, it lists the provider's refunds for the payment's intent and walks them: known refunds (ours) get their local record updated, while unknown successful refunds are imported as settled records so the credit note, buyer mail, and order stamp follow the same path as an in-app refund.
- `src/modules/payments/services/index.ts` — Barrel module that aggregates every payment-flow function (intent, settlement, refunds, effects, offline, transfer, notifications, scope, view, retention, listing, stats) into a single `paymentService` object. It exists so that the rest of the codebase has exactly one import path for all payment operations, and so the module-level docblock can document the invariants (order-gate, at-most-once refunds, provider authority) in one place.
- `src/modules/payments/services/intent.ts` — Entry point into the payments module's money-moving flow: creates (or refreshes) a provider payment intent for an order, and closes open intents when an order is cancelled. Guarantees the amount is frozen via the order's own `orderTotal`, enforces single-intent-per-payment, and coordinates with the orders module for status validation.
- `src/modules/payments/services/list.ts` — Server-side read queries behind the staff Payments page: the paginated payment list, the cross-payment refund list, and the "needs a person" attention feed. All three are `display:Payment` routes, so every row carries provider identifiers. The file composes data from the payments repository with order lookups and domain-pure checks to produce display-ready rows.
- `src/modules/payments/services/notify.ts` — Sends all buyer-facing emails for the payment lifecycle: payment received, refund issued, refund undeliverable, bank-transfer instructions, and transfer-expired cancellation. Two exports are registered as event listeners (`payment.succeeded`, `payment.refunded`) so they fire on every settlement path (webhook, browser confirm, offline record, crash-recovery sweep); the other two are called directly by the code that opens or cancels a transfer payment. A failed email never rolls back a financial action — all failures are logged and swallowed.
- `src/modules/payments/services/offline.ts` — Records payments that arrived outside the card provider (cash at the counter, bank transfer, phone-order payment) and settles them through the same `settlePayment` pipeline every card payment uses — moving the order `pending → paid`, committing stock, and firing the standard status/payment events.
- `src/modules/payments/services/refund-settlement.ts` — Handles the terminal states of a refund record: settling it to `succeeded` (stamping the order's payment status and emitting `payment.refunded` via the outbox) or recording a provider refusal with retry scheduling. Split out from `refunds.ts` so that provider-side flows (`refund-sync.ts`) and outgoing flows (`refunds.ts`) can share settlement logic without importing each other.
- `src/modules/payments/services/refund-sync.ts` — Bridges the provider-side lifecycle of a refund to the local record. It re-reads a refund from the provider until it reaches a terminal state, and converts the provider's reported status (success or failure) into the record's next state via conditional writes. The provider's own word is the sole authority; no delivery body or local assumption overrides it.
- `src/modules/payments/services/refunds.ts` — The sole mechanism for moving money out of a payment. Exposes the operator-facing `refundPayment` action and the `order.cancelled` listener's compensation (`refundForOrder`), both funnelled through `performRefund`. A refund is a conditional write on the payment document that reserves the amount, then asks the provider; the record settles only on provider confirmation.
- `src/modules/payments/services/retention.ts` — Handles the post-transaction lifecycle of payments: detaching `userId` when an account is erased, producing the account's full payment export, and sweeping out abandoned (never-succeeded) payment attempts past their retention window.
- `src/modules/payments/services/scope.ts` — Centralises the row-scoping rules for the payments collection so that every other service in this module applies a consistent "who can see/do what" filter. It separates **read** scope (possibly broad, role-driven) from **payer** scope (strictly the payer's own rows) to prevent a `display:Payment` role from accidentally granting cross-customer write or payment-intent access.
- `src/modules/payments/services/settlement.ts` — The single reconciliation point for payment success. Whether the signal arrives via a browser-driven confirm/sync poll or a provider webhook, both paths funnel into this file's settlement logic so that money is reconciled exactly once. It handles both the happy path (provider confirms the frozen payment) and the mismatch path (provider reports a success whose amount, currency, or payment id disagrees with what was frozen), ensuring the order is either marked paid or cancelled with a refund opened atomically.
- `src/modules/payments/services/stats.ts` — Computes the "payments mix" statistic: how much money came in broken down by payment method, provider, and currency within a given reporting window. It translates raw aggregate rows from the persistence layer into a clean `MixRow` shape suitable for reporting.
- `src/modules/payments/services/transfer.ts` — Opens the payment record for an order placed with the `bank_transfer` method. Acts as the `order.created` event listener: when a transfer order is placed it inserts a `requires_action` row (carrying the RF reference, deadline, and wire instructions) and mails the instructions to the buyer. Downstream settlement (`settlePayment`) and operator recording (`./offline`) consume that row later.
- `src/modules/payments/services/view.ts` — Read-layer for the payment domain. Serves the order page's payment panel and the standalone `GET /payments/:id` surface, always attaching a computed `actions` block (the same shape `orders` publishes as `OrderActions`) so the caller knows exactly which next-step endpoints are open to them.
- `src/modules/payments/tests/contract/api.contract.test.ts` — HTTP-level contract tests for every `/payments` route. Each test asserts that the correct status code, response shape, error code, and authentication requirement are reachable over a real HTTP round-trip.
