# src/modules/users/

## Purpose

The `users` module owns the **User record** and everything an administrator can do to it: create, read, update, activate/deactivate, assign or revoke roles, place or lift purchase holds, soft-delete, hard-delete (GDPR erasure), and restore. It also publishes the cross-module contracts other modules depend on—domain events, webhook payloads, audit-action vocabulary, and the typed `friends/` gateways that enforce the strategic-DDD boundary between `users` and its consumers.

## Key parts

- **Data & persistence** — `model.ts` (Mongoose schema, password-hash hook, `select:false` guards), `repository.ts` (CRUD + credential/2FA/OAuth/deletion operations), `presenter.ts` (pure `UserWire → Account | User | UserListItem` mapping).
- **Business services** — `services/index.ts` assembles the public `userService`; individual files handle `create`, `activation`, `credentials`, `actions` (per-caller permission block), `cleared-account` (shared staff guard), `audit-changes`, `image` (async digest), `lookups` (read-only passes for `account`), and purchase-hold logic.
- **HTTP layer** — `routes.ts` mounts the main admin router; `role-routes.ts` isolates the two role-door endpoints behind `isAuth`-only; `controllers/` holds one thin handler per endpoint (no domain logic).
- **Cross-module contracts** — `friends/account.ts` (the gateway `account` uses for auth/register/erase calls), `friends/orders.ts` (the single permitted write: `takeAutomaticPurchaseHold`), `erasure-registry.ts` (injected lists of `PersonalDataEraser`/`Minimiser` hooks from sibling modules), `events.ts` (augments the kernel `DomainEventMap`).
- **Operational metadata** — `audit.ts` (typed audit-action constants), `analytics.ts` (event names), `authorization.yaml` (permission keys), `config.ts` (PII key + mail links), `jobs.ts` (nightly purchase-hold reaper).
- **API & webhook contracts** — `openapi.yaml` (REST fragment), `asyncapi.webhooks.yaml` (`user.erased`, `user.updated` webhook fragment merged by the contract bundler).
- **Module wiring** — `module.ts` (routes, event subscriptions, personal-data export sections, erase-hook resolution, job registration), `index.ts` (public barrel—the only import surface siblings are allowed to use), `factories.ts` (seed/test fixtures).

## How it connects

- **`src/modules/account/`** — The primary consumer. `account` calls into `users` exclusively through `friends/account.ts` for credential writes, 2FA, session teardown, and erasure. In the other direction, `users` delegates self-service flows (signup, login, email verification) to `account`'s services. The `index.ts` barrel and `friends/` pattern keep the two modules from importing each other's internals.
- **`src/modules/orders/`** — May invoke exactly one write: `takeAutomaticPurchaseHold`, reached via `friends/orders.ts`. `users` owns the purchase-hold state; `orders` owns the cancellation count that justifies it.
- **`src/modules/webhooks/`** — `asyncapi.webhooks.yaml` here is a fragment that the contract bundler merges into the root `webhooks/asyncapi.yaml`, so `users` declares its outgoing events without duplicating server/schema definitions.
- **`src/infrastructure/`** — Supplies the generic `createRepository` factory, the `auditChanges` diff engine, config validation for the PII key, and the analytics event map that `analytics.ts` and `audit.ts` register into.
- **Other sibling modules** (`cart`, `delivery`, `invoicing`, `notifications`, `payments`, `products`, `returns`, `shop-tasks`, `tasks`, `example`) — Consume user data read-side and register `personalData.erase` / `minimise` hooks that `module.ts` resolves at boot so a hard-delete cascades across the whole aggregate in one transaction.

## Where to start

1. **`model.ts`** — Read the Mongoose schema and the `select:false` annotations to understand what a `UserDocument` looks like, which fields are credential-sensitive, and how the pre-save hook hashes passwords.
2. **`services/index.ts`** — Shows the full `userService` surface (what controllers and `account` can call) and, by what it *excludes*, makes the `users` / `account` boundary immediately visible.

From there, `module.ts` is the natural next read: it is the single manifest that ties routes, events, jobs, and erase-hooks together, giving you the wiring map for the rest of the module.

## Files
- `src/modules/users/analytics.ts` — Declares the analytics event names for admin-initiated user lifecycle actions (account creation and deactivation) and registers them into the app-wide analytics event map. It exists so that event names live in one typed location and are available to any service that fires them, without duplicating string literals.
- `src/modules/users/asyncapi.webhooks.yaml` — Declares the two webhook events that the users module emits (`user.erased`, `user.updated`). It is a **fragment**—not a standalone AsyncAPI document—that gets merged into the `webhooks` section of `src/modules/webhooks/asyncapi.yaml` by the contract bundler. Its existence lets the users module describe its outgoing events without duplicating shared servers or schemas.
- `src/modules/users/audit.ts` — Declares the full set of audit-action string constants for user-record writes and registers them into the app-wide `AuditActionMap` via TypeScript module augmentation. It exists so every audit event emitted anywhere in the users module uses a single, type-safe vocabulary, and so the audit log can answer specific operational questions (e.g. "was this account banned?", "was the erasure actually discharged?") without a reader diffing row revisions.
- `src/modules/users/authenticatable.ts` — Single source of truth for the "is this account allowed to authenticate?" check. It pairs a Mongo query filter with an in-memory predicate so that database lookups and post-load checks always agree on the state of banned or soft-deleted accounts, eliminating a class of disagreement bugs between the two code paths.
- `src/modules/users/authorization.yaml` — Declares the authorization keys and named permission sets for the `users` module. Every rule is scoped to `tenant` and governs actions on **other** people's `User` records (self-service actions live under `account`, not here). It exists so that role definitions and API gates can reference stable, human-readable permission names instead of ad-hoc strings.
- `src/modules/users/config.ts` — Defines the `users` module's runtime configuration: the encryption key for personal fields and the two frontend links (contact + privacy) embedded in purchase-hold mail. It owns the *requirement* that the PII key be set, while the shape/validation lives in `infrastructure/security/config.ts`. Deleting this module removes that requirement.
- `src/modules/users/controllers/delete-users.ts` — Admin-facing controller that handles `DELETE /users/:id` with an optional `?hardDelete=true` query parameter. Soft delete is the default; hard delete permanently removes the user and runs all registered `personalData.erase` hooks in a single transaction. Only the hard path discharges an Art. 17 erasure request.
- `src/modules/users/controllers/get-user.ts` — Controller for `GET /users/:id`. Resolves a single user by path id for admin callers, shapes the response via the user service's contract mapper, and records the read in the staff-audit log.
- `src/modules/users/controllers/get-users.ts` — Controller for the admin-facing `GET /users` (query-parameter search) and `POST /users/search` (body search) endpoints. It validates incoming parameters against a Zod schema, delegates to `userService.search`, then transforms raw records into permission-aware `UserListItem` contracts before returning a paginated response.
- `src/modules/users/controllers/post-lift-purchase-hold.ts` — Thin Express controller for `POST /users/:id/lift-purchase-hold`. It validates the path parameter, delegates all business logic to `userService.liftPurchaseHold`, serializes the returned user, and sends a 200 response. It exists so the route table can wire a named, catch-wrapped handler without inlining logic.
- `src/modules/users/controllers/post-place-purchase-hold.ts` — HTTP controller for `POST /users/:id/place-purchase-hold`. It validates the request (user ID, body schema) and delegates the actual purchase-hold mutation to `userService.setPurchaseHold`, then shapes the successful response as an RFC 9110 §8.8.3 resource. The controller contains no domain logic.
- `src/modules/users/controllers/post-user-activation.ts` — Thin HTTP controller layer for `POST /users/:id/activate` and `POST /users/:id/deactivate`. It extracts the user id, calls the appropriate `userService` method, and serializes the result into a 200 response with ETag/Location headers. All business rules (404, 403 for staff, 409 for a repeat, audit logging) live in the service, not here.
- `src/modules/users/controllers/post-user-restore.ts` — Controller for `POST /users/:id/restore`. Undoes an admin soft-delete of a user account, returning the restored user in its standard contract shape. Returns **409** if the account is not currently in a deleted state.
- `src/modules/users/controllers/post-user-role.ts` — HTTP controllers for the two role-door endpoints (`POST /users/:id/assign-role` and `POST /users/:id/revoke-role`). They extract the target user ID, validate the request body (assign only), delegate the actual permission/audit logic to `userService`, and shape the successful response as a resource with an ETag.
- `src/modules/users/controllers/post-user.ts` — Request handler for `POST /users` (staff user creation). It validates the incoming body against a strict Zod schema, optionally processes an uploaded image, delegates to the user service, and responds with the created user as a 201 resource.
- `src/modules/users/controllers/update-user.ts` — Defines the HTTP handler pair for `PUT /users/:id` (full replace) and `PATCH /users/:id` (partial merge). Both delegate to `userService.updateById`, which performs the field merge and audit internally. The file exists as the thin presentation-layer binding between the route table and the user service, adding locale validation, image-upload handling, and response shaping.
- `src/modules/users/emails.ts` — Produces the single email the `users` module sends to a buyer when a purchase hold is placed on their account. It resolves all copy into finished, locale-aware strings (via i18n) and returns an `EmailContent` object whose template only interpolates — no logic lives in the template. Follows the same "finished-text, not template" rule as `@modules/account/emails`.
- `src/modules/users/erasure-registry.ts` — Holds the in-memory lists of `PersonalDataEraser` and `PersonalDataMinimiser` registrations that the `users` module uses at runtime. It exists because `users` cannot import sibling modules under `src/modules/*` to collect their manifest entries directly (circular-dependency wall); instead the lists are injected once at boot by the module registration hook.
- `src/modules/users/events.ts` — Declares the domain event payloads owned by the users module by augmenting the kernel's `DomainEventMap` (via `declare module '@kernel/events'`), so the global event catalogue grows per-module without a shared enumeration file. Also exports the string constants used to reference each event name at emit sites.
- `src/modules/users/factories.ts` — Builds user fixtures (partial `UserDocument` objects) for seed accounts and tests. It intentionally omits fields the Mongoose schema defaults (`imageUrl`, `locale`, `active`, `verifiedAt`) so a seeded row reflects what the schema actually does rather than a factory's guess. Passwords stay plaintext through the builder; the model's pre-save hook handles hashing.
- `src/modules/users/friends/account.ts` — A friend-facing facade that bundles the specific `users`-domain functions the `account` module needs to authenticate, register, protect (2FA), change, and erase User documents. It exists so `account` can call these operations without importing the public `userService` barrel, and so tests can `jest.spyOn` the exact object the code under test receives.
- `src/modules/users/friends/orders.ts` — A single re-export that exposes `takeAutomaticPurchaseHold` (defined in `src/modules/users/services/purchase-hold.ts`) as the **only** `users` write operation the `orders` module is permitted to invoke. It exists to enforce a strategic-DDD boundary: because `orders` owns the cancellation count that justifies a purchase hold, it must be the sole caller that triggers one, and this "friend" file is the gate through which that access is granted. See `docs/theory/strategic-ddd.md` §5.
- `src/modules/users/index.ts` — Public barrel for the `users` module — the **only** import surface a sibling module (currently `account`) is allowed to use. It re-exports the module's public API (services, events, emails, model types) while deliberately keeping the repository, the model runtime, and the `friends/account.ts` step file internal. See `docs/theory/strategic-ddd.md` §5 for the governing rule.
- `src/modules/users/jobs.ts` — Declares the scheduled job(s) owned by the `users` module. Currently exposes a single nightly job that reaps expired purchase holds, wiring together the domain service, structured logging, and a lease TTL so the kernel scheduler can dispatch it safely.
- `src/modules/users/model.ts` — Defines the Mongoose schema and document interfaces for the user record. It is intentionally a single file: the pre-save password-hashing hook and the `select: false` fields that guard sensitive data (password, pending/previous email) must stay colocated so a future split can't accidentally separate them.
- `src/modules/users/module.ts` — Module manifest for the `users` domain object. It declares the routes, event subscriptions, personal-data export sections, reencryption hook, and job registrations that the kernel uses to wire the module into the running application. It also resolves cross-module `personalData.erase` / `minimise` hooks at registration time so that hard-deleting a user cascades through every other module in a single transaction.
- `src/modules/users/openapi.yaml` — The OpenAPI 3.1.0 contract for the **users** module: it declares the REST endpoints, request/response schemas, error codes, and tag metadata that the users service exposes. The file is a *module fragment* intended to be merged into a single API document by a bundler, so it intentionally omits global servers, security schemes, and shared components (those live in the root contract).
- `src/modules/users/presenter.ts` — Pure mapping layer that turns a stored `UserWire` document into the three API contract shapes (`Account`, `User`, `UserListItem`). It is the single point where a persisted account becomes a wire-ready object; it contains no business logic, no lookups, and no side effects—only field selection, `Date → ISO string` conversion, and the one permitted PII decryption (phone).
- `src/modules/users/repository.ts` — The persistence layer for the `users` collection. It composes the generic `createRepository` factory (standard CRUD, search, sort) with the credential, 2FA/MFA, OAuth, deletion-lifecycle, and activity-tracking operations that the `account` module needs. All credential fields are `select: false` on the schema; this file centralises the only sanctioned re-selection paths.
- `src/modules/users/role-routes.ts` — Dedicated Express router that exposes the only two staff-role mutation endpoints — `POST /users/:id/assign-role` and `POST /users/:id/revoke-role`. It exists as a separate router (rather than living in `./routes`) so that it can require `isAuth` exclusively, rejecting API-key callers with a 401 before any role logic runs.
- `src/modules/users/routes.ts` — Express router that mounts every admin-facing `/users` endpoint (search, CRUD, purchase-hold, activation, restore, hard-delete). It wires each route to the correct permission check, cache headers, upload handling, and conditional re-authentication so that individual controllers stay free of routing concerns.
- `src/modules/users/services/actions.ts` — Computes the `User.actions` boolean block for a single account — the set of operations a given caller is permitted to perform against that account. It exists so that a client can render only the actions the server will actually accept, keeping the UI and the authorization boundary in lockstep. The function is pure: all external lookups (staff-role check, caller's rule set) are performed by the caller and passed in as plain values.
- `src/modules/users/services/activation.ts` — Service layer for toggling an account's active state (`activate` / `deactivate`). Deactivation is modeled as a ban: it ends every held session within the same transaction that persists the flag and announces `user.deactivated`, preventing stale one-time links from surviving a later re-activation. Both operations are non-idempotent—they return 409 on a repeat rather than silently succeeding.
- `src/modules/users/services/audit-changes.ts` — Defines the field-level audit diff for user account edits (admin edit and owner self-edit alike). It classifies which user fields are recorded by value versus by name—a privacy decision—then delegates the actual before/after comparison to the generic infrastructure `auditChanges`.
- `src/modules/users/services/cleared-account.ts` — Single, shared guard that every staff-facing account action runs first: load the user by ID, reject with 404 if absent, and reject with 403 (`ROLE_MANAGEMENT_REQUIRED`) if the caller lacks permission to manage a staff account. Exists as one canonical implementation so that no sibling service can accidentally skip the staff-role protection.
- `src/modules/users/services/create.ts` — Admin-side user creation endpoint service. It atomically creates a user document, grants a role (if specified), and enqueues a setup-password event—all in a single transaction—then records audit and analytics side-effects. It exists as the privileged alternative to the self-service `accountService.signup` flow.
- `src/modules/users/services/credentials.ts` — Write-side service for user account credentials. Provides one narrow, single-purpose mutation per operation (set password, verify email, swap email, persist 2FA, end sessions, etc.). Each function takes an already-loaded `UserDocument` and performs exactly one save or update, deliberately leaving validation, orchestration, and follow-up side-effects (role promotion, link purging, session-row deletion) to the caller.
- `src/modules/users/services/image.ts` — Single-purpose service that enqueues the image-digest job for a user document immediately after its persisting write commits. It decouples "the user is saved" from "the uploaded image is processed," so a digest failure never blocks account creation or update.
- `src/modules/users/services/index.ts` — Barrel module that aggregates the User document's admin-facing CRUD, search, role management, and purchase-hold operations into a single `userService` object. It exists so controllers and sibling modules have one stable import point rather than reaching into individual sub-module files. Deliberately excludes authentication, registration, verification, 2FA, and erasure flows, which belong to the `account` module behind `../friends/account.ts`.
- `src/modules/users/services/lookups.ts` — Read-side named lookups for the `account` domain (the shared-kernel "account" end described in `docs/theory/strategic-ddd.md` §5). Every function is a thin, single-purpose pass-through over `userRepository`, named for the question it answers. Writes are deliberately excluded: the design intent is that a sibling importing from the barrel can never obtain a raw `save`, `build`, `create`, or arbitrary-filter `findOneWithCredentials` handle through this module.
- `src/modules/users/services/own-account.ts` — Provides the owner-facing and system-facing account operations that the admin doors (`updateById`, `removeById`) cannot serve: the owner editing their own profile, the inactivity reaper's soft-delete and purge, the owner's scheduled deletion lifecycle (lock → restore → erase), and the ops reapply-erasures workflow. Each function narrows the internal `update` / `remove` primitives (which skip ban checks and staff protection) into a safe, audited surface.
- `src/modules/users/services/personal-data-subject.ts` — Defines the single canonical shape of a "personal data subject" (who an export or erasure targets) derived from a stored `UserDocument`. Both the account export flow and the user-removal cascade consume this so every downstream module sees the same identity fields without re-deriving them independently.
- `src/modules/users/services/purchase-hold.ts` — Implements the **purchase hold** on a user account: a time-boxed block on checkout only (payments, cancellations, withdrawals, and data-rights requests are unaffected). Holds are set either manually by staff or automatically by the orders module after repeated buyer cancellations. The file owns reading, setting, lifting, sweeping, and notifying.
- `src/modules/users/services/read.ts` — Admin-facing read operations for the user module: searching, fetching by ID or email, and projecting already-loaded user documents into the outward contract shapes (`User`, `UserListItem`, `StaffContact`). It sits between the repository (raw documents) and the HTTP layer (serialised responses), adding role resolution, permission-aware actions, and pagination.
- `src/modules/users/services/reaper.ts` — Read and write helpers for the inactivity reaper — the background process that progressively takes dormant customer accounts offline through four stages (warn → soft-delete → hard-delete → personal-data minimise). Each exported function corresponds to one stage's candidate selection or execution, and every path excludes staff and administrator accounts.
- `src/modules/users/services/reencrypt.ts` — Provides user-scoped re-encryption operations for the two encrypted fields stored on the `users` collection: phone numbers (PII) and per-method 2FA secrets. It is the user-module half of the key-rotation pipeline orchestrated by the `reencrypt` ops script in `@infrastructure/security/reencrypt`. It deliberately never imports the `account` module; 2FA secret metadata is passed in by the caller that owns that ring.
- `src/modules/users/services/remove.ts` — Implements the full user deletion and restoration lifecycle: soft delete (stamp `deletedAt`, revoke sessions), hard delete (transactional erasure cascade across all registered personal-data hooks), and undoing either form. It exists as the single implementation layer beneath the route handlers so that soft-delete, hard-delete, restore, and scheduled-purge-cancel all share one set of transaction and audit guarantees.
- `src/modules/users/services/role-refusal.ts` — Maps a refused role grant (from the access layer) to an HTTP rejection response. It encodes the two distinct failure modes—granter lacking the `assign:Role` permission (→ 403) versus a role name that is not assignable (→ 422 with a `role` field error)—so that the user create and update services share one consistent rejection shape.
- `src/modules/users/services/role.ts` — The "role door" for existing user accounts: the sole entry points for granting (`assignUserRole`) or removing (`revokeUserRole`) a staff role. Each call is a state change with its own permission gate, idempotency check (409 on no-op), and audit row, executed inside a database transaction so the user stamp and the membership write commit atomically.
- `src/modules/users/services/sign-in-methods.ts` — Produces the `signInMethods` section of a GDPR Art. 15 account data export: the linked OAuth providers and armed second factors an account holds, expressed as non-secret facts. It exists as a separate section because those credential fields live behind `select: false` on the User document and therefore are not reachable through the plain `profile` projection.
- `src/modules/users/services/signup.ts` — Service layer that encapsulates the four account-creation paths (self-service, OAuth-vouched, anti-automation decoy, and the link/unlink operations) and delegates all persistence to the repository. Its primary design goal is compile-time enforcement of which fields each path is allowed to set, so a caller cannot accidentally grant a self-service signup the privileges of a provider-vouched one.
- `src/modules/users/services/update.ts` — Admin-side user update service: assigns requested fields onto a loaded `UserDocument`, saves it inside a database transaction (atomically with any caller-supplied `SaveHook`), cleans up a replaced avatar image, and enqueues a GDPR rectification event only when a personal-data field actually changed. It also exposes the public `updateById` entry point that wraps the core `update` with a staff-role check and an admin audit row.
- `src/modules/users/tests/contract/api.contract.test.ts` — Contract tests for the user-facing API surface (`GET /users`, `GET /users/{id}`, `GET /account`, `POST /account/signup`, `POST /users`, `PUT /users/{id}`). The primary guarantee is a **credential-leak guard**: because `openapi.yaml` declares `additionalProperties: false` on the `User` schema, any undeclared field (a plaintext password, an argon2 hash) causes a test failure even if no one wrote an explicit assertion for it. Secondary guarantees cover response shape, locale normalization, PII exclusion, domain-event emission, and error-status correctness.
- `src/modules/users/tests/factories.ts` — Test-database factories for the users module. It sits one layer above `../factories` (the plain-payload builder) and adds persistence via `userRepository`, role/membership seeding, and password-policy fixtures. Its job is to give every users-module test a single `createUser` entry point and a small set of named password constants so tests never hand-roll credentials.
- `src/modules/users/tests/integration/admin-user-grant-atomicity.test.ts` — Integration tests that verify the atomicity guarantee between user creation/role assignment and the underlying role-grant (membership) write. If the membership write fails, no partial user row should remain. Also asserts that a role-escalation attempt is rejected and audited without any write.
- `src/modules/users/tests/integration/authenticatable.test.ts` — Integration tests that verify the Mongo filter (`AUTHENTICATABLE_FILTER`) and the in-memory predicate (`isAuthenticatable`) produce the same answer for every combination of the `active` and `deletedAt` flags, using a real database. A second block exercises `linkOAuthAccount` on the user repository.
- `src/modules/users/tests/integration/erasure-announce.test.ts` — Integration tests verifying the `user.erased` outbox event lifecycle: it must be written exactly once on every hard-delete path (admin removal, scheduled purge), must be absent on soft deletes and lost purge claims, and must be consumed by the analytics provider's `forget` method—with the outbox row kept `pending` for retry when that call fails.
- `src/modules/users/tests/integration/erasure-roles.test.ts` — Integration test verifying that a hard-delete of a user account atomically removes the account's roles via the `access` module's erase hook, and that if a *later* module's erasure hook fails the entire transaction rolls back (account and roles both survive). Requests are sent over real HTTP so the production module bootstrap path builds the eraser chain.
- `src/modules/users/tests/integration/external-key-lookups.test.ts` — Integration tests proving that user-lookup queries keyed by external identifiers (email, OAuth subject) reject MongoDB query operators supplied as values, failing with a cast error rather than silently matching every document. The file guards the "Zod is the only thing stopping an injection" assumption at the service layer.
