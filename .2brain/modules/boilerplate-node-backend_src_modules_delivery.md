# src/modules/delivery/

## Purpose

The delivery module owns everything that happens **after** a sale: splitting a paid order into fulfillment orders, cutting shipments from those orders, tracking each shipment through its lifecycle (shipped → delivered / lost / found), managing shipping-rate quotes, handling preorder date changes, and giving staff the operations to hold, release, correct, or reship parcels. It exposes a set of HTTP endpoints, emits domain events and webhooks, and sends buyer-facing emails for every lifecycle transition.

## Key parts

- **`domain/`** — Pure, side-effect-free business rules. `fulfillment.ts` splits order lines into fulfillment orders; `lifecycle.ts` is the shipment state-transition table; `lost.ts` and `reship.ts` encode the invariants for lost parcels and legal-guarantee replacements; `rates.ts` holds the static shipping-rate table; `preorder.ts` computes board state and buyer-notification decisions; `hold-notice.ts` maps internal hold reasons to buyer-safe copy. `index.ts` is the single import point for the domain layer.
- **`controllers/`** — One file per HTTP endpoint (reads for fulfillment orders, shipments, shipping methods, preorder board; writes for processing, shipping, delivering, holding, marking lost, correcting tracking). All are thin: validate, delegate to the service layer, shape the response.
- **`model.ts` / `repository.ts`** — Mongoose schemas for **FulfillmentOrder** and **Shipment**, plus the persistence layer (reads, optimistic-concurrency writes, board search, idempotent inserts) that every service call goes through.
- **`module.ts` / `module.yaml`** — The module manifest consumed by the kernel at boot: registers HTTP mounts, subscribes to cross-module domain events, declares webhook projections and GDPR sections.
- **`events.ts` / `emails.ts` / `asyncapi.webhooks.yaml`** — Outbound communication: typed domain-event payloads (transactional outbox), fully-resolved email copy per language, and the AsyncAPI fragment for the three public webhook events.
- **`pii.ts` / `authorization.yaml` / `config.ts` / `audit.ts`** — Cross-cutting concerns: field-level address encryption, role/action rules, the single config value (hold-note retention), and audit-action identifiers registered into the shared map.
- **`presenter.ts`** — Shapes stored documents into the wire forms declared by `openapi.yaml`, applying per-request visibility (staff notes, computed fields like `remaining`).
- **`jobs.ts`** — Two scheduled jobs: a delivery reaping sweep and a daily preorder sweep.
- **`openapi.yaml`** — The OpenAPI 3.1 contract that pins every route's request/response shape for consumers and contract tests.
- **`tests/`** — Contract tests (validated against the OpenAPI spec) and unit/integration suites for domain and service logic.

## How it connects

- **`orders`** — Delivery subscribes to order lifecycle events (e.g. `paid`) and transitions the order through `processing → shipped → delivered`. The `post-process-order` controller lives under `/orders/:id/process` to keep the path natural.
- **`inventory`** — Subscribed events (stock availability, restock) feed fulfillment-order holds and release-date-impact previews.
- **`products`** — Product data (weight, dimensions) feeds the shipping-rate and weight checks in `domain/rates.ts`.
- **`cart`** — Consumes the public `GET /delivery/methods` endpoint and `rates.ts` logic to show shipping costs before checkout.
- **`returns`** — The `domain/reship.ts` rules determine which fulfillment orders reopen when a delivered item is returned and replaced.
- **`account`** — `emails.ts` follows the same resolved-copy contract (`language` in → final text out) as `@modules/account/emails`, so the mailer adapter renders both identically.
- **`payments`** — Order processing (the `paid → processing` transition) is gated on a successful payment event; delivery acts only after that state change.
- **`infrastructure/adapters`** — The mailer adapter, outbox publisher, and job scheduler that the module's events, emails, and jobs flow through.
- **`delivery/services/`** — The service layer (a sibling directory) sits between controllers and the domain/repository, holding the transactional business-logic acts that controllers delegate to.

## Where to start

1. **`domain/lifecycle.ts`** — A short, pure data table of the three allowed shipment transitions and the birth status. Understanding this state machine makes every controller, event, and email in the module click.
2. **`domain/fulfillment.ts`** — The core splitting logic: how a paid order's lines become fulfillment orders, what remains, and what a shipment may carry. Reading this before touching any controller or service will give you the vocabulary and invariants the rest of the module assumes.

## Files
- `src/modules/delivery/asyncapi.webhooks.yaml` — AsyncAPI fragment that declares the delivery module's three outbound webhook events (`shipment.shipped`, `shipment.delivered`, `shipment.lost`). It is not a standalone document; a build script merges it into the root `webhooks/asyncapi.yaml` contract, and it disappears from the published contract the moment the delivery module is unregistered.
- `src/modules/delivery/audit.ts` — Declares the set of audit-action identifiers that the delivery module emits and registers them into the shared `AuditActionMap` so that the observability layer can type-check every delivery audit entry at compile time.
- `src/modules/delivery/authorization.yaml` — Declares the authorization rules and role sets for the delivery module. It defines which actions a tenant-scoped principal may perform against `Shipment` (update and start) and groups them into named sets that other modules or identity providers reference when granting permissions.
- `src/modules/delivery/config.ts` — Declares the delivery module's single configuration value — the retention window for a staff's free-text hold note — and exposes a typed getter. It follows the read-per-call pattern (rather than a cached constant) so tests can vary the value case by case.
- `src/modules/delivery/controllers/get-date-impact.ts` — Defines the two staff-facing preview endpoints (`GET /delivery/fulfillment-orders/release-date-impact` and `…/restock-date-impact`) that let a user see what would change before actually committing a date move. Both handlers are produced by a single factory so the only differences are the query field, the business cause, and the Zod schema.
- `src/modules/delivery/controllers/get-fulfillment-order.ts` — Thin Express handler for `GET /delivery/fulfillment-orders/:id`. It validates the route parameter, delegates to the delivery service, and maps the service result to an HTTP response. Exists as the single HTTP-facing entry point for fetching one fulfillment order (buyer-scoped or staff-visible, per the service layer).
- `src/modules/delivery/controllers/get-order-fulfillment-lists.ts` — Provides the two HTTP handlers that power the order shipping panel: one returns the fulfillment orders (the plan) for a given order, the other returns the shipments cut from them (what left). Both are unpaged lists, expected to be small, and are only meaningful once the order is paid.
- `src/modules/delivery/controllers/get-preorder-fulfillment-orders.ts` — Defines the two read-only controllers behind the preorder board: one returns a paginated list of fulfillment orders, the other returns per-product unit-count summaries. Both are thin adapters that parse/validate query params and delegate to the delivery service.
- `src/modules/delivery/controllers/get-shipment.ts` — HTTP controller for the `GET /delivery/shipments/:id` endpoint. It retrieves a single shipment by ID for staff viewing/correction and serializes the result into a standard success or refusal response.
- `src/modules/delivery/controllers/get-shipping-methods.ts` — Express route handler for `GET /delivery/methods`. Returns the full list of shipping methods the shop offers (flat rates, free-above thresholds, etc.). Deliberately public so a guest can see shipping costs before deciding to sign up.
- `src/modules/delivery/controllers/patch-shipment.ts` — HTTP handler for `PATCH /delivery/shipments/:id`. It lets staff correct a shipment's tracking code by validating the request, delegating to the delivery service, and returning the updated `Shipment`.
- `src/modules/delivery/controllers/post-deliver-shipment.ts` — Handler for `POST /delivery/shipments/:id/deliver`. It lets staff mark a shipment as delivered; when the *last* pending shipment for an order is delivered, the order transitions `shipped → delivered` (logic lives in the service layer).
- `src/modules/delivery/controllers/post-fulfill-fulfillment-order.ts` — HTTP controller handler for `POST /delivery/fulfillment-orders/:id/fulfill`. Fulfills a *digital* fulfillment order — a shipment with no physical parcel that is born in the delivered state. Delegates the business logic to the delivery service and translates the result into an HTTP response.
- `src/modules/delivery/controllers/post-hold-fulfillment-order.ts` — Express route handlers for holding and releasing a fulfillment order (`POST /delivery/fulfillment-orders/:id/hold` and `…/release`). They validate the request, delegate to the delivery service, and shape the HTTP response.
- `src/modules/delivery/controllers/post-mark-shipment-lost.ts` — HTTP controller for `POST /delivery/shipments/:id/mark-lost`. It validates the route parameter and request body, then delegates the actual "mark shipment lost" operation to the delivery service. It exists to keep route-handling logic (parsing, auth, error formatting) separate from domain logic in the service layer.
- `src/modules/delivery/controllers/post-process-order.ts` — HTTP controller handler for `POST /orders/:id/process`. It is the single endpoint that transitions an order from `paid` to `processing`, called by staff to signal that fulfillment has begun — before any parcel or shipment record exists.
- `src/modules/delivery/controllers/post-ship-fulfillment-order.ts` — HTTP controller that handles `POST /delivery/fulfillment-orders/:id/shipments`. It validates the request, delegates to the delivery service to cut one or more shipments from the remaining quantity of a fulfillment order, and returns the created shipment.
- `src/modules/delivery/domain/fulfillment.ts` — Pure domain rules that decide how an order's lines split into fulfillment orders, what remains on each line, what status a fulfillment order derives, and which lines a shipment may carry. No I/O, no database — every rule is unit-testable in isolation.
- `src/modules/delivery/domain/hold-notice.ts` — Maps an internal `FulfillmentHoldReason` to the buyer-safe notice string and decides whether the hold warrants a buyer notification (mail + inbox row). The mapping deliberately collapses risk-related and "other" holds into a generic "delayed" notice so that the screening rationale is never exposed to the buyer, while still surfacing actionable states (address correction, stock waiting).
- `src/modules/delivery/domain/index.ts` — Barrel (re-export) file that exposes the delivery domain's full public API—lifecycle, rates, fulfillment, lost-shipment, reship, tracking, and preorder rules—without pulling in the module's HTTP or service surface. It is the single import point consumers use to access domain logic, as described in `docs/theory/domain-layer.md`.
- `src/modules/delivery/domain/lifecycle.ts` — Defines the shipment lifecycle as a pure data table (no I/O) that maps the three allowed status transitions—`deliver`, `lose`, `find`—and declares the birth status for physical parcels. Every repository write and service action validates against this table rather than spelling out statuses independently.
- `src/modules/delivery/domain/lost.ts` — Pure domain logic for a delivery fulfillment order's lines when a shipment is reported lost and when that same parcel later turns up. Encodes the invariant that shipped + canceled never exceeds what was bought, and defines when restoration is allowed (all-or-nothing). No I/O or database access, so every case is unit-testable.
- `src/modules/delivery/domain/preorder.ts` — Pure domain rules for preorders whose release date slips. Given a current date, a new date, and a shop timezone, it decides whether the buyer must be told (email) or left in silence, computes the date a fulfillment order is now expected, and derives the board state and lateness a UI or sweep reads. All functions are side-effect-free; the clock is always an argument, so every branch is testable in isolation.
- `src/modules/delivery/domain/rates.ts` — Pure-function module that defines the shop's static shipping-rate table and all price/eligibility queries over it. It exists so that shipping quotes, weight checks, and the refund ceiling for shipping are computed in exactly one place, with all money arithmetic in minor units. It lives in `domain/` (not `services/`) because it has no I/O — just a table and math over it.
- `src/modules/delivery/domain/reship.ts` — Pure domain logic that decides which fulfillment orders must reopen when a customer returns delivered goods and a replacement is resent (legal-guarantee replacement), and how to distribute the "owed" portion (the part the shelf could not cover) across those reopened orders. Extracted as side-effect-free functions so every case is testable in isolation.
- `src/modules/delivery/domain/tracking.ts` — Defines the single rule that determines whether a shipment is "awaiting tracking" — i.e. it shipped via a tracked method but the carrier's code has not yet been recorded. This one predicate drives the `Shipment.awaitingTracking` flag and the "tracked, still without a code" row in the staff digest.
- `src/modules/delivery/emails.ts` — Builds the finished, fully-resolved email copy for all delivery lifecycle notifications (shipped, delivered, lost, hold-notice, fulfillment-delayed). The language is an input argument; the output is final text that the mailer adapter renders without further resolution — the same contract as `@modules/account/emails`.
- `src/modules/delivery/events.ts` — Defines the domain-event payload types for the delivery module and registers them into the kernel's shared `DomainEventMap` via TypeScript module augmentation. Every payload here corresponds to an event that rides the transactional outbox, written in the same transaction as the act that caused it. `shipment.*` events are public (projected into the webhooks catalogue); `fulfillment_order.*` events are internal.
- `src/modules/delivery/index.ts` — Public barrel for the delivery module. It is the **only** import surface that sibling modules (cart, returns, tests) may use, enforcing the strategic-DDD boundary rule. It re-exports domain pricing logic, events, email helpers, service functions, and type definitions, while keeping repositories and runtime model internals private.
- `src/modules/delivery/jobs.ts` — Declares the two scheduled jobs owned by the `delivery` module—a delivery reaping job and a daily preorder sweep—by wrapping domain service calls into `JobDeclaration` objects that the kernel registry can schedule.
- `src/modules/delivery/model.ts` — Defines the two Mongoose schemas and compiled models for the delivery module: **FulfillmentOrder** (a group of an order's lines that should leave together, created when the order is paid) and **Shipment** (what actually left, with one tracking code). Both are keyed by a unique `{ orderId, number }` pair. The file also declares the TypeScript document interfaces, embedded sub-schemas, indexes, and serialization transforms consumed by the repository and service layers.
- `src/modules/delivery/module.ts` — Module manifest entry that wires the delivery domain (shipping rates, fulfillment orders, shipments) into the application kernel. It registers HTTP mounts, subscribes to domain events from `orders`/`inventory`/`products`, declares the public webhook projections, and declares GDPR export/re-encryption sections — all in a single object the kernel registry consumes at boot.
- `src/modules/delivery/module.yaml` — Declarative module definition for the **delivery** subdomain (group: `shop`). It scopes the delivery domain — shipping-rate rules, fulfillment orders, staff shipment operations (cut, arrive, lost, hold/release), and late-preorder buyer notifications — and declares the module's cross-module dependencies and two scheduled background jobs.
- `src/modules/delivery/openapi.yaml` — The OpenAPI 3.1.0 contract for the **delivery** module — the "after the sale" family. It declares the module's public API surface (shipping-method catalogue, fulfillment-order and shipment reads, order-processing transition, preorder board) together with its error taxonomy and personal-data export bindings, so that every consumer (UI, bundler, docs) agrees on the same shapes before any code is written.
- `src/modules/delivery/order-routes.ts` — Defines the Express router for the three delivery operations that live under an order path (`/orders/:id/…`): starting fulfillment via `process`, and reading the order's fulfillment-orders and shipments lists. It exists to keep those routes colocated with the delivery module while still mounting under the `/orders` prefix.
- `src/modules/delivery/pii.ts` — Field-level encryption/decryption of the destination address stored on a shipment. It is the delivery-side twin of `orders/pii.ts`, using the same `NODE_PII_ENCRYPTION_KEY` ring. The encrypted address records *where this parcel went*; the AAD binds every field to the shipment's `_id` so a ciphertext cannot be replayed against a different shipment.
- `src/modules/delivery/presenter.ts` — Single place where stored delivery documents (fulfillment orders, shipments) are shaped into the wire forms declared by `openapi.yaml` and the board/export views. Shapes are *built*, not serialized: computed fields like `remaining` don't exist on the stored document, and per-request decisions (caller `actions`, staff-only notes) are applied here.
- `src/modules/delivery/repository.ts` — Persistence layer for the delivery module. It wires the two Mongoose collections (fulfillment orders, shipments) to the act/services above them, providing the reads, optimistic-concurrency writes (`claim`), idempotent inserts, board search, and product summarisation that every delivery act is driven through.
- `src/modules/delivery/routes.ts` — Defines the Express route table for the delivery module. It maps HTTP paths to controllers, attaching the appropriate authentication, permission, idempotency, and cache middleware per route. The guard strategy is tiered: shipping-methods lookups are public, fulfillment reads require `read:Order`, and every write requires `update:Shipment`.
