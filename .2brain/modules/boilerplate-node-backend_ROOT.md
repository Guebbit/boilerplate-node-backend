# / (repository root)

## Purpose

The repository root holds everything that surrounds the application: project conventions, generated API/event contracts, the Docker deployment and observability stacks, backup infrastructure, and the documentation site. It is the "shell" that turns the TypeScript source in `src/` into a runnable, observable, contract-first service.

## Key parts

- **Project docs & conventions** — `README.md`, `CLAUDE.md`, `INSTALL.md`, `SECURITY.md`, and the `docs/` directory (VitePress site with per-module pages). `CLAUDE.md` encodes the golden rule: contracts are authored at module leaves and generated outward; `docs/api/` explains the regeneration workflow.
- **Generated event contracts** — `asyncapi.yaml` and `asyncapi.public.yaml`. Both are produced by `npm run contracts:bundle` from per-module fragments; they are the single source of truth for SSE streams, webhook deliveries, and RabbitMQ queue channels. Do not edit by hand.
- **Compose stacks** — `docker-compose.yml` (local dev: app + Mongo + Redis + RabbitMQ + observability), `docker-compose.production.yml` (single-tenant production image), `docker-compose.proxy.yml` (shared Traefik overlay), `docker-compose.test.yml` (wired E2E gate). All runtime knobs are `${VAR:-default}` overrides.
- **Container infrastructure (`docker/`)** —
  - *Backup pipeline*: `backup.sh`, `restore-drill.sh`, `drill.sh`, `maintenance.sh`, `server-maintenance.sh`, `entrypoint.sh`, `common.sh` — a full restic-based backup/restore/dedup/check cycle driven by supercronic.
  - *Observability*: OpenTelemetry Collector, Tempo, Prometheus (+ alert rules), Loki, Promtail, Grafana provisioning, Alertmanager — a complete local tracing/metrics/logs/alerting stack with zero external dependencies.
  - *MongoDB bootstrap*: `mongo-init.js` (least-privilege users), `mongo-rs-init.sh` (replica-set initiation), `mongo-entrypoint.sh` (keyFile/TLS cert provisioning).
  - *Smoke test & tooling*: `boot-check.sh` (fail-closed boot + `/livez` + filesystem-permission check), `install-supercronic.mjs` (cron binary for unprivileged containers).
- **Build & tooling config** — among the 394 additional files: `package.json` scripts (e.g. `contracts:bundle`, `backup:drill`), TypeScript config, lint/format rules, CI workflows, and `.env` templates that every stack above reads.

## How it connects

- **`src/` and its sub-modules** (`src/modules/account/`, `src/modules/orders/`, `src/modules/webhooks/`, etc.) are the application code whose event fragments feed `asyncapi.yaml` and whose HTTP routes are exposed by the Docker stacks. The root never contains business logic; it only packages, deploys, and documents it.
- **`src/infrastructure/`** (adapters, HTTP layer) is the runtime that the Compose files configure via environment variables and the observability stack instruments via OTLP/Prometheus endpoints.
- **`scripts/`** contains the build tooling invoked by `package.json` scripts (contract bundling, codegen, seeding) referenced throughout `CLAUDE.md` and `docs/api/`.
- **`scenarios/`** holds E2E test scenarios that `docker-compose.test.yml` and `docker-compose.yml` spin up to validate the full request→response→event pipeline against real backing services.

## Where to start

1. **`README.md`** — a two-minute orientation: tech stack, the contract-first philosophy, and the canonical `npm run` commands for dev, test, and deploy.
2. **`docker-compose.yml`** — reading the local dev stack top-to-bottom shows you every external service the app expects, the env-var contract, and how the optional observability services plug in. Once you can `docker compose up` and hit the API, you have the full mental model of the runtime environment before touching a single line of `src/`.

Runs the production image (built by `docker/Dockerfile.production`) with no source mounts, no host-exposed database port, and no demo seeder. - `docker-compose.proxy.yml` — A Compose overlay that adds a shared Traefik reverse proxy in front of a client stack. It is layered via a second `-f` on top of `docker-compose.production.yml` so that many client stacks on the same host share one proxy instance (one `traefik` container, one set of ACME certs) while each client keeps its own data, network, and project name. It defines routing, TLS termination, and trust-proxy configuration only — no database, volume seeding, or data-plane changes.
- `docker-compose.test.yml` — Composable gate stack that proves the external-service code path (`NODE_TEST_MONGO_URI` / `NODE_TEST_REDIS_URL`) works end-to-end against services the app container did not start itself. It is the "wired" counterpart to the hermetic CI gate (which builds the image and runs `npm run complete` with no external services). Intended for manual pre-merge verification, not as a second CI job.
- `docker-compose.yml` — Orchestrates the local development stack: a single Node.js `app` service (API + seed data), its backing stores (`database`, `redis`, `limits`, `rabbitmq`), and optional observability/analytics services. All runtime configuration (ports, rate limits, worker count, analytics provider) is surfaced as `${VAR:-default}` overrides so that a live E2E run can tune values from the shell without editing `.env`.
- `docker/backup/backup.sh` — Orchestrates a single scheduled backup run: streams a `mongodump` into restic, records the per-collection counts from the dump log, backs up the uploads and mail-spool directories, then applies retention via `restic forget`. Scheduled by supercronic on `BACKUP_SCHEDULE`; the design and failure contract are documented in `docs/tools/backups.md#one-run`.
- `docker/backup/common.sh` — Shared library sourced (never executed) by the backup scripts in this stack. It centralises the configuration knobs with their defaults, sets up the restic environment, provides a Gatus heartbeat, and supplies a small set of helpers (logging, repository bootstrap, job wrapping, Mongo config-file writing, and a mongodump/mongorestore log parser).
- `docker/backup/drill.sh` — End-to-end integration drill that proves the backup system works as a whole: it spins up a production-shaped replica-set MongoDB on a private `--internal` Docker network, seeds data, runs the backup image's `backup-job` and `backup-restore-drill` scripts, verifies restic deduplication across three runs, restores into a throwaway Mongo and compares row counts, exercises the Gatus heartbeat (green on success, red on failure), and tests the cron scheduler (active and dormant). It is the single command (`npm run backup:drill`) that CI runs to confirm nothing in the backup pipeline is broken.
- `docker/backup/entrypoint.sh` — Entrypoint for the `backup` Docker service. It translates a small set of environment-variable "knobs" into a crontab file, validates that crontab, then `exec`s **supercronic** as PID 1 to run the scheduled backup jobs. An empty `BACKUP_REPOSITORY` yields a dormant (no-op) container that still reports healthy.
- `docker/backup/maintenance.sh` — Weekly restic repository upkeep, scheduled by supercronic via `BACKUP_CHECK_SCHEDULE`. It reclaims space from previously forgotten snapshots and reads a rotating slice of stored data to surface corruption well before a restore would be needed.
- `docker/backup/restore-drill.sh` — Performs a full restore drill against a **throwaway** MongoDB instance and a temp directory to prove the latest backup snapshots are actually restorable and byte-identical, then reports elapsed wall-clock time as the estimated shop-downtime on a bad day. Never touches the live database. Exits 0 only if every step passes.
- `docker/backup/server-maintenance.sh` — Scheduled maintenance script (run by supercronic on `BACKUP_SERVER_SCHEDULE`) that prunes and integrity-checks every client's restic repository stored on the backup server's local disk. It is the **only** code path that deletes old snapshots, because the application side of each client is append-only and never issues `forget`.
- `docker/boot-check.sh` — Integration smoke-test that boots a production Docker image against a real MongoDB container and proves two things unit tests cannot: the image starts with fail-closed config and answers `/livez`, and the runtime `node` user cannot write under `/app/src/`. Used by both CI (`boot` job) and local development so the proof cannot drift between environments.
- `docker/install-supercronic.mjs` — Downloads, verifies, and installs the [supercronic](https://github.com/aptible/supercronic) cron scheduler binary into `/usr/local/bin` during Docker image builds. It exists because busybox `crond` resets supplementary groups before each job (requiring `CAP_SETGID`), which breaks under the unprivileged `node` user; supercronic runs jobs as-is. Written in Node (rather than shell) because Node is the one download tool guaranteed on both Alpine and Debian slim base images.
- `docker/mongo-entrypoint.sh` — Wrapper around the official MongoDB image's `docker-entrypoint.sh` that guarantees the replica-set keyFile and wire-TLS certificates exist (with correct ownership) before mongod starts. It replaces an earlier one-shot Compose service because podman-compose 1.6 / libpod refuses to start containers that transitively depend on an already-exited container; wrapping the entrypoint avoids that dependency chain entirely.
- `docker/mongo-init.js` — One-time MongoDB bootstrap script that runs only against an empty data directory (via `docker-entrypoint-initdb.d`). It creates least-privilege application and backup users so the app never authenticates as the instance root, limiting blast radius if a connection string leaks.
- `docker/mongo-rs-init.sh` — One-shot Compose service that initiates the `rs0` replica set on the `database` container and blocks until that node becomes PRIMARY. - `shared/contracts/spectral.modules.yaml` — Spectral ruleset for linting a single module's OpenAPI file (`src/modules/<name>/openapi.yaml`) in isolation. It inherits the full rule set from the base config and selectively disables the rules that presuppose a single file is the entire API, since cross-cutting concerns (tags, security schemes, servers, info prose) are declared once in the root contract.
- `shared/contracts/spectral.yaml` — Spectral linter configuration for the project's OpenAPI 3.1 specifications. Extends the base `spectral:oas` preset and layers on project-specific rules that enforce security declarations, correct verb/operationId alignment, naming conventions for operations and schemas, and mandatory `maxLength` on request strings. Every rule is set to `severity: error`, so violations block the CI pipeline.
- `stryker.json` — Stryker mutation-testing configuration for this repository. It defines which source files are mutated, how Jest is invoked during mutation runs, where reports are written, and what thresholds gate the result. It exists so that CI (and local runs) can execute a consistent, incremental mutation-testing pass without hard-coding options elsewhere.

The unit suite mocks `amqplib` and only verifies the arguments passed to the broker; this file answers questions only a live broker can: whether topology actually declares on the running version, whether a retry republish carries the `x-retry-attempt` header, and where a message lands once its delivery limit is exhausted.
- `tests/broker/support/rabbitmq.ts` — Provides a ready-to-use RabbitMQ broker for the queue-broker test suite, scoped to a throwaway vhost so each run is isolated from prior topology. It either connects to a pre-existing broker (via `NODE_TEST_RABBITMQ_URL`) or spins one up in a container, then hands back an AMQP URL, a typed management-API handle, and a cleanup function.
- `tests/cluster/rate-limit.test.ts` — Cluster-level integration test that proves the rate limiter enforces **one** shared budget across all worker processes when counters live in Redis, and (as a control) demonstrates the per-worker doubling that occurs with the default in-memory store. It exists because no single-process test can distinguish a shared counter from a per-process one, so a regression to the in-memory store would otherwise pass every test in the repository.
