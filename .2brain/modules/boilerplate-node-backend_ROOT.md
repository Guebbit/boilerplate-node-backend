# / (repository root)

## Purpose

The repository root holds the project-level identity, deployment orchestration, observability stack, and generated API contracts for an Express 5 + TypeScript + Mongoose REST API. It is the "shell" that wraps the application code: it defines how the service is built, deployed, observed, backed up, and contracted to external consumers.

## Key parts

- **Identity & onboarding docs** — `README.md`, `CLAUDE.md`, `INSTALL.md`, `SECURITY.md` describe the project's architecture philosophy (contract-first, modular, observable), the external prerequisites (accounts, keys, domains), and the vulnerability-reporting channel.
- **Generated AsyncAPI contracts** — `asyncapi.yaml` and `asyncapi.public.yaml` are the single, versioned source of truth for all SSE streams, webhooks, and RabbitMQ job-queue messages. They are produced by `npm run contracts:bundle` from per-module fragment files and feed the type-generator, Spectral lint rules, and downstream consumers. Never hand-edited.
- **Compose stacks** — `docker-compose.yml` (local/CI dev stack with hot-reload, demo data, optional observability), `docker-compose.production.yml` (the four-service production unit consumed by `docker/deploy.sh`), `docker-compose.proxy.yml` (shared Traefik overlay for multi-client hosts), and `docker-compose.test.yml` (wired gate for external-service code paths).
- **Deployment & ops scripts** (`docker/`) — `deploy.sh` (single-command deploy with auto-rollback), `deploy-drill.sh` (end-to-end rollback verification), `boot-check.sh` (fail-closed image smoke-test), `mongo-entrypoint.sh` / `mongo-init.js` / `mongo-rs-init.sh` (MongoDB bootstrap and replica-set initiation), and `install-supercronic.mjs` (cron binary provisioning).
- **Backup pipeline** (`docker/backup/`) — A complete scheduled-backup system: `entrypoint.sh` (supercronic PID 1), `backup.sh` (mongodump → restic), `restore-drill.sh` (throwaway restore verification), `drill.sh` (CI integration gate), `maintenance.sh` (restic upkeep), and `server-maintenance.sh` (cross-client snapshot pruning).
- **Observability stack** (`docker/observability/`) — Configs and provisioning for Prometheus, Alertmanager, Loki, Tempo, OpenTelemetry Collector, Promtail (Docker and Podman variants), Grafana datasources/dashboards, and Umami analytics, plus `validate-configs.sh` to catch image/config drift.
- **Docs site** (`docs/`) — VitePress-powered documentation with sidebar navigation, Mermaid rendering, and API workflow pages.

## How it connects

- **`src/` and its sub-modules** (`src/modules/*`, `src/infrastructure/*`) are the application code that the Compose stacks deploy and the observability stack instruments. Each module contributes an AsyncAPI fragment that the root-level `contracts:bundle` step aggregates into `asyncapi.yaml`.
- **`scripts/`** houses the `contracts:bundle`, type-generation, and lint tooling referenced by the root's contract files and CI workflow.
- **`scenarios/`** likely contains the end-to-end integration test scenarios that `docker-compose.test.yml` and `boot-check.sh` exercise against a running stack.
- The root's `docker/` infrastructure is the execution environment for all `src/` code in production; the backup and deploy scripts operate on the image that `src/` is built from, without modifying its source.

## Where to start

1. **`README.md`** — gives the one-paragraph architecture summary (Express 5, TypeScript, Mongoose, contract-first, modular, observable) and the top-level `npm run` commands, so you understand the shape before diving in.
2. **`docker-compose.yml`** — reading the dev stack reveals every service the API depends on (Mongo, Redis, RabbitMQ, optional Prometheus/Grafana), the environment variables that wire them together, and the volume/network topology that the rest of `src/` assumes at runtime.

- `docker-compose.production.yml` — The production deployment stack for a single client's API instance. Unlike `docker-compose.yml` (development), it runs the built image (`APP_IMAGE`), exposes no database port to the host, omits all dev observability tooling, and provisions only the four services the application requires: `app`, `cron`, `setup`, and (optionally) the bundled data services. It is the unit that `docker/deploy.sh` builds, starts, health-checks, and rolls back per client.
- `docker-compose.proxy.yml` — A Compose overlay that adds a shared Traefik reverse proxy in front of a client stack. It is layered via a second `-f` on top of `docker-compose.production.yml` so that many client stacks on the same host share one proxy instance (one `traefik` container, one set of ACME certs) while each client keeps its own data, network, and project name. It defines routing, TLS termination, and trust-proxy configuration only — no database, volume seeding, or data-plane changes.
- `docker-compose.test.yml` — Composable gate stack that proves the external-service code path (`NODE_TEST_MONGO_URI` / `NODE_TEST_REDIS_URL`) works end-to-end against services the app container did not start itself. It is the "wired" counterpart to the hermetic CI gate (which builds the image and runs `npm run complete` with no external services). Intended for manual pre-merge verification, not as a second CI job.
- `docker-compose.yml` — Defines the local (and CI) container stack for the Node.js API and its backing services. It wires together the app, database, caches, message broker, and optional observability/analytics services into a single `compose up` experience that is hot-reloadable, seeded with demo data, and compatible with both Docker and Podman.
- `docker/backup/backup.sh` — Orchestrates a single scheduled backup run: streams a `mongodump` into restic, records the per-collection counts from the dump log, backs up the uploads and mail-spool directories, then applies retention via `restic forget`. Scheduled by supercronic on `BACKUP_SCHEDULE`; the design and failure contract are documented in `docs/tools/backups.md#one-run`.
- `docker/backup/common.sh` — Shared library sourced (never executed) by the backup scripts in this stack. It centralises the configuration knobs with their defaults, sets up the restic environment, provides a Gatus heartbeat, and supplies a small set of helpers (logging, repository bootstrap, job wrapping, Mongo config-file writing, and a mongodump/mongorestore log parser).
- `docker/backup/drill.sh` — End-to-end integration drill that proves the backup system works as a whole: it spins up a production-shaped replica-set MongoDB on a private `--internal` Docker network, seeds data, runs the backup image's `backup-job` and `backup-restore-drill` scripts, verifies restic deduplication across three runs, restores into a throwaway Mongo and compares row counts, exercises the Gatus heartbeat (green on success, red on failure), and tests the cron scheduler (active and dormant). It is the single command (`npm run backup:drill`) that CI runs to confirm nothing in the backup pipeline is broken.
- `docker/backup/entrypoint.sh` — Entrypoint for the `backup` Docker service. It translates a small set of environment-variable "knobs" into a crontab file, validates that crontab, then `exec`s **supercronic** as PID 1 to run the scheduled backup jobs. An empty `BACKUP_REPOSITORY` yields a dormant (no-op) container that still reports healthy.
- `docker/backup/maintenance.sh` — Weekly restic repository upkeep, scheduled by supercronic via `BACKUP_CHECK_SCHEDULE`. It reclaims space from previously forgotten snapshots and reads a rotating slice of stored data to surface corruption well before a restore would be needed.
- `docker/backup/restore-drill.sh` — Performs a full restore drill against a **throwaway** MongoDB instance and a temp directory to prove the latest backup snapshots are actually restorable and byte-identical, then reports elapsed wall-clock time as the estimated shop-downtime on a bad day. Never touches the live database. Exits 0 only if every step passes.
- `docker/backup/server-maintenance.sh` — Scheduled maintenance script (run by supercronic on `BACKUP_SERVER_SCHEDULE`) that prunes and integrity-checks every client's restic repository stored on the backup server's local disk. It is the **only** code path that deletes old snapshots, because the application side of each client is append-only and never issues `forget`.
- `docker/boot-check.sh` — Integration smoke-test that boots a production Docker image against a real MongoDB container and proves two things unit tests cannot: the image starts with fail-closed config and answers `/livez`, and the runtime `node` user cannot write under `/app/src/`. Used by both CI (`boot` job) and local development so the proof cannot drift between environments.
- `docker/deploy-drill.sh` — End-to-end integration drill that exercises `docker/deploy.sh` against the real production Compose file using a throwaway client (generated secrets, unique project name). It verifies the full deploy → broken-deploy (auto-rollback) → second-deploy → manual `--rollback` lifecycle, asserting container state, log entries, and a live `/livez` endpoint after each step. Invoked via `npm run deploy:drill`.
- `docker/deploy.sh` — Single-command deploy/rollback script for one client's production stack. It brings up (or re-runs) the compose-defined services against a specific image, polls until the stack is provably healthy, and — if it is not — restores the last known-good image. All successful states are appended to a per-client log that doubles as the sole rollback history.
- `docker/install-supercronic.mjs` — Downloads the **supercronic** static binary, verifies it against a pinned SHA-256 digest, and installs it at `/usr/local/bin/supercronic` during Docker image builds. It is written in Node (rather than a shell script) because Node is the single tool guaranteed present in both the Alpine and Debian-slim base images. Supercronic replaces busybox `crond` because `crond` requires `CAP_SETGID` to reset supplementary groups per job, which breaks under the unprivileged `node` user.
- `docker/mongo-entrypoint.sh` — Wrapper around the official MongoDB image's `docker-entrypoint.sh` that guarantees the replica-set keyFile and wire-TLS certificates exist (with correct ownership) before mongod starts. It replaces an earlier one-shot Compose service because podman-compose 1.6 / libpod refuses to start containers that transitively depend on an already-exited container; wrapping the entrypoint avoids that dependency chain entirely.
- `docker/mongo-init.js` — One-time MongoDB bootstrap script that runs only against an empty data directory (via `docker-entrypoint-initdb.d`). It creates least-privilege application and backup users so the app never authenticates as the instance root, limiting blast radius if a connection string leaks.
- `docker/mongo-rs-init.sh` — One-shot Compose service that initiates the `rs0` replica set on the `database` container and blocks until that node becomes PRIMARY. It exists because MongoDB's own entrypoint init-scripts run against a temporary standalone mongod (no `--replSet` flag), so `rs.initiate()` is impossible there; this script targets the real, replSet-enabled instance after it has already started.
- `docker/observability/alertmanager-render.sh` — Renders `alertmanager.config.template.yaml` into a final `alertmanager.yml` by substituting environment variables and stripping inactive receiver groups, then optionally `exec`s Alertmanager as the container's main process. Written in POSIX sh (busybox, no bash, no `envsubst`) so it runs inside the Alertmanager container image itself.
- `docker/observability/alertmanager-routes-test.sh` — End-to-end test that verifies the rendered Alertmanager routing and inhibit rules work as intended for every combination of notification "knobs" (email, webhook, heartbeat). It renders the config template, validates it with `amtool check-config`, asserts receiver routing with `amtool config routes test`, and—because `amtool` has no static inhibit-rule check—spins up a live Alertmanager daemon to confirm which alerts are suppressed. Designed to run inside the `prom/alertmanager` image, which ships `amtool` and `busybox`.

- `docker/observability/prometheus.alert-rules.yaml` — Defines the full set of Prometheus alert rules for the local API stack, covering availability, error rate, latency, saturation, memory pressure, queue/outbox failures, webhook delivery, and scheduled-job liveness. Without it Prometheus starts with no targets, no alert routing, and no rule evaluation.

It pins all non-default settings—listening ports, OTLP ingest endpoints, block lifecycle, and the local-disk storage backend—so Tempo can run as a single container with zero external dependencies while still accepting real OTLP traffic from the collector.

Committed byte-identical in both `boilerplate-node-backend` and `boilerplate-php-laravel-backend`; `--check` (wired into `complete`) fails the build if the bundle drifts from its source fragments.

- `shared/contracts/asyncapi.root.yaml` — The service-level preamble for the AsyncAPI 3.0.0 contract. - `shared/contracts/asyncapi.workers.yaml` — A standalone AsyncAPI 3.0.0 document that declares the application-level worker queues (`worker.email.send`, `worker.image.digest`) which do not belong to any single domain module. It exists so these cross-cutting job contracts live beside the root contract rather than being trapped inside whichever module happens to enqueue the most jobs, and so they can be linted independently via `npm run lint:asyncapi:modules`.
- `shared/contracts/openapi.root.yaml` — Root OpenAPI 3.1.0 document for the "Boilerplate API". It defines the global contract surface that every module fragment inherits: the API's i18n and response-shape conventions, the shared error-code catalogue, app-level error responses that no single module owns, server URLs, and the base security scheme. Module fragments (e.g. `src/modules/*/openapi.yaml`) are merged into this document by the bundler to produce the final published spec.
- `shared/contracts/spectral.asyncapi.modules.yaml` — Spectral ruleset for linting **individual** AsyncAPI section files (`src/modules/<name>/asyncapi.yaml`, `shared/contracts/asyncapi.workers.yaml`) in isolation via `npm run lint:asyncapi:modules`. It selectively disables rules that check service-wide facts already declared once in the root contract, so each section can be validated as a standalone document without being penalised for not restating the full service identity.
- `shared/contracts/spectral.modules.yaml` — Spectral linting configuration for individual module OpenAPI files (`src/modules/<name>/openapi.yaml`). It relaxes the rules that assume a file describes an entire deployed API (global tags, security schemes, servers, `info` prose) because those concerns are declared once in the root contract rather than restated by every module. Used by `npm run lint:openapi:modules`.
- `shared/contracts/spectral.yaml` — Spectral (OpenAPI linter) ruleset that enforces the project's API contract conventions. It extends `spectral:oas` and adds custom rules covering security declaration, naming, error/response shape, and schema hygiene so that contract drift is caught at lint time rather than in review.
- `shared/rules/schemas/audit-actions.schema.json` — JSON Schema (draft 2020-12) that validates the structure of audit-action rule definitions. It enforces that every action entry carries a namespaced `security.*` identifier and a human-readable description, ensuring a consistent vocabulary across audit rules in the shared rules directory.
- `shared/rules/schemas/defaults.schema.json` — JSON Schema (draft 2020-12) that validates a top-level `defaults` configuration object.
