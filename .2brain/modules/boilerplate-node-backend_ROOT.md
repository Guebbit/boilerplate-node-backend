# / (repository root)

## Purpose

The repository root is the control plane for a contract-first, modular Express 5 + TypeScript + Mongoose REST API boilerplate. It defines the project's identity, deployment topology (development, production, multi-client, backup), the quality gates that guard every merge, and the generated OpenAPI contract that drives client/server codegen. Application logic lives in `src/`; this layer governs *how* it is built, tested, deployed, and documented.

## Key parts

- **Project identity & contracts** — `README.md`, `CLAUDE.md`, `INSTALL.md`, `package.json`, `SECURITY.md`. The manifest declares dependencies, the full script surface, and the `postinstall` hook that regenerates API types and the permission vocabulary. `openapi.yaml` is the bundled (read-only) OpenAPI 3.1 spec; `orval.config.ts` turns it into TypeScript models and Zod validators.
- **Deployment stacks (Docker Compose)** — `docker-compose.yml` (single-command dev stack), `docker-compose.production.yml` (per-client production image, no source bind-mounts), `docker-compose.proxy.yml` (Traefik overlay for multi-client TLS/routing on one host), `docker-compose.backup-server.yml` (off-host restic backup receiver with write-only history protection), `docker-compose.test.yml` (hand-run proof of the external-service env-var path).
- **Quality gates** — `eslint.config.ts` (flat-config lint rules), `jest.config.js` + `jest.config.broker.js` / `cluster.js` / `mutation.js` (four distinct test suites), `mutation-baseline.json` (per-file mutation-coverage reference), `commitlint.config.cjs` (Conventional Commits enforcement), `knip.config.ts` (dead-code audit input).
- **Documentation site** — `docs/` rendered by VitePress (config in `docs/.vitepress/`). Covers getting-started, API standards, authorization model, data-protection obligations, ops reference, and tool-by-tool guides (Prometheus, Gatus, idempotency, mutation testing, backups, etc.).
- **Docker images** — `docker/` holds the development and production Dockerfiles consumed by the compose files above.

## How it connects

- **`src/`** is the application entry point (`src/cluster.ts`) and the code the compose stacks run, the Jest configs test, and the ESLint config lints. Root files configure *how* `src/` is built and verified; they contain no runtime application logic.
- **`shared/`** supplies the per-module OpenAPI fragments and the permission vocabulary that `scripts/contracts/` bundles into `openapi.yaml`; `orval.config.ts` then turns that artifact into the `@api/models` and `@api/schemas.zod` imports used throughout `src/`.
- **`scripts/`** (and `scripts/contracts/`) hold the build, audit, and codegen tooling invoked by `package.json` scripts; root configs (ESLint, Jest, Knip, Orval) feed into them.
- **`docker/`** provides the image layers that `docker-compose.production.yml` and `docker-compose.test.yml` pull or build.
- **`src/modules/*`** (account, cart, orders, payments, etc.) are the feature verticals whose routes, services, and per-module `openapi.yaml` fragments collectively form the API surface described in `openapi.yaml` and documented under `docs/`.
- **`scenarios/`** supplies end-to-end test scenarios consumed by the cluster and integration Jest suites defined at the root.

## Where to start

1. **`README.md`** — a two-minute tour of the architecture, the five-command dev workflow, and the contract-first rule ("edit at the leaves, generate everywhere else").
2. **`CLAUDE.md`** — a short, opinionated guide to the project's non-negotiable conventions (contract order, test philosophy, module boundaries) that will shape how you navigate every sub-module.

- `tests/cluster/rate-limit.test.ts` — Verifies that the rate-limit budget is **shared across all cluster workers** when a Redis store is configured, and deliberately reproduces the per-process bug when it is not. A single-process test cannot distinguish a shared counter from a per-process one, so without this suite a regression back to the in-memory store would pass the entire repository's test run.
- `tests/cluster/redis-idle.test.ts` — Integration test that verifies a Redis client created by the production adapter stays connected and responsive after sitting idle longer than node-redis' `socketTimeout` ceiling. It guards against a regression where the absence of a keepalive ping causes a healthy client to self-close and the cache to report `unavailable` between requests.
- `tests/cluster/support/cluster.ts` — Boots the real cluster entry point (`src/cluster.ts`) as a spawned child process with genuine worker forks and a real TCP port, so that tests can observe cross-process state — the class of bug a single-process `supertest` setup structurally cannot reproduce. Every test in the `tests/cluster/` directory talks to a live multi-process cluster over sockets rather than mounting an Express app in-process.
- `tests/cluster/support/redis.ts` — Provides a Redis instance for the cluster test suite. It either connects to an already-listening Redis (via `NODE_TEST_REDIS_URL`, as in CI) or starts a throwaway container using the repo's existing container-engine helper, so cluster tests that depend on Redis can run in both local and CI environments without a hard dependency on a specific orchestrator.
- `tests/contract/authorization-contract.test.ts` — A contract-derived authorization sweep that asserts, over HTTP, two invariants for every mounted route: (1) any route behind an identity guard returns **401** to a callerless request, and (2) any route behind `requirePermission` returns **403** to exactly the tenant personas whose role file does not grant the required permission. Instead of 40+ hand-written 401/403 assertions scattered across per-module contract files, this file derives expected outcomes from the authorization model (`holds` + `PRESET_ROLES`) and tests them in one table-driven pass per route.
- `tests/contract/config.contract.test.ts` — Contract tests for the `GET /config` endpoint. Pins the public response shape (session config, OAuth providers, antibot/human-challenge settings, operator identity, and Terms version) to guarantee all pieces arrive together, require no credential, and carry a short public cache header. Exists to catch regressions where a field silently disappears, changes type, or gains an unintended dependency on request-specific state.
- `tests/contract/cookie-auth.test.ts` — Contract test for the `cookie` session mode. While every other suite authenticates via `transport: 'bearer'`, this file exercises the `cookieAuth` alternative: it verifies that a browser-style request (no bearer token, just a `__Host-session` cookie) can read, can write from the declared CORS origin, and is refused with `403` on a write from a foreign origin. It sets the session mode itself, so it runs in both contract lanes.
- `tests/contract/idempotency.test.ts` — Integration test for the `Idempotency-Key` middleware, exercised against a real database through `POST /tasks` (chosen as the simplest opted-in route: public, single-field, no auth friction). It covers the three-way branch on key collision—replay, mismatch, and in-flight conflict—that the unit test (`tests/unit/…/idempotency.test.ts`, which covers pure fingerprinting logic) cannot reach.
- `tests/contract/ownership-contract.test.ts` — Contract test that enforces two invariants about IDOR defense: **completeness** — every customer-reachable ID in a URL path, request body, or query parameter is classified in exactly one ownership list (derived live from mounted routes + `openapi.yaml`, never hand-written) — and **the sweep** — for the foundation families (saved addresses, login sessions, notifications), a foreign ID in the URL or body returns 404, identical to a missing ID. This is the ownership half; `authorization-contract.test.ts` covers the permission half (role → route reachability).
- `tests/contract/ownership-shop.contract.test.ts` — Contract test for the "shop half" of the ownership sweep. It verifies that Customer B, hitting any shop-module route (orders, payments, delivery, invoicing, returns, cart) with Customer A's ID in a path param, request body, or list filter, receives a 404 indistinguishable from a missing ID. The world is built through the modules' own factories; the attacks go exclusively over HTTP.
- `tests/contract/password-set-paths.test.ts` — Contract test that verifies **every** route which writes a password enforces the same breached-password rejection. Instead of testing the check once per module (and risking a gap when a new entry point is added), it exercises all three owner-facing paths over HTTP with one known-breached fixture, and a second "canary" block reads the bundled OpenAPI spec to assert no *other* route sets a password. Scoped system-wide because the invariant spans the contract, not a single module.
- `tests/contract/product-write.test.ts` — Contract tests for the multilingual product **write** surface (`POST /products`, `PUT /products/{id}`, `PATCH /products/{id}`) exercised over real HTTP. The file lives at top-level `tests/contract/` rather than under `src/modules/products/tests/` because driving these routes requires a real `locales` collection row, which the `products` module may only reach through the `kernel/translation.ts` port — making the suite inherently cross-module.
- `tests/contract/request-contract.test.ts` — Contract-derived **request** tests: for every write endpoint the OpenAPI spec declares, this file verifies the API accepts every payload the spec declares legal (2xx) and rejects every payload the spec declares illegal (422). It is the mirror image of the sibling `tests/contract/*` files, which compare real responses against the spec; here the spec is the source of the *inputs*. It also sweeps every `in: query` parameter constrained by `enum` or `pattern` and asserts a violating value yields 422. Generated test data is used so the suite stays exhaustive as the spec evolves.
- `tests/contract/request-sources.test.ts` — Contract test that statically compares the input sources each controller declares via `readInput` / `requireId` against the `in:` / `requestBody` declarations in `openapi.yaml`. It asserts that a controller's declared sources are a **subset** of what the spec allows, catching undocumented input (e.g. a path-form delete reading an undeclared body). No server is booted; everything is recovered by reading source files and the spec with regex/`yaml.parse`.
- `tests/contract/route-spec-parity.test.ts` — Contract test that asserts the routes the Express app actually mounts are identical, operation-for-operation, to the operations declared in the bundled `openapi.yaml`. It guards against undocumented endpoints (mounted but not declared) and broken promises (declared but not mounted), and also catches duplicate route registrations.
- `tests/contract/system.test.ts` — Contract tests that assert the exact response shape, status code, and content-type of system-level routes (`/`, `/livez`, `/readyz`, `/.well-known/security.txt`) and the shared error envelopes (404, 422). These tests lock down the public API contract for infrastructure endpoints so that implementation changes cannot silently break downstream consumers.
- `tests/contract/unknown-query-params.test.ts` — Contract test that enforces a **422 response** (not a silent no-op) when an undeclared query parameter is sent to any list-read route. It exists because a dropped filter can return the full result set as though the filter were honoured — a data-leak class of bug that is invisible to happy-path tests.
- `tests/contract/upload-types.test.ts` — Contract test that guards the single source of truth for accepted image upload types. It verifies that every multipart operation in the published OpenAPI spec declares the exact same `imageUpload` content-type list as the runtime constant `ACCEPTED_UPLOAD_TYPES`, preventing drift between the documented contract and the code that enforces it.
- `tests/contract/write-methods.test.ts` — Cross-module contract tests for the write-method standard (spec: `docs/api/write-methods.md`). Verifies rules that must hold for every module's mutations over real HTTP: empty-string rejection, content-type enforcement, idempotency-key replay, `Location` on 201, conditional requests (ETag / If-Match / 412), and 304 revalidation. Module-specific write rules belong in each module's own test files.
- `tests/cross-cutting/account-protection-routes.test.ts` — Guarantees that every write route mounted on the `users` module is explicitly accounted for in the account-protection matrix. A new write route added to `users` will fail this test until it is either added to `PROTECTION_ROWS` or documented in `UNOWNED_WRITES` with a reason, making the protection rule only as strong as the list it audits.
- `tests/cross-cutting/account-protection.test.ts` — Integration test that verifies staff-account protection through the real HTTP app and a real database. For every protection row (a user-mutating endpoint), it asserts that any caller can modify a plain customer, but can only modify an account that holds a staff role (staff, admin, platform-only) if that caller also holds `assign:Role`. It also confirms that API keys can never be minted with `assign:Role`, so no key path can reach a staff account.
- `tests/cross-cutting/alert-rules-metrics.test.ts` — Guards against a silent failure mode: an alert rule referencing a metric name that the code never registers. Such a rule evaluates to an empty vector, never fires, and produces no error. This test statically cross-checks every `*_total` counter used in the Prometheus alert-rules YAML against the metric names registered in `src/`, without booting any process.
- `tests/cross-cutting/analytics-events.test.ts` — Cross-cutting sweep that verifies analytics event names declared across all `src/modules/*/analytics.ts` files remain globally unique. Because every event is reported to a single Umami website keyed by name, a name claimed by two modules produces indistinguishable rows. The test guards both the constant *keys* and the event *string values* to catch both kinds of collision.
- `tests/cross-cutting/api-key-authentication.test.ts` — Proves that an `sk_…` credential actually traverses the real Express chain to reach a route whose identity guard is `isAuthOrCredential` — the "middle link" that neither the unit-level `resolveCredential` tests nor the session-token contract tests cover. A second half statically verifies that no module mounts both identity guards (`isAuth` and `isAuthOrCredential`), keeping the credential-eligibility of a route a property of its module rather than of individual lines.
- `tests/cross-cutting/api-key-security.test.ts` — Cross-checks the OpenAPI contract (`openapi.yaml`) against the actual mounted route guards to verify that `apiKeyAuth` appears in an operation's `security` **exactly** when the route mounts `isAuthOrCredential` and carries no step-up permission. Also pins a small hand-maintained list of anonymous-readable product operations that grant API keys a wider view. The test fails in either direction: a route gaining or losing the guard, or the spec drifting from the code.
- `tests/cross-cutting/api-standards.test.ts` — Enforces two REST standards that the docs state in prose but nothing else mechanically checks: (1) every resource whose `status` enum has more than one value must list `actions` as required, and (2) every 409 refusal in source must carry an error code that a contract fragment declares. Both rules read from **source** (module `openapi.yaml` fragments and `.ts` files under `src/`), never from a generated bundle, so a failure points at a file a developer edits.
