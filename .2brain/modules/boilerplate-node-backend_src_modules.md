# src/modules/

## Purpose

`src/modules/` is the application's feature layer: each subdirectory is a self-contained bounded context (e.g. `access`, `analytics`, `antibot`, `audit-logs`, and dozens more) that owns its data models, business rules, HTTP routes, and tests. Modules communicate with one another only through their public barrel (`index.ts`), keeping internal schemas, repositories, and service invariants private to the owning context.

## Key parts

- **`access/`** — The identity-and-authorization domain. Defines the `Tenant` and `Membership` Mongoose collections, enforces grant/revoke invariants (`services/grants.ts`, `services/protection.ts`), centralises role-change audit emission (`services/role-audit.ts`), and exposes a single `accessService` object for sibling modules.
- **`analytics/`** — A stateless relay for browsing events. Validates a closed set of event schemas at the controller, routes each event to its declaring module's `toReport` via `services/relay.ts`, and forwards to the analytics port. Always returns 204 regardless of whether the event was stored.
- **`antibot/`** — Exposes two read-only endpoints (`GET /antibot/config`, `GET /antibot/challenge`) so a frontend can bootstrap the active human-challenge widget. The enforcement middleware (`humanChallengeGate`) lives in infrastructure; this module only handles the "tell the caller what to expect" side.
- **`audit-logs/`** — Persists the app-wide audit trail behind `GET /audit` (tenant) and `GET /observability/audit` (platform). Wires the write-side sink in `module.ts` so any `emitAuditEvent` call lands in this module's repository; handles retention via a TTL index and operator pseudonymisation in `presenter.ts`.
- **Remaining sub-modules** (87+ additional files) — Cover account, orders, payments, products, inventory, delivery, invoicing, returns, tickets, users, cart, notifications, locales, api-keys, and observability, each following the same manifest → barrel → service → repository → test structure.

## How it connects

- **`src/infrastructure/`** provides the HTTP server, database drivers, and cross-cutting middleware (e.g. `humanChallengeGate`, the analytics emitter port) that module controllers and services consume.
- **`src/` (kernel)** — The kernel's permission and ability resolvers read tenant/membership data from `access/` on every authenticated request; module manifests (`module.ts`) register routes, browser events, and personal-data obligations into the kernel's module registry.
- **Sibling modules** (account, orders, payments, products, etc.) import each other's public barrels for cross-domain operations (e.g. an order service checking a membership, a ticket controller invoking the antibot gate). No module reaches into another's internals.
- **`scenarios/` and `scripts/`** exercise the full module stack in end-to-end or operational flows.

## Where to start

1. **`src/modules/access/index.ts`** — Shows the barrel contract every module follows; reading it tells you exactly what the rest of the codebase may import from `access`.
2. **`src/modules/audit-logs/module.ts`** — A compact, self-contained module manifest that demonstrates how a sub-module wires its router, config, service, and write-side hook into the kernel in one file.

## Files
- `src/modules/access/audit.ts` — Declares the audit-action vocabulary for the access module (role assignment and revocation) and registers it into the app-wide `AuditActionMap` via TypeScript module augmentation. It exists so that compliance queries can find access-mutating events by the `access.*` prefix while distinguishing them from read-only operations like `membershipsOf` or `rolesOf`.
- `src/modules/access/index.ts` — Public barrel (entry point) for the Access module. Sibling modules are restricted to importing **only** from this file (per `docs/theory/strategic-ddd.md` §5); it curates what is exposed externally while keeping internal runtime schemas private.
- `src/modules/access/model.ts` — Defines the two Mongoose collections that persist the authorization domain: **Tenant** (the single shop this deployment serves) and **Membership** (which user holds which role in which scope). It is the data-layer anchor for the `access` module — the "what is stored" that the services in `./services/` enforce write-invariants on and that the kernel resolver reads on every authenticated request.
- `src/modules/access/module.ts` — Defines the **access** module manifest — the identity-and-access domain that `kernel/permissions.ts` and `kernel/ability.ts` query for tenants and memberships. It is intentionally routeless (no HTTP endpoints) and exists purely to expose the tenant/membership collections to other modules via the barrel, while also declaring the module's personal-data obligations (GDPR Art. 15 collection and hard-delete erasure).
- `src/modules/access/repository.ts` — Data-access layer for the **tenant** and **membership** Mongoose collections. It contains only query shaping (filters, update operators, transaction-session pass-through); all business invariants live in `./services/`. Callers in the services layer are the sole consumers.
- `src/modules/access/services/grants.ts` — Defines the authorization rules for assigning and revoking roles. Enforces two invariants at the code level (not documentation): a grant is refused if the role name is not declared in the preset catalog for the target scope, or if the granter does not hold the `assign:Role` permission. Exposes several entry points — throwing, non-throwing, and audited — so callers in different contexts (synchronous validation, HTTP error mapping, pre-transaction checks) can pick the right shape.
- `src/modules/access/services/index.ts` — Barrel file for the access service. It re-exports the public API of the three sub-services (`grants`, `memberships`, `protection`) plus `role-audit`, and bundles every database-reading or writing operation into a single `accessService` object so callers have one import site for all access-related work.
- `src/modules/access/services/memberships.ts` — The service layer for the membership half of the authorization model: creating tenants, assigning and revoking roles (who holds which role in which scope), and bulk operations for reads and erasure. It sits between the repository (raw MongoDB/Mongoose access) and the callers that need business-logic-level membership mutations with validation, audit, and transaction support.
- `src/modules/access/services/protection.ts` — Encapsulates the "protecting people" authorization rule: an account that holds a staff role may only be modified by a caller holding the `assign:Role` ability, and money-step operations on one's own order are flagged in the audit trail. Exposes both the pure decision logic and the async lookup helpers so services can enforce the rule consistently without duplicating the condition.
- `src/modules/access/services/role-audit.ts` — Centralises the audit-row emission for every role change (grant, revoke, refused attempt) so the three writer paths produce a single, consistent audit-trail shape instead of each spelling it differently. It exists to prevent the drift that historically caused one branch (revoke's failure) to silently drop `role` from its metadata.
- `src/modules/access/tests/factories.ts` — Test-side facade that exposes `access`'s internals (membership rows, audit action names, and a granter-less role write) to **sibling modules'** tests. Siblings import from this file instead of `../model` or `../audit` directly, because their import boundaries forbid reaching into another module's internals (see `docs/reference/tests.md`).
- `src/modules/access/tests/integration/access.test.ts` — Integration tests for the access module's **storage layer** — membership seeding, assignment, revocation, and the invariants that guard them — run against the in-memory MongoDB wired up by `setupTestDb`. Unlike the cross-cutting conformance suite (which proves both backends *agree* on a decision), this file proves the decisions are read **from a correctly-writable store**: one role per person per tenant, no privilege escalation, no undeclared roles, and audit events fired on both success and failure.
- `src/modules/access/tests/unit/grantable-roles.test.ts` — Unit-tests the `grantableRoles` service function in isolation: for each preset caller role, it asserts exactly which tenant-scoped roles that caller may assign, and cross-checks the read-side list against the write-side `assertCanGrant` guard so the two can never drift apart.
- `src/modules/access/tests/unit/protection.test.ts` — Unit tests for the staff-account protection logic in the access module. It verifies that `holdsStaffRole`, `staffHoldersAmong`, `mayChangeAccount`, `canChangeAccount`, `roleProtectedRefusal`, and `ownOrderFlag` enforce the rule that only a holder of `assign:Role` (or the account owner, or the system actor) may modify a staff account, and that a refusal is both returned and audited. All repository and audit I/O is mocked so the tests exercise pure decision logic in isolation.
- `src/modules/analytics/controllers/post-analytics-event.ts` — HTTP controller for `POST /analytics/events`. Validates the request body against a closed set of browsing-event schemas, hands a valid event to the analytics service for optional relay, and always returns **204 No Content** so the client can never distinguish whether the event was stored or dropped.
- `src/modules/analytics/index.ts` — Public barrel (entry point) for the analytics module. It is the **only** surface a sibling module may import from, per the strategic DDD rule documented in `docs/theory/strategic-ddd.md` §5. Internally it simply re-exports the relay service; all other module-owned wiring (`module.ts`, `routes.ts`, `controllers/`) is deliberately excluded from the public API.
- `src/modules/analytics/module.ts` — Module manifest that wires the analytics browsing-event relay into the kernel. It mounts the `/analytics` route, registers the declared browser events (product page opened, search made, etc.) with the analytics service after all modules are known, and marks the module as stateless. Business-fact events (cart, checkout, order, payment, signup, login) are explicitly out of scope here.
- `src/modules/analytics/routes.ts` — Defines the Express route table for the analytics relay. It exposes a single public `POST /analytics/events` endpoint for recording one browsing event. The route is intentionally open to guests; authentication is optional and only serves to attach a signed-in visitor's id when present.
- `src/modules/analytics/services/index.ts` — Barrel file that re-exports the analytics relay API as a single `analyticsService` object. It exists so that consumers (controllers, other modules) import from one well-known path rather than reaching into the `relay.ts` implementation directly.
- `src/modules/analytics/services/relay.ts` — Dispatch layer that receives a validated browsing-event request (from the analytics controller) and forwards it to the analytics port via the event's registered `BrowserEventTarget`. It owns no consent logic (the port handles that) and knows no concrete event names (modules declare those in `AppModule.browserEvents`). It exists to decouple the controller from the per-event provider-mapping logic.
- `src/modules/analytics/tests/contract/api.contract.test.ts` — Contract test for `POST /analytics/events` that pins the API's closed-set behavior: the two known event types (`product_viewed`, `products_searched`) must return `204 No Content`, and any event outside that set must be rejected with `422 Unprocessable Entity`.
- `src/modules/analytics/tests/integration/relay.test.ts` — Integration test for the `POST /analytics/events` relay endpoint. Verifies the relay's core guarantee — that no event reaches the analytics provider without an explicit consent header, and that the HTTP response is `204` in both the consented and non-consented paths. Also covers payload validation (closed event-name set, unknown-field rejection, format checks) driven through the real application stack.
- `src/modules/analytics/tests/unit/relay.test.ts` — Unit tests for the analytics relay service. Verifies that `relayEvent` routes a request body to the owning module's `toReport` function (looked up by the body's `event` field) and forwards the module-built report to the analytics emitter, while silently dropping events that no registered module claims.
- `src/modules/antibot/controllers/get-antibot-challenge.ts` — Express route handler for `GET /antibot/challenge`. It asks the active human-challenge adapter whether it can issue a self-hosted challenge; if so, it returns the challenge object, otherwise it returns a 404. This endpoint is only meaningful for self-hosted (non-vendor) providers—vendor-hosted widgets fetch their challenge from the vendor and never hit this route.
- `src/modules/antibot/controllers/get-antibot-config.ts` — Controller for the public `GET /antibot/config` endpoint. It reports which human-challenge provider is active, supplies the parameters the frontend needs to render that provider's widget, and returns a `rungs` summary of the other antibot mechanisms (identity budgets, email policy). It is one of two routes in the antibot module, the other being `GET /antibot/challenge`.
- `src/modules/antibot/index.ts` — Public barrel (entry point) for the `antibot` module. It is intentionally empty because, per the project's strategic DDD rule (`docs/theory/strategic-ddd.md` §5), sibling modules must import through this barrel—and everything this module owns is internal wiring (`module.ts`, `routes.ts`, `controllers/`) that a barrel never re-exports. The actual runtime concern (the `humanChallengeGate` middleware) is consumed by other modules via `infrastructure/` paths directly, bypassing this file entirely.
- `src/modules/antibot/module.ts` — Module manifest for the **antibot** module. Its job is minimal: declare two public HTTP routes (at `/antibot`) that expose which human-challenge provider is active, so a frontend can decide whether to render a challenge widget before submitting a guarded form. The actual enforcement gate (`humanChallengeGate`) is a cross-cutting middleware owned elsewhere; this module only handles the "tell the caller what to expect" side.
- `src/modules/antibot/openapi.yaml` — OpenAPI 3.1.0 contract for the antibot module (rung 3 of the anti-automation ladder). It declares the two public, unauthenticated endpoints that expose the active human-challenge provider's configuration and (for self-hosted providers) a challenge to solve, plus the schemas the API returns.
- `src/modules/antibot/routes.ts` — Defines the two public HTTP routes for the antibot module — exposing which human-challenge provider is active and, when the server self-hosts that provider, the challenge payload the client must render. Both endpoints are read-only and exist solely to let a browser client bootstrap the challenge flow without hitting a heavier API.
- `src/modules/antibot/tests/contract/api.contract.test.ts` — Contract tests for the `/antibot/challenge` and `/antibot/config` endpoints, plus an end-to-end proof that selecting a provider actually gates a downstream route (`POST /tickets`). The E2E gate case lives here rather than in the tickets suite because `antibot` is the only module that understands both the client-facing challenge and the token-validation side without importing the guarded routes.
- `src/modules/audit-logs/config.ts` — Defines the single configuration surface for the audit-logs module: the retention period (in days) for audit entries. It declares the config shape so the rest of the module and the global configuration loader can validate and supply the value at startup.
- `src/modules/audit-logs/controllers/get-audit.ts` — Controller for `GET /audit`. Returns a paginated, filtered page of the current shop's own action history (audit entries), accessed with a tenant key rather than a platform key. It answers the same query that `observability`'s `listObservabilityAuditEntries` does, but scoped to the tenant.
- `src/modules/audit-logs/index.ts` — Public barrel (single import surface) for the audit-logs module. Sibling modules must import only through this file rather than reaching into `service.ts` or `model.ts` directly, enforcing the strategic DDD encapsulation rule.
- `src/modules/audit-logs/metrics.ts` — Defines the domain-owned Prometheus counter for the audit-logs module. The counter tracks audit entries that made it into the compliance log but failed to persist into the queryable trail, giving operators a signal for the deliberate fail-open path in `record()`.
- `src/modules/audit-logs/model.ts` — Defines the Mongoose schema, indexes, serialization transform, and model for the `AuditLog` collection — the durable store behind `GET /observability/audit`. It persists the same shape that the audit logger (`@infrastructure/observability/audit`) emits, so no translation layer exists between write and read.
- `src/modules/audit-logs/module.ts` — Module manifest for the audit-logs feature. It assembles the router, config slice, and service into an `AppModule` and, via the `onRegistered` hook, wires the write-side sink so that `emitAuditEvent` calls from anywhere in the codebase persist rows through this module's service.
- `src/modules/audit-logs/openapi.yaml` — OpenAPI 3.1.0 contract for the audit-logs module. It defines the shop-scoped `GET /audit` endpoint, the shared `AuditEntryItem` row schema (also referenced by the platform observability endpoint and the account export), and the module's contribution to `AccountExportResponse`.
- `src/modules/audit-logs/presenter.ts` — Transforms a stored audit-log entry into the **platform operator's** view by replacing the raw IP address with a pseudonymised correlation digest. The tenant view serves the entry as stored; this file exists solely to produce the one-field operator variant so the operator can correlate repeated attempts without seeing end-user IPs.
- `src/modules/audit-logs/repository.ts` — Data-access layer for the audit log. Strictly append-and-read: one write entry point (`create`) and two read paths (filtered page search, keyset-cursor pagination for an actor's own entries). There is no update or delete by design — expiry is delegated to a Mongo TTL index on the model.
- `src/modules/audit-logs/routes.ts` — Defines the tenant-facing `/audit` Express router. It exposes a single read endpoint (`GET /audit`) that returns a shop's own action history, gated behind the `read:AuditLog` permission. The router is deliberately tenant-scoped, not platform-operator-scoped.
- `src/modules/audit-logs/service.ts` — The audit-log service that bridges the write path (recording emitted audit entries into the persistence layer) and the three read paths (tenant-staff listing, platform-operator incident view, and per-account data export). It applies the collection's scoping, sorting, and filtering policies on top of the raw repository, keeping those decisions out of the repository itself.
- `src/modules/audit-logs/tests/contract/audit.test.ts` — Contract tests for the `GET /audit` endpoint — the single route owned by the audit-logs module. They verify that an authorized caller (holder of `read:AuditLog`) can filter and retrieve entries, while several invalid filter inputs are rejected with `422` rather than silently returning partial or unfiltered results.
- `src/modules/audit-logs/tests/integration/incidents.test.ts` — Integration tests for the operator-facing `searchIncidents` read path. They pin the exact allow-list of actions the platform operator may see (security failures, failed sign-ins, credential-attack signals) and, equally explicitly, the actions that must be withheld (customer orders, admin actions on customers, successful sign-ins, shop-internal role-protection rows). They also verify that raw IP addresses are replaced by a keyed HMAC digest in the operator view while remaining untouched in the admin view.
- `src/modules/audit-logs/tests/integration/repository.test.ts` — Integration tests for `auditLogRepository` (and one service-level filter) executed against an in-memory MongoDB instance. Verifies create, search-with-filters, pagination semantics, deep-paging correctness, and the `ownOrder` filter — guarding against regressions like capped reads and `Number()`-coerced date bounds.
- `src/modules/audit-logs/tests/unit/retention.test.ts` — Unit test that verifies the TTL index declared on the audit log collection resolves to the correct `expireAfterSeconds` value, both for the default (90 days) and a caller-supplied retention period. Because the TTL is baked in at module-load time from an environment variable, the tests must force a fresh import to exercise different values.
- `src/modules/audit-logs/tests/unit/schema-contract.test.ts` — A compliance contract test that pins down the `auditLogSchema` (Mongoose) as a regulatory artifact rather than a convenience. It asserts the required fields, closed-set enums, schema options (`timestamps`, `bufferCommands`), index topology, and TTL retention window. Unlike typical unit tests, it documents *why* each constraint exists (e.g., a silent buffer would swallow audit-loss signals) and fails if the schema drifts from the operational contract.
- `src/modules/audit-logs/tests/unit/service.test.ts` — Unit tests for `auditLogService.record` and `auditLogService.search`, focused exclusively on their deliberate failure asymmetry: `record` is fail-open (swallows write failures into a log line + metric, never throws) while `search` is fail-closed (propagates read failures to the caller). The repository and logger are mocked because a real repository cannot be made to fail on demand.
- `src/modules/shop/config.ts` — Declares the shop's identity and operational settings—legal name, address, contact, return address, ship-to countries, return-postage rule, and default currency. Every value is read at call time (not captured at import) so tests can vary them per case; a production change requires a restart.
- `src/modules/shop/controllers/get-shop.ts` — Handler for the public `GET /shop` endpoint. It returns the shop's identity, shipping/return addresses, and trade currency so that any caller can identify the seller before making a purchase. No authentication is required by design.
- `src/modules/shop/index.ts` — Public barrel for the shop module. It is the **only** surface a sibling module may import from, enforcing the module-boundary rule codified in `docs/theory/strategic-ddd.md` §5. All exports are re-exported from `./service`; nothing else (config, manifest) is exposed.
- `src/modules/shop/module.ts` — Declares the shop module's manifest: a single routing mount, one config-slice boot gate, and no data persistence. It is the registration point that tells the kernel *what* the shop module exposes and *how* to wire it in.
- `src/modules/shop/routes.ts` — Defines the Express route table for the shop module. It registers a single read-only endpoint (`GET /shop`) that returns the shop's identity, currency, ship-to countries, and return address. Because the response is static (changes only on redeploy) and there are no write paths, the endpoint relies solely on the global burst rate-limit for protection.
- `src/modules/shop/service.ts` — Single reader surface for all shop-level configuration (country, timezone, identity, currency, shipping, returns). Every sibling module that needs a "which country", "where do returns go", or "what's the VAT jurisdiction" answer imports from here instead of reading `shopConfig` directly. Also composes the public `Shop` record returned by `GET /shop`.
- `src/modules/shop/tests/contract/api.contract.test.ts` — Contract tests for the public `GET /shop` endpoint. They verify the exact public payload (seller identity, currency, ship-to countries, return address, terms version) and, just as importantly, that internal/operator data (time zone) is never leaked and that optional fields (VAT number, trade register, registration number) are omitted when unset.
- `src/modules/shop/tests/unit/config.test.ts` — Unit-tests the shop module's configuration layer: both the boot-time gate (`assertModuleConfig`) and the per-call reader functions (jurisdiction, timezone, identity, return address, postage payer, ship-to countries, currency). Verifies required-variable enforcement, value normalization (upper-casing, trimming, canonical timezone names), fallback behavior (return address → shop address), and sensible defaults (currency → EUR, postage payer → consumer).
- `src/modules/sitemap/config.ts` — Defines the sitemap module's configuration surface: the per-file URL limit (a deployment-tunable value) and the list of static frontend pages (a fixed fact derived from the router rules). It exists to keep these two kinds of knowledge separate — one is a product-page setting, the other is a property of the paired frontend.
- `src/modules/sitemap/controllers/get-sitemap-index.ts` — Express handler for `GET /sitemap/index.xml` — the top-level sitemap index that lists all other sitemap files (shop pages + per-run product sitemaps). It delegates file discovery to the sitemap service and XML serialization to a shared helper.
- `src/modules/sitemap/controllers/get-sitemap-pages.ts` — Express controller that serves `GET /sitemap/pages.xml`. It fetches the shop's static pages from the sitemap service, serializes them into an XML sitemap via a `SitemapStream`, and writes the XML to the HTTP response.
- `src/modules/sitemap/controllers/get-sitemap-products.ts` — Express GET handler for `/sitemap/products-{page}.xml`. Validates the page-number path parameter, fetches that page's product entries from the sitemap service, and streams them back as an XML sitemap response.
- `src/modules/sitemap/controllers/send-xml.ts` — Single shared output path for every sitemap file. Given a set of entries and the appropriate `sitemap` XML stream writer, it streams the result into an Express response with a 1-hour public cache header, guaranteeing consistent headers, backpressure handling, and cleanup across all sitemap endpoints.
- `src/modules/sitemap/index.ts` — Public barrel (re-export) for the `sitemap` module. It exists so that sibling modules have a single, stable import target and never reach into the module's internal file layout. Per the strategic-DDD rule (see `docs/theory/strategic-ddd.md` §5), this file is the **only** surface a sibling module is allowed to import from.
- `src/modules/sitemap/module.ts` — Module manifest for the **sitemap** feature. It declares how the `sitemap.xml` endpoint is mounted into the application (route table, config slice, personal-data classification) so the kernel registry can wire it in. The module itself owns no collection; it reads `products` and `locales` through their services to build the XML on request.
- `src/modules/sitemap/routes.ts` — Defines the Express route table for the public, unauthenticated sitemap endpoints. It maps three GET paths to their respective controllers so the module can expose XML sitemaps to crawlers.
- `src/modules/sitemap/service.ts` — Pure read-side logic for generating XML sitemap content. It answers three questions—*which files the index lists, what the pages file contains, and what a given products file contains*—by reading the live product catalogue and the served-locale list on every call. Nothing is persisted here; the HTTP layer is free to cache the results.
- `src/modules/sitemap/tests/contract/api.contract.test.ts` — Contract tests that assert the HTTP-level guarantees of every `/sitemap/*` endpoint: status code, `Content-Type`, and `Cache-Control`. They deliberately do **not** inspect XML body content (entries, alternates, `lastmod`, pagination split)—that responsibility belongs to the integration test in `tests/integration/sitemap.test.ts`.
