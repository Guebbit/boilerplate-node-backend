# src/modules/

## Purpose

`src/modules/` is the collection of all domain (bounded-context) modules in the application. Each subdirectory—`access/`, `addresses/`, `account/`, `cart/`, `orders/`, `payments/`, `users/`, and roughly two dozen others—is a self-contained unit that owns its data, business rules, and HTTP surface. A project-level import-boundary rule enforces that one module may only import from another through that module's public barrel (`index.ts`), keeping internal layers (model, repository, controllers) private.

## Key parts

- **Module layout convention** — Every module follows the same internal structure: `domain/` (pure rules, no I/O), `services/` (business invariants + orchestration), `repository.ts` (Mongoose data access), `model.ts` (schemas), `module.ts` (kernel manifest: routes, config, personal-data hooks), `openapi.yaml` (contract), `controllers/` + `routes.ts` (HTTP adapters), `tests/` (unit, integration, contract). Two fully documented exemplars are `access/` (authorization, roles, tenants) and `addresses/` (per-user address book with PII encryption).
- **Public barrel (`index.ts`)** — The single import surface a sibling module may use. Re-exports the service layer and pure domain rules while keeping schemas, repositories, and routes internal.
- **`module.ts` manifests** — Register the module with the kernel, declare routes (or explicitly none), personal-data lifecycle hooks (GDPR Art. 15 / erasure), and configuration. This is how the kernel discovers and wires modules at boot.
- **`openapi.yaml` contracts** — Authoritative request/response shapes per module; some (like `access`) expose no routes and serve only as shared schema references for sibling modules (e.g. `account`).
- **Tests per module** — Unit (pure logic), integration (in-memory Mongo), and contract (real HTTP) suites live alongside the code they verify, keeping ownership local.

## How it connects

- **Sibling modules** communicate only through each other's `index.ts` barrels (e.g. `cart` reads an address snapshot from `addresses`; `users` calls `access` protection rules before mutating an account; `account` consumes the `access` OpenAPI schema for its authorization payload).
- **`src/infrastructure/` and `src/infrastructure/adapters/`** provide the shared runtime (Express app factory, Mongoose connection, AEAD encryption pipeline, key-rotation scripts) that modules' repositories and PII helpers plug into.
- **`shared/`** supplies cross-cutting vocabulary (role presets, authorization rules in YAML, typed-config wrappers, audit-action map) that every module's domain and service layers reference.
- **`scenarios/` and `scripts/`** contain end-to-end test scenarios and operational scripts (e.g. the PII re-encryption run) that drive multiple modules together.
- **`src/` (top-level)** holds the kernel/registry that loads each `module.ts` manifest and assembles the final application.

## Where to start

1. **`src/modules/access/index.ts`** — the smallest complete public surface; reading it alongside `src/modules/access/domain/protection.ts` shows the "pure rules → service → barrel" layering that every other module repeats.
2. **`src/modules/addresses/module.ts`** — a richer manifest that declares routes, config, personal-data hooks, and PII re-encryption, giving a newcomer a concrete picture of what "registering a module with the kernel" looks like.

## Files
- `src/modules/access/audit.ts` — Declares the audit-action vocabulary for the `access` module and registers it into the app-wide `AuditActionMap` via TypeScript declaration merging. Only two actions exist here (`access.role.assigned`, `access.role.revoked`) because role grant/revocation is the sole operation in this module that changes a user's permissions; all other access operations (e.g. `membershipsOf`, `rolesOf`) are reads and do not emit audit events. Compliance queries can filter by the `access.*` prefix.
- `src/modules/access/authorization.yaml` — Declarative authorization policy for the access module. It defines the single staff-role permission (`assign:Role`) and bundles it into the `RoleManagement` set, governing who may hand a staff role to an account, revoke it, or mutate an account that already holds one.
- `src/modules/access/domain/index.ts` — Barrel file for the access **domain** layer. It re-exports the pure protection rules from `./protection` so that other modules (e.g. `users`, money) can consume access logic without a DB lookup or any framework dependency. A lint rule guarantees this file and its subtree remain free of Express, Mongoose, and every other tier.
- `src/modules/access/domain/protection.ts` — Pure authorization rules for protecting people: whether a caller may modify an account and whether a resource (order, payment, return) belongs to the caller. Contains no I/O — the lookups that supply inputs live in the service layer.
- `src/modules/access/index.ts` — Public barrel for the **access** module. It is the *only* import surface a sibling module is allowed to use (enforced by the module-boundary rule in `docs/theory/strategic-ddd.md` §5). It re-exports the service layer and pure domain rules while deliberately keeping runtime schemas and persistence details internal.
- `src/modules/access/model.ts` — Defines the two Mongoose schemas and exported models that back the authorization domain: **Tenant** (the single shop per deployment) and **Membership** (which user holds which role in which scope). This is the data-shape layer of the access module; it deliberately has no route of its own and is consumed by the kernel's permission resolvers, other modules, and test harnesses.
- `src/modules/access/module.ts` — Module manifest for the **access** domain (tenants and memberships). It registers the module with the kernel registry, declares a single personal-data section for GDPR Art. 15 / erasure compliance, and deliberately exposes no HTTP routes. It exists as a module (not kernel code) because it owns the tenant/membership collections and is consumed by several sibling modules.
- `src/modules/access/openapi.yaml` — OpenAPI 3.1.0 contract for the `access` module. It defines no HTTP routes of its own (`paths: {}`); it exists purely as a shared schema reference so that the `account` module can type the authorization payload it returns on `GET /account`, sign-in, and refresh responses. It also declares the module's `x-personal-data` section (the role list in account data exports).
- `src/modules/access/repository.ts` — Data-access layer for the **tenant** and **membership** MongoDB collections. It exposes a small set of query and write primitives so that the service layer (`./services/`) can focus entirely on business invariants without repeating Mongoose boilerplate. No authorization checks or validation live here.
- `src/modules/access/services/grants.ts` — Defines the authorization invariants for assigning and revoking roles. It enforces two rules as executable code: a role name must be a declared preset in the caller's scope, and the granter must hold the `assign:Role` permission. It exposes both throwing and non-throwing validation paths so callers can check before committing unrelated state, and an audited-refusal path so HTTP responses carry a typed 403/422 reason.
- `src/modules/access/services/index.ts` — Barrel file that assembles the access module's public API. It re-exports pure constants and helper types (role checks, error types, refusal reasons) directly and bundles every database-reading or writing operation into a single `accessService` object, giving consumers one stable import surface for the three service files (`grants`, `memberships`, `protection`) plus the `role-audit` helpers.
- `src/modules/access/services/memberships.ts` — The membership half of the access model: it owns every read and write of the "who holds which role in which place" relationship. A role lives exclusively in a membership row (never on the user document), and this module provides the service-level API for creating tenants, assigning/reviewing/revoking roles, batch-resolving roles, and the idempotent seed a fresh deployment needs to boot.
- `src/modules/access/services/protection.ts` — Implements the "protecting people" rule: an account that holds a staff role may only be modified by a caller holding `assign:Role`. Provides the gate check, the standardised 403 refusal envelope, and the audit-trail side-effect in one composable unit.
- `src/modules/access/services/role-audit.ts` — Centralises the audit-row format for every role mutation (assign, revoke, refused attempt) so that the three call-sites in `grants.ts` emit structurally identical trail entries rather than each hand-rolling a near-identical `recordAudit` block. It exists to eliminate the drift that lets one branch silently drop a field (e.g. `role`) while the others keep it.
- `src/modules/access/tests/factories.ts` — Test-side entry point into the `access` module's storage and audit surfaces. Sibling modules' tests (users, account, payments, returns, api-keys) cannot import `../model` or `../audit` directly due to import-boundary rules; this file re-exports those internals and provides a granter-less `seedMembership` helper so those tests can seed roles and assert on real audit action names without reaching across the boundary.
- `src/modules/access/tests/integration/access.test.ts` — Integration test suite that exercises the authorization module's **storage and writer layer** against an in-memory MongoDB (wired up by `setupTestDb`). It verifies that membership rows can be created, reassigned, and refused correctly, that every invariant enforced by the services is actually executable, and that `bootstrapAccess` behaves idempotently. It is deliberately distinct from the cross-cutting conformance suite: this file proves the data *can be written*, not that two backends *decide the same way*.
- `src/modules/access/tests/unit/grantable-roles.test.ts` — Unit tests for `grantableRoles` and `assertCanGrant` in isolation, verifying which tenant-scoped roles a preset caller is permitted to assign to other members. The test table is the executable model of the grant rule defined in `shared/rules/authorization-roles.yaml`: adding a role or changing its `assignable` flag should surface here as a new or updated row.
- `src/modules/access/tests/unit/protection.test.ts` — Unit tests for the staff-account protection rules in the access service. It verifies that `holdsStaffRole`, `staffHoldersAmong`, `canChangeAccount`, `roleProtectedRefusal`, and the pure helpers `mayChangeAccount` / `ownOrderFlag` behave correctly when membership data comes from an in-memory table rather than a real database. The file exists so the role-gate logic can be exercised in isolation, without a live repository or route.
- `src/modules/addresses/config.ts` — Defines the single configuration knob for the addresses module: the maximum number of entries a single address book may hold. It wraps that value in the project's typed-config infrastructure so other parts of the module can read it with validation.
- `src/modules/addresses/controllers/delete-address.ts` — Thin HTTP adapter for `DELETE /account/addresses/:addressId`. Validates the path-param ID, delegates deletion to `addressService.remove`, and returns a bodyless `204 No Content` on success. Exists to keep Express request/response concerns out of the service layer.
- `src/modules/addresses/controllers/get-address.ts` — Thin HTTP adapter for `GET /account/addresses/:addressId`. It validates the path parameter, delegates to `addressService.get`, and maps the result to a standard HTTP response. Exists so the Express route table stays declarative and all I/O shaping lives in one small, testable function.
- `src/modules/addresses/controllers/get-addresses.ts` — Thin HTTP adapter that exposes `GET /account/addresses`, returning the authenticated caller's full address book in one service call. It exists to decouple Express plumbing from domain logic so the service layer stays transport-agnostic.
- `src/modules/addresses/controllers/post-address.ts` — Handler for `POST /account/addresses`. Validates the request body against a Zod schema, delegates creation to the address service, and returns a `201 Created` response with a `Location` header pointing to the new entry.
- `src/modules/addresses/controllers/put-address-default.ts` — Thin HTTP adapter for `PUT /account/addresses/:addressId/default`. Translates the request (auth context + `addressId` param) into a call on the address service's `setDefault` method, then serializes the result as a `200` JSON response. Exists so the address service stays transport-agnostic.
- `src/modules/addresses/controllers/update-address.ts` — Builds the two HTTP handlers for `PUT /account/addresses/:addressId` (full replace) and `PATCH /account/addresses/:addressId` (partial merge) by calling the shared `createUpdateController` factory. The actual write and ownership check live in the addresses service; this file only wires the transport layer to it.
- `src/modules/addresses/factories.ts` — Builds address-book fixtures for use with `addressBookRepository.create`. It encodes the domain rule that a book is identified by its owner (`userId` is unique on the wire, so no book `_id` is generated) while individual entries are identity-bearing (each carries its own `_id`). The file exists so test and scenario code can produce valid, type-safe book payloads without hand-assembling Mongoose shapes.
- `src/modules/addresses/index.ts` — Barrel (public API) file for the **Addresses** module. It is the single import surface that sibling modules are permitted to use, enforcing the strategic-DDD rule that cross-module access goes through the module's public facade rather than reaching into its internals.
- `src/modules/addresses/model.ts` — Defines the Mongoose schema and compiled model for the user address book. One document per `userId` (the same pattern as the cart), so editing an address updates a small document rather than the whole account. Subdocuments carry their own `_id` because two entries can have identical fields yet represent "home" vs. "office".
- `src/modules/addresses/module.ts` — Module manifest for the address book (one document per user, used at checkout). It declares routes, config, personal-data lifecycle hooks, and PII re-encryption so the address book is a self-contained module: `cart`'s checkout is the only sibling consumer, and `users` reaches it solely through the `personalData.erase` hook below — no direct imports into or from `account`.
- `src/modules/addresses/openapi.yaml` — OpenAPI 3.1.0 contract for the **addresses** module, defining the REST surface (`/account/addresses/*`) that manages a per-user address book. It is the authoritative schema for request/response shapes, status codes, and idempotency semantics that the route handlers in `module.ts` must satisfy.
- `src/modules/addresses/pii.ts` — Encrypts and decrypts the PII fields on a single address-book entry — the postal-address fields GDPR specifically names. It is the one module that bridges the address domain model with the AEAD encryption infrastructure, providing the shared encrypt/decrypt operations that both the repository (writes) and every reader path (service wire-mapping, checkout snapshot) rely on.
- `src/modules/addresses/presenter.ts` — Single mapping layer that converts the internal `AddressBookDocument` shape into the wire shape declared in `openapi.yaml`. Every endpoint in `./service.ts` serialises its response through one of the functions exported here, keeping the "stored → wire" translation in exactly one place.
- `src/modules/addresses/reencrypt.ts` — Thin adapter that feeds address-book documents into the generic PII key-rotation pipeline. It knows *which* fields are encrypted on an address entry and *how* to bind them, then hands the work off to the repository. Exists so the ops `reencrypt` script (see `@infrastructure/security/reencrypt`) has an address-domain entry point without the infrastructure layer needing to know address schema details.
- `src/modules/addresses/repository.ts` — Read-modify-write repository for the per-user address book. It owns all reads and writes to `addressBookModel`, enforcing the "exactly one default" invariant, the `NODE_ADDRESS_BOOK_MAX` entry cap, and PII encryption at the field level. Every value it returns to callers is already decrypted.
- `src/modules/addresses/routes.ts` — Defines the Express router for the address-book endpoints, mounted at `/account` alongside the account module's own router (see `./module.ts`). It wires the six controller functions to their HTTP verbs and paths, applying auth, cache, and idempotency middleware in the correct order for each route.
- `src/modules/addresses/service.ts` — Service layer for the address-book module. It translates controller calls into repository operations, shapes the results via the presenter, and enforces the HTTP response contract (status codes, error payloads). It also exposes the lifecycle hooks (hard-delete, minimisation) and the checkout address-resolution logic that other modules depend on.
- `src/modules/addresses/tests/contract/api.contract.test.ts` — Contract tests for the address-book REST API (`/account/addresses`), exercising every route over real HTTP against a test database. The suite lives in the `addresses` module (not `account`) because the routes are owned by the addresses module even though they are mounted under the `/account` prefix.
- `src/modules/addresses/tests/factories.ts` — Test-helper module that provisions a default address-book entry for an account. It exists so that cart/checkout and user tests, which exercise database-backed flows, can give an account a valid billing address in one call instead of repeating inline `addressService.create` boilerplate.
- `src/modules/addresses/tests/integration/addresses.test.ts` — Integration tests for the address-book service. They verify three core invariants end-to-end against a real database: a non-empty book always holds exactly one default, foreign entries are indistinguishable from invented ones (404), and the book cap is enforced even under concurrent writes. A secondary block confirms PII fields are stored encrypted (not plaintext) yet round-trip correctly through the repository.
- `src/modules/addresses/tests/integration/checkout.test.ts` — Integration tests for address resolution during checkout: which address (default, named, or none) gets frozen as the shipping and/or billing snapshot on an order. Covers the full decision matrix — standard vs. pickup shipping, physical vs. digital baskets, stale/foreign IDs, and empty address books — verifying both the happy-path snapshot content and that refused checkouts leave no side effects.
- `src/modules/addresses/tests/integration/fixtures.ts` — Shared test fixtures providing two fully-specified address objects used by the address-book and checkout integration suites. Exists so both test files reference identical data rather than duplicating inline literals.
- `src/modules/addresses/tests/integration/idempotent-create.test.ts` — Integration test that verifies `POST /account/addresses` honours the `Idempotency-Key` header: a retry after a lost response replays the original entry (201 + `idempotent-replayed: true`) instead of writing a duplicate, while a different key still creates a new address. It guards against the cap-burning scenario where a client double-submits the same logical address.
- `src/modules/addresses/tests/integration/reencrypt.test.ts` — Integration test for the addresses module's `reencrypt` walk. Simulates a PII key rotation (v1 → v2) and verifies three guarantees in a single flow: dry-run writes nothing, the real run re-encrypts all stamped fields to v2, and a second run is a no-op (idempotent). Also confirms the address still reads back correctly under the new key.
- `src/modules/addresses/tests/unit/factories.test.ts` — Unit tests for the `makeAddressBook` fixture builder. They verify that the factory produces MongoDB-ready documents with correct `ObjectId` instances, respects optional-field absence (key not present vs. set to `undefined`), and passes deliverable fields through unchanged.
- `src/modules/addresses/tests/unit/routes.test.ts` — Unit test for the addresses router that asserts the complete route table (signatures, order, middleware, guards) without executing any handler logic. It exists to catch unintended route additions, missing `noStore`/`isAuth` guards, and stray middleware (rate-limiting, caching) in the first-person address-book module.
- `src/modules/addresses/tests/unit/schema-contract.test.ts` — Pins the public contract of `addressBookSchema` so that schema-level semantics (required fields, indexes, sub-document identity, defaults) are verified in isolation. It exists to catch accidental "alignment" with sibling schemas (cart, wishlist) that would silently change address-book behavior — particularly the `_id` on entries and the `default` promotion strategy.
- `src/modules/analytics/controllers/post-analytics-event.ts` — Single controller handler for the public `POST /analytics/events` endpoint. It validates the request body against a closed schema of browsing events, hands the event to the analytics service (which decides whether to relay it based on consent), and always responds `204` so the page can never tell whether its action was measured.
- `src/modules/analytics/index.ts` — Public barrel for the analytics module. It exists as the single, mandated import surface for any sibling module, enforcing the architectural rule (see `docs/theory/strategic-ddd.md` §5) that cross-module access goes only through the relay service and never through internal wiring (routes, controllers, module registration).
- `src/modules/analytics/module.ts` — Module manifest for the analytics relay. Wires together the `POST /analytics/events` route, the analytics service, and the browser-event collection hook so the app can forward consent-gated, browser-reported interaction events (page views, searches) to an external analytics provider. Business events (cart, order, payment, etc.) are explicitly out of scope — they are emitted by the services that perform them.
- `src/modules/analytics/openapi.yaml` — OpenAPI 3.1.0 contract for the analytics module's single browser-facing endpoint. It defines what events a browser may report, the consent semantics around them, and the module's error surface, serving as the canonical API description for both the implementation (`module.ts`) and any client tooling.
- `src/modules/analytics/routes.ts` — Defines the single public write route for the analytics relay (`POST /analytics/events`). It exists to keep the module's HTTP surface in one place: one endpoint, one middleware, one controller, mounted on a shared Express `Router` that the module entry point registers on the app.
- `src/modules/analytics/services/index.ts` — Barrel file for the analytics services layer. It re-exports the browser-event relay functions from `./relay` as a single `analyticsService` object, providing a stable public surface for the rest of the analytics module.
- `src/modules/analytics/services/relay.ts` — Relays a validated browsing event to the analytics port by name. It holds no knowledge of individual event types; instead it looks up a registered `BrowserEventTarget` and delegates the shaping to that target's `toReport`. It exists so that the analytics module can remain decoupled from whichever feature modules define the events.
- `src/modules/analytics/tests/contract/api.contract.test.ts` — Contract tests for the `POST /analytics/events` endpoint. They lock in the closed set of accepted event types (`product_viewed`, `products_searched`) and assert that any event outside that set is rejected, ensuring the API's public contract remains stable.
- `src/modules/analytics/tests/integration/relay.test.ts` — Integration test for the `POST /analytics/events` relay endpoint. Verifies the relay's core contract: the response is always `204` for well-formed events (consented or not), but the analytics provider's `capture` is only invoked when the visitor has consented. Also exercises the validation gate (closed event set, no extra fields, field-format checks) which returns `422` regardless of consent.
- `src/modules/analytics/tests/unit/relay.test.ts` — Unit tests for the relay service's dispatch protocol: verifying that `relayEvent` resolves an event name to the module that registered it, delegates to that module's `toReport`, and emits the resulting analytics payload — while safely dropping unregistered names and inherited prototype keys.
- `src/modules/antibot/controllers/get-antibot-challenge.ts` — Controller for the public `GET /antibot/challenge` endpoint. It resolves the deployment's active self-hosted antibot provider and returns a challenge object for the provider's widget to consume. Vendor-hosted providers never call this route.
- `src/modules/antibot/index.ts` — Public barrel (re-export) for the **antibot** module. It is the *only* surface a sibling module is permitted to import from (per the DDD rule in `docs/theory/stragnostic-ddd.md` §5). It exposes solely the service that the `GET /config` route composes; all internal wiring (`module.ts`, `routes.ts`, `controllers/`) stays private to the module.
- `src/modules/antibot/module.ts` — Module manifest for the **antibot** module. It declares the module's name, HTTP mount point, and data classification so the kernel can discover and wire it into the app. It does **not** implement the anti-automation gate itself — that is cross-cutting middleware (`humanChallengeGate`) living elsewhere. This file exists purely as a registration record.
- `src/modules/antibot/openapi.yaml` — OpenAPI 3.1.0 contract for the antibot module. It defines the single self-hosted challenge endpoint (`GET /antibot/challenge`), the `AntibotConfig` schema that `GET /config` publishes so clients know what anti-bot posture is active, and the ALTCHA-specific challenge shapes. It exists so the API surface of the module is declarative, versioned, and consumable by codegen or documentation tooling.
- `src/modules/antibot/routes.ts` — Defines the Express route table for the antibot module. It exposes a single public endpoint (`GET /challenge`) that delivers the challenge configuration a self-hosted provider needs to render its widget. The route is intentionally stateless and write-free, so it is bounded only by the global burst brake in `app/security.ts`.
- `src/modules/antibot/service.ts` — Provides the antibot module's slice of the `GET /config` endpoint: which human-challenge provider is active, the parameters the client needs to render its widget, and a summary of the other antibot rungs (identity budgets, email policy).
- `src/modules/antibot/tests/contract/api.contract.test.ts` — Contract tests for `GET /antibot/challenge` and a short end-to-end proof that a selected anti-bot provider actually gates a guarded route (`POST /tasks`). The E2E gate test lives here (rather than in `tasks`'s own suite) because `antibot` is the one module that understands both sides of the handshake—what the client renders and what counts as a valid token—without importing the routes it guards. `GET /config` is deliberately excluded; it has its own contract test file.
- `src/modules/antibot/tests/unit/service.test.ts` — Unit test verifying that `antibotService.config` signals a misconfigured provider via promise rejection rather than a synchronous throw, ensuring the controller's `.catch` chain can intercept the error.
- `src/modules/api-keys/audit.ts` — Declares the audit-action vocabulary for API-key lifecycle events (mint, revoke, compromise-triggered bulk revoke) and registers those actions into the application-wide `AuditActionMap` via TypeScript module augmentation. This ensures the audit infrastructure is type-aware of the specific events this module can emit.
- `src/modules/api-keys/authorization.yaml` — Declares the authorization policy for the `api-keys` module: which actions on the `ApiKey` subject are permitted, at what scope, under what credential constraints, and which require step-up authentication. The rules and rule-sets here gate every read, create, and delete operation on API keys within a tenant.
- `src/modules/api-keys/controllers/delete-api-key.ts` — Handles the `DELETE /api-keys/:id` endpoint, which revokes an API key (a soft state change) rather than deleting it. It is hand-written instead of using the `createDeleteController` factory because revocation has no hard-delete counterpart and does not fit the soft/hard delete triplet pattern.
- `src/modules/api-keys/controllers/get-api-key.ts` — HTTP controller that handles `GET /api-keys/:id`. It validates the route parameter, looks up a single API key scoped to the caller's tenant via the service layer, and returns the key's metadata (never its secret). All failure modes—malformed id, unknown id, cross-tenant access—produce an identical 404 to avoid leaking existence.
- `src/modules/api-keys/controllers/get-api-keys.ts` — Defines the single exported controller for `GET /api-keys`, returning the calling tenant's API keys (newest-first by default, or per `sort`). It is a thin adapter: it validates/parses query params and delegates the actual listing to the API-keys service. Never returns a key's secret.
- `src/modules/api-keys/controllers/post-api-key.ts` — HTTP controller that handles `POST /api-keys`. It validates the request body against a Zod schema, delegates to the api-keys service to mint a new credential, and emits a `201 Created` response with a `Location` header pointing to the new resource.
- `src/modules/api-keys/credentials.ts` — Mints and verifies machine-to-machine API-key credentials using one-way SHA-256 hashing (via `hashToken`). The plaintext is shown to the caller exactly once at creation; only the hash and the non-secret public prefix are persisted. It deliberately avoids bcrypt/argon2 because the 256-bit `randomBytes` secret has no search space for a KDF to make expensive.
- `src/modules/api-keys/emails.ts` — Resolves the finished, localized text for the two emails the API-keys module sends: one when a credential is minted (to alert the owner of a potentially stolen session) and one when credentials are revoked wholesale (to tell the owner what stopped working). - `src/modules/stats/tests/unit/calendar.test.ts` — Unit tests for the pure calendar-arithmetic domain module. The suite locks down edge-case behavior (month/year rollover, leap-year February, week-start-on-Monday, Sunday-as-week-end) without any clock, timezone, or I/O involvement.
- `src/modules/stats/tests/unit/figures.test.ts` — Unit tests for the sales-figures domain logic. They lock down three guarantees: net sales subtract reversals while shipping and VAT are charged-minus-refunded; a shop with zero orders never divides by zero; and currencies without a minor unit (e.g. JPY) are formatted correctly.
- `src/modules/stats/tests/unit/range.test.ts` — Unit tests for the `checkRange` validation function and the `previousOf` period-shift helper in the stats domain layer. - `src/modules/stats/tests/unit/routes.test.ts` — Unit test for the stats route table that verifies structural invariants: the exact set of mounted routes, that every route is a read-only `GET`, that each requires an authenticated session, and that every route is guarded by the single `read:Stats` permission. It exists to catch accidental privilege escalation (a route gaining a write action) or route drift (an undocumented endpoint appearing).
- `src/modules/stock-alerts/config.ts` — Defines the single tunable for the stock-alerts module: the maximum number of back-in-stock requests one account may hold simultaneously. This cap guarantees that `GET /stock-alerts` stays unpaginated.
- `src/modules/stock-alerts/controllers/delete-stock-alert.ts` — Thin HTTP adapter that handles `DELETE /stock-alerts/:productId`. It validates the route parameter, delegates to `stockAlertService.cancel`, and maps the result (or rejection) onto the HTTP response. All business logic lives in the service; this file only translates between the Express request/response cycle and the service API.
- `src/modules/stock-alerts/controllers/get-stock-alerts.ts` — Thin HTTP controller that handles `GET /stock-alerts`. It extracts the authenticated user's ID, delegates to `stockAlertService.list`, and returns the result (or a standardized error) via the shared response helpers. No business logic lives here.
- `src/modules/stock-alerts/controllers/post-stock-alerts.ts` — Thin HTTP adapter that handles `POST /stock-alerts`. It validates the request body, delegates to `stockAlertService.ask`, and returns **200** with the full stock-alerts list. Because the endpoint is idempotent (repeating the request is the same request), it intentionally uses 200 rather than 201.
- `src/modules/stock-alerts/emails.ts` — Builds the single email the stock-alerts module sends — a "back in stock" notification. It turns a product name, a product URL, a buyer's name, and a locale into a finished, localized `EmailContent` object ready for the mailer to render. By design it is the only email in this module and carries no cross-promotion.
- `src/modules/stock-alerts/events.ts` — Declares the stock-alerts module's domain event (`stock_alert.sent`) by augmenting the kernel's `DomainEventMap` rather than editing the central map directly, and exports a single spelling constant so emitters and listeners agree on the event name.
- `src/modules/stock-alerts/index.ts` — Public barrel (module facade) for the **stock-alerts** bounded context. It is the *only* import surface that sibling modules are permitted to use, enforcing the strategic-DDD encapsulation rule described in `docs/theory/strategic-ddd.md` §5.
- `src/modules/stock-alerts/jobs.ts` — Declares the single scheduled job owned by the `stock-alerts` module: a periodic sweep that picks up preorders whose release date has passed and makes them buyable. Separated from `service.ts` so the job's scheduling metadata, lease, and execution entry-point live in one place.
- `src/modules/stock-alerts/model.ts` — Defines the Mongoose model for a back-in-stock request — a single, one-shot consent record linking a user to a product for exactly one notification email. It contains the document shape, schema, indexes, serialization transform, and the model instance consumed by the rest of the stock-alerts module.
- `src/modules/stock-alerts/module.ts` — Module manifest for the stock-alerts feature: a signed-in buyer registers to receive a single notification when a product they could not order becomes buyable again. This file wires together the module's routes, config, jobs, personal-data handlers, and domain-event subscriptions into one `AppModule` object that the kernel registry discovers.
- `src/modules/stock-alerts/module.yaml` — Module manifest for the back-in-stock alerts feature. It declares the module's identity, organizational placement, dependencies, and the single scheduled job that fulfils waiting alerts, so the platform runner can register the module without inspecting implementation code.
- `src/modules/stock-alerts/openapi.yaml` — OpenAPI 3.1.0 contract for the stock-alerts module. It defines the REST surface for letting an authenticated user create, list, and cancel "notify me when this product is back in stock" requests, and declares the module's contribution to the account data export (`x-personal-data`). It also registers module-specific error codes that the bundler surfaces to clients.
- `src/modules/stock-alerts/presenter.ts` — Transforms internal `StockAlertDocument` records into the exact wire shape declared in `openapi.yaml`. The response object is constructed field-by-field rather than serialized from the model, so any field absent from the contract can never leak to the client.
- `src/modules/stock-alerts/repository.ts` — Data-access layer for stock alerts. Encapsulates every MongoDB read/write the stock-alert domain needs—creating an idempotent request, cancelling, listing, and the cleanup writes owed when an account or product is deleted—so the service layer never touches Mongoose directly.
- `src/modules/stock-alerts/routes.ts` — Express route table for the stock-alerts (back-in-stock) feature. Defines the three HTTP endpoints (list, ask, cancel) and applies authentication to every route. No admin/permission key is required — the same "signed-in only" pattern used by the wishlist module.
- `src/modules/stock-alerts/service.ts` — Service layer for the back-in-stock (stock-alerts) feature. It exposes the buyer-facing operations (ask, cancel, list, export, hard-delete) and the "buyable again" reaction that answers every pending request with exactly one email and one inbox row, then deletes the request. The single click on "Notify me" is the buyer's sole consent for that one notification; no further mail is ever sent on the same request.
- `src/modules/stock-alerts/tests/contract/api.contract.test.ts` — HTTP contract tests for the `/stock-alerts` endpoints. Each declared status branch (200, 404, 405, 409, 422) is exercised over real HTTP and the response envelope is checked for shape and error codes. The file deliberately does **not** verify inventory-signal behavior (stock levels, signal emission); that is covered by the integration test suite.
- `src/modules/stock-alerts/tests/integration/stock-alerts.test.ts` — Integration tests for the stock-alerts module that exercise the full HTTP surface (create, list, cancel a back-in-stock request) and the restock signal path, with real module wiring registered. The goal is to verify the module's behavior end-to-end—including the `module.ts` registration—without mocking the service layer or repositories.
- `src/modules/stock-alerts/tests/unit/schema-contract.test.ts` — Unit test that verifies the **structural declarations** of `stockAlertSchema` (required paths, references, index specs, options) rather than document contents. It exists because constraints like a dropped `unique` flag on the compound index are invisible to fixture-based document tests: the pair still exists as data, it just loses its uniqueness guarantee.
- `src/modules/wishlist/analytics.ts` — Defines the wishlist module's analytics event names and registers them into the shared analytics port's type map. This exists so event names are single-sourced, type-safe, and follow the project-wide naming convention, while the wishlist save funnel (add/remove) is clearly linked to the purchase funnel via the `WISHLIST_MOVED_TO_CART` exit event.
- `src/modules/wishlist/config.ts` — Defines the single tunable for the wishlist module — the maximum number of products a single list may hold. It exists to keep `GET /wishlist` unpaginated yet bounded, exposing the value through a typed config object and a convenience getter.
- `src/modules/wishlist/controllers/delete-wishlist-item.ts` — Thin HTTP adapter for `DELETE /wishlist/items/:productId`. It extracts the authenticated user and product ID from the request, delegates to `wishlistService.remove`, and shapes the response (200 with the updated wishlist, or 404 / error) without containing business logic.
- `src/modules/wishlist/controllers/get-wishlist.ts` — Thin HTTP adapter for the `GET /wishlist` endpoint. It extracts the authenticated user's id, delegates to `wishlistService.get`, and shapes the result into a standard success response. The wishlist payload contains product ids only; the client is expected to join them against its own product store.
- `src/modules/wishlist/controllers/post-move-to-cart.ts` — Thin HTTP adapter for `POST /wishlist/items/:productId/move-to-cart`. It extracts the authenticated user and the `productId` path param, then delegates all business logic (cart line creation/increment + wishlist item removal) to `wishlistService.moveToCart`. It exists solely to translate between Express request/response objects and the service's typed API.
- `src/modules/wishlist/controllers/post-wishlist-items.ts` — Thin HTTP adapter that handles `POST /wishlist/items`. It validates the incoming body, extracts the authenticated user's ID, and delegates to `wishlistService.add`, then serialises the result. It exists so the wishlist module's route table stays declarative and all request/response plumbing stays in one place.
- `src/modules/wishlist/events.ts` — Declares the wishlist module's domain events by augmenting the kernel's `DomainEventMap` interface (via TypeScript module augmentation), so the event catalogue grows per-module without editing the kernel. Also exports a shared event-name constant so emitters and listeners reference a single spelling.
- `src/modules/wishlist/factories.ts` — Factory for building wishlist fixtures in tests. It accepts a bare `userId` and optional product ids, then wraps them into the `{ productId }` shape the Mongoose schema stores. The design mirrors `../cart/factories` (owner-addressed, no `_id` override) but diverges on one point: a wishlist line is just a product id, not a full `WishlistItem` with quantity, because a wishlist encodes "do I want this," not "how many."
- `src/modules/wishlist/index.ts` — Public barrel (module facade) for the Wishlist module. Internal consumers (tests, other wishlist files) import sub-modules directly; everything outside the module goes through this file.

Establishes the persisted shape (one document per user holding an array of `{ productId }` lines), enforces the one-wishlist-per-user constraint at the database level, and exposes a serialization transform for lean reads. All queries live in `./repository`; business rules in `./service`.
- `src/modules/wishlist/module.ts` — Module manifest for the wishlist feature. Wires together the module's routes, config, data-portability/erasure hooks, and domain-event subscriptions into a single `AppModule` export that the kernel registry can mount. It exists so the wishlist's cross-cutting concerns (lifecycle hooks, event reactions, locale resolution) live in one place rather than scattered across service or route files.
