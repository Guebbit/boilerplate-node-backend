# src/modules/orders/

## Purpose

The orders module is the bounded context that owns the full order lifecycle: creation (admin path and cart completion), status transitions, customer cancellation, withdrawal, anonymization, and retention scrubbing. It provides the HTTP API surface for reading, writing, exporting, and auditing orders; defines the pure domain rules (totals, tax, backorder, deletion, fulfillment interpretation, EU withdrawal logic) that every service and controller enforces; and publishes the module's events, webhooks, audit vocabulary, and authorization policy as declarative contracts.

## Key parts

- **Domain layer (`domain/`)** — A cluster of pure-logic files with no I/O. `lifecycle.ts` and `status-traits.ts` together define the status state machine and per-status invariants; `totals.ts`, `tax.ts`, and `backorder.ts` compute money and delivery promises; `withdrawal.ts`, `deletion.ts`, and `purchase-hold.ts` encode regulatory and policy rules; `projections.ts` and `fulfillment.ts` interpret data stamped by other modules. `index.ts` is the tier's barrel.
- **Controllers (`controllers/`)** — One thin handler per HTTP endpoint (list, get, create, cancel, override-status, restore, update, export, timeline, notes, delete, shipping-address). All delegate business logic to the order service and use shared helpers (`respond.ts`, `createDeleteController`, `createSearchController`, `createUpdateController`) so no bespoke HTTP plumbing is duplicated.
- **Cross-cutting declarations** — `analytics.ts`, `audit.ts`, `events.ts`, `metrics.ts`, `jobs.ts` register the module's vocabulary into app-wide maps (analytics events, audit actions, domain events, Prometheus counters, scheduled jobs). `authorization.yaml` and `asyncapi.webhooks.yaml` declare the policy and contract surface declaratively.
- **Config & contracts** — `config.ts` centralises tunables (line caps, withdrawal window, PII retention, export limits, purchase-hold thresholds) behind per-call getters. `emails.ts` resolves all customer-facing order email strings.
- **Boundary & barrel files** — `index.ts` is the sole public import surface for sibling modules. `friends/payments.ts` is the single narrow entry point `payments` may use inside orders. `factories.ts` builds valid order documents for tests and builders.

## How it connects

- **payments** — The only write-side interaction permitted into orders is through `friends/payments.ts`; a settled payment is the sole event that transitions an order to `paid`. Orders never import payment internals.
- **delivery** — Dependency arrow is `orders → delivery`: delivery writes a `FulfillmentSummary` record onto the order, and `domain/fulfillment.ts` interprets it to answer stock, dispatch, and filter questions. Orders never query delivery collections directly.
- **returns** — `domain/projections.ts` provides the helpers through which the returns module stamps `returnStatus` onto an order; orders reads the value but does not compute it.
- **invoicing** — Invoice-document email copy lives in invoicing's own `emails.ts`; orders' `emails.ts` only handles order-lifecycle notifications.
- **products** — VAT rates are resolved by the products module at placement time and frozen into the order line; orders' `domain/tax.ts` then computes figures from that frozen rate so a later product change never restates a past order.
- **cart** — `POST /orders` (admin) bypasses cart entirely; the cart path presumably feeds the same `orderService.create`. Both draw on `domain/totals.ts` for a single money implementation.
- **observability** — `metrics.ts` exposes `order_created_total`; the kernel's observability layer collects it.
- **infrastructure / adapters** — The order repository (Mongoose), mailer, and job scheduler live outside this module; orders only declares *what* to do (events, jobs, emails) and lets the infrastructure layer execute it.

## Where to start

1. **`domain/lifecycle.ts`** — Reading this first gives you the complete status state machine (allowed transitions, permitted actors) that every controller and service ultimately enforces. Once you know the graph, the rest of the module's rules (withdrawal, deletion, fulfillment) slot in naturally.
2. **`index.ts`** — This barrel shows the full public API the rest of the app can import. Skimming it tells you exactly what the module exposes versus what stays internal, which orients you before diving into individual files.

## Files
- `src/modules/orders/analytics.ts` — Declares the set of analytics event names the orders module emits and registers them into the app-wide `AnalyticsEventMap` union so the analytics port can type-check them at the call site. It is a pure declaration file: no runtime logic, no side effects beyond exporting a frozen const.
- `src/modules/orders/asyncapi.webhooks.yaml` — Defines the orders module's four outbound webhook events (`order.created`, `order.paid`, `order.canceled`, `order.redacted`) as an **AsyncAPI fragment**. It is not a standalone document: the bundler (`scripts/contracts/asyncapi-section-fragments.ts`) merges it into the top-level `webhooks` section, and `GET /webhooks/events` lists these events only while the orders module is registered. Deleting the module removes its events from the contract.
- `src/modules/orders/audit.ts` — Declares the audit-action vocabulary for the orders module and registers it into the application-wide `AuditActionMap` via TypeScript module augmentation. Every service and controller in `src/modules/orders/` references one of these constants when it writes an audit record, so the set of valid `orders` actions lives in exactly one place.
- `src/modules/orders/authorization.yaml` — Declarative authorization policy for the orders module. It defines the seven permitted actions on the `Order` entity (read, display, create, update, delete, override, export), any conditions or step-up requirements attached to each, and groups them into named rule sets that roles can reference when granting access.
- `src/modules/orders/config.ts` — Centralises every tunable rule that governs the orders module — line caps, withdrawal window, PII retention periods, export limits, purchase-hold thresholds, and the one frontend link path — behind per-call getter functions so tests can vary any value without re-importing. Shop identity, currency, and return address intentionally live in `shop`; VAT rates are resolved by `products`. A deployment changes a value via restart.
- `src/modules/orders/controllers/delete-orders.ts` — A thin admin delete controller for orders. It wires the shared `createDeleteController` factory to `orderService.removeById`, so the module's route can dispatch `DELETE /orders(/:id)(/hard)` without any bespoke HTTP logic living here.
- `src/modules/orders/controllers/get-order-timeline.ts` — Controller for `GET /orders/:id/timeline`. Returns a paginated, newest-first list of events that happened to a given order, filtered by what the caller is allowed to see. The order is resolved through the same visibility scope as `GET /orders/:id`, so an invisible order produces the same 404.
- `src/modules/orders/controllers/get-order.ts` — Handles `GET /orders/:id`. Validates the path id before any service call, fetches the order scoped to the caller's role (non-admins see only their own), records a staff-read audit event, and serialises the order into a response that includes caller-specific permissions and a version token for optimistic concurrency.
- `src/modules/orders/controllers/get-orders-export.ts` — Implements the `GET /orders/export` endpoint: streams the full filtered order list as a CSV download. It reuses the same search filters as the paginated list view but strips paging, and pipes the result directly into the HTTP response so the file is never buffered in memory.
- `src/modules/orders/controllers/get-orders.ts` — Thin search/list controller for orders. Wires the shared `createSearchController` factory to the orders domain service, scoping results to the caller's own visibility via `orderService.callerScope`. Exists so the HTTP layer stays declarative while permission enforcement and pagination normalization live in the shared infrastructure and kernel.
- `src/modules/orders/controllers/order-notes.ts` — Thin HTTP controller layer for staff notes on an order. It maps `POST /orders/:id/timeline/notes` (create a note) and `DELETE /orders/:id/timeline/notes/:eventId` (withdraw a note's text) onto `orderService`, handling only request parsing, ID validation, and response shaping. Authorization (`requirePermission('update', 'Order')`) is enforced upstream by the route, not here.
- `src/modules/orders/controllers/post-cancel-order.ts` — HTTP controller for `POST /orders/:id/cancel` — the single order-write operation a customer is permitted to perform. It is a thin wiring layer that validates the route params and body, extracts the caller's auth context, and delegates the actual write to `orderService.cancelOnRequestById`.
- `src/modules/orders/controllers/post-order-override-status.ts` — Admin controller for `POST /orders/:id/override-status`. It is a thin HTTP-layer handler that validates the request, delegates to `orderService.overrideStatus`, and formats the response. It enforces a **status-only** override (no parcel or email side-effects). Authorization (`requirePermission('override', 'Order')`, step-up gated) is handled upstream at the route, not here.
- `src/modules/orders/controllers/post-order-restore.ts` — Thin admin-facing controller that exposes the "restore a soft-deleted order" endpoint (`POST /orders/:id/restore`). All business logic and audit side-effects live in the order service; this file only wires the shared `createRestoreController` factory to the order-specific service methods.
- `src/modules/orders/controllers/post-order.ts` — Handler for `POST /orders` — the admin path that creates an order directly from an explicit payload in the request body, bypassing the cart. It validates the body, delegates to `orderService.create`, records a metric, and returns a `201` with the created order.
- `src/modules/orders/controllers/put-shipping-address.ts` — Thin HTTP handler for `PUT /orders/:id/shipping-address`. Validates the route parameter and request body, then delegates to `orderService.correctShippingAddress` to replace the shipping address on an unshipped order. All business logic lives in the service; this file only performs extraction, validation, and response shaping.
- `src/modules/orders/controllers/respond.ts` — Shared success-path helper for every order controller (reads and writes). It hydrates the order document returned by the service with the caller's `actions` (via `orderService.withActions`) and sends it as the HTTP response. Extracted from the individual controllers so the hydrate-then-send shape is written once, while each call site still declares its own status code and error context.
- `src/modules/orders/controllers/update-order.ts` — Builds the two HTTP handlers for `PUT /orders/:id` (full replace) and `PATCH /orders/:id` (partial merge) by delegating to the shared `createUpdateController` factory. The only writable field exposed through either verb is `email`; `status` transitions are intentionally excluded from the request body and must go through a dedicated action endpoint.
- `src/modules/orders/domain/anonymization.ts` — Defines the single placeholder email value written into an order's `email` field when the order is anonymized. Exists as a shared constant so every consumer (repository writes, notification checks, tests) references the same string without hard-coding it.
- `src/modules/orders/domain/backorder.ts` — Defines the "owed" portion of an order line — how many units are backordered and when the buyer was promised delivery. Pure domain logic: it computes a frozen snapshot at order-placement time so that later catalogue changes (e.g. restock-date edits) don't silently alter what was already promised to the buyer.
- `src/modules/orders/domain/deletion.ts` — Defines the two pure predicates that determine whether an order may be soft-deleted (hidden) or hard-deleted (destroyed). Centralizing these rules here ensures the UI "delete door" and the service-layer actions agree on the same criteria and cannot diverge.
- `src/modules/orders/domain/export.ts` — Defines the shape and mapping of a single orders-CSV row: which columns appear (and in what order), what fields an order must supply, and the pure function that converts an order into a row of cells. It exists so the CSV contract is declarative, testable, and decoupled from the transport (writing, escaping, streaming) handled elsewhere.
- `src/modules/orders/domain/fulfillment.ts` — Pure domain logic that interprets the fulfillment summary a `delivery` module writes onto an order. Because the dependency arrow points `orders → delivery` (not the reverse), `orders` cannot inspect fulfillment orders directly; instead `delivery` reports a small record (`FulfillmentSummary`) and this file derives every question `orders` asks about the goods—settlement moves, the user-facing fulfillment status, and the listing filter—from that single record. No I/O.
- `src/modules/orders/domain/index.ts` — Barrel (re-export) file for the orders **domain layer**. It aggregates the public API of every sibling domain module into a single import surface and, by its own doc comment, declares the invariant for the tier: pure rules only, with no Express, Mongoose, or any other framework/tier dependency. Consumers import from here rather than reaching into individual submodules.
- `src/modules/orders/domain/lifecycle.ts` — Single source of truth for the order status lifecycle: which status may follow which, and which actor (`customer`, `admin`, `system`, `withdrawal`) is permitted to make each move. The status *set* comes from the `OrderStatus` enum; this file adds the directed edges and actor restrictions. Services name an event to read the `from`/`to`/`actors` triple rather than hard-coding status comparisons.
- `src/modules/orders/domain/projections.ts` — Defines how the two "adjacent" statuses on an order — Shopify's `financial_status` (payment) and `returnStatus` — are **derived on read** and **queried on write**. Because `orders` cannot import `payments` or `returns`, those modules stamp the stored field through this file's helpers rather than the order module computing them. Everything here is pure (no I/O) so the mappings are trivially unit-testable.
- `src/modules/orders/domain/purchase-hold.ts` — Pure domain logic that computes when an **automatic** purchase hold expires based on a buyer's recent cancellations. All time values (cancellation timestamps, "now", window, limit) are passed in as parameters so the module has no clock or I/O dependency.
- `src/modules/orders/domain/rules.ts` — Pure validation and classification predicates for order data. Functions take structured input and return a simple verdict or boolean — no side effects, no status codes, no i18n. The calling layer (primarily `services/place`) is responsible for translating verdicts into HTTP responses or user-facing messages.
- `src/modules/orders/domain/status-traits.ts` — Single source of truth for what each `OrderStatus` means in isolation. Every question the orders module asks of a status alone—stock commitment, dispatch state, withdrawal eligibility, fulfillment position—is answered by reading this one record instead of each consumer maintaining its own status list. Exhaustiveness is enforced at compile time via `satisfies Record<OrderStatus, OrderStatusTraits>`, so a new status in the contract fails the build here rather than silently falling into a wrong category.
- `src/modules/orders/domain/tax.ts` — Computes VAT arithmetic for an order from each line's **frozen** price, quantity, and tax rate, plus an apportioned shipping share. It exists so that tax figures are derived at serialization time from what was actually charged, never re-resolved against a product's current tax class — a config rate change must not restate a past order. Mirrors `totals.ts`'s approach to `totalPrice`: computed on demand, never stored.
- `src/modules/orders/domain/timeline.ts` — Defines the closed set of order-timeline entry types and assigns each one a fixed audience (`buyer` or `staff`). It provides the compile-time guard that no type can exist without an audience decision, and the type-safe input shape (`TimelineEntryInput`) that writers must use when creating a timeline row. Visibility is decided here, up front, rather than by stripping fields at read time.
- `src/modules/orders/domain/totals.ts` — Pure arithmetic for "what does this set of priced lines add up to, and what is the grand total including shipping?" All money math runs in minor units via `money.ts` primitives and is converted to decimal text once at the boundary. The file exists so that cart previews, order totals, payment intents, and confirmation emails all derive the same number from one implementation instead of summing independently.
- `src/modules/orders/domain/withdrawal.ts` — Pure domain logic for the EU right of withdrawal (Consumer Rights Directive 2011/83/EU) and the statutory guarantee of conformity as they apply to a single order. It answers, without any I/O: when the withdrawal window opens and closes, whether a withdrawal is a cancel or a return, whether staff can still redirect unshipped units, when the shop must refund, and when the conformity guarantee expires. Every service, email, timeline row, and UI button reads from these functions so the answer is computed in exactly one place.
- `src/modules/orders/emails.ts` — Resolves every customer-facing email this module sends into finished, locale-specific strings. Language is an input argument; the output is complete text that the mailer template only interpolates. The same "resolve-then-interpolate" contract applies here as in `@modules/account/emails`. Invoice-document copy intentionally lives in `@modules/invoicing`'s own `emails.ts`, not in this file.
- `src/modules/orders/events.ts` — Declares every domain event the orders module emits by augmenting the kernel's `DomainEventMap` interface (via `declare module '@kernel/events'`), so the app-wide event catalogue grows with the module that owns each event rather than being edited centrally. Also exports one string constant per event name so emitters and listeners share a single spelling instead of duplicated literals.
- `src/modules/orders/factories.ts` — Factory module for constructing order fixtures ready for `orderRepository.create`. It converts API-contract-shaped data (ids as strings, ISO dates, product references) into a Mongoose `OrderDocument` shape with `ObjectId` fields, real `Date` values, and embedded product **snapshots** (value copies, not references). It exists so test code and other builders can create valid order documents without hand-assembling the nested structure or re-deriving serialization-time fields.
- `src/modules/orders/friends/payments.ts` — A single re-export that serves as the only write-side entry point `payments` is permitted to use inside the `orders` module. It exists to enforce a narrow, auditable boundary between the two bounded contexts: a settled payment is the sole event allowed to transition an order to `paid`.
- `src/modules/orders/index.ts` — Public barrel for the orders module. Per the strategic DDD rule (docs/theory/strategic-ddd.md §5), this is the **only** import surface a sibling module is allowed to use. It re-exports the module's services, domain, events, emails, and model types so callers never reach into internal files directly.
- `src/modules/orders/jobs.ts` — Declares the single scheduled job (`reapOrders`) that the orders module owns: a retention scrub that anonymizes overdue orders and then strips their data from timeline text. The file exists so the kernel's job registry can discover and invoke this work without the orders module hard-coding scheduling logic elsewhere.
- `src/modules/orders/metrics.ts` — Defines the single Prometheus counter owned by the orders module — `order_created_total` — which tracks admin-created orders. Counters live in the owning domain module (not in infrastructure) so each module is self-contained; the pattern rationale is documented in `modules/account/metrics.ts`.
- `src/modules/orders/model.ts` — Defines the Mongoose schema, TypeScript interfaces, and serialization transform for the Order document. It is the single persistence-layer contract that pins what an order stores (embedded product snapshot, quantities, frozen timestamps, stamped statuses) and what is derived at read time (totals, wire-level status fields), so that no later catalogue edit, locale change, or config drift can rewrite purchase history.
- `src/modules/orders/module.ts` — Module entry point (the `AppModule` manifest) for the **orders** module. It wires together the order module's routes, jobs, config, rate limits, event subscriptions, public webhook mappings, PII/personal-data hooks, and scenario-state list so the kernel can mount and coordinate the module. It also encodes the key invariants in its header comment: line items snapshot catalogue fields into a local schema (no live warehouse counter), inventory claims are released on cancel/expiry, and the module never imports `invoicing`.
- `src/modules/orders/module.yaml` — Module manifest for the **orders** subdomain (group `shop`). It declares what a checkout produces (status machine, totals, invoice link), the modules it depends on with a one-line note on *why*, the rate-limit budgets that guard two sensitive endpoints, and the single scheduled job that handles PII retention.
- `src/modules/orders/openapi.yaml` — The OpenAPI 3.1.0 contract for the orders module. It declares the module's public API surface (paths, parameters, request/response schemas), the module-specific error-code vocabulary, and the orders slice of the account personal-data export. Other modules and the bundler consume this file to compose the full API spec, generate code, and enforce error semantics.
- `src/modules/orders/pii.ts` — Field-level encryption/decryption of personal text in an order record: the embedded shipping/billing addresses and the buyer's notes. It is the order-side twin of `addresses/pii.ts`, sharing the same `NODE_PII_ENCRYPTION_KEY` ring. It deliberately avoids mongoose getters/setters (ciphertext leaks through `toJSON`, double-encryption on subdoc copies, and encrypted paths silently break query filters) in favour of an explicit codec applied at the repository boundary.
- `src/modules/orders/presenter.ts` — The single translation point that converts order storage documents into the `Order` wire contracts consumed by API responses. Every order read path funnels through this module so that formatting, PII handling, and audience-based field stripping live in exactly one place.
- `src/modules/orders/probes.ts` — Declares a set of **probes** — manual API requests that exercise authorization/scoping rules the OpenAPI contract cannot express on its own. Each probe documents a subtle ownership or role-scoping case in the orders module and tells the test runner how to seed variables before the real collection runs.
- `src/modules/orders/rate-limits.ts` — Declares the two rate-limit budgets specific to the orders module (export and timeline-note endpoints) and exposes them as ready-to-use Express `RequestHandler` middlewares. It converts the raw budget data into middleware via the shared `buildRateLimiter` factory so the orders routes can enforce per-account request windows without re-implementing limiter logic.
- `src/modules/orders/repository.ts` — Repository for the Order aggregate. Unlike other collections, orders are read through the Mongoose aggregation framework because product data is embedded (a snapshot per line item) and filtering on `items.product._id` is a pipeline concern. The factory still supplies plain CRUD; `search`, `countMatching`, and `streamMatching` override the default with pipeline-based reads. The file is also the single write path for PII encryption, atomic status transitions, and re-encryption.
- `src/modules/orders/routes.ts` — Express router that wires every order-management endpoint (list, read, create, cancel, override-status, shipping-address, timeline, notes, export, soft/hard delete, restore) behind a session-only auth guard and attaches the correct permission, cache, idempotency, and rate-limit middleware per route. Route registration order is load-bearing: static segments (`/search`, `/export`) and longer parameter paths (`/:id/hard`, `/:id/override-status`) must precede the bare `/:id` wildcard.
- `src/modules/orders/services/actions.ts` — Computes the `actions` flag object attached to every order (single or list) that a caller may act upon. The state-derivation predicates live in `../domain` (shared with the write-path guard); this file layers caller identity (keys, ownership, buyer vs. operator) on top so no client re-derives the rules. The two exports — `withActions` and `withListActions` — are the only async surfaces: they resolve live images and (for lists) hydrate documents, then stamp the pure `orderActionsOf` result onto the wire shape.
- `src/modules/orders/services/address.ts` — Implements the staff-facing `PUT /orders/{id}/shipping-address` handler: it replaces the shipping address on units that have not yet left, since no other code path can change an address after checkout. It is intentionally narrow — it writes the new address, emits one timeline entry, and records one audit row, and nothing else.
- `src/modules/orders/services/announce.ts` — Factory functions that build typed `OutboxAnnouncement` payloads for order lifecycle events. Each returned object is passed to `announceInTransaction` so the event row commits atomically with the corresponding status write (or not at all), guaranteeing per-order event ordering via a shared `aggregateId`.
- `src/modules/orders/services/cancel-mail.ts` — Handles the buyer-facing email that explains why their order was canceled. It is invoked from the `order.canceled` domain-event listener so that every cancellation path (regardless of origin) produces the same explanation, and a crash between the DB commit and the send still results in the email going out.
- `src/modules/orders/services/cancel.ts` — Executes an order cancellation as a single atomic transaction: the conditional status move to `canceled`, the release (or committed-release) of the order's stock claim, and the `order.canceled` outbox row all commit or roll back together. The refund is deliberately excluded from the transaction (it is an external-provider action that cannot roll back); instead it is carried as a `refund` flag on the outbox event, which the `payments` module consumes to open its own refund record.
- `src/modules/orders/services/crud.ts` — Admin-facing write operations for orders: **create** and **update** (email amendment). The file deliberately scopes itself to the "admin door" — creating an order composes around `placeOrder` (which owns the actual write, stock hold, and rollback), and updating delegates the raw save to `updateById`. Reads live in `./read`, deletes in `./remove`, and cancellation in `./cancel`.
- `src/modules/orders/services/current.ts` — Resolves each order line's live product images (`imageUrl`, `thumbnailUrl`) from the catalogue at the serialization boundary. It exists because the frozen order snapshot schema (`orderLineProductSchema`) deliberately omits image fields, so callers need a single, batched lookup that enriches serialized orders just before they leave the API layer.
- `src/modules/orders/services/digest.ts` — Provides the order-side counts for the daily staff digest: bank-transfer orders approaching or past their `payBy` deadline, and paid orders still awaiting shipment beyond a configurable allowance. Also exposes a small lookup for the shipping method each order froze at checkout. The digest holds counts only—no order records are returned.
- `src/modules/orders/services/export.ts` — Produces a streaming CSV export of orders. The function validates the result size against a configurable cap, writes an audit entry, and returns a pipeable pair (object-mode `Readable` source + `csv-stringify` `Transform`) that the caller wires into the HTTP response. Nothing is written to disk or emailed; the stream is discarded if the client disconnects.
- `src/modules/orders/services/fulfillment.ts` — The transactional write path that the `delivery` module calls when a fulfillment act changes where an order's goods stand. Every door accepts the act's Mongoose session so the shipment, summary, status move, and events commit atomically or not at all.

The `returns` module calls in; `orders` owns the underlying field.
