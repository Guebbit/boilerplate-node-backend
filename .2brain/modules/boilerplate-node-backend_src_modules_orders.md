# src/modules/orders/

## Purpose

The orders module owns the **Order** aggregate end-to-end: its Mongoose schema, the pure domain rules (lifecycle transitions, totals, tax, withdrawal rights, backorder snapshots, purchase-hold, PII anonymization), the HTTP controllers that expose it, the domain events it emits, its emails, and its scheduled retention job. It sits low in the dependency graph—payments, delivery, returns, and invoicing all depend on it, never the reverse—so its only outward channels are the events it emits and the small read-only records other modules stamp onto it.

## Key parts

- **`domain/`** — Pure, I/O-free business logic, re-exported through `domain/index.ts`. Includes the status lifecycle and trait tables (`lifecycle.ts`, `status-traits.ts`), monetary arithmetic (`totals.ts`, `tax.ts`), consumer-rights date math (`withdrawal.ts`), backorder snapshots (`backorder.ts`), purchase-hold expiry (`purchase-hold.ts`), validation predicates (`rules.ts`), and the derived-status helpers that let payments/returns write back without a circular import (`projections.ts`, `fulfillment.ts`).
- **`controllers/`** — Thin HTTP handlers (one file per endpoint) that validate input, call `orderService`, and shape the response. A shared `respond.ts` adds the caller's permitted actions to every write/single-read response. Search, create, update, and delete endpoints delegate to shared factory helpers in infrastructure.
- **`model.ts` / `config.ts`** — The Mongoose schema + serialization transform, and the centralised tunable rules (caps, retention windows, export limits) exposed as per-call getters.
- **Cross-cutting declarations** — `events.ts` (domain-event catalogue via module augmentation), `analytics.ts`, `audit.ts`, `authorization.yaml` (role-based action policy), `asyncapi.webhooks.yaml` (public webhook contract), `metrics.ts` (Prometheus counter), `jobs.ts` (retention scrub).
- **`index.ts`** — The single public import surface for sibling modules, per the project's strategic-DDD rule.
- **`emails.ts` / `factories.ts`** — Locale-resolved email copy and a test-fixture factory that builds a ready-to-insert `OrderDocument`.

## How it connects

- **`src/modules/delivery/`** — Delivery is the *writer*; it calls `orderService.recordFulfillmentProgress` to stamp a `FulfillmentSummary` onto the order. Orders reads that record via `domain/fulfillment.ts`. The arrow is delivery → orders; orders never imports delivery.
- **`src/modules/payments/` & `src/modules/returns/`** — Both depend on orders. They stamp `financial_status` / `returnStatus` through the helpers in `domain/projections.ts` rather than orders computing them, keeping the arrow one-directional.
- **`src/modules/cart/`** — The buyer-facing order-creation path flows cart → orders (the admin `POST /orders` bypasses cart). Orders consumes the cart's priced lines to build the frozen order snapshot.
- **`src/modules/products/`** — Supplies VAT rates and product data that orders freezes into the embedded product snapshot at placement time.
- **`src/modules/shop-tasks/`** — Provides shop identity, currency, and return address that orders references for emails and display but does not own.
- **`src/modules/account/` & `src/modules/users/`** — Account services supply buyer context; users provides the authenticated actor for authorization scoping.
- **`src/infrastructure/`** — Shared controller factories (`createSearchController`, `createDeleteController`, `createRestoreController`, `createUpdateController`), the kernel event bus, and the job registry all live here; orders plugs into them via thin controller files and `jobs.ts`.
- **`src/modules/observability/`** — Consumes the `AnalyticsEventMap` entries declared in `analytics.ts` and the Prometheus counter from `metrics.ts`.
- **`scenarios/`** — End-to-end test scenarios exercise the orders HTTP surface.

## Where to start

1. **`src/modules/orders/domain/lifecycle.ts`** — It defines the status set, the legal transitions, and which actor may make each move. Understanding this table makes every controller and service guard make sense immediately.
2. **`src/modules/orders/index.ts`** — It is the module's entire public API. Reading what is exported (and what is deliberately *not*) gives a newcomer the boundary: everything internal is an implementation detail, and the exports show exactly what sibling modules are allowed to touch.

## Files
- `src/modules/orders/analytics.ts` — Declares the set of analytics event names the orders module emits and registers them into the app-wide `AnalyticsEventMap` union so the analytics port can type-check them at the call site. It is a pure declaration file: no runtime logic, no side effects beyond exporting a frozen const.
- `src/modules/orders/asyncapi.webhooks.yaml` — AsyncAPI fragment declaring the four `order.*` webhook events exposed by the orders module. It is not a standalone document: it references shared servers and schema definitions owned by the root `webhooks/asyncapi.yaml` and is merged in by the bundler only while the orders module is registered. Its lifecycle is bound to the module—deleting the module removes these events from the public contract.
- `src/modules/orders/audit.ts` — Declares the audit-action vocabulary for the orders module and registers it into the application-wide `AuditActionMap` via TypeScript module augmentation. Every service and controller in `src/modules/orders/` references one of these constants when it writes an audit record, so the set of valid `orders` actions lives in exactly one place.
- `src/modules/orders/authorization.yaml` — Declarative authorization policy for the orders module. It defines the seven permitted actions on the `Order` entity (read, display, create, update, delete, override, export), any conditions or step-up requirements attached to each, and groups them into named rule sets that roles can reference when granting access.
- `src/modules/orders/config.ts` — Centralises every tunable rule that governs the orders module — line caps, withdrawal window, PII retention periods, export limits, purchase-hold thresholds, and the one frontend link path — behind per-call getter functions so tests can vary any value without re-importing. Shop identity, currency, and return address intentionally live in `shop`; VAT rates are resolved by `products`. A deployment changes a value via restart.
- `src/modules/orders/controllers/delete-orders.ts` — A thin admin delete controller for orders. It wires the shared `createDeleteController` factory to `orderService.removeById`, so the module's route can dispatch `DELETE /orders(/:id)(/hard)` without any bespoke HTTP logic living here.
- `src/modules/orders/controllers/get-order-timeline.ts` — Express controller handler for `GET /orders/:id/timeline`. It resolves the order under the caller's visibility scope (same rules as `GET /orders/:id`), then returns the order's timeline entries filtered for that caller—staff see all rows with actor info, buyers see only buyer-visible types with no actor exposed.
- `src/modules/orders/controllers/get-order.ts` — Handles `GET /orders/:id` — fetches a single order for the authenticated caller and returns a permission-aware view. It exists to isolate the read path (validation → scoped fetch → audit → ETag → response) from the shared response formatter and the order service, keeping the route handler thin.
- `src/modules/orders/controllers/get-orders-export.ts` — Implements the `GET /orders/export` endpoint: streams the full filtered order list as a CSV download. It reuses the same search filters as the paginated list view but strips paging, and pipes the result directly into the HTTP response so the file is never buffered in memory.
- `src/modules/orders/controllers/get-orders.ts` — Thin search/list controller for orders. Wires the shared `createSearchController` factory to the orders domain service, scoping results to the caller's own visibility via `orderService.callerScope`. Exists so the HTTP layer stays declarative while permission enforcement and pagination normalization live in the shared infrastructure and kernel.
- `src/modules/orders/controllers/order-notes.ts` — Thin HTTP controller layer for staff notes on an order. It maps `POST /orders/:id/timeline/notes` (create a note) and `DELETE /orders/:id/timeline/notes/:eventId` (withdraw a note's text) onto `orderService`, handling only request parsing, ID validation, and response shaping. Authorization (`requirePermission('update', 'Order')`) is enforced upstream by the route, not here.
- `src/modules/orders/controllers/post-cancel-order.ts` — HTTP controller for `POST /orders/:id/cancel` — the single order-write operation a customer is permitted to perform. It is a thin wiring layer that validates the route params and body, extracts the caller's auth context, and delegates the actual write to `orderService.cancelOnRequestById`.
- `src/modules/orders/controllers/post-order-restore.ts` — Thin controller wiring that exposes an admin `POST /orders/:id/restore` endpoint. It delegates all real work to the shared `createRestoreController` factory and the `orderService`, so the file itself contains no business logic—only the binding of entity name, service calls, and a 404 message key.
- `src/modules/orders/controllers/post-order-status-override.ts` — Thin HTTP controller for `POST /orders/:id/status-override` — an admin endpoint that forces an order's status to a new value with a required reason, without triggering parcel or email side-effects. All business logic lives in the service; this file only validates inputs, calls the service, and shapes the response.
- `src/modules/orders/controllers/post-order.ts` — Handler for `POST /orders` — the admin path that creates an order directly from an explicit payload in the request body, bypassing the cart. It validates the body, delegates to `orderService.create`, records a metric, and returns a `201` with the created order.
- `src/modules/orders/controllers/put-shipping-address.ts` — Thin HTTP controller for `PUT /orders/:id/shipping-address`. It validates the order ID and request body, delegates to `orderService.correctShippingAddress`, and formats the response. All business logic lives in the service layer; this file only wires the HTTP boundary.
- `src/modules/orders/controllers/respond.ts` — Shared "success tail" for every order controller (all write operations plus the single-order read). It hydrates the order document returned by a service with the caller's `actions` (via `orderService.withActions`) and sends it as the HTTP response body. Kept separate from the service layer on purpose: `withActions` stays framework-free, and the HTTP status / `Response` concerns live here where they genuinely differ per call site (e.g. 201 on create vs. 200 elsewhere).
- `src/modules/orders/controllers/update-order.ts` — Builds the two HTTP handlers for `PUT /orders/:id` (full replace) and `PATCH /orders/:id` (partial merge) by delegating to the shared `createUpdateController` factory. The only writable field exposed through either verb is `email`; `status` transitions are intentionally excluded from the request body and must go through a dedicated action endpoint.
- `src/modules/orders/domain/anonymization.ts` — Defines the single placeholder email value written into an order's `email` field when the order is anonymized. Exists as a shared constant so every consumer (repository writes, notification checks, tests) references the same string without hard-coding it.
- `src/modules/orders/domain/backorder.ts` — Defines the "owed" portion of an order line — how many units are backordered and when the buyer was promised delivery. Pure domain logic: it computes a frozen snapshot at order-placement time so that later catalogue changes (e.g. restock-date edits) don't silently alter what was already promised to the buyer.
- `src/modules/orders/domain/deletion.ts` — Defines the two pure predicates that determine whether an order may be soft-deleted (hidden) or hard-deleted (destroyed). Centralizing these rules here ensures the UI "delete door" and the service-layer actions agree on the same criteria and cannot diverge.
- `src/modules/orders/domain/export.ts` — Defines the shape and mapping of a single orders-CSV row: which columns appear (and in what order), what fields an order must supply, and the pure function that converts an order into a row of cells. It exists so the CSV contract is declarative, testable, and decoupled from the transport (writing, escaping, streaming) handled elsewhere.
- `src/modules/orders/domain/fulfillment.ts` — Defines the `FulfillmentSummary` record that the `delivery` module writes onto an order, plus pure helper functions that `orders` uses to interpret that record. Because the dependency arrow runs `delivery → orders` (not the reverse), `orders` cannot ask `delivery` directly; instead `delivery` reports state through this one small record (written only via `orderService.recordFulfillmentProgress`), and everything `orders` needs to know about the goods is read off it here.
- `src/modules/orders/domain/index.ts` — Barrel re-export for the orders domain layer. Aggregates every pure business rule (totals, lifecycle transitions, tax, withdrawal, etc.) behind a single import path so consumers never reach into individual domain files. The module doc block and a lint rule guarantee it contains no Express, Mongoose, or other infrastructure dependencies.
- `src/modules/orders/domain/lifecycle.ts` — Defines the order status lifecycle: which status may follow which, and which actor may make each move. It imports the generated `OrderStatus` set and layers on the directed edges (events) plus the permitted actor per edge, then exposes guard functions that services call instead of comparing status literals by hand. The file is the single source of truth for "is this transition legal, and by whom."
- `src/modules/orders/domain/projections.ts` — Defines how the two "adjacent" statuses on an order — Shopify's `financial_status` (payment) and `returnStatus` — are **derived on read** and **queried on write**. Because `orders` cannot import `payments` or `returns`, those modules stamp the stored field through this file's helpers rather than the order module computing them. Everything here is pure (no I/O) so the mappings are trivially unit-testable.
- `src/modules/orders/domain/purchase-hold.ts` — Pure domain logic that computes when an **automatic** purchase hold expires based on a buyer's recent cancellations. All time values (cancellation timestamps, "now", window, limit) are passed in as parameters so the module has no clock or I/O dependency.
- `src/modules/orders/domain/rules.ts` — Pure validation and classification predicates for order data. Functions take structured input and return a simple verdict or boolean — no side effects, no status codes, no i18n. The calling layer (primarily `services/place`) is responsible for translating verdicts into HTTP responses or user-facing messages.
- `src/modules/orders/domain/status-traits.ts` — Single source of truth for what each `OrderStatus` means in isolation. Every question the orders module asks of a status alone—stock commitment, dispatch state, withdrawal eligibility, fulfillment position—is answered by reading this one record instead of each consumer maintaining its own status list. Exhaustiveness is enforced at compile time via `satisfies Record<OrderStatus, OrderStatusTraits>`, so a new status in the contract fails the build here rather than silently falling into a wrong category.
- `src/modules/orders/domain/tax.ts` — Computes VAT arithmetic for an order from each line's **frozen** price, quantity, and tax rate, plus an apportioned shipping share. It exists so that tax figures are derived at serialization time from what was actually charged, never re-resolved against a product's current tax class — a config rate change must not restate a past order. Mirrors `totals.ts`'s approach to `totalPrice`: computed on demand, never stored.
- `src/modules/orders/domain/timeline.ts` — Defines the audience (buyer vs. staff) for every timeline entry type and derives the per-type write-input shape from the generated contract. It exists so that the "who can see this row" decision is made once, at the type level, rather than by stripping fields at read time — a new timeline type cannot compile without an explicit audience assignment.
- `src/modules/orders/domain/totals.ts` — Pure arithmetic for "what does this set of priced lines add up to, and what does the customer owe on top?" It exists as a single shared source of truth so that a cart preview, the order it becomes, the frozen payment intent, and the confirmation email all agree on the same number without any of them summing independently. All rounding is delegated to `money.ts`; this module only composes.
- `src/modules/orders/domain/withdrawal.ts` — Pure domain logic for the consumer's right of withdrawal and the legal guarantee of conformity, per the Consumer Rights Directive (Art. 9, 11a, 16) and Directives 2019/771 & 2019/770. Answers three questions for an order in isolation: *when does the withdrawal window close*, *may the withdrawal button show*, and *when does the two-year conformity guarantee end*. All date math is UTC calendar-day based (Regulation 1182/71); no I/O, no side effects.
- `src/modules/orders/emails.ts` — Resolves the copy of every order-related email into finished, locale-specific strings before handing them to the mailer template. The language is an input argument and the output is fully interpolated text; the template behind it only does variable substitution. This mirrors the convention in `@modules/account/emails` and keeps translation, money formatting, and legal-copy assembly in one place per module.
- `src/modules/orders/events.ts` — Declares the six domain events the orders module emits and exports their name constants. It augments the kernel's `DomainEventMap` (via `declare module '@kernel/events'`) so the event catalogue grows per-module without a central registry. Because `orders` sits low in the dependency graph (payments and delivery depend on it, never the reverse), emitting events is its only channel outward.
- `src/modules/orders/factories.ts` — Test-fixture factory that builds a MongoDB-ready `OrderDocument` for `orderRepository.create`. It bridges the contract-level `Order` wire type and the stored document, handling the product-snapshot embedding (data, not reference), wire-to-DB conversions (`id` → `ObjectId`, ISO strings → `Date`), and sensible defaults so test callers only pin what they care about.
- `src/modules/orders/index.ts` — Public barrel for the orders module. Per the strategic DDD rule (docs/theory/strategic-ddd.md §5), this is the **only** import surface a sibling module is allowed to use. It re-exports the module's services, domain, events, emails, and model types so callers never reach into internal files directly.
- `src/modules/orders/jobs.ts` — Declares the single scheduled job (`reapOrders`) that the orders module owns: a retention scrub that anonymizes overdue orders and then strips their data from timeline text. The file exists so the kernel's job registry can discover and invoke this work without the orders module hard-coding scheduling logic elsewhere.
- `src/modules/orders/metrics.ts` — Defines the single Prometheus counter owned by the orders module — `order_created_total` — which tracks admin-created orders. Counters live in the owning domain module (not in infrastructure) so each module is self-contained; the pattern rationale is documented in `modules/account/metrics.ts`.
- `src/modules/orders/model.ts` — Defines the Mongoose schema, TypeScript document interfaces, and the serialization transform for the order aggregate. It is the single source of truth for what an order document looks like in the database (embedded product snapshots, stamped status fields, PII clock fields) and what `applyOrderTransform` adds at read time (the wire-only totals `totalItems`, `totalQuantity`, `totalPrice`).
- `src/modules/orders/module.ts` — Module entry point (the `AppModule` manifest) for the **orders** module. It wires together the order module's routes, jobs, config, rate limits, event subscriptions, public webhook mappings, PII/personal-data hooks, and scenario-state list so the kernel can mount and coordinate the module. It also encodes the key invariants in its header comment: line items snapshot catalogue fields into a local schema (no live warehouse counter), inventory claims are released on cancel/expiry, and the module never imports `invoicing`.
- `src/modules/orders/module.yaml` — Module manifest for the **orders** subdomain (group `shop`, subdomain `core`). It declares the module's upstream dependencies, the rate-limit budgets that govern its write-heavy endpoints, and the single background job responsible for post-retention PII cleanup. It exists so that tooling, the rate-limiter, and the job scheduler can resolve orders-module policy without parsing code.
- `src/modules/orders/openapi.yaml` — OpenAPI 3.1.0 contract for the **orders** module. It declares the REST surface (list, create, export), the module-specific error-code vocabulary, the account-data-export section this module contributes, and the shared parameter/schema components other order-related specs reuse. It is the single source of truth that codegen tools, clients, and the authorization module consume.
- `src/modules/orders/pii.ts` — Explicit field-level encryption/decryption codec for the PII an order freezes: the two embedded postal addresses (shipping, billing) and the buyer's free-text notes. It exists as a deliberate alternative to Mongoose getters/setters, avoiding the pitfalls where `toJSON` leaks ciphertext, subdocument copies double-encrypt, or query filters silently match nothing. It is the order-side twin of `addresses/pii.ts` under the same `NODE_PII_ENCRYPTION_KEY` ring.
- `src/modules/orders/presenter.ts` — Single translation point from stored order documents (Mongoose schemas) to the wire-level `Order` contract and `OrderTimelineEntry[]` shapes. It owns audience-aware rendering (buyer vs. staff) and PII decryption for timeline notes, so no other layer re-implements that logic.
- `src/modules/orders/probes.ts` — Declares a set of **probes** — manual API requests that exercise authorization/scoping rules the OpenAPI contract cannot express on its own. Each probe documents a subtle ownership or role-scoping case in the orders module and tells the test runner how to seed variables before the real collection runs.
- `src/modules/orders/rate-limits.ts` — Declares the two rate-limit budgets specific to the orders module (export and timeline-note endpoints) and exposes them as ready-to-use Express `RequestHandler` middlewares. It converts the raw budget data into middleware via the shared `buildRateLimiter` factory so the orders routes can enforce per-account request windows without re-implementing limiter logic.
- `src/modules/orders/repository.ts` — The order repository. Orders embed product snapshots, so filtering (e.g. by `items.product._id`) is a pipeline concern rather than a simple query. This module extends the generic repository factory with aggregation-based search, PII encryption on write, scoped single-reads, atomic conditional status transitions, and streaming exports.
- `src/modules/orders/routes.ts` — Express router that wires every order-management HTTP endpoint to its controller, attaching the appropriate authentication, permission, cache-control, rate-limit, and idempotency middleware to each route. It exists as the single registration point for the `/orders` path segment within the orders module.
- `src/modules/orders/services/actions.ts` — Computes the full set of actions a caller may perform on an order by combining state-based rules (imported from `../domain`) with caller-specific checks (permission keys, buyer identity). It exposes two wire-level entry points — `withActions` for a single order response and `withListActions` for a paginated list — so that every order the API returns already carries its `actions` object and no client re-derives the rules.
- `src/modules/orders/services/address.ts` — Implements the staff-facing `PUT /orders/{id}/shipping-address` endpoint: correcting the destination of order units that have not yet been dispatched. It exists because nothing else in the system can change an address after checkout, and each shipment retains its own frozen copy (Solidus model), so a held `incorrect_address` order has no other path to fix its delivery.
- `src/modules/orders/services/announce.ts` — Factory functions that build typed `OutboxAnnouncement` payloads for order lifecycle events. Each returned object is passed to `announceInTransaction` so the event row commits atomically with the corresponding status write (or not at all), guaranteeing per-order event ordering via a shared `aggregateId`.
- `src/modules/orders/services/cancel-mail.ts` — Sends the buyer-facing email explaining why their order was canceled. Listens to the `order.canceled` domain event so that every cancellation path (manual, automatic, hold-expiry) produces the same buyer-visible explanation, and so the email is still dispatched even if a crash occurs between the DB commit and the send.
- `src/modules/orders/services/cancel.ts` — Atomic order cancellation: the status move, stock release, and `order.canceled` outbox event are committed in a single transaction so a failed release rolls back the status too. The refund is deliberately *outside* the transaction (it is a provider-side operation that cannot roll back); instead a `refund` flag rides on the outbox event, which the `payments` module later acts on. The file also owns the cause taxonomy that drives mail, analytics, lifecycle column, and refund rules.
- `src/modules/orders/services/crud.ts` — Admin-facing write operations for orders: **create** and **update** (email amendment). The file deliberately scopes itself to the "admin door" — creating an order composes around `placeOrder` (which owns the actual write, stock hold, and rollback), and updating delegates the raw save to `updateById`. Reads live in `./read`, deletes in `./remove`, and cancellation in `./cancel`.
- `src/modules/orders/services/current.ts` — Resolves each order line's live product images (`imageUrl`, `thumbnailUrl`) from the catalogue at the serialization boundary. It exists because the frozen order snapshot schema (`orderLineProductSchema`) deliberately omits image fields, so callers need a single, batched lookup that enriches serialized orders just before they leave the API layer.
- `src/modules/orders/services/digest.ts` — Provides the two aggregate figures the daily staff digest reads from the orders domain: bank transfers about to lapse and paid orders left unshipped. Returns counts only — no order data is materialized or held, keeping the digest lightweight.
- `src/modules/orders/services/export.ts` — Produces a streaming CSV export of orders. The function validates the result size against a configurable cap, writes an audit entry, and returns a pipeable pair (object-mode `Readable` source + `csv-stringify` `Transform`) that the caller wires into the HTTP response. Nothing is written to disk or emailed; the stream is discarded if the client disconnects.
- `src/modules/orders/services/fulfillment.ts` — Service layer that provides the transactional write paths through which a fulfillment act (shipment, cancellation, lost-parcel recovery, payment hold) mutates the order's fulfillment summary and the inventory shelf. It exists so that `orders` remains the sole writer of its own fields while delegating stock-counters to `inventory`, with every read-then-write pair sharing one Mongoose session so concurrent acts (e.g. ship vs. cancel) resolve atomically.
- `src/modules/orders/services/guarantee.ts` — Implements the one-time guarantee extension for repaired goods under EU Directive 2024/1799. When a repair is performed under the statutory warranty, the order's `conformityUntil` date is pushed forward by twelve months — but only once per order. The `returns` module calls in; `orders` owns the underlying field.
- `src/modules/orders/services/index.ts` — Barrel and facade for the entire Order service layer.
