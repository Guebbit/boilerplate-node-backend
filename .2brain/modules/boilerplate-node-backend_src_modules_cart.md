# src/modules/cart/

## Purpose

The cart module owns the full lifecycle of a user's shopping basket: adding, updating, removing, and clearing product lines; selecting a shipping method; merging a guest cart after sign-in; reordering a past order; and orchestrating checkout (the single transition that turns a cart draft into a committed order). It encodes the pure domain rules that decide line validity, stock fit, and availability, and it exposes the REST surface described in its OpenAPI contract.

## Key parts

- **Domain layer** (`domain/`) — Pure, side-effect-free rules: `rules.ts` (cart-line validation verdicts), `stock.ts` (per-line stock fit), `availability.ts` (precedence rule for "can this line do what right now?"), and `merge.ts` (how many units a guest line contributes). `index.ts` is the barrel that enforces the framework-free boundary.
- **Services** (`services/`) — Business logic between controllers and the repository. `items.ts` (CRUD + shipping-method), `checkout.ts` (pre-flight → place-order → confirm, the only cart op that writes into orders), `merge.ts` (guest-cart fold), `reorder.ts` (past-order → cart), `shelf.ts` (single-product catalogue + inventory join), `view.ts` (projection to the OpenAPI `CartView`), `preorder.ts` (preorder allowance lookup), and `cleanup.ts` (external erase / product-deletion hooks). `index.ts` exposes them as the `cartService` object controllers consume.
- **Controllers** (`controllers/`) — Thin Express adapters (one per route) that validate the body, call `cartService`, and map the result to a status code. No business logic lives here.
- **Persistence & routes** — `model.ts` (Mongoose schema, one document per user), `repository.ts` (six write operations with inline concurrency guards), `routes.ts` (middleware chain + handler wiring), `module.ts` (manifest consumed by the kernel at startup).
- **Contract & ops** — `openapi.yaml` (REST contract + error codes), `probes.ts` (edge-case requests beyond the spec), `config.ts` (retention, quantity cap, unpaid-order cap), `rate-limits.ts` (budgets for checkout and merge), `factories.ts` (test/seed fixture builder).
- **Cross-cutting declarations** — `analytics.ts`, `audit.ts`, `events.ts`, `metrics.ts` — each augments a kernel-wide type map or registers Prometheus counters so the catalogue stays self-documenting and typed.
- **Tests** (`tests/`) — `contract/` asserts the exact wire shape of every cart endpoint; `integration/` covers the `expectedTotal` invariant and other checkout edge cases.

## How it connects

- **orders** — `services/checkout.ts` calls `placeOrder` and reads the resulting order back via `orderService.withActions`. `services/reorder.ts` reads a past order to repopulate the cart. The dependency direction is strictly `cart → orders`.
- **inventory** — `services/shelf.ts` and `domain/stock.ts` query the inventory ledger for units-for-sale and preorder allowance to decide line availability.
- **products** — `services/shelf.ts` joins the catalogue document; `services/items.ts` applies the catalogue gate (listed / delisted) before accepting a line.
- **users** — The cart document is keyed by `userId`; `services/cleanup.ts` subscribes to the `personalData.erase` hook and to product-deletion domain events to tidy up orphaned references.
- **addresses** / **payments** / **delivery** — `services/checkout.ts` resolves the billing address, shipping address, payment method, and shipping option as part of the pre-flight before calling `placeOrder`.
- **wishlist** — The wishlist's "move-to-cart" path calls the same `cartService.cartItemAdd` entry point; `services/merge.ts` and `domain/merge.ts` enforce the per-line cap that the wishlist must also respect.
- **notifications** — `services/merge.ts` emits a `cart.merge_refused` domain event so the notifications module can deliver a persistent refusal notice.
- **infrastructure / infrastructure/http** — The shared CRUD factory underpins `repository.ts`; Express middleware (auth, rate limiting, idempotency) is wired in `routes.ts`.
- **observability** — `metrics.ts` registers domain-owned Prometheus counters into the shared registry read by the overview endpoint.
- **locales** — Service-layer refusal reasons are mapped to i18n strings before reaching the HTTP boundary.

## Where to start

Read **`routes.ts`** first: in one file you see every endpoint, the middleware chain, and which controller handles what, giving you the full HTTP surface in ~2 minutes. Then read **`services/checkout.ts`**: it is the most complex service and shows how the cart module orchestrates across orders, payments, addresses, and inventory, as well as how the `expectedTotal` invariant and domain-rule verdicts flow into the final response. Together they anchor the module's role as the bridge between a user's draft basket and a committed order.

## Files
- `src/modules/cart/analytics.ts` — Declares the analytics event names emitted by the cart module and registers them into the application-wide `AnalyticsEventMap` via TypeScript module augmentation. It exists so that event-name strings live alongside the code that emits them, keeping the global catalogue self-documenting and typed.
- `src/modules/cart/audit.ts` — Declares the audit action names the cart module emits and registers them into the app-wide `AuditActionMap` via TypeScript module augmentation. The actions exist to create an auditable trail of customer-initiated cart mutations (item removal, bulk reorder) that serve as the authoritative record for support disputes about cart contents.
- `src/modules/cart/config.ts` — Defines the three runtime-adjustable knobs for the cart module—retention period, per-line quantity ceiling, and open-unpaid-order cap—and exposes typed accessor functions that read them. It exists so that inventory-denial guards (OWASP OAT-021) and cart lifecycle rules can be tuned without code changes.
- `src/modules/cart/controllers/delete-cart-all.ts` — Thin HTTP adapter that handles the `DELETE /cart/all` endpoint. It delegates to `cartService.cartRemove` to remove every item from the authenticated user's cart. It lives on a dedicated URL (not `DELETE /cart`) so that a missing or stripped request body can never accidentally trigger a full cart wipe.
- `src/modules/cart/controllers/delete-cart-item.ts` — Thin HTTP adapter that maps `DELETE /cart/:productId` (canonical) and `DELETE /cart` (alias) to `cartService.cartItemRemoveById`. It extracts the target `productId` from either the path segment or the request body, delegates to the cart service, and shapes the HTTP response (200 / 404 / 422) without business logic.
- `src/modules/cart/controllers/get-cart-summary.ts` — Thin HTTP controller for the `GET /cart/summary` endpoint. It extracts the authenticated user's ID, delegates to `cartService.cartGetForBadge`, and sends back only the `summary` portion of the result. All business logic lives in the service layer; this file exists solely to bridge the HTTP boundary.
- `src/modules/cart/controllers/get-cart.ts` — Thin HTTP adapter that exposes the current user's cart over `GET /cart`. It exists solely to bridge the Express request/response cycle to `cartService.cartGetForView`, keeping business logic in the service layer.
- `src/modules/cart/controllers/post-cart-merge.ts` — Thin HTTP adapter for the `POST /cart/merge` endpoint. It validates the request body, delegates to `cartService.cartMerge`, and formats the response. Exists solely to bridge the Express route to the cart service without business logic.
- `src/modules/cart/controllers/post-cart.ts` — Thin HTTP adapter that handles `POST /cart`. It validates the incoming body, extracts the authenticated user, and delegates to `cartService.cartItemAdd`. It maps the service result to the appropriate HTTP status (201 if a new line was created, 200 if an existing line's quantity grew) and serializes the response. It intentionally contains no cart-eligibility logic — that decision belongs to the service layer so it stays consistent across `PUT /cart/{productId}` and the wishlist's move-to-cart path.
- `src/modules/cart/controllers/post-checkout.ts` — HTTP controller for `POST /cart/checkout`. It validates the request body, delegates to `cartService.orderConfirm`, records the `cart_checkout_total` metric on every outcome, transforms the resulting order through `orderService.withActions` into its wire shape, and returns a `201` with the created order. Exists to keep the HTTP/response concerns out of the cart service layer.
- `src/modules/cart/controllers/post-reorder.ts` — HTTP adapter for `POST /cart/reorder/:orderId`. Validates the `orderId` path param, delegates to `cartService.reorderIntoCart`, and maps the result (or refusal) onto an Express response. It exists to keep route handling and business logic in separate layers.
- `src/modules/cart/controllers/put-cart-item.ts` — Thin HTTP adapter for `PUT /cart/:productId`. It extracts the product ID from the path, parses the quantity from the body, delegates to `cartService.cartItemUpdateQuantity`, and maps the service result to a `201` (line created) or `200` (line updated) response.
- `src/modules/cart/controllers/put-cart-shipping-method.ts` — Thin HTTP adapter for `PUT /cart/shipping-method`. It validates the request body, delegates to the cart service to set (or clear with `null`) the shipping method, and returns the re-priced cart. Contains no business logic itself.
- `src/modules/cart/domain/availability.ts` — Defines the single precedence rule that decides what a saved cart/wishlist line "can do right now." It is pure (no I/O, no side effects) so the same judgment can drive cart-line status, wishlist display, merge results, and checkout refusal without duplicating logic.
- `src/modules/cart/domain/index.ts` — Barrel (re-export) file for the cart **domain layer**. It provides a single, stable public surface for all pure business rules and types, so that services and tests import from one path rather than reaching into individual submodules. The file declares no logic of its own — it exists purely to aggregate exports and enforce the "framework-free" boundary noted in `docs/theory/domain-layer.md`.
- `src/modules/cart/domain/merge.ts` — Pure domain rule that decides how many units a single guest cart line adds to an existing cart, given the current held quantity, whether the product is listed, and the per-line cap. It is side-effect-free and intentionally knows nothing about stock, the catalogue, or persistence — the caller supplies all context.
- `src/modules/cart/domain/rules.ts` — Pure domain rules for cart validation. Given joined cart-line data, it produces typed verdicts (pass or a named refusal reason with details) without touching status codes, i18n, or side effects. The service layer maps these verdicts to HTTP responses. It intentionally mirrors `orders`' `checkOrderLines` logic but is kept separate: a cart is a draft, an order is a commitment.
- `src/modules/cart/domain/stock.ts` — Pure stock-checking rule for the cart: determines whether a line's quantity fits what is currently for sale. Exists as a single shared predicate so that checkout pre-flight, cart merge, and the cart view all agree on the same verdict without re-implementing the logic.
- `src/modules/cart/events.ts` — Declares the cart module's domain event payloads by augmenting the kernel's `DomainEventMap` interface (via `declare module '@kernel/events'`), so the event catalogue grows per-module without editing a central file. Also exports the event-name string constants so emitters and listeners share a single spelling.
- `src/modules/cart/factories.ts` — Factory for building cart fixtures ready to pass to `cartRepository.create`. It centralises the string-to-`ObjectId` conversion and the partial-document shape so that seed scripts and test setup don't each re-implement that logic. A cart is addressed solely by its owner (`userId`); no separate cart `_id` is produced here.
- `src/modules/cart/index.ts` — Public barrel for the cart module. It is the **only** import surface a sibling module is allowed to use (per `docs/theory/strategic-ddd.md` §5). It re-exports the module's services, events, and domain types while deliberately keeping `cartRepository` and the model's runtime values internal, so siblings cannot bypass service-layer rules.
- `src/modules/cart/metrics.ts` — Declares the domain-owned Prometheus counters for the cart module. Metrics live here (rather than in `infrastructure`) so the module is the single source of truth for what it tracks; the overview endpoint reads them from the shared registry without needing to import this file.
- `src/modules/cart/model.ts` — Defines the Mongoose schema, document interface, and model for the cart collection. One document per user (enforced by a unique index on `userId`) stores the cart's items and an optional shipping-method id. Field names are chosen to match the OpenAPI `CartItem` shape so stored and wire representations stay identical.
- `src/modules/cart/module.ts` — Module manifest (entry point) for the shopping-cart module. It assembles the cart's HTTP routes, configuration, rate limits, personal-data hooks, and domain-event subscriptions into a single `AppModule` object that the kernel registry consumes at startup.
- `src/modules/cart/openapi.yaml` — OpenAPI 3.1.0 contract for the cart module. Defines the REST surface (list, add, update, remove, clear, checkout) for a signed-in user's cart and the set of module-specific error codes that checkout and cart mutations can return. Serves as the machine-readable source of truth for client SDK generation and for the shared error-code vocabulary other modules reference.
- `src/modules/cart/probes.ts` — Declares the cart module's list of "probes" — concrete API requests that the OpenAPI contract can describe but cannot express on its own (e.g., a 404-earning body, a forbidden zero quantity, a catalogue-gate bypass). These probes are consumed by the runnable-collections pipeline to exercise edge cases the spec alone cannot capture.
- `src/modules/cart/rate-limits.ts` — Defines the two per-account rate-limit budgets that protect the cart module's expensive endpoints (`POST /cart/checkout` and `POST /cart/merge`), and exports the resulting Express middleware handlers plus a registry array consumed by the module declaration.
- `src/modules/cart/repository.ts` — Cart persistence layer. Wraps `cartModel` with the six writes a cart actually takes (upsert/remove/clear a line, version-guarded clear, shipping-method set, product/user deletion) on top of the shared CRUD factory. All line-level writes handle concurrency inline—conditions live in the MongoDB filter, not in a preceding read—so two simultaneous requests cannot both conclude "absent" and both append.
- `src/modules/cart/routes.ts` — The Express route table for the cart domain. It wires the shared auth/authorization middleware chain, per-route security controls (fresh-auth, second permission, rate limiter, idempotency, cache invalidation), and the individual cart controller handlers onto a single `Router` instance. Every HTTP request under the cart path passes through this file before reaching a controller.
- `src/modules/cart/services/checkout.ts` — The checkout service for the cart module. It is the single cart operation that writes into another module's collection (orders) and the only one where a race condition can cost a customer money. It orchestrates the full pre-flight → place-order → confirm flow: resolving payment method, shipping, and billing; evaluating the basket against domain rules; calling `placeOrder`; and emitting analytics.
- `src/modules/cart/services/cleanup.ts` — Provides the two external cleanup entry points for the cart module: one for hard-deleting a user's cart (called as a `personalData.erase` hook from another module's transaction) and one for removing a product from all carts (subscribed as a domain-event handler). Neither is reachable from a cart route; they exist because a cart references a user and a product it does not own, and no other code tidies up after either.
- `src/modules/cart/services/index.ts` — Barrel (re-export) file for the cart services sub-module. It collects the public API from the individual service files (`items`, `checkout`, `reorder`, `merge`, `cleanup`, `shelf`) and publishes them both as named exports and as the single `cartService` object that controllers consume. It exists as a thin forwarding layer so callers never import sub-files directly.
- `src/modules/cart/services/items.ts` — Service-layer functions that read and mutate a user's cart contents: add, set, remove, and clear product lines, plus selecting (or clearing) a shipping method. Sits between HTTP controllers and the repository, layering the catalogue gate, per-line quantity limits, response envelopes (200/201/404/422/409), analytics emission, and audit recording on top of raw repository calls.
- `src/modules/cart/services/merge.ts` — Implements the guest-cart merge (`POST /cart/merge`): folds every line from an unsigned-out cart into the signed-in user's cart in a single server-side call. It exists server-side because refused lines must produce a persistent notification (via `cart.merge_refused`) and the per-line cap must be enforced against the same cart document that is being written—neither is possible with a browser loop of individual `POST /cart` calls.
- `src/modules/cart/services/preorder.ts` — Pre-computes which cart-line products are preorders and reshapes their fields into the shape the availability rule expects. It exists so that cart services can ask the inventory ledger for *allowance* (preorder) rather than *shelf* stock, without the ledger ever knowing what a release date is.
- `src/modules/cart/services/reorder.ts` — Implements the "reorder" feature: takes a past order's items, re-resolves them against the current product catalogue, and fills the caller's cart with whatever is still available. It lives in the **cart** module (not orders) because it *writes* to the cart and only *reads* the order — keeping the dependency direction `cart → orders` that the module manifests declare.
- `src/modules/cart/services/shelf.ts` — Defines the "shelf" — a single-product join of its catalogue document and inventory-ledger units for sale — and the two-query read that materialises it for any set of product ids. Exists so cart operations (merge, wishlist checks) get a consistent availability answer from one place instead of scattering catalogue and inventory calls.
- `src/modules/cart/services/view.ts` — Cart projection: transforms a stored `CartDocument` into the `CartView` shape that `openapi.yaml` declares as the cart response. It joins cart lines to their products, computes line availability, prices shipping, and assembles the summary — all in one pipeline that every cart endpoint (reads and mutation payloads) returns. Lives inside `services/` and is shared by the sibling service files (`checkout`, `items`, `merge`, `reorder`, `preorder`) rather than owned by any one of them.
- `src/modules/cart/tests/contract/api.contract.test.ts` — Contract tests for every `/cart` route. Because all six endpoints share one `CartResponseEnvelope` shape, a serialization change in one endpoint silently breaks the others; these tests assert the exact wire format each branch produces. Carts are built through the live API (not fixture builders) because `CartResponse` is a computed view, not a document dump — a hand-written fixture would assert a shape the app never serializes. Behavioural logic lives in the service suites; this file only verifies that each contract branch is reachable and shaped correctly.
- `src/modules/cart/tests/integration/checkout-expected-total.test.ts` — Integration tests for `POST /cart/checkout` that verify the **`expectedTotal` invariant**: the buyer is charged only the total the cart screen showed them, and any drift (price, shipping, or basket change) between read and checkout is refused with a `409 CART_TOTAL_CHANGED` carrying both the expected and actual totals. Tests also confirm that a refused checkout is fully clean (no order, no held stock, cart unchanged) and that a buyer can recover by re-submitting with the new total.
- `src/modules/cart/tests/integration/checkout-rate-limit.test.ts` — Integration test that verifies the per-account checkout rate limiter (`POST /cart/checkout`) over real HTTP. It exercises the limiter with a trivial Express handler rather than the full checkout flow, so the property under test (budget enforcement) is isolated from database I/O. The real-route wiring is covered separately in `routes.test.ts`.
- `src/modules/cart/tests/integration/checkout-version.test.ts` — Integration test (real MongoDB, no mocks) that guarantees two invariants protecting the checkout race guard: (1) every cart mutation that actually changes state bumps the document's `__v`, and (2) `clearLinesIfUnchanged` empties the cart atomically only when `__v` still matches the value read earlier. Together these ensure a line added or removed mid-checkout is detected rather than silently dropped.
- `src/modules/cart/tests/integration/line-availability.test.ts` — Integration tests that verify how cart lines reflect product availability state driven by the `active` and `purchasable` flags. The core invariant under test: a hidden product's line is **kept** and reads `removed`, an off-sale product's line is **kept** and reads `unavailable`, and checkout refuses both but for different reasons. No test here asserts line removal—only deletion does that.
- `src/modules/cart/tests/integration/merge-effects.test.ts` — Integration tests that verify the **observable side effects** of cart merge and product-removal operations — analytics emissions and domain-event announcements — which the primary answer/return-value tests do not cover. Ensures dashboards keep receiving data and that `CART_LINES_REMOVED` fires only when there is actually something to announce.
- `src/modules/cart/tests/integration/merge-rate-limit.test.ts` — Integration test that verifies the per-account merge rate limiter (`mergeLimiter`) enforces its budget on `POST /cart/merge`: it returns 429 once an account's allowance is exhausted and keeps accounts isolated from each other. It uses a trivial success handler because the property under test belongs to the limiter itself; route mounting is asserted separately in `../unit/routes.test.ts`.
- `src/modules/cart/tests/integration/merge.test.ts` — Integration test suite for `cartMerge` — the operation that folds a guest cart into a signed-in user's cart. Verifies the line-by-line response contract (summed, capped, removed, flagged), confirms stock availability is reported without mutating quantities, and asserts that a `CART_MERGE_REFUSED` domain event fires for lines that could not be added. Every test reads the cart back via `cartGet` rather than trusting the merge response to self-describe.
- `src/modules/cart/tests/integration/preorder.test.ts` — Integration tests for the preorder cart flow: verifying that a line's availability is judged against the preorder allowance (not shelf stock), that checkout claims the allowance while leaving the shelf untouched and freezes the preorder promise on the order line, and that a basket may mix preorder items with ordinary in-stock goods.
- `src/modules/cart/tests/integration/schema-contract.test.ts` — Integration test that verifies schema-level guarantees (unique index, defaults, `required`, `select: false`) against a real MongoDB instance. It exists because these are Mongoose/Mongo behaviours—not application logic—and a mock would only assert its own opinion rather than the actual schema contract.
- `src/modules/cart/tests/integration/service.test.ts` — Integration tests for the cart service layer (`src/modules/cart/services/`). Runs against a real MongoDB instance (`setupTestDb`) to exercise behaviour that only lives in repository guarded writes — specifically the `set` vs `add` distinction (shared `upsertCartItem` differing by `$set` vs `$inc`), the over-serialization contract on the cart view, the per-user cart document shape (no per-line `_id`), live shipping pricing, and the checkout/order-confirmation flow.
- `src/modules/cart/tests/integration/stock-flag.test.ts` — Integration tests verifying two invariants of cart-line availability: (1) each line in `GET /cart` and `POST /cart/merge` carries the correct `availability` name (`in_stock`, `insufficient_stock`, `out_of_stock`, `removed`) derived from the stock ledger and catalogue, and (2) no field in any cart response ever exposes a numeric stock quantity—the flag is a name, never a count.
- `src/modules/cart/tests/integration/stock.test.ts` — Integration suite verifying the reservation invariant across the full order lifecycle: units are held (reserved) at checkout, not sold; they leave `onHand` only after payment; and they are recoverable via cancellation or TTL expiry. Runs against a real Mongo instance because the guarantees depend on conditional writes that mocks cannot represent.
- `src/modules/cart/tests/integration/totals.test.ts` — Integration test that verifies the cart's `totalPrice` is identical to the value carried by the resulting order and payment intent. It guards against floating-point drift by exercising prices (e.g. 0.56) where summing two decimals directly would differ by an epsilon from the expected total.
- `src/modules/cart/tests/integration/upsert-retry.test.ts` — Deterministically exercises the retry budget (3 attempts) inside `cartRepository.upsertLine` by forcing the model's atomic write to fail or miss on demand. It verifies three invariants: a duplicate-key loss is retried and the increment is applied exactly once; exhausting the budget throws (duplicate-key or "exhausted retries") and writes nothing; and non-duplicate-key errors are surfaced immediately without retry. The actual race condition is covered in `concurrency/cart-races.test.ts`; this file isolates the *bound* that a real race cannot trigger deterministically.
- `src/modules/cart/tests/unit/config.test.ts` — Unit tests for the cart's checkout-cap configuration, specifically `maxOpenUnpaidOrdersPerAccount`. Because the function under test is a pure environment-variable read (no I/O, no HTTP), the unit suite is sufficient here; the resulting 409 response is exercised separately in the integration suite.
- `src/modules/cart/tests/unit/domain-rules.test.ts` — Unit tests for the three pure cart domain functions in `rules.ts` (`evaluateCheckout`, `basketWeight`, `evaluateShippingRequirement`). No mocks, no database — the input lines are constructed inline to exercise every branch of the decision logic. The verdict-to-HTTP-status mapping is explicitly out of scope (covered in `service.test.ts`).
- `src/modules/cart/tests/unit/factories.test.ts` — Unit tests for the `makeCart` factory builder. They verify the factory's one critical transformation—converting string product/user IDs into real `Types.ObjectId` instances—and that it handles the absence vs. explicit empty-cart distinction correctly, ensuring seeded carts actually join against the catalogue rather than silently matching nothing.
- `src/modules/cart/tests/unit/line-availability.test.ts` — Unit tests for the `lineAvailability` function — the single precedence rule that determines the status of a cart line, wishlist line, merge result, or checkout refusal. Every row of the precedence table is exercised with no mocks and no database.
- `src/modules/cart/tests/unit/merge-rule.test.ts` — Unit tests for `planMergeLine`, the cart's merge rule in the domain layer. The suite asserts the rule's invariants over a full input grid (quantity × held × visibility) rather than relying on a handful of examples, and pins the precedence order when multiple reasons apply. No mocks, no database — the function under test is pure.
- `src/modules/cart/tests/unit/retention.test.ts` — Unit test that verifies the cart collection's TTL index is created with the correct `expireAfterSeconds` value derived from `NODE_CART_RETENTION_DAYS`. Because the TTL index is built once at import time in the model, the test re-imports the model under a fresh module registry to trigger that import-time read again.
- `src/modules/cart/tests/unit/routes.test.ts` — Unit test for the cart router (`src/modules/cart/routes.ts`). It locks down the route table (which endpoints exist, in what order), the authorization and permission guards on every route, the placement of rate-limit budget keys and idempotency middleware in the checkout/merge chains, and the cache-invalidation / no-cache invariants. The file exists to make regressions in guard order or accidental cache writes fail immediately rather than in production.
- `src/modules/cart/tests/unit/schema-contract.test.ts` — Unit test that pins the Mongoose schema contract for the `cart` collection: required fields, indexes, defaults, TTL expiry, and the shape of each line item. It exists so that any accidental schema drift (a missing index, a wrong default, an extra field) fails at test time rather than surfacing as a production query or data bug.
- `src/modules/cart/tests/unit/stock-rule.test.ts` — Unit test for the `fitsStock` stock rule in the cart domain layer. It verifies the boundary conditions of `fitsStock` (including zero and unknown availability) and cross-checks its verdict against `evaluateCheckout` to guarantee the checkout gate and the cart view never disagree on whether a quantity fits.
