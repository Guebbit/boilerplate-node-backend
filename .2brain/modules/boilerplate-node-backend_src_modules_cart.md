# src/modules/cart/

## Purpose

The cart module owns the signed-in user's basket: reading, mutating, and clearing its line items; selecting a shipping method; merging a guest cart; reordering a past order; and—most critically—orchestrating checkout, the one cart operation that crosses into other modules' collections (orders, inventory, payments). It enforces per-line and per-cart quantity ceilings, stock-fit and listing-status rules, and the single authorization gate (confirmed email) that guards spending.

## Key parts

- **Domain rules** (`domain/`) — Pure, side-effect-free functions: `availability` (seven-state line classification), `rules` (checkout pre-flight verdicts), `stock` (quantity-vs-for-sale fit), and `merge` (guest-line fold calculation). A barrel (`domain/index.ts`) exposes them as one import surface.
- **Service layer** (`services/`) — One file per flow: `items` (add / set / remove / clear / shipping), `checkout` (orchestrates the purchase across orders, inventory, payments), `merge`, `reorder`, `cleanup`, `preorder`. `errors.ts` centralises the status-code + message pairs shared by multiple services. `services/index.ts` aggregates them behind a single `cartService` object.
- **HTTP layer** (`controllers/`, `routes.ts`, `rate-limits.ts`) — Thin Express adapters (one per endpoint) that extract auth context, validate the body, delegate to `cartService`, and shape the response. `routes.ts` wires controllers, auth, permissions, rate limits, idempotency, and cache-invalidation middleware in a safety-relevant order. `rate-limits.ts` supplies the two per-account budgets (checkout, merge).
- **Persistence** (`model.ts`, `repository.ts`) — Mongoose schema (one document per user, TTL retention, `__v` version guard) and the data-access layer. Line mutations enforce ceilings atomically in the MongoDB filter.
- **Contract & presentation** (`openapi.yaml`, `presenter.ts`, `probes.ts`, `authorization.yaml`) — Machine-readable API spec, pure response-mapping, boundary-path probes, and the single email-confirmation rule.
- **Telemetry & events** (`analytics.ts`, `audit.ts`, `metrics.ts`, `events.ts`) — Typed event-name and audit-action registries, a domain-owned Prometheus counter for checkout attempts, and `DomainEventMap` augmentation for domain events.
- **Module wiring** (`module.ts`, `module.yaml`, `config.ts`, `index.ts`) — Kernel registration, rate-limit and personal-data hooks, four operator-tunable numeric limits, and the public barrel that is the only import surface allowed to sibling modules.

## How it connects

- **orders** — Checkout writes an order document; `reorder` reads a past order to copy lines back into the cart. Dependency direction is strictly `cart → orders`.
- **inventory** — Checkout holds stock; the domain `stock` rule and `availability` function both consume inventory ledger counts supplied by this module.
- **payments** — Checkout delegates payment capture after stock is held.
- **products** — Catalogue lookups (listing status, preorder/backorder flags, product facts) feed the domain rules; product deletion triggers the cart cleanup hook.
- **users** / **account** — Email-confirmation check (the sole authorization rule) and user-deletion cleanup hook both depend on account/user data.
- **delivery** — Shipping-method selection and pricing consume delivery-module data.
- **invoicing** — Checkout or order-creation flow references invoicing for billing context.
- **locales** — Error messages and user-facing text are resolved through the locales module.
- **observability** — Audit events, analytics events, and Prometheus metrics are consumed by the observability layer; cart declares its vocabulary, observability collects it.
- **shared / infrastructure** — `createRepository`, `buildRateLimiter`, the analytics port, and other cross-cutting utilities come from these layers.
- **scenarios** — Integration/E2E scenarios exercise cart endpoints against the OpenAPI contract and probes.

## Where to start

1. **`services/items.ts`** — The daily-driver service (add, set quantity, remove, clear, shipping). Reading it shows how a controller delegates, how the domain rules are applied, how the repository is called, and how the presenter shapes the response—all in one file.
2. **`domain/rules.ts`** — The checkout pre-flight verdicts are the tightest expression of "what can go wrong" in the module. They are pure, short, and reference the exact conditions that `services/checkout.ts` enforces, making them the best map of the module's business constraints.

## Files
- `src/modules/cart/analytics.ts` — Declares the analytics event names emitted by the cart module and registers them into the analytics port's app-wide `AnalyticsEventMap`. It exists so that event-name strings live alongside the code that fires them (e.g. checkout events are here because `POST /cart/checkout` is a cart endpoint), giving the module a single source of truth for its telemetry vocabulary.
- `src/modules/cart/audit.ts` — Declares the cart module's audit action names and registers them into the app-wide `AuditActionMap` via TypeScript module augmentation. This file exists so that any audit event the cart emits has a stable, typed identifier that the observability layer can consume without circular imports.
- `src/modules/cart/authorization.yaml` — Defines the single authorization rule for the cart module: verifying that a caller's account has a confirmed email before they can *spend* their basket (i.e., check out). Cart contents themselves (add, remove, set-quantity) are intentionally rule-free; only the act of spending is gated because it is a fact about the account, not the basket.
- `src/modules/cart/config.ts` — Defines the four operator-tunable numeric limits for the cart module (retention period, per-line quantity, per-cart line count, and open-unpaid-order cap) and exposes typed accessor functions that the rest of the module reads at call time.
- `src/modules/cart/controllers/delete-cart-item.ts` — Thin HTTP adapter that handles `DELETE /cart/items/:productId`. It extracts and validates the product ID from the URL, delegates the actual removal to `cartService.removeItemById`, and shapes the HTTP response (success or error). Exists so the service layer stays transport-agnostic.
- `src/modules/cart/controllers/delete-cart-items.ts` — Thin HTTP adapter that handles `DELETE /cart/items` — removing **all** items from the authenticated user's cart. It delegates to `cartService.remove` and exists as a dedicated, bodyless endpoint so the destructive operation is unambiguously opt-in by URL rather than hidden behind a query flag or body parameter.
- `src/modules/cart/controllers/get-cart-summary.ts` — Thin HTTP adapter for the `GET /cart/summary` endpoint. It extracts the authenticated user's ID from the request, delegates to `cartService.getForBadge`, and sends back only the `summary` sub-field of the resulting cart object.
- `src/modules/cart/controllers/get-cart.ts` — Thin HTTP adapter for the `GET /cart` endpoint. It extracts the authenticated user's ID and caller context from the incoming request, delegates to `cartService.getForView`, and formats the resulting cart into a standard HTTP success or error response.
- `src/modules/cart/controllers/patch-cart-item.ts` — Thin HTTP adapter for `PATCH /cart/items/:productId`. Extracts the product ID from the path and the quantity from the body, then delegates to `cartService.updateItemQuantity` and serialises the result (or an error) back to the client.
- `src/modules/cart/controllers/post-cart-items.ts` — Thin HTTP adapter for `POST /cart/items` ("Add to cart"). Validates the request body, delegates to `cartService.addItem`, and serialises the result. It contains no business logic — eligibility rules live in the service layer so they stay consistent with `PATCH` and wishlist move-to-cart.
- `src/modules/cart/controllers/post-cart-merge.ts` — Thin HTTP adapter for the `POST /cart/merge` endpoint. It validates the incoming body, delegates the actual merge logic to `cartService.merge`, and formats the response — keeping transport concerns separate from cart-domain logic.
- `src/modules/cart/controllers/post-checkout.ts` — Thin HTTP adapter for `POST /cart/checkout`. It validates the request body, delegates to `cartService` to convert the cart into an order, records the `cart_checkout_total` metric on every outcome, and shapes the created order into a `201 Created` response.
- `src/modules/cart/controllers/post-reorder.ts` — Thin HTTP adapter for `POST /cart/reorder`. Validates the request body, delegates to `cartService.reorderIntoCart`, and maps the service result (or rejection) to an HTTP response. Exists so the cart service stays transport-agnostic while the Express layer handles parsing, auth context extraction, and status-code selection.
- `src/modules/cart/controllers/put-cart-shipping-method.ts` — Thin HTTP adapter for `PUT /cart/shipping-method`. Validates the incoming body, delegates to `cartService.setShippingMethod`, and serialises the updated (re-priced) cart back to the client. Exists so the Express route layer stays a single-line registration.
- `src/modules/cart/domain/availability.ts` — Defines the single precedence rule that assigns a `LineAvailability` state to a cart, wishlist, or merge-result line. It is a pure domain function: given a joined product and the ledger's unit counts, it returns exactly one of seven states in a fixed order. No side effects, no I/O.
- `src/modules/cart/domain/index.ts` — Barrel (re-export) file for the cart domain layer. It aggregates the public API of the four domain submodules—`rules`, `merge`, `stock`, and `availability`—into a single import surface, so consumers can `import { … } from '@/modules/cart/domain'` instead of reaching into individual files. Contains no logic of its own.
- `src/modules/cart/domain/merge.ts` — Pure domain rule that decides how many units a single guest line adds to a cart, given the current cart state and the product's listing status. It exists to keep the merge calculation free of I/O—no catalogue lookups, no model access—so the cap and listing flag are supplied by the caller.
- `src/modules/cart/domain/rules.ts` — Pure decision functions for the cart domain: given joined cart-line data, they return a verdict (ok / refused + reason) without touching status codes, i18n, or the network. The service layer maps each verdict to a response. This keeps the "why is checkout blocked?" logic testable and free of side effects.
- `src/modules/cart/domain/stock.ts` — Defines the cart's single stock-fit rule as a pure function. It exists so that checkout pre-flight, cart merge, and the cart view all share one definition of "does this line's quantity fit what is for sale," preventing the three call sites from drifting apart.
- `src/modules/cart/events.ts` — Declares the cart module's domain events by augmenting the kernel's `DomainEventMap` interface (in `@kernel/events`), and exports the event-name constants so emitters and listeners share a single spelling. This keeps the catalogue of events composable—each module adds its own payloads without editing a central file.
- `src/modules/cart/factories.ts` — Builds cart fixtures (documents ready for `cartRepository.create`) from bare string product/user ids and quantities. It exists so that test and seed code can construct a valid `CartDocument` without manually wrapping every id in `Types.ObjectId` or re-declaring the line-item shape.
- `src/modules/cart/index.ts` — Public barrel (re-export) for the cart module. It is the **only** import surface allowed to sibling modules, per the strategic-DDD rule in `docs/theory/strategic-ddd.md` §5. It exposes service APIs, events, and domain logic by value, while the model and presenter are exposed as **types only**, keeping their runtime implementations (and the `cartRepository`) internal so siblings cannot bypass the service's rules.
- `src/modules/cart/metrics.ts` — Declares the domain-owned Prometheus counters for the cart module (currently: checkout attempts). Metrics live here—colocated with the cart domain—rather than in `infrastructure`, so the module is the single source of truth for what it measures. The overview endpoint reads these counters without importing this file directly (see `modules/account/metrics.ts` for the full rationale).
- `src/modules/cart/model.ts` — Defines the Mongoose schema, document interface, and model instance for the persistent cart collection (one document per user). It establishes the stored shape of cart lines, the shipping-method slot, TTL-based retention, and the serialization transform that the repository factory consumes. It deliberately does **not** produce the API response shape; that is a computed view built by `services/view`.
- `src/modules/cart/module.ts` — Module manifest that registers the cart module with the kernel: it wires the router, config, rate limits, personal-data hooks, and a single domain-event subscription into one `AppModule` object that `src/modules.ts` collects at startup.
- `src/modules/cart/module.yaml` — Module descriptor for the cart subdomain. It declares the module's position in the architecture (core/shop), enumerates its runtime dependencies with the specific data each one supplies, and defines rate-limit policies for the two write endpoints (`POST /cart/checkout` and `POST /cart/merge`). It does not define routes or schemas — that lives in the sibling OpenAPI spec.
- `src/modules/cart/openapi.yaml` — OpenAPI 3.1.0 contract for the cart module. It defines the HTTP surface for reading, mutating, and clearing the signed-in user's cart (add, set-quantity, remove, clear) and declares the module's error-code vocabulary and its contribution to the account data export. It exists so that every consumer—front-end, SDK, test harness—shares a single machine-readable source of truth for the cart API.
- `src/modules/cart/presenter.ts` — Pure mapping layer that takes already-computed cart facts (lines, totals, shipping) and shapes them into the `CartResponse` the OpenAPI contract requires. It exists so that the "what goes on the wire" logic — including derived flags like `canIncrease` and `checkoutable` — lives in one testable, side-effect-free function rather than being scattered across services.
- `src/modules/cart/probes.ts` — Exports the cart module's probe collection: a set of `Probe` request definitions that exercise failure and boundary paths the OpenAPI contract can describe but cannot trigger. Each probe encodes *why* it exists in a `why` string so the intent is self-documenting.
- `src/modules/cart/rate-limits.ts` — Declares the two cart-specific rate-limit budgets (checkout and merge) and converts them into ready-to-use Express middleware via the shared `buildRateLimiter` factory. It exists because these two endpoints are the most expensive per-request operations in the cart module and need per-account limits beyond the global brake.
- `src/modules/cart/repository.ts` — Provides the cart's data-access layer: a standard CRUD repository (via `createRepository`) plus the six domain-specific writes a cart actually performs — upsert/remove/clear lines and the two cleanup writes triggered by product or user deletion. All line mutations enforce per-line and per-cart quantity ceilings atomically inside the MongoDB filter, and bump `__v` so checkout's version-guarded clear can detect in-flight modifications.
- `src/modules/cart/routes.ts` — Defines the Express route table for the cart domain. It wires each cart HTTP endpoint to its controller, applies the shared auth middleware, and layers per-route middleware (permissions, rate limits, idempotency, cache invalidation) in a specific order that matters for safety.
- `src/modules/cart/services/checkout.ts` — Orchestrates the checkout flow — the single cart operation that writes into another module's collection (orders) and the only one where a race can cost a customer money. It runs pre-flight validations (payment, address, shipping) that refuse the request *before* any stock is held, then delegates to the order, inventory, and payment services to complete the purchase.
- `src/modules/cart/services/cleanup.ts` — Provides the two cleanup entry points the cart module exposes for when entities it references (a user or a product) are hard-deleted elsewhere. Neither function is reachable from a cart route; they are hooks and event handlers wired up in the module manifest so that other modules can trigger cart-side tidying.
- `src/modules/cart/services/errors.ts` — Single source of truth for HTTP rejection responses raised by multiple cart services (basket and checkout). By centralising the code + message pair in one leaf module, the file guarantees that any service raising the same business error returns identical status, error code, and user-facing text.
- `src/modules/cart/services/index.ts` — Barrel file for the cart service layer. It aggregates the six sub-service modules (`items`, `checkout`, `reorder`, `merge`, `cleanup`, `shelf`) behind a single `cartService` object so that controllers and other modules never import individual flow files directly. This keeps the public API surface in one place and enforces the one-file-per-flow convention documented in `docs/theory/layers.md`.
- `src/modules/cart/services/items.ts` — Service-layer operations for reading a cart and mutating its lines (add, set, remove, clear, shipping-method selection). Every write path funnels through a single `upsertCartItem` helper that enforces the catalogue gate, per-line quantity ceiling, and line-count limit, then prices the result via a join. The file also splits the "view the cart" read into a badge-polling variant and a `cart_viewed` analytics variant so analytics intent is encoded at the call site, not inferred from the route.
- `src/modules/cart/services/merge.ts` — Server-side implementation of `POST /cart/merge`: folds a guest (signed-out) cart into the signed-in cart in a single call. It exists here rather than as a browser-side loop of `POST /cart/items` because (1) refused lines must produce a durable notification event, and (2) per-line caps and stock availability must be evaluated against the cart's own state in one place.
- `src/modules/cart/services/preorder.ts` — Classifies cart-line products as preorder or backorder *before* the cart asks the inventory/ledger service for availability. Because `inventory` has no concept of a release date, the cart uses the catalogue's product facts (`isPreorder`, `isBackorder`) to decide which product IDs to route through the allowance path versus the shelf path, and to hand the availability rule the correct product shape.
- `src/modules/cart/services/reorder.ts` — Reorders a past order by copying its line items into the caller's current cart. It lives in the cart module (not orders) because it **writes** to the cart and only **reads** the order — keeping the dependency direction `cart → orders` and avoiding a circular `orders → cart` import.
- `src/modules/cart/services/shelf.ts` — Provides the "shelf" abstraction: a single read of a product's catalogue document **and** its inventory ledger units, combined into one record. All cart availability decisions (merge, wishlist, preorder checks) funnel through this file so the catalogue and ledger are fetched in exactly two queries regardless of product count.
- `src/modules/cart/services/view.ts` — Cart projection layer: transforms a stored `CartDocument` (keyed by `userId`) into the `CartView` that the API contract declares. Shared internally by the other cart service files (`items`, `checkout`, `preorder`); none of them own this module. Treats absence of a cart document as an empty cart, never a 404.
- `src/modules/cart/tests/contract/api.contract.test.ts` — Contract tests that verify every `/cart` endpoint returns the correct `CartResponseEnvelope` shape, status codes, and error structure. Because `CartResponse` is a computed view (not a document serialization), tests exercise the real API rather than hand-written fixtures, ensuring each contract branch—stock flags, ceiling enforcement, merge results, role-gating—is actually reached through the HTTP boundary.
- `src/modules/cart/tests/integration/analytics-consent.test.ts` — Integration test that verifies which analytics consent value a `cart_item_added` event carries after traversing the real HTTP stack (auth middleware → route → service). It asserts the consent-priority rule defined in `docs/theory/data-protection.md`: a stored account answer always outranks the `Analytics-Consent` banner header; only an account that was never asked falls back to the header (or defaults to `false`).
- `src/modules/cart/tests/integration/backorder.test.ts` — Integration tests for the backorder feature as seen through the cart: verifying the four availability states a line can report, and confirming that `orderConfirm` correctly splits a line into shelf-fulfilled and backordered portions, freezes the owed quantity and promise date, serialises the promise as a shop-day string on the wire, and refuses the order (409) when shelf + cap cannot cover the requested quantity.
- `src/modules/cart/tests/integration/checkout-expected-total.test.ts` — Integration test for `POST /cart/checkout` that verifies the `expectedTotal` guard: checkout must match the total the buyer was shown, refuse (409) if any component moved, leave zero side effects on refusal, and reject malformed input with 422. It exists to lock down the atomicity invariant and the error-contract surface of the endpoint.
- `src/modules/cart/tests/integration/checkout-interleavings.test.ts` — Integration test that verifies checkout's optimistic-concurrency guard against a **deterministic** cart-write interleaving. Unlike `cart-races.test.ts` (nondeterministic scheduler overlap) or `stock.test.ts` (stubbed `null`), this file injects a real cart mutation at a fixed point inside the checkout — after the version is captured, before the clear — and asserts that the losing checkout leaves zero side effects and that a retry succeeds. It also confirms that a mid-checkout reprice cannot produce a mix of old and new prices across lines, shipping, and the payment intent.
- `src/modules/cart/tests/integration/checkout-rate-limit.test.ts` — Integration test for the per-account checkout rate limiter (`POST /cart/checkout`). It exercises the limiter against a trivial Express handler rather than the real checkout route, because the property under test (budget enforcement per account) belongs to the limiter itself and routing through the real handler would only add a database round trip per attempt. Route-mounting is covered separately in `routes.test.ts`.
- `src/modules/cart/tests/integration/checkout-stock-divergence.test.ts` — Integration test that pins the invariant "the `stocklevels` ledger is the source of truth" whenever the catalogue's cached counters disagree with it. It covers two scenarios: (1) the cache over-reports availability (or under-reports reservations) and checkout must still honour the ledger, and (2) the post-checkout cache sync rejects and the checkout must not fail as a result. Together with `cart/tests/integration/stock.test.ts` (which pins the "cache sits low" half), this suite ensures a stale cache can neither oversell nor falsely refuse.
- `src/modules/cart/tests/integration/checkout-terms-version.test.ts` — Integration test verifying that a checkout stamps the order with the Terms version in force at the moment of placement, and that bumping `NODE_TERMS_VERSION` between two checkouts leaves each order on its respective version — analogous to how currency is frozen at order time.
- `src/modules/cart/tests/integration/checkout-version.test.ts` — Integration tests that verify the `__v` (MongoDB version) counter on a cart document is bumped by every state-changing write, and that `cartRepository.clearLinesIfUnchanged` correctly acts as a compare-and-swap guard so a concurrent cart mutation invalidates an in-flight checkout rather than silently dropping the mutation. The tests run against a real MongoDB instance because the guarantee under test is the driver's `$inc` atomicity, which a mock cannot exercise.
- `src/modules/cart/tests/integration/idempotent-add.test.ts` — Integration test verifying the idempotency contract for `POST /cart/items` and `POST /cart/reorder`: a retried request under the same `Idempotency-Key` must replay the original response (cart line grows once), while a new key must add the line again ("two clicks make two").
- `src/modules/cart/tests/integration/line-availability.test.ts` — Integration tests that pin down how the cart presents product lines when a product's state changes after the line was added. The core contract verified: a hidden product (`active: false`) keeps its line but reads `removed`; an off-sale product (`purchasable: false`) keeps its line but reads `unavailable`. Neither state causes the line to be deleted, and each state triggers a distinct checkout-refusal reason.
- `src/modules/cart/tests/integration/line-cap.test.ts` — Integration tests for the cart line cap (`NODE_CART_MAX_LINES`). Verifies that `GET /cart` is never paginated and that the cap is enforced at write time: a new product is refused once the cart is full, an existing line can still grow, and merge/reorder report `cart_full` per line rather than failing wholesale. Because the cap lives in the write's own filter, these tests also assert it holds under concurrent adds.
- `src/modules/cart/tests/integration/merge-effects.test.ts` — Integration tests that verify the **observable side effects** of cart merge and product-removal operations: the analytics events emitted per line outcome, the refusal shape when a quantity-cap race occurs, and the `CART_LINES_REMOVED` domain event. These effects are not exercised by the merge answer's own unit tests.
- `src/modules/cart/tests/integration/merge-rate-limit.test.ts` — Integration test that verifies the per-account rate-limiting behaviour of the merge limiter exposed by the cart module. It mounts `mergeLimiter` on a minimal Express route and asserts two properties: an account receives 429 after exhausting its budget, and one account's exhaustion does not starve a neighbouring account. The limiter is tested in isolation from the real route (see `../unit/routes.test.ts` for mount assertions).
- `src/modules/cart/tests/integration/merge.test.ts` — Integration test suite for the guest-cart-into-signed-in-cart merge operation. It verifies the per-line contract (quantities sum, ceiling caps, stock flags without mutation, one bad line never strands the rest) and the `CART_MERGE_REFUSED` event announcement, using a real database and live cross-module services.
- `src/modules/cart/tests/integration/preorder.test.ts` — Integration tests that verify the cart's preorder path end-to-end: how a preorder line's availability is computed (against the backorder allowance, not shelf stock), how checkout claims the allowance while leaving the shelf untouched, how the preorder promise is frozen onto the order line, and how a basket can mix preorder and in-stock goods in a single order.
- `src/modules/cart/tests/integration/product-removal-protects-orders.test.ts` — Integration test verifying that a product removed (hard or soft) or deactivated *after* an order is placed does not invalidate that order. Confirms the order stays `pending`, card/offline payments still succeed, no spurious emails fire, and inventory level rows are cleaned up (hard delete only) or preserved (soft delete / deactivation). Also guards that a failed write never emits the `PRODUCT_DELETED` event.
- `src/modules/cart/tests/integration/product-restored-meanwhile.test.ts` — Integration test for a specific event-ordering race: a `product.deleted` delivery that is retried by the relay *after* the product has already been restored. Because a restore writes no compensating event, the retried deletion is the only remaining "deleted" signal; this test proves that cart lines and wishlist entries for the now-restored product survive, while a normal (non-late) deletion still clears the cart.
- `src/modules/cart/tests/integration/schema-contract.test.ts` — Integration test for the **schema-level declarations** on the cart Mongoose model — `required` constraints, default values, and `select: false` fields — as opposed to the transform logic covered by sibling specs. It runs against a real MongoDB instance because these are Mongoose-native behaviours (index enforcement, field exclusion) that a mock would only assert its own opinion about.
- `src/modules/cart/tests/integration/service.test.ts` — Integration test suite for the cart service (`cartService`) that verifies the highest-risk seam in the cart domain: the `set` vs `add` distinction (backed by `$set` vs `$inc` in a shared private `upsertCartItem`). It also pins the over-serialization guard on `getForBadge`, the per-user single-document cart shape (no per-line `_id`), and the checkout/hold interaction rules. Runs against a real MongoDB instance rather than mocks, because the guarded write logic lives in the repository layer.
- `src/modules/cart/tests/integration/stock-flag.test.ts` — Integration tests for the cart line `availability` flag. They verify that the flag (`in_stock`, `insufficient_stock`, `out_of_stock`, `removed`) is derived from the stock ledger (not the catalogue cache), that reserved units from open orders reduce what "fits," and that the flag is always a name string—never a numeric stock count—across both `GET /cart` and `POST /cart/merge` responses.
- `src/modules/cart/tests/integration/stock.test.ts` — Integration suite that verifies the reservation invariant across the full checkout→payment→cancel/expiry lifecycle: units are *held* (not deducted from `onHand`) between checkout and payment, are recoverable on cancel or TTL expiry, and only leave the shelf once PAID. Runs against a real MongoDB instance so that conditional-write guarantees (the atomic reserve that prevents two checkouts from sharing the last unit) are actually exercised rather than mocked.
- `src/modules/cart/tests/integration/totals.test.ts` — Integration test that verifies the cart's `totalPrice` matches the amount carried by the resulting order and payment intent. It guards against a class of bugs where summing decimal amounts separately (vs. summing integer minor units and converting once) introduces floating-point epsilon drift — e.g. `0.56 + 5.00` in float arithmetic.
- `src/modules/cart/tests/integration/upsert-retry.test.ts` — Deterministic integration tests for `upsertLine`'s bounded retry loop. While the sibling `cart-races.test.ts` exercises real concurrency, this file *forces* the failure modes a race would produce (duplicate-key rejection, or the atomic filter persistently missing) to verify the retry budget, its termination behavior, and that no partial writes leak on exhaustion.

Because the function only reads an environment variable (no I/O, no HTTP), a unit suite is sufficient here; the 409 response it ultimately causes is covered in the integration suite instead.
