# src/modules/account/

## Purpose

The `account` module is the bounded context responsible for every aspect of a user's identity and authentication lifecycle: signup, login (password and OAuth), token minting and refresh, two-factor authentication, password reset, email verification and change, personal-data export, and scheduled account deletion. It owns the domain rules, persistence schemas, API surface, and security policies for these flows, and exposes a single public barrel so sibling modules interact with it through one well-defined seam.

## Key parts

- **Domain layer (`domain/`)** — Pure, I/O-free rule tables: the email-change state machine (`email-change.ts`), the session-epoch invalidation check (`epoch.ts`), the AMR / session-proof rules (`session-proof.ts`), and the revocation lookup table (`revocation.ts`). Re-exported through `domain/index.ts`; lint-guaranteed to have no Express or Mongoose imports.
- **Module wiring** — `module.ts` (runtime manifest: routes, jobs, event subscriptions, auth resolver, GDPR contracts) and `module.yaml` (static manifest: dependencies, rate-limit budgets, job list, group membership). `index.ts` is the sole public barrel other modules may import.
- **Persistence** — `model.ts` defines the four Mongoose schemas (sessions, verification tokens, account exports, erasure ledgers); `repository.ts` provides the low-level lean reads and atomic writes.
- **HTTP surface** — `routes.ts` mounts every endpoint under `/account/`; `presenter.ts` maps internal rows to wire shapes; `controllers/` and `services/` hold the request-handling and orchestration logic respectively.
- **OAuth sub-module (`oauth/`)** — Provider adapters (Google, GitHub) behind a shared `OAuthProvider` port, with per-attempt cookie state (`state.ts`), MFA and deletion-redirect cookie carriers, and centralized config/URL building (`config.ts`, `providers/client.ts`).
- **Security & policy** — `rate-limits.ts` (Express middleware for credential-guessing, Sybil, MFA surfaces), `cooldown.ts` (resend back-off for 2FA and verification), `mail-budget.ts` (per-recipient daily cap), `rules.yaml` + `rules.schema.ts` (2FA numeric policy shared with the PHP twin via codegen).
- **Observability & events** — `analytics.ts`, `audit.ts`, `metrics.ts` register this module's vocabulary into shared type maps and the Prometheus registry; `events.ts` augments the kernel's `DomainEventMap`.
- **Operational** — `jobs.ts` declares the four scheduled jobs (reaping, lapsed-email cleanup, export sweep, deletion purge); `emails.ts` builds fully-localised email content for the adapter worker; `openapi.yaml` / `asyncapi.internal.yaml` / `probes.ts` supply the API contract and test-probe data for the bundling pipeline.

## How it connects

- **`src/infrastructure/`** — The module registers its audit-action strings into infrastructure's `AuditActionMap` and its analytics names into the shared `AnalyticsEventMap`. Its `globals.d.ts` augments the infrastructure-layer Express `Request` type with an account-specific field. `metrics.ts` pushes counters onto the infrastructure-provided `metricsRegistry`.
- **`src/infrastructure/adapters/`** — `emails.ts` produces `EmailContent` objects that are consumed later by `adapters/email.worker.ts`, which performs the actual transport without a request context.
- **`src/modules/users/`** — `roles.ts` reads the live membership store to resolve the caller's effective role for audit records and login emit logic, since the account document itself carries no role field.
- **`src/modules/account/controllers/` and `src/modules/account/services/`** — Internal tiers within this module; `routes.ts` delegates to controllers, which in turn call services and the domain layer.
- **`shared/`** — Type-level registration sites (`AnalyticsEventMap`, `DomainEventMap`) live here; the account module merges its names into them via declaration merging.
- **`scenarios/`** — Integration-level test scenarios exercise the account module's public API surface (login, 2FA, deletion) end-to-end.
- **Sibling modules (`orders/`, `payments/`, `notifications/`, etc.)** — Interact with the account module exclusively through `index.ts`, the single permitted import entry point, per the strategic-DDD rule.

## Where to start

Read `domain/index.ts` (and the four files it re-exports) first: together they are under 200 lines of pure logic and reveal the core invariants—epoch invalidation, AMR proofs, revocation causes, and the email-change state machine—that every other file in the module enforces. Then open `module.ts` to see how those rules are wired into routes, jobs, events, and the auth resolver in a single declarative object.

## Files
- `src/modules/account/analytics.ts` — Declares the canonical set of analytics event names owned by the account module and registers them into the shared `AnalyticsEventMap` type. Every account-related event fired anywhere in the backend must use a name from this catalogue, giving the analytics port a single, type-checked vocabulary for the account domain.
- `src/modules/account/asyncapi.internal.yaml` — AsyncAPI fragment that declares the account module's private worker queue for personal-data export jobs. It exists separately from the module's public contract so the paired frontend never sees the `backend`-only channel, and so the fragment can be merged into `asyncapi.yaml` without carrying its own `asyncapi`/`info`/`servers` envelope.
- `src/modules/account/audit.ts` — Declares the full set of audit action strings the account/auth domain emits and registers them into infrastructure's `AuditActionMap` via type-only declaration merging. This lets log tooling, alert rules, and downstream code reference the vocabulary by name while keeping the strings owned by the domain module rather than the infrastructure layer.
- `src/modules/account/config.ts` — Central configuration surface for the `account` module: declares every tunable (frontend link templates, token TTLs, export/grace periods, legal-identity fields) in one `defineConfig` block, and exposes small pure helpers that resolve a link or a duration from the resolved config so callers never touch `process.env` directly.
- `src/modules/account/consent-record.ts` — Defines the consent "stamp" shapes an account carries for terms acceptance and analytics choice. Each exported function produces the exact object (timestamp + version/value) that a signup, provider sign-in, or first-password flow writes onto the account record, so the controller can later answer "who agreed to what, and when."
- `src/modules/account/cooldown.ts` — Shared helper that computes the remaining cooldown before a "resend" action is allowed and produces the 429 response the client turns into a countdown. It exists so the two flows that publish mail on a button press — the 2FA delivered code and the verification link — share one source of truth for both the arithmetic and the error shape.
- `src/modules/account/domain/email-change.ts` — Defines the email-change state machine as a pure transition table with no I/O. It encodes every legal (state, event) → next-state edge in one place so callers can derive the account's email-change status from two optional User fields and determine where an event leads, without touching the database or network.
- `src/modules/account/domain/epoch.ts` — Single source of truth for the "session epoch" rule: a token or login proof is invalid if it predates the account's `tokensValidAfter` timestamp. Kept as pure functions so that the resolver, refresh path, and mint path all apply the same check and cannot drift apart.
- `src/modules/account/domain/index.ts` — Barrel (re-export) file for the **account domain layer**. It publishes the pure-rule exports from `email-change.ts`, `session-proof.ts`, and `revocation.ts` so that upper tiers (services, tests) can import domain logic through a single entry point without reaching into individual files. The domain layer is lint-guaranteed to contain no Express, Mongoose, or other tier dependencies.
- `src/modules/account/domain/revocation.ts` — A pure, I/O-free lookup table that enumerates every way an account's sessions can end. Each row describes what a cause does to the session epoch, pending one-time links, event announcements, caller re-minting, and applicable session modes. Downstream services read this table to decide *what* to do; the event reason type for `account.sessions_revoked` is derived directly from it so the list is never restated.
- `src/modules/account/domain/session-proof.ts` — Pure, side-effect-free rules for the `amr` (Authentication Methods Reference) field on a session token. It defines which proof values this app mints, how to merge proofs across re-mints, and when a **first** session must be refused because a second factor is armed but unproved. Every mint path (login, signup, password change, 2FA flows) imports from here so the logic lives in one place.
- `src/modules/account/emails.ts` — Every account-module email's finished content (template name, subject, localized body fields) is built here. Because emails render later in `adapters/email.worker.ts` with no request or locale store available, each builder binds its own translator to the recipient's locale up front and returns a complete `EmailContent` object. Templates only interpolate; they never translate.
- `src/modules/account/events.ts` — Declares the account module's domain events by augmenting the kernel's `DomainEventMap` interface, so the app-wide event catalogue grows per-module without a shared enumeration file. Also provides the string-constant names used at emit/subscribe sites.
- `src/modules/account/globals.d.ts` — Augments the Express `Request` interface with an account-specific field (`credentialAttemptFailed`) via TypeScript declaration merging. It exists as a separate file because the infrastructure layer's `globals.d.ts` must remain module-agnostic (per `docs/theory/layers.md`), so any `Request` property that only the account module sets and reads is declared here.
- `src/modules/account/index.ts` — Public barrel for the `account` module. Per the strategic DDD rule (see `docs/theory/strategic-ddd.md` §5), this file is the **only** entry point a sibling module is permitted to import from. It re-exports the module's public surface while deliberately withholding internal sub-surfaces.
- `src/modules/account/jobs.ts` — Declares the four scheduled jobs the `account` module owns — inactive-account reaping, lapsed-previous-email cleanup, expired-export sweep, and scheduled-deletion purge — as a single exported `JobDeclaration[]` that the registry picks up at startup.
- `src/modules/account/mail-budget.ts` — Per-recipient mail budget that caps how many mails the app will deliver to a single mailbox within a 24-hour window (default 10), regardless of which flow (signup, reset, email-change, export) triggered the send. It protects the *victim's* inbox from being turned into a weapon by a caller who can point arbitrary flows at stranger addresses.
- `src/modules/account/metrics.ts` — Declares the full set of Prometheus counters for the account/auth domain (login, sign-up, password flows, 2FA, email verification, account lifecycle, OAuth, data export). Each counter registers itself on the shared `metricsRegistry` so a single `/metrics` scrape includes them alongside HTTP-level metrics. Nothing in the codebase reads these counters programmatically; dashboards and alerts resolve them by metric name off the registry.
- `src/modules/account/model.ts` — Defines the four Mongoose schemas and compiled models that make up the account module's persistence layer: `accountexports`, `sessions`, `verificationtokens`, and `erasureledgers`. This file owns the shape of each collection, its indexes, and its serialization rules. All queries live in `./repository`; this file is the contract for what a row looks like.
- `src/modules/account/module.ts` — Module manifest for the **account** module. It installs the application-wide auth resolver, declares the module's routes, jobs, rate-limit budgets, queue consumers, event subscriptions, and GDPR export/erasure contracts. It exists so the kernel's `registerModules` pass can wire the account lifecycle (signup, login, refresh, password reset, two-step deletion) into the app in a single declarative object.
- `src/modules/account/module.yaml` — Module manifest for the **account** subdomain (group `foundation`). It declares the module's dependencies, its full set of rate-limit budgets, and its scheduled jobs. Everything an operator or the runtime needs to understand what the account module *is*, what it *depends on*, and what it *enforces* lives here.
- `src/modules/account/oauth/config.ts` — Centralizes all OAuth-related environment-variable access, timeout policy, and URL-building logic so that providers and controllers never reference a `NODE_OAUTH_*` variable name or construct a redirect/callback URL themselves. It reads configuration and derives URLs; it does not hold sessions or mint tokens.
- `src/modules/account/oauth/deletion-redirect.ts` — Carries the deletion-restore claim check (minted by `buildDeletionPending`) in a cookie across the OAuth provider's redirect, rather than in the URL. This mirrors the pattern used by `./mfa-redirect.ts` for the 2FA challenge. The `POST /account/login/restore` endpoint reads this cookie when its request body omits `challenge`.
- `src/modules/account/oauth/mfa-redirect.ts` — Manages the single cookie (`oauthMfaChallenge`) that carries an MFA login challenge token across an OAuth provider's redirect round-trip. It exists so the challenge never appears in the URL (where it would leak via browser history and `Referer` headers), and so the two 2FA endpoints can serve both password-originated and OAuth-originated logins from the same code path.
- `src/modules/account/oauth/providers/client.ts` — Shared OAuth client plumbing used by every provider adapter on top of `openid-client`. It supplies the single `fetch` implementation every provider call goes through (deadline, body cap, no-redirect policy) and the helper that turns a provider's static server metadata into a ready-to-use `client.Configuration`. Because endpoints are hard-coded in each provider file rather than discovered over the network, login flow has no extra request that can fail or be spoofed.
- `src/modules/account/oauth/providers/github.ts` — Implements the GitHub OAuth2 provider behind the shared `OAuthProvider` port. GitHub is plain OAuth 2.0 (no OIDC, no ID token), so after the code exchange the identity is assembled from two REST calls (`/user` + `/user/emails`) because a primary email marked private never appears on `/user`.
- `src/modules/account/oauth/providers/google.ts` — Concrete `OAuthProvider` implementation for Google's OAuth 2.0 / OIDC flow, built on `openid-client`. It hard-codes Google's endpoints (no runtime discovery), enforces the `iss` callback parameter via RFC 9207, and extracts the user's identity directly from the verified ID token's claims—eliminating a separate `userinfo` round trip.
- `src/modules/account/oauth/providers/index.ts` — OAuth provider registry that supports **multiple simultaneously enabled** providers (unlike the single-winner pattern in `payments/providers/index.ts`). It exposes "which providers are configured right now" via closures re-evaluated on every call, so a provider becomes active the moment its env vars appear—no stale import-time memoisation.
- `src/modules/account/oauth/providers/port.ts` — Defines the `OAuthProvider` port — the structural contract that every identity provider (Google, GitHub, …) implements. Unlike the payments module's single-provider switch, multiple OAuth providers can be enabled simultaneously, so selection is delegated to the registry in `./index`. This file contains no runtime logic; it is purely the seam's type surface.
- `src/modules/account/oauth/state.ts` — Defines the per-attempt cookie set and helper functions that carry an OAuth login from the start controller through the provider round-trip and back to the callback. It mints CSRF `state` and PKCE `verifier` tokens, provides idempotent cookie set/destroy pairs, and supplies the validation predicates (`isSameOriginPath`, `isLocaleTag`, `stateMatches`) that the callback must apply before trusting any client-writable cookie value.
- `src/modules/account/openapi.yaml` — OpenAPI 3.1.0 module contract for the **account** domain. It declares the module's tags, custom error codes, its slice of the personal-data export payload, and the full request/response schemas for authentication and self-service profile endpoints. It exists as the single source of truth for the account API surface so that clients, bundlers, and code generators can consume it without parsing handler code.
- `src/modules/account/presenter.ts` — Pure mapping layer that converts internal row types (sessions, exports, OAuth links) into the wire shapes returned by the account API. It performs no business logic—rules like expiry caps and ownership decisions are made upstream in `session/` and `services/`—and only reshapes already-resolved values into the JSON the controllers send.
- `src/modules/account/probes.ts` — Declares four API requests that the OpenAPI contract for the account module cannot express on its own (error-triggering states, cross-identity logins, rate-limit exhaustion). The array is consumed by the client-collections bundling pipeline to emit runnable Postman/Insomnia-style probe steps alongside the contract-generated collection.
- `src/modules/account/rate-limits.ts` — Defines the account module's rate-limit budgets as `RateLimitBudget` data objects and converts them into Express middleware via `buildRateLimiter`. It covers four distinct abuse surfaces: credential guessing (public and signed-in), password-strength lookups, Sybil signups/resets, and MFA challenges. Numeric thresholds live in `rate-limits.generated`; this file only wires keying, skip logic, and escalation policy.
- `src/modules/account/repository.ts` — Low-level query functions for three Mongoose collections (`accountexports`, `sessions`, `verificationtokens`). It exposes plain lean reads and atomic writes only—no pagination, no compound search—so it bypasses the shared repository factory entirely. Services in the account module call into this file instead of touching Mongoose models directly.
- `src/modules/account/roles.ts` — Provides a single helper that determines whether a given user holds an unrestricted (admin) role on the deployment tenant. It exists so that login emit logic and audit records can record the caller's effective role (`actorRole`) by reading the live membership store, since the account document itself carries no role field.
- `src/modules/account/routes.ts` — Express router that mounts every endpoint in the account module under the `/account` prefix. It wires up authentication (login, signup, token refresh, logout), password reset, email verification, email change, 2FA, re-authentication/step-up, session management, OAuth linking, account export, and account deletion. It also applies the cross-cutting middlewares (auth context, no-cache, origin checks) that every route in the module needs.
- `src/modules/account/rules.schema.ts` — Declares the Zod schema for the `account` module's section of `rules.yaml` and specifies what `npm run regenerate` should emit as `rules.generated.ts`. It covers the two-factor lockout thresholds and the delivered-code limits (digits, TTL, resend cadence, attempt ceiling).
- `src/modules/account/rules.yaml` — Single source of truth for the numeric policy constants that govern two-factor authentication (lockout thresholds, delivered-code parameters). It exists so that the TypeScript runtime (via a generated file) and the PHP twin both copy the same plain-data values, keeping the security policy consistent across languages without hand-maintaining duplicated numbers.
- `src/modules/account/session-mode.ts` — A single-leaf module that defines the two session modes a deployment can use (`jwt` and `cookie`). It exists as a shared constant so that the schema, the runtime configuration, and the session strategies can all reference the mode names **without importing each other**, avoiding circular dependencies across the account/session feature.
- `src/modules/account/session/account-view.ts` — Shapes the response body for session-related endpoints: it packages the caller's CASL abilities (in both tenant and platform scopes), the idle-clock snapshot, and—on sign-in—the account record itself—into a single payload so the client never needs a follow-up read. The shipped abilities are strictly a rendering hint; every request is still re-evaluated server-side.
- `src/modules/account/session/activity.ts` — Provides a single, fire-and-forget helper that stamps an account's `lastActiveAt` timestamp whenever a session is minted or refreshed. It exists so both session strategies can share one uniform "keep-alive" signal that the inactivity reaper reads, without either strategy owning that concern.
- `src/modules/account/session/auth-context.ts` — Resolves a session proof (`authTime` + `amr`) into the `AuthContext` object that authorization guards read. It is the strategy-agnostic half of request authentication: the cookie and JWT strategies each decide *how* a credential becomes a proof, and this file decides *what* that proof means — whether the account may still act, whether the epoch has invalidated it, and which roles apply right now.
- `src/modules/account/session/config.ts` — Declares and validates the full set of session-related environment variables (mode selector, per-tier TTLs, signing key rings, TOTP encryption ring, device-cookie HMAC secret, issuer/audience, rotation windows) in a single `defineConfig` block, then exposes a battery of typed getter functions that the JWT and cookie strategies read at runtime. It holds no token and issues none; it is the single source of truth for *how long* and *with what key* a session lives.
- `src/modules/account/session/cookie-strategy.ts` — Implements the **cookie** session strategy: a single random session ID (stored only as its SHA-256 hash in a `sessions` row) that travels to browsers in an HttpOnly `__Host-session` cookie and to other clients as a `ses_…` Bearer token. No signing key, no refresh token, no rotation race — logging out is a row delete and the row is read on every request anyway. This file provides the full lifecycle: issue, resolve, replace (OWASP id renewal), and retire sessions.
- `src/modules/account/session/cookies.ts` — Centralized HTTP cookie service for the account session layer. It owns the two cookies the browser holds on the user's behalf — `__Host-session` (the actual credential: a refresh token in JWT mode or a `ses_…` id in cookie mode) and `isAuth` (a non-secret, script-readable hint so the client shell can render auth chrome before its first API call returns) — and exposes create/destroy pairs so callers never hand-roll cookie flags.
- `src/modules/account/session/device-cookie.ts` — Implements the OWASP "familiar device" cookie: after a fully successful login, a token is written to a host-only, httpOnly cookie so that the same browser can keep signing in to that account even after an attacker has exhausted the account's per-login failure budget. Without this, spending an account's lockout budget also locks out its legitimate owner. The cookie skips only the per-account budget; per-address and per-block rate limits still apply.
- `src/modules/account/session/device-label.ts` — Parses the `User-Agent` header at sign-in into a short, human-readable device label (e.g. `"Firefox on Linux"`) that is stored on the session so an account owner can distinguish their own devices in a sign-in list. Deliberately omits version numbers, model names, and IP addresses to avoid creating an identifier beyond what the owner already knows (see `docs/theory/data-protection.md`).
- `src/modules/account/session/family-liveness.ts` — Determines whether a session **family** is still valid: it must have a live row in the repository, and (for staff roles) it must not have idled out or exceeded the staff lifetime cap. This logic is shared by the JWT bearer path (which names its family via the `sid` claim) and by SSE stream rechecks (which follow the family across credential rotation). If the family is dead, the session is revoked on the spot.
- `src/modules/account/session/idle.ts` — Backend enforcement of the staff-only session idle timeout and lifetime cap. A session whose holder (tenant or platform role) has not made a real request within the configured window is considered idled out; a session that outlives its absolute lifetime is expired. Shopper sessions are never subject to either check. Enforced server-side because a client timer is treated as advisory only.
- `src/modules/account/session/jwt-strategy.ts` — Adapter that implements the `SessionStrategy` port for the **jwt** session mode. It wraps the raw token operations in `./jwt.ts` (signing, rotation, reuse detection) behind the `SessionStrategy` interface so upstream code never sees tokens directly. It covers the full lifecycle: minting a session, resolving access/refresh credentials, retiring replaced sessions and families, and wiring SSE stream liveness checks.
- `src/modules/account/session/jwt.ts` — Core JWT signing and verification for the account session module, built on `jose`. Owns the wire format of access and refresh tokens, enforces token-kind separation via `typ`/`aud`, resolves signing keys from a rotation ring, and checks refresh-token revocation against the session repository. All secrets, TTLs, and audience/issuer values are sourced from `./config`; this file contains no policy of its own.
- `src/modules/account/session/key-ring.ts` — Pure utility module that maps secrets to stable identifiers (`kid`) and resolves a `kid` back to its ring member. It exists so `./jwt` can locate the correct signing key from a token's header without importing any crypto signing logic, keeping the "ring math" independently testable.
- `src/modules/account/session/listing.ts` — Lists an account's live sessions for one session mode, returning them as the wire `Session` array. It deduplicates JWT refresh families, filters out rows that are effectively dead (pre-epoch, idled, past staff cap), and marks the caller's own session as `current`.
- `src/modules/account/session/login-observability.ts` — The metrics, audit, and analytics "tail" that fires after a completed login. Extracted from `post-login.ts` so that `post-login-2fa.ts` (the second step of a 2FA login) reuses it instead of duplicating what "a login happened" means. It lives at the controller layer — not in `services/login.ts` — because the success signal must only fire once a session actually exists (cookies, access token), a fact the credential-check functions don't know.
- `src/modules/account/session/mint-guard.ts` — Enforces the two invariants a **first** (not re-minted) session must satisfy at the moment it is issued: the proof must carry a second factor when one is armed, and the proof must not predate the account's current epoch. Both session modes call these guards inside `issue`; they are the last line of defense against a login path that skipped the challenge or raced an epoch transition.
- `src/modules/account/session/resolver.ts` — Provides the account module's concrete `AuthResolver` so the kernel can turn a presented credential (Bearer token or session cookie) into an `AuthContext` for its auth guard. It is a thin delegation layer: every method forwards to whichever session strategy the deployment has activated, keeping the kernel decoupled from account-specific auth logic.
- `src/modules/account/session/session-id.ts` — Generates and shape-checks opaque session IDs used in `cookie` authentication mode. A session ID is a 256-bit random token (`ses_` + base64url of 32 random bytes) whose **sha256 hash** (via `@infrastructure/security/hash-token`) is what gets persisted, so no plaintext ever leaves the one call-site that creates it. Because the entropy is sufficient, no HMAC or signing secret is required.

- `src/modules/account/tests/unit/emails.test.ts` — Unit tests for the fourteen account email builder functions exported by `@modules/account/emails`. Because these builders "fail like code" (a wrong `template`, `linkUrl`, or token silently produces a wrong or broken email), the tests assert the fully-built payload: correct template ID, correct link kind and token, resolved i18n copy (not raw keys), and correct locale passthrough.
- `src/modules/account/tests/unit/epoch.test.ts` — Unit tests for the two epoch-comparison predicates in the account domain: `predatesSessionEpoch` (shared by the resolver and the refresh path) and `proofPredatesEpoch` (used for a login's proof at the mint). The tests pin down boundary behavior at the exact epoch instant and the no-op case where no epoch has ever been set.
- `src/modules/account/tests/unit/family-liveness.test.ts` — Unit tests for `resolveInLiveFamily` (from `../../session/family-liveness.ts`), verifying the decision logic that determines whether a session family is revoked, idle-ended, expired, or allowed through, and whether a "stamp" (`touchFamily`) is written. The store is fully mocked; the tests exercise only the in-memory branching.
- `src/modules/account/tests/unit/get-refresh-token.test.ts` — Unit tests for the `getRefreshToken` controller covering the **outage branch**: when the underlying database refresh query fails (timeout or server-selection error), the response must be a retryable **503** (not a 401, which clients interpret as "signed out"), and the error must be logged through `rejectDatabaseError`.
- `src/modules/account/tests/unit/jwt-strategy.test.ts` — Unit-level tests for the `jwtStrategy` adapter (`session/jwt-strategy.ts`), verifying the wiring between the strategy port and the token layer: which mint path a login vs. re-mint takes, what lands in which cookie, and how a token refusal becomes a resolver miss while an infrastructure outage stays a thrown rejection. The token layer itself is replaced (mocked) here; its own behavior is covered by `session-jwt.test.ts`.
- `src/modules/account/tests/unit/key-ring.test.ts` — Unit tests for the pure key-ID functions in `key-ring.ts`. They pin down the invariants that JWT verification depends on: key IDs are deterministic, collision-free, and independent of ring position. This file deliberately tests only the ID math—signing is covered separately in `session-jwt.test.ts`.
- `src/modules/account/tests/unit/oauth-github.test.ts` — Unit-test suite for the GitHub OAuth provider: verifies the authorize-URL construction (client id, PKCE, scope, redirect) and the three-call `exchangeCode` flow (token → user → emails), plus the env-var configuration gate. `fetch` is mocked globally once per call, in provider order.
- `src/modules/account/tests/unit/oauth-google.test.ts` — Unit tests for the Google OAuth provider (`googleOAuthProvider`). They verify that the authorize URL is built correctly, that `exchangeCode` validates the callback query (state, issuer, duplicate params, errors) before making any network call, that the token-endpoint response is validated (issuer, audience, expiry, subject, `email_verified`), and that transport-level safeguards (redirect policy, byte cap, abort-on-timeout) are enforced. `fetch` is fully mocked; no real network or signature verification occurs.
- `src/modules/account/tests/unit/oauth-state.test.ts` — Unit tests for the pure comparison and token-generation helpers in `oauth/state.ts`. Covers the OAuth CSRF state mint/compare logic, the PKCE verifier/challenge pair, and the two input-validation guards (`isSameOriginPath`, `isLocaleTag`). Cookie and HTTP plumbing is deliberately left to the integration/contract suites; this file exercises only the decision logic.
- `src/modules/account/tests/unit/operator-identity.test.ts` — Unit tests for the account module's operator-identity service and its boot gate. Verifies that `assertModuleConfig` refuses to boot when any required `NODE_LEGAL_*` variable is missing, and that `operatorIdentity()` correctly reads required fields, omits unset optional fields, falls back to `NODE_SUPPORT_EMAIL`, and prefers `NODE_LEGAL_EMAIL` when both are set.
- `src/modules/account/tests/unit/presenter.test.ts` — Unit tests for the account presenter's three wire-mapping functions. They verify that stored domain objects (`SessionRow`, export request rows) are shaped correctly for the API response and—critically—that the credential (`tokenHash`) never appears in the serialized output.
- `src/modules/account/tests/unit/rate-limits.test.ts` — Unit tests that pin the **relationships** between the account module's rate-limit budgets (identity, address, block, MFA) rather than any individual value. They verify ordering invariants (identity ≤ address ≤ block), that per-identity budgets stay a small fraction of the global browsing cap, and that MFA windows align with the challenge TTL. The file exists so that any change to a single budget number is immediately checked against its neighbors.
- `src/modules/account/tests/unit/reauth-policy.test.ts` — Unit tests for the pure decision logic of `amrAfterReauth` — the function that determines which Authentication Method References (AMR) a re-minted session should claim. This file covers the rule-level "what claims are produced" concern; the HTTP/transport behaviour lives in a separate contract test (`contract/reauth.contract.test.ts`).
- `src/modules/account/tests/unit/revocation-table.test.ts` — Cross-cutting invariant tests for the `REVOCATION` table. Each test asserts a relationship *between* fields across causes (e.g., "every `callerKeeps` cause must also have `epoch: 'with-write'`") that a per-cause test would not catch. The file exists so that adding or editing a cause in the domain table is immediately checked against these structural guarantees.
- `src/modules/account/tests/unit/routes.test.ts` — Locks in the security-relevant invariants of the account Express router: exact endpoint order, per-route middleware placement (`noStore`, `isAuth`, rate-limit budgets, mail budget, human-challenge gate), and the deliberate public exposure of token-bearing credential routes. It exists because these arrangements are invisible to TypeScript and a silent reordering would be an account-takeover vector.
- `src/modules/account/tests/unit/schema-contract.test.ts` — Unit tests that pin the **declarative** (index, constraint, option) contracts of the account module's three Mongoose schemas — `accountExportSchema`, `sessionSchema`, and `verificationTokenSchema`. They exist because these database facts (unique indexes, TTL settings, partial filters) are invisible in a valid data fixture and would silently regress without an explicit assertion.
- `src/modules/account/tests/unit/session-id.test.ts` — Unit tests for the cookie-mode session ID primitives (`newSessionId`, `looksLikeSessionId`). Because the kernel dispatches on the token's shape and 256 bits of entropy underpin its security, the tests assert both structural invariants (prefix, length, alphabet) and behavioral ones (uniqueness, non-collision with JWTs/machine keys, at-rest hashing) rather than relying on implementation details.
- `src/modules/account/tests/unit/session-jwt.test.ts` — Unit test suite for the session JWT token layer (`src/modules/account/session/jwt.ts`). It asserts security invariants at the token level—secret separation (access vs. refresh), refresh-token validity tied to a stored row, `jti` uniqueness, key-ring rotation without mass logout, and claim-shape enforcement—while the session store and user service are stubbed out. Query-level correctness is deliberately left to `../integration/auth-storage.test.ts`.
- `src/modules/account/tests/unit/session-listing.test.ts` — Unit tests for the two exports of `@modules/account/session/listing` (`newestPerFamily` and `listSessions`). They verify the public shape of the session list: one entry per family regardless of rotation-race duplicates, correct `current` marking, absence (not invention) of optional fields, account-epoch (ban) filtering, and the staff idle-timeout rule. The store is fully replaced; what `listLive` returns is controlled per-case.
- `src/modules/account/tests/unit/session-proof.test.ts` — Unit tests for the session-proof domain logic in `../../domain/session-proof`. They verify two rules: proofs are combined without duplicates while preserving the input array, and first-session refusal only applies to armed accounts lacking an `otp` proof.
- `src/modules/account/tests/unit/session-strategy.test.ts` — Unit tests that verify the session-strategy seam: the `activeStrategy` factory picks the correct adapter per call based on `NODE_SESSION_MODE`, the resolver consults that live selection (not a frozen snapshot) when deciding whether a cookie can authenticate ordinary routes, and the mint guard enforces second-factor proof on armed accounts.
- `src/modules/account/tests/unit/tokens.test.ts` — Unit tests for the session/token configuration module (`session/config.ts`). Every value in that module controls a JWT lifetime, cookie `maxAge`, or signing secret — misreads cause silent security or availability bugs rather than request failures. The tests pin the documented contract: per-tier env-var routing, integer parsing with safe fallbacks, ring shape invariants, and the boot-gate validation logic.
- `src/modules/account/tests/unit/two-factor-outcomes.test.ts` — Unit tests for the `rejectLocked` helper in the two-factor outcomes service. Verifies that the 429 rejection carries the correct error code and that the `retryAfter` value is computed as the remaining lock time (rounded up to whole seconds), with sensible fallbacks, without touching a database.
- `src/modules/account/tests/unit/two-factor.test.ts` — Unit tests for the pure (no-database) layer of the `account/two-factor` module. Covers TOTP secret encryption/decryption, TOTP code verification with replay protection, backup-code generation and salted hashing, delivered-code lifecycle (arm → check → cooldown → expiry), and the Prometheus disable-counter metric. All time-dependent assertions use fixed clocks or injected timestamps so the suite is deterministic and never races wall time.
- `src/modules/account/token-types.ts` — Defines the closed, named set of one-time token types stored in the `verificationtokens` table. Exists as a leaf module so that the schema, the services that issue tokens, and the service that purges them can all reference the same string constants and TTLs without importing each other.
- `src/modules/account/two-factor/backup-codes.ts` — Pure utility module that mints, salts, and hashes one-time backup codes for account recovery. Backup codes recover the **account** itself (not a single factor), are generated once when a method is first armed, shown to the user exactly once, and then only their scrypt digests persist. The module intentionally has no project-internal imports — it depends solely on `node:crypto`.
- `src/modules/account/two-factor/delivered-code-verify.ts` — Single-point verification of a delivered (2FA / step-up) code against an account. It splits the work into a **pure comparison** (`checkDeliveredCode`) and **conditional writes** (spend on match, record a miss on failure) so that concurrent callers cannot double-spend a code. The same path is used for a second factor's code and for a step-up reauth code.
- `src/modules/account/two-factor/delivered-codes.ts` — Pure logic for the short numeric codes a "delivered" two-factor method (e.g. email) produces: generation, hashing for at-rest storage, TTL/attempt/cooldown checks, and the final match/miss verdict. It reads and writes only an in-memory `DeliveredCodeState` entry — never the database — so the time-bound rules are testable against an injected clock.
- `src/modules/account/two-factor/index.ts` — Barrel (re-export) file for the two-factor subsystem. It has no logic of its own — it simply re-exports the public API surface of the six sibling modules (`registry`, `backup-codes`, `delivered-codes`, `delivered-code-verify`, `lockout`, `totp`) so that consumers can `import` from a single path. Per its own JSDoc, it exposes the method registry that services drive and the pure crypto helpers used by unit suites and the admin recovery path.
- `src/modules/account/two-factor/lockout.ts` — Defines the per-account 2FA lockout policy: how many consecutive wrong codes are tolerated and how long the resulting lock persists. The actual thresholds are not hard-coded here; they are sourced from a generated rules file so that operators can tune them via `rules.yaml`.
- `src/modules/account/two-factor/methods/email.ts` — Implements the email two-factor method as a "delivered code" handler: both setup and login reduce to minting a one-time code, mailing it to the account's verified address, and recording its digest. Code lifecycle (TTL, resend cooldown, attempt ceiling) is delegated to the shared `delivered-codes` module so every future delivery channel inherits the same rules.
- `src/modules/account/two-factor/methods/totp.ts` — Registry adapter for the TOTP two-factor method. It exposes a `TwoFactorMethodHandler` object whose `setup` mints an encrypted TOTP secret and whose `verify` checks a six-digit code against it. All cryptographic work is delegated to the sibling `../totp.ts`; this file only wires the handler into the registry contract.
- `src/modules/account/two-factor/registry.ts` — Defines the set of second-factor methods this deployment supports and the handler contract each must satisfy. It exists so that adding a new 2FA channel means registering a handler here rather than branching inside the login or verification flow; all upper-layer services resolve a method by wire-name string against this registry.
- `src/modules/account/two-factor/totp.ts` — Pure crypto layer for TOTP: encrypts/decrypts the base32 secret at rest (versioned, bound to a specific method entry) and verifies a 6-digit code against that secret with constant-time comparison, clock-skew tolerance, and replay protection. Deliberately has no database or user-document access so it can be unit-tested against fixed clocks; the persistence adapter lives in `methods/totp.ts`.
