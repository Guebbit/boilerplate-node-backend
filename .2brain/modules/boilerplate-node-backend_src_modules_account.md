# src/modules/account/

## Purpose

The account module owns the full authentication and account-lifecycle surface of the application: signup, login, session management, email verification, password reset, two-factor authentication, OAuth sign-in, personal-data export, and account deletion with grace period. It enforces per-recipient mail budgets, per-flow rate limits, and the session-epoch / revocation model that invalidate tokens across the system.

## Key parts

- **Domain layer (`domain/`)** — Pure, I/O-free business rules: the email-change state machine, session-epoch invalidation, revocation-cause table, and AMR session-proof helpers. Upper tiers import through `domain/index.ts`; a lint rule forbids Express/Mongoose imports here.
- **Configuration & generated constants** — `config.ts` (link templates, token TTLs), `module.yaml` + `rate-limits.generated.ts` + `rules.generated.ts` (rate-limit budgets, 2FA lockout thresholds, job schedules). The YAML files are the editable source; the `.ts` files are regenerated via `npm run regenerate`.
- **OAuth sub-module (`oauth/`)** — Provider adapters (Google, GitHub) behind a shared `OAuthProvider` port, a live provider registry, CSRF/PKCE cookie management (`state.ts`), and redirect-carried challenge cookies for 2FA and deletion-grace flows.
- **Data & presentation** — `model.ts` (Mongoose schemas for sessions, verification tokens, account exports), `repository.ts` (single-row reads/writes), `presenter.ts` (row-to-wire mapping with no business logic).
- **Policy & security** — `rate-limits.ts` (Express middleware for credential-guess, Sybil, and MFA budgets), `cooldown.ts` (shared "wait before resending" 429 envelope), `mail-budget.ts` (per-recipient 24 h cap), `session-mode.ts` (jwt vs. cookie vocabulary).
- **Module wiring** — `module.ts` (single kernel entry point: routes, auth resolver, consumers, event subscriptions), `routes.ts` (Express router under `/account` composing per-route middleware), `jobs.ts` (scheduled reaping/cleanup), `index.ts` (public barrel; the only cross-module import surface).
- **Observability & events** — `analytics.ts`, `audit.ts`, `events.ts`, `metrics.ts` (typed event/action/counter declarations), `emails.ts` (template content for every outbound mail).
- **Contract & tests** — `openapi.yaml` (API specification), `probes.ts` (hand-written edge-case requests the contract cannot express).

## How it connects

- **`src/modules/account/controllers/` & `src/modules/account/services/`** — Controllers parse HTTP and delegate to services; services apply domain rules and call the repository. The `index.ts` barrel is the only surface sibling modules may import, so cross-module access funnels through services.
- **`src/modules/users/`** — Provides the live tenant membership store that `roles.ts` queries to resolve admin status for audit and login events; account documents reference user records but do not own role data.
- **`src/modules/addresses/`** — Supplies canonicalised / pseudonymised addresses used as keys by `mail-budget.ts` so `+tag` or dot tricks cannot create new budget buckets.
- **`src/modules/observability/`** — Reads the Prometheus counters registered by `metrics.ts` off the shared registry; the account module only writes.
- **`src/infrastructure/http/`** — The account module never imports it by name (see `config.ts` comment); link-URL construction is delegated to infrastructure so the layering rule in `docs/theory/layers.md` holds.
- **`src/modules/api-keys/`** — A sibling that imports the account barrel for session/identity checks, per the strategic-DDD rule.
- **`src/infrastructure/`** — Provides the mailer worker, queue consumers, and shared repository factory that the account module's jobs and email builders rely on at runtime.
- **`src/modules/orders/`, `src/modules/cart/`, `src/modules/payments/`** — Downstream consumers that require a valid session (minted here) and read consent/epoch state before executing commerce flows.
- **`src/modules/notifications/`** — Receives the `EmailContent` objects produced by `emails.ts` for delivery.

## Where to start

1. **`module.ts`** — The single entry point the kernel calls; reading it shows how routes, the auth resolver, consumers, event subscriptions, and rate-limit budgets are all installed in one place, giving you a map of the module's moving parts.
2. **`routes.ts`** — Lists every endpoint under `/account` with its middleware chain (rate limiter, challenge gate, idempotency, auth predicate), so you can trace a request from URL to controller to service without hunting through sub-directories.

## Files
- `src/modules/account/analytics.ts` — Declares the analytics event names emitted by the account module and registers them in the analytics port's type map. It is a pure declaration file — no runtime logic — that lets the account services reference a shared, type-safe catalogue of event strings while keeping ownership of each name in one place.
- `src/modules/account/audit.ts` — Declares the full vocabulary of audit action strings emitted by the account module and injects them into the shared `AuditActionMap` type via a declaration merge. It exists so that every account service can fire typed, self-documenting audit events without the infrastructure layer needing to know which module owns which string.
- `src/modules/account/config.ts` — Central configuration surface for the `account` module: frontend link templates (with their `NODE_FRONTEND_LINK_*` env overrides), token/TTL lifetimes, and account-lifecycle constants. It exists so that every account-related setting has one typed, overridable home, and so that the five token-bearing link kinds are declared alongside the infrastructure that turns them into URLs—without `infrastructure/http` ever naming the `account` module (see `docs/theory/layers.md`).
- `src/modules/account/consent-record.ts` — Defines the shape of consent data stamped onto an account at signup: which Terms version was accepted, when, and what analytics choice (if any) the user made. It centralises the "who agreed to what, and when" record so that downstream consumers (controllers, the shop endpoint) can read a consistent structure without re-deriving it.
- `src/modules/account/cooldown.ts` — Single source of truth for the "please wait before resending" logic shared by every account flow that publishes a one-time mail (2FA code, verification link, password-reset link, reauth token, etc.). Centralising the countdown calculation and the 429 response shape ensures every client renders the same semantics without each service re-implementing the arithmetic or the error envelope.
- `src/modules/account/domain/email-change.ts` — A pure, I/O-free state machine that models the email-change lifecycle. It encodes every valid `(state → event → next state)` edge in a single lookup table, so the service layer never re-derives "what is allowed here." The state itself is not persisted; it is derived on the fly from two optional fields on the User document.
- `src/modules/account/domain/epoch.ts` — Centralises the single "session epoch" rule: a token (or a login proof) is invalid if it predates the account's `tokensValidAfter` timestamp. Keeping the comparison in one pure module guarantees the resolver, the refresh path, and the mint all apply the identical cutoff and cannot drift apart.
- `src/modules/account/domain/index.ts` — Barrel file for the account **domain layer**. It re-exports the pure business rules (email-change transition table, session-proof helpers, revocation constants) so that upper tiers (services, controllers) import a single entry point. The file itself contains no logic—only `export` statements. A lint rule guarantees the domain layer has zero imports of Express, Mongoose, or any other tier.
- `src/modules/account/domain/revocation.ts` — A single, I/O-free declaration of every way an account's sessions can end. Each cause is a row of behavior flags (epoch strategy, pending-link purge, event announcement, caller retention, session-mode scope). `services/revocation.ts` reads these flags to execute; the `account.sessions-revoked` event's reason type is derived from this table, so the list is defined in exactly one place.
- `src/modules/account/domain/session-proof.ts` — Pure, I/O-free rules for a session's `amr` (Authentication Method Reference) values: what the app mints, how proofs accumulate, and when a first session is denied for lacking a second-factor proof. Exists so that every mint path (login, signup, 2FA confirmation, etc.) shares one source of truth without reaching into I/O.
- `src/modules/account/emails.ts` — Defines the finished email content (template name, subject, and rendered body data) for every account-flow email the application sends. Templates here only interpolate; actual translation is deferred to the mailer worker, which has no request context. Each builder binds its own locale-bound translator and returns a complete `EmailContent` object ready for the outbox.
- `src/modules/account/events.ts` — Declares the domain events emitted by the account module by augmenting the kernel's `DomainEventMap` interface (via `declare module '@kernel/events'`), so the event catalogue grows per-module without a shared enumeration file. Also re-exports the `SessionsRevokedReason` type and provides runtime string constants for each event name.
- `src/modules/account/index.ts` — Public barrel for the Account module. It is the **only** import surface that sibling modules (e.g. `api-keys`) are permitted to use, per the strategic-DDD rule in `docs/theory/strategic-ddd.md` §5. Internal sub-surfaces (`session`, `oauth`, `two-factor`, and the export-build services) are deliberately excluded so that cross-module access funnels through the service layer.
- `src/modules/account/jobs.generated.ts` — A generated data file that declares the account module's scheduled jobs (name, cron schedule, human-readable summary) as a frozen constant. It exists so the job *metadata* can be derived from a single YAML source (`module.yaml`) via `npm run regenerate`, keeping the scheduling config in one editable place while `jobs.ts` supplies the actual execution logic.
- `src/modules/account/jobs.ts` — Defines the scheduled jobs owned by the `account` module: inactive-account reaping, previous-email cleanup, expired-export reaping, and purge of accounts past their self-deletion grace period. Each service call is wrapped into a `JobDeclaration` (schedule metadata from the generated file + a `run` function + optional runtime requirements) and exported as a single array for the kernel to register.
- `src/modules/account/mail-budget.ts` — Enforces a per-recipient mail budget: a hard cap (default 10) on how many mails this app may deliver to a single mailbox in a rolling 24-hour window, regardless of which flow (signup, reset, verification, export, deletion) triggers the send. The budget protects the *recipient* (whoever's inbox is targeted), not the caller, and is keyed on the canonicalised, pseudonymised address so `+tag` or dot tricks cannot create new buckets.
- `src/modules/account/metrics.ts` — Defines the full set of domain-level Prometheus counters for the account/authentication module. Every counter is registered on the shared `metricsRegistry` so a single `/metrics` scrape carries them alongside HTTP metrics. This file is strictly a *write* surface for the account controllers; nothing in this module reads the counters back — the observability overview endpoint resolves them by name off the registry.
- `src/modules/account/model.ts` — Defines the three Mongoose schemas and compiled models that the account module owns — `accountexports`, `sessions`, and `verificationtokens`. This file is the single source of truth for the shape, indexes, and serialization rules of those collections; all read/write queries live in `./repository`, and the contract-layer wire shapes are built from these rows separately.
- `src/modules/account/module.ts` — Module manifest for the **account** module. It wires together everything the account module installs at registration time: the app-wide auth resolver, routes under `/account`, rate-limit budgets, queue consumers, personal-data export/erase declarations, and domain-event subscriptions. It exists as the single entry point that the kernel calls once every enabled module is known.
- `src/modules/account/module.yaml` — Module declaration for the account domain (signup, login, sessions, 2FA, OAuth, account lifecycle). It declares the module's dependencies, its full set of rate-limit budgets with their bounds and audit flags, and the scheduled background jobs that drive account lifecycle transitions (inactivity, email change, exports, deletions). It is the single source of truth for "what the account module owns" so that `module.ts` and the rate-limit enforcement layer can be generated or validated against it.
- `src/modules/account/oauth/config.ts` — Centralised OAuth configuration: declares the four `NODE_OAUTH_*` env vars, computes the absolute redirect/callback URIs from `NODE_URL`, and builds the frontend redirect URLs (success, 2FA, deletion-grace). It exists so that `./providers/*` and the account controllers never spell an env-var name or assemble a redirect URI themselves.
- `src/modules/account/oauth/deletion-redirect.ts` — Manages the single `__Host-oauth_deletion_challenge` cookie that carries a deletion-grace claim check (minted by `buildDeletionPending`) across an OAuth provider redirect. The claim check travels in a cookie rather than a URL parameter, mirroring the pattern used by `mfa-redirect.ts` for 2FA challenges. `POST /account/login/restore` falls back to this cookie when its request body omits `challenge`.
- `src/modules/account/oauth/mfa-redirect.ts` — Provides a single-purpose cookie (`__Host-oauth_mfa_challenge`) for carrying the `buildLoginChallenge` token across an OAuth provider redirect. The cookie exists so the challenge is never exposed in a URL query string (where it would persist in browser history and `Referer` headers) while still letting `POST /account/login/2fa` and `POST /account/login/2fa/send` serve both password-originated and OAuth-originated logins through the same endpoints.
- `src/modules/account/oauth/providers/client.ts` — Shared OAuth client layer for every provider adapter, built on top of `openid-client`. It centralises three things that all providers need identically: a hardened `fetch` (deadline, redirect rejection, body-size cap) that every library call goes through, the construction of a provider's `Configuration` from statically-declared endpoints and deployment credentials, and the two OAuth flow steps—building the consent URL and redeeming the authorization code. Endpoints are written down in each provider's own file rather than discovered over the network, so login requires no extra request that could fail or be spoofed.
- `src/modules/account/oauth/providers/github.ts` — Implements the `OAuthProvider` port for GitHub's plain OAuth 2.0 flow. Because GitHub publishes no issuer metadata and requires two separate API calls to reconstruct a full identity (`/user` + `/user/emails`), this file hard-codes the server endpoints, performs the code exchange via the shared `client` helpers, and maps the results into the canonical `OAuthIdentity` shape.
- `src/modules/account/oauth/providers/google.ts` — Implements the Google OAuth/OIDC provider behind the shared `OAuthProvider` port. It builds the authorization URL, exchanges the authorization code for tokens, and extracts the user's identity directly from the verified ID-token claims — avoiding a separate `userinfo` round trip.
- `src/modules/account/oauth/providers/index.ts` — Central registry that tracks which OAuth providers (Google, GitHub) are currently enabled based on their environment variables. Unlike the payments module (single active provider), multiple OAuth providers can be active simultaneously, so this exposes a live "who is configured" query rather than a memoized winner. Providers are re-evaluated on every call so that setting/unsetting env vars takes effect without a restart.
- `src/modules/account/oauth/providers/port.ts` — Defines the OAuth/OIDC provider **port** — the structural contract that concrete identity providers (Google, GitHub) implement. Unlike the analogous `PaymentProvider` port in `payments/providers/index.ts`, more than one OAuth provider may be enabled simultaneously, so selection is delegated to the registry in `./index` rather than a single environment switch.
- `src/modules/account/oauth/state.ts` — Manages the per-attempt cookies that an OAuth login requires before the browser is redirected to the provider: the CSRF `state` (double-submit), the PKCE `code_verifier`, and the untrusted `continue` / `locale` values the visitor supplied. It provides the generation primitives, the Express cookie set/clear helpers, and the read-back validators, all in one place so the start and callback controllers never touch `node:crypto` or cookie-flag logic directly.
- `src/modules/account/openapi.yaml` — OpenAPI 3.1.0 contract for the **account** module. It defines the full API surface for authentication (signup, login, session lifecycle, email verification) and self-service account operations (profile CRUD, email-change flow, two-factor, data export, account deletion with grace period). Serves as the machine-readable specification that `src/modules/account/module.ts` must implement and that clients consume.
- `src/modules/account/presenter.ts` — Pure mapping layer that converts internal database rows (`SessionRow`, `AccountExportRow`) and service results into the wire shapes clients expect. It contains no business logic: decisions such as "which sessions belong to the caller" or "when the staff lifetime cap ends a session" are made upstream in services, and this file only serializes already-decided values.
- `src/modules/account/probes.ts` — Defines four hand-written API requests (probes) that the OpenAPI contract cannot express on its own — e.g. deliberate 401/409/429 responses and a non-admin login. These are emitted alongside the contract-generated collection to fill testing gaps.
- `src/modules/account/rate-limits.generated.ts` — Auto-generated data file that declares every rate-limit budget belonging to the account module as a single typed constant. It exists so that the human-readable source of truth stays in `module.yaml` while the runtime gets a compile-time-checked `as const` object. The file is produced by `npm run regenerate` and must not be edited by hand.
- `src/modules/account/rate-limits.ts` — Defines the account module's rate-limit budgets and the Express middleware arrays that enforce them. Covers four credential-guess dimensions (per-account, per-device, per-address, per-address-block), two success-spent Sybil budgets (signup, password-reset-request), a password-strength advisory budget, and two MFA challenge budgets. Each budget is a `RateLimitBudget` object built from generated data in `rate-limits.generated.ts` and turned into a limiter via `buildRateLimiter`.
- `src/modules/account/repository.ts` — Thin MongoDB query layer for three collections — `accountexports`, `sessions`, and `verificationtokens`. All operations are single-row lean reads or atomic writes (insert, `findOneAndUpdate`, `deleteOne/Many`); nothing here paginates or free-text-searches, so the shared repository factory adds nothing and is intentionally not used.
- `src/modules/account/roles.ts` — Provides a single helper that determines whether a given user holds an unrestricted (admin) role on the current deployment's tenant. It exists so that login-emit and audit-record code can resolve `actorRole` from the live membership store instead of relying on a role value that does not exist on the account document itself.
- `src/modules/account/routes.ts` — Express router that wires every account-domain endpoint (auth, profile, email verification, password, 2FA, sessions, OAuth links, export, deletion/restore) under the `/account` prefix. It composes per-route middleware—rate limiters, human-challenge gates, idempotency, upload, and authorization predicates—around thin controller handlers so that policy is declared once at the route level.
- `src/modules/account/rules.generated.ts` — Generated configuration constants for two-factor authentication limits (lockout thresholds and delivered-code parameters). It exists as a single source of truth produced from `rules.yaml` so that tuning these values never requires code changes to consumer modules.
- `src/modules/account/rules.schema.ts` — Defines the Zod schema that validates `rules.yaml` for the account module (two-factor lockout and delivered-code limits), and declares the `GenerateSpec` consumed by `npm run regenerate` to produce `rules.generated.ts`. These numeric values are copied verbatim into the PHP twin as data.
- `src/modules/account/session-mode.ts` — Defines the shared vocabulary for the two session strategies a deployment can use (`jwt` and `cookie`). It is a dependency-free leaf module so that the schema, configuration, and strategy code can all reference the same literals without importing each other.
- `src/modules/account/session/activity.ts` — Provides a single fire-and-forget stamp of an account's `lastActiveAt` timestamp, written whenever a session is minted or kept alive. It serves as the input clock for the inactivity reaper and is shared by both session modes (cookie and JWT).
- `src/modules/account/session/auth-context.ts` — Resolves a session's proof (auth timestamp + authentication methods) into the `AuthContext` that downstream guards consume. Both session modes (cookie and JWT) produce a `SessionProof`; this file is the single, shared layer that decides what a valid proof *means*—account still active, epoch not expired, current roles, fresh factor state. The mode decides how a credential becomes a proof; this file decides what a proof grants.
- `src/modules/account/session/config.ts` — Declares the full session-policy surface (mode, TTL tiers, signing rings, rotation windows, issuer/audience, staff timeouts, device-cookie secret, TOTP encryption key) as a single typed config object, then exposes narrow getter functions so consumers never touch raw env vars directly. It is policy, not tokens: it defines *what* `jwt-strategy` signs against, what `cookie-strategy` stores against, and what `device-cookie` HMACs against.
- `src/modules/account/session/cookie-strategy.ts` — Implements the `cookie` session strategy: a single random session id stored only as its SHA-256 hash in a `sessions` row, delivered to browsers via an HttpOnly `__Host-session` cookie and to other clients as a `ses_…` Bearer token. Owns the full lifecycle — mint, resolve, rotate-on-re-proof, retire, and activity stamping — without signing keys, refresh tokens, or rotation races.
- `src/modules/account/session/cookies.ts` — HTTP cookie creation and destruction for the account session, decoupled from the session-keep strategy. It manages two cookies: `__Host-session` (carries the credential — refresh token in `jwt` mode, session id in `cookie` mode) and `isAuth` (a readable UI hint so the client shell renders the correct chrome before its first network round-trip).
- `src/modules/account/session/device-cookie.ts` — Implements the OWASP "familiar device" cookie: after a fully successful login it marks the browser as trusted for that account so the account's per-login-attempt failure budget is skipped on subsequent logins from the same browser. This prevents an attacker who exhausts the budget from also locking out the legitimate owner. One cookie carries up to five HMAC tokens (one per account), so a multi-account browser keeps all its familiarities.
- `src/modules/account/session/device-label.ts` — Produces a short, privacy-conscious label for a sign-in's origin (e.g. "Firefox on Linux") by parsing the `User-Agent` header at login time. The label is stored on the session so the account owner can distinguish their own devices in a session list. It intentionally omits versions, models, and IPs to avoid singling out a device beyond what the owner already knows.
- `src/modules/account/session/family-liveness.ts` — Determines whether a session **family** is still valid: it must have a live row in the repository, and—when the caller is staff—must not have idled out or exceeded the staff lifetime cap. If the family has lapsed, it is revoked. Otherwise, the request is counted as activity (throttled to one stamp per minute). This logic is shared by JWT bearer resolution (an access token names its family via `sid`) and by SSE stream rechecks, which must follow the family across credential rotations.
- `src/modules/account/session/idle.ts` — Implements the **staff idle timeout** and **staff lifetime cap**: two independent backend-enforced expiry rules that apply only to callers holding a tenant or platform role. Shopper sessions are never affected. The logic lives here (rather than in a client timer) so it is authoritative.
- `src/modules/account/session/jwt-strategy.ts` — Implements the `jwt` session strategy: a short-lived (10-minute) access token held client-side plus a rotating refresh token in an HttpOnly cookie, one `sessions` row per refresh token. This file is the adapter that places the token primitives from `./jwt.ts` behind the `SessionStrategy` port, so callers never see raw tokens.
- `src/modules/account/session/jwt.ts` — Owns all JWT issuance and verification for the account module. Wraps `jose` with this app's specific policy (key rings, TTLs, audiences, issuer, token-type headers, required claims) so that callers get a small, typed surface (`verifyAccessToken`, `verifyRefreshWithRow`, signing) instead of repeating configuration. Policy knobs live in `./config`; this file is the single point where a token is signed or checked.
- `src/modules/account/session/key-ring.ts` — Pure helper module that gives each signing secret in the key ring a stable identifier (`kid`) and provides lookup by that identifier. It contains no signing logic — it only derives and matches identifiers so that `./jwt` can stamp and resolve the `kid` header without this file needing to import the signer.
- `src/modules/account/session/listing.ts` — Provides the "list my sessions" read path shared by both session modes (cookie and JWT). It fetches the caller's live session rows, filters out rows that are no longer valid (pre-epoch, idled, or past the staff lifetime cap), deduplicates JWT token-family rows, marks the caller's current session, and shapes the result into the wire `Session` list.
- `src/modules/account/session/login-observability.ts` — Extracts the post-login observability tail (Prometheus counter, audit record, analytics event) so that both `post-login.ts` and `post-login-2fa.ts` share one definition of "a login completed." It lives at the controller/session layer rather than in `services/login.ts` because the SUCCESS emit must only fire after a session (cookies, access token) actually exists — a fact credential-checking services do not know.
- `src/modules/account/session/mint-guard.ts` — Guards that must pass before a **first** session is minted for an account. They enforce two invariants at the mint site (rather than relying on each login branch to check them): (1) a session cannot be issued when a second factor is armed but the proof carries none, and (2) a session cannot be issued on a proof whose check preceded the account's current epoch (e.g. a password change committed mid-login). Both session strategies invoke these from their `issue` path, never from a re-mint.
- `src/modules/account/session/resolver.ts` — Implements the kernel's `AuthResolver` port for the account module. It is a thin delegation layer that forwards every credential-resolution call to whichever session strategy the deployment has activated, and is registered by `module.ts` so the kernel's auth guard can identify callers.
- `src/modules/account/session/session-id.ts` — Generates and classifies opaque session IDs used in `cookie` mode. They verify that `authorizeUrl` builds a correct consent-screen URL, and that `exchangeCode` correctly validates the callback (state, issuer, PKCE) and the returned ID token (audience, issuer, expiry, subject) before resolving an identity. `fetch` is mocked throughout so the tests exercise the library's own claim checks without any network I/O.
- `src/modules/account/tests/unit/oauth-state.test.ts` — Unit tests for the pure-function OAuth security helpers in `oauth/state.ts`. Covers the CSRF state comparison, PKCE verifier/challenge generation, the `continue` redirect-path guard, and locale-tag validation. Cookie/session plumbing is intentionally excluded here (covered by integration/contract suites); this file isolates the comparison logic and token-shape guarantees.
- `src/modules/account/tests/unit/presenter.test.ts` — Unit tests for the account presenter's three mapping functions (`presentSession`, `presentExportSession`, `presentExport`). The tests verify that stored repository rows are correctly shaped into wire responses and that the credential digest (`tokenHash`) never leaks into any output.
- `src/modules/account/tests/unit/rate-limits.test.ts` — Unit test that pins the **ordinal relationships** between the account module's rate-limit budgets (credential, signup, reset, MFA) rather than their absolute values. It enforces invariants like "identity budget < global browsing budget / 5" and "identity ≤ address ≤ block" so that the budgets remain meaningful relative to one another, even if individual numbers are later tuned.
- `src/modules/account/tests/unit/reauth-policy.test.ts` — Unit tests for the two pure rules the step-up (reauth) flow adds: the `amrAfterReauth` claim set a re-minted session carries, and the boot-time refusal `oauthConfig` enforces when an enabled provider has no deliverable mail transport. HTTP-level behaviour is deliberately excluded (see `contract/reauth.contract.test.ts`).
- `src/modules/account/tests/unit/revocation-table.test.ts` — Verifies cross-cutting invariants of the `REVOCATION` table — constraints that hold *across* all causes simultaneously and would not be caught by a test targeting a single cause in isolation (e.g. "every cause that keeps the caller's session must announce `false`").
- `src/modules/account/tests/unit/routes.test.ts` — Security-invariant tests for the account router. The file asserts that middleware presence, ordering, and authorization placement match the documented contract — invariants a type checker cannot see (e.g. `noStore` must cover every route, credential routes must carry all four rate-limit dimensions, token-bearing routes must stay public). A single mis-order or missing guard on any of these routes is an account-takeover vector.
- `src/modules/account/tests/unit/schema-contract.test.ts` — Verifies the *declarative* shape of the account module's three Mongoose schemas (export, session, verification token) — required fields, unique constraints, index definitions, and TTL semantics. These are "database facts" that a valid data fixture cannot express (e.g., a TTL that deletes a spent row), so the test asserts them directly against the schema objects.
- `src/modules/account/tests/unit/session-id.test.ts` — Unit tests for the `cookie`-mode session ID. The kernel dispatches on the ID's shape and 256 bits of entropy is the entire security guarantee, so this file locks in both invariants rather than assuming them.
- `src/modules/account/tests/unit/session-jwt.test.ts` — Unit-level tests for the token layer in `@modules/account/session/jwt`. Asserts safety invariants: the access and refresh secrets never cross-verify, refresh tokens are only valid while still stored, `jti` prevents same-second mutual revocation, and key-ring rotation does not mass-logout. The session store and `userService` are replaced with stubs; the actual query behaviour is covered in `../integration/auth-storage.test.ts`.
- `src/modules/account/tests/unit/session-listing.test.ts` — Unit tests for the session-listing module (`@modules/account/session/listing`). Verifies that `newestPerFamily` deduplicates rotation-race rows and that `listSessions` publishes the correct shape, marks the caller's family as current, omits absent optional fields, enforces the account token epoch, and applies the staff idle-timeout rule. The repository's `listLive` is fully stubbed; query construction is left to the integration suite.
- `src/modules/account/tests/unit/session-proof.test.ts` — Unit tests for the session-proof domain rules: verifying that proofs are combined without duplicates (and without mutating the caller's array) and that only an armed account lacking an `otp` proof is refused a first session.
- `src/modules/account/tests/unit/session-strategy.test.ts` — Unit tests for the session-strategy seam: verifying that the active adapter is selected per-call from `NODE_SESSION_MODE`, that the resolver delegates (rather than caching) to whichever adapter is active, and that the shared mint guard enforces second-factor requirements before a session is issued.
- `src/modules/account/tests/unit/tokens.test.ts` — Unit tests for the session/token configuration module (`@modules/account/session/config`). Validates that every env-var-driven value (tier expiry times, access-token TTL, signing rings, cookie max-age, session mode, rotation/reuse windows) parses correctly, routes to the right tier, falls back to documented defaults instead of `NaN`/`undefined`, and that the slice's boot gate enforces the correct required keys per session mode.
- `src/modules/account/tests/unit/two-factor.test.ts` — Unit tests for the pure (database-free) two-factor logic in `src/modules/account/two-factor/`: TOTP secret encryption/decryption, code verification against fixed clocks, backup-code minting and salted hashing, and the shared delivered-code state machine (TTL, cooldown, attempt ceiling). Exists to pin down security invariants—replay protection, keyed (non-bare) hashing, and clock determinism—without requiring a live service or wall-clock timing.
- `src/modules/account/token-types.ts` — A leaf module that names every token kind stored in the `verificationtokens` table and declares their TTL and uniqueness constraints. It exists so the schema, the issuing flows, and the revocation service can all reference token types by name without importing one another, preventing circular dependencies within the account module.
- `src/modules/account/two-factor/backup-codes.ts` — Provides the full lifecycle utilities for one-time account-recovery backup codes: generation, per-user salting, and scrypt hashing. Backup codes recover the account itself (not a specific factor), are minted once when an account first arms two-factor, and are shown to the user exactly once before being stored only as salted digests.
- `src/modules/account/two-factor/delivered-code-verify.ts` — Verifies a delivered (e.g. emailed) code against an account using a pure comparison followed by conditional writes. It avoids a read-modify-write cycle: the comparison itself (`checkDeliveredCode`) is stateless, and the side-effects (spending the code on a match, incrementing the miss counter on a failure) are issued as separate conditional writes through the users service. The same function serves both a second-factor code and a step-up (reauth) code.
- `src/modules/account/two-factor/delivered-codes.ts` — Pure (no I/O, no database) helper module for the short numeric codes that a "delivered" 2FA method (e.g. email) mints, stores as an HMAC, and checks against a user's typed input. It centralises the TTL, attempt-limit, and cooldown logic so those rules can be unit-tested against an injected clock without touching the persistence layer.
- `src/modules/account/two-factor/index.ts` — Barrel (re-export) file for the two-factor module. It is the single import surface that services, admin-recovery code, and test suites use to access the method registry and the pure crypto/validation helpers, without reaching into individual sub-modules.
- `src/modules/account/two-factor/lockout.ts` — Exports the two constants that define the per-account wrong-code lockout policy for armed 2FA: how many consecutive failures are allowed and how long the resulting lock lasts. The actual enforcement (storing the counter, applying the lock) lives elsewhere (`users`); this file only supplies the policy numbers.
- `src/modules/account/two-factor/methods/email.ts` — Implements email as a "delivered" two-factor method: setup and verification both reduce to minting a one-time code, mailing it, and recording its digest. Serves as the concrete `TwoFactorMethodHandler` for the `email` method in the 2FA registry, and is shared verbatim by the step-up re-authentication flow.
- `src/modules/account/two-factor/methods/totp.ts` — Registry adapter that exposes TOTP (authenticator-app) as a two-factor method. All cryptographic logic lives in the sibling `../totp.ts`; this file only wires the `setup` and `verify` lifecycle steps to the `TwoFactorMethodHandler` contract, adds per-enrollment secret encryption, and enforces single-use via a conditional step claim.
- `src/modules/account/two-factor/registry.ts` — Central registry of the second-factor methods this deployment supports. It defines the `TwoFactorMethodHandler` contract, registers the concrete handlers (TOTP, email), and provides lookup and ordering utilities so that services and the login flow address a method by wire-name string rather than branching on a specific channel. Adding a new 2FA channel means adding a handler here, not touching the login flow.
- `src/modules/account/two-factor/totp.ts` — Pure crypto layer for TOTP two-factor: encrypts/decrypts the base32 secret for storage and verifies user-supplied 6-digit codes against a known secret. Deliberately free of database or session concerns so it can be unit-tested against fixed clocks; the database-touching adapter lives in `methods/totp.ts`.
