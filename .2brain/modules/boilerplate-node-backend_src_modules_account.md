# src/modules/account/

## Purpose

The account module is the bounded context responsible for the full identity-and-session lifecycle: signup, login, token refresh, two-factor authentication, OAuth (Google, GitHub), email verification and change, password reset, session management (both JWT and cookie strategies), account deletion, and personal-data export. It owns *who is signed in and how*, while deliberately leaving the `User` document in the `users` module so an identity-provider swap remains possible.

## Key parts

- **Domain rules (pure, I/O-free):** `domain/email-change.ts` (finite-state machine for email change), `domain/revocation.ts` (session-termination causes and their effects), `domain/session-proof.ts` (AMR accumulation and second-factor denial). `domain/index.ts` re-exports them as one import surface. `session/epoch.ts` and `cooldown.ts` add the epoch-refusal and resend-countdown rules.
- **Session strategies:** `session/config.ts` (policy: mode, lifetimes, key rings), `session/cookie-strategy.ts` (server-side `ses_…` row), `session/cookies.ts` (HttpOnly cookie transport), `session/auth-context.ts` (proof → downstream context), `session/device-cookie.ts` (OWASP familiar-device), `session/family-liveness.ts`, `session/activity.ts`, `session/device-label.ts`.
- **OAuth sub-module (`oauth/`):** `providers/port.ts` (structural contract), `providers/client.ts` (shared `openid-client` plumbing), `providers/github.ts` and `providers/google.ts` (adapters), `providers/index.ts` (live registry), `state.ts` (CSRF/PKCE cookies), `mfa-redirect.ts` (MFA challenge cookie), `config.ts` (env + URL construction).
- **Persistence:** `model.ts` (Mongoose schemas for `accountexports`, `sessions`, `verificationtokens`) and `repository.ts` (targeted Mongoose queries—claim-once updates, scoped deletes, throttled stamps).
- **Cross-cutting declarations:** `analytics.ts` (event-name map), `audit.ts` (audit-action vocabulary), `events.ts` (domain-event map), `metrics.ts` (Prometheus counters), `config.ts` (frontend-link templates, token lifetimes, export retention).
- **Policy & protection:** `rate-limits.ts` (per-account/address/session budgets + challenge escalation), `mail-budget.ts` (per-recipient daily cap).
- **Routing & module wiring:** `routes.ts` (Express router under `/account`), `module.ts` (kernel entry point, resolver wiring, event subscriptions), `module.yaml` (machine-readable descriptor), `index.ts` (public barrel—sole cross-module import surface), `openapi.yaml` (HTTP contract), `probes.ts` (hand-written API tests), `roles.ts` (admin-role helper), `emails.ts` (locale-bound email builders).

## How it connects

- **`src/modules/users/`** — The `User` document lives there; this module reads role membership (via `roles.ts`) and subscribes to `USER_SETUP_REQUESTED` events, but owns no identity record itself.
- **`src/modules/api-keys/`** and other sibling modules — May import only through this module's public barrel (`index.ts`), never into internal sub-surfaces like `session/` or `oauth/`.
- **`src/infrastructure/`** — Supplies the shared analytics port (augmented by `analytics.ts`), the audit logger (augmented by `audit.ts`), the `metricsRegistry` (registered by `metrics.ts`), the `frontend-link` helper (consumed by `config.ts`), and `buildRateLimiter` middleware (used by `rate-limits.ts`).
- **`src/modules/account/controllers/` and `src/modules/account/services/`** — Internal sub-modules that implement the HTTP handlers and orchestration logic against the domain rules, repository, and session strategies defined here.
- **`scenarios/` and `scripts/`** — Consume the OpenAPI contract and probes for integration/E2E test generation.
- **`src/modules/notifications/`** — Downstream consumer of the `EmailContent` objects produced by `emails.ts`; the account module builds content, the notifications module handles delivery.

## Where to start

1. **`module.ts`** — The single entry point that wires the auth resolver into the kernel, declares the module's erase/export contract, registers the export consumer, and subscribes to domain events. Reading it first gives you the module's scope and its integration points with the rest of the system.
2. **`domain/index.ts`** → follow into `email-change.ts` and `revocation.ts` — These pure, I/O-free lookup tables encode the "what can happen and when" for the two most complex flows. They have no imports beyond type definitions, so they are easy to read in isolation and make the business invariants concrete before you touch any service or controller code.

## Files
- `src/modules/account/analytics.ts` — Declares the canonical set of analytics event names emitted by the account module and augments the shared analytics port's event-name map so TypeScript enforces type-safety at every emit site. It exists to keep the "one name → one emitter" invariant and to let each module grow the catalogue independently (same pattern as `./audit.ts` for audit actions).
- `src/modules/account/audit.ts` — Centralizes the audit-action vocabulary for the account/auth domain. It defines the canonical wire-format strings (e.g. `auth.login`, `auth.email_change.completed`) that every account service fires through the shared audit logger, and registers them on the infrastructure `AuditActionMap` via a type-only module augmentation so log tooling and alert rules get a single typed union without a runtime import cycle.
- `src/modules/account/config.ts` — Centralises the account module's frontend-link templates, token lifetimes, and export-retention defaults into a single typed config (`accountConfig`), and exposes small helpers that resolve those values into concrete frontend URLs. It exists so that the account module owns *which* links it uses and their defaults, while the generic `infrastructure/http/frontend-link.ts` stays unaware of account-specific kinds (layering rule: infrastructure must not name a module).
- `src/modules/account/cooldown.ts` — Single source of truth for the "please wait before resending" logic shared by every account flow that publishes a one-time mail (2FA code, verification link, password-reset link, reauth token, etc.). Centralising the countdown calculation and the 429 response shape ensures every client renders the same semantics without each service re-implementing the arithmetic or the error envelope.
- `src/modules/account/domain/email-change.ts` — Pure, I/O-free finite-state machine for the account email-change flow. It encodes every valid state, event, and transition as a lookup table so the *where* and *what* of an email change is defined in exactly one place. The service layer and tests consume this table; no HTTP, no database, no email is touched here.
- `src/modules/account/domain/index.ts` — Barrel (re-export) module for the **account domain layer**. It exposes the pure business rules—email-change state transitions, session-proof validation, and session revocation—as a single import surface. The file contains no logic of its own; it exists so consumers (services, tests) can import from one path rather than reaching into individual domain files.
- `src/modules/account/domain/revocation.ts` — A single, I/O-free lookup table that enumerates every cause by which an account's sessions can be terminated and specifies exactly what each cause does (epoch strategy, pending-link cleanup, subscriber announcement, caller re-mint, applicable session modes). All downstream consumers—services, event types, tests—derive their behavior and types from this table so the list of causes is declared in exactly one place.
- `src/modules/account/domain/session-proof.ts` — Pure, I/O-free rules for a session's `amr` (Authentication Method Reference) values: what the app mints, how proofs accumulate, and when a first session is denied for lacking a second-factor proof. Exists so that every mint path (login, signup, 2FA confirmation, etc.) shares one source of truth without reaching into I/O.
- `src/modules/account/emails.ts` — Single home for every email the account module sends. Each exported builder takes an explicit `locale` string (no request or locale store exists at render time in the mailer worker), binds a translator to it, and returns a fully-resolved `EmailContent` — template name, subject, and interpolation data together. Templates only interpolate; all translation happens here at build time.
- `src/modules/account/events.ts` — Declares the domain events the account module emits by augmenting the kernel's `DomainEventMap` via TypeScript module declaration merging. This keeps the event catalogue distributed across owning modules rather than centralised in a shared file.
- `src/modules/account/index.ts` — Public barrel for the Account module. It is the **only** import surface that sibling modules (e.g. `api-keys`) are permitted to use, per the strategic-DDD rule in `docs/theory/strategic-ddd.md` §5. Internal sub-surfaces (`session`, `oauth`, `two-factor`, and the export-build services) are deliberately excluded so that cross-module access funnels through the service layer.
- `src/modules/account/mail-budget.ts` — Defines and enforces a per-recipient daily mail budget (default 10 mails / 24 h) so that no single mailbox can be flooded regardless of how many distinct callers target it. It exists because caller-side rate limits bound the attacker, not the victim; this budget bounds the mailbox that would receive the mail.
- `src/modules/account/metrics.ts` — Defines and exports Prometheus `Counter` instances that track every major authentication and account-management event (login, signup, 2FA, email changes, password resets, OAuth, token lifecycle, data export). All counters register on the shared `metricsRegistry` so a single `/metrics` scrape includes both HTTP-level and domain-level signals. Nothing reads these counters programmatically; they are consumed exclusively by the metrics endpoint and alerting rules.
- `src/modules/account/model.ts` — Defines the three Mongoose schemas, document interfaces, and compiled models that make up the account module's persistence layer: `accountexports` (data-export progress), `sessions` (signed-in sessions or refresh tokens), and `verificationtokens` (one-time links/challenges in flight). This file is the single source of truth for the shape of those collections; all queries live elsewhere in `./repository`.
- `src/modules/account/module.ts` — Module entry point for the `account` domain: authentication, signup, login, token refresh, password reset, logout, two-step account deletion, and personal-data export. It wires the auth resolver into the kernel, declares the module's `personalData` erase/export contract, registers the export-queue consumer, and subscribes to the `USER_SETUP_REQUESTED` domain event. It deliberately keeps the `User` document on the `users` module rather than merging them, so that an identity-provider swap stays possible.
- `src/modules/account/module.yaml` — Machine-readable module descriptor for the account subdomain. It declares the module's scope (signup, login, sessions, two-factor, OAuth, account lifecycle), its classification, and its hard dependencies so the module system and tooling can resolve imports without parsing TypeScript.
- `src/modules/account/oauth/config.ts` — Centralizes all OAuth environment-variable access and URL construction for the account module. Providers and controllers consume the exports here rather than spelling `NODE_OAUTH_*` names or deriving redirect URIs from untrusted request data. The file reads and validates configuration only; it does not hold tokens or mint sessions.
- `src/modules/account/oauth/mfa-redirect.ts` — Manages a single HTTP cookie (`oauth_mfa_challenge`) that carries an MFA login-challenge token across an OAuth provider redirect. Because placing the challenge in the query string would expose it in browser history and `Referer` headers, it is transmitted as a cookie instead. This lets the two `POST /account/login/2fa*` endpoints serve both password-originated logins (challenge in the JSON body) and OAuth-originated logins (challenge in the cookie) through the same code path.
- `src/modules/account/oauth/providers/client.ts` — Shared OAuth client plumbing on top of `openid-client`. It centralises the one `fetch` wrapper every provider call goes through (deadline, body cap, no redirects) and the helpers that turn a provider's static server description into a working configuration, authorization URL, and code redemption. Both provider adapters (GitHub, Google) import from here rather than re-implementing this logic.
- `src/modules/account/oauth/providers/github.ts` — Implements the `OAuthProvider` port for GitHub's plain OAuth 2.0 flow. Because GitHub publishes no issuer metadata and requires two separate API calls to reconstruct a full identity (`/user` + `/user/emails`), this file hard-codes the server endpoints, performs the code exchange via the shared `client` helpers, and maps the results into the canonical `OAuthIdentity` shape.
- `src/modules/account/oauth/providers/google.ts` — Implements the Google OAuth/OIDC provider behind the shared `OAuthProvider` port. It builds the authorization URL, exchanges the authorization code for tokens, and extracts the user's identity directly from the verified ID-token claims — avoiding a separate `userinfo` round trip.
- `src/modules/account/oauth/providers/index.ts` — Central registry that tracks which OAuth providers (Google, GitHub) are currently enabled based on their environment variables. Unlike the payments module (single active provider), multiple OAuth providers can be active simultaneously, so this exposes a live "who is configured" query rather than a memoized winner. Providers are re-evaluated on every call so that setting/unsetting env vars takes effect without a restart.
- `src/modules/account/oauth/providers/port.ts` — Defines the OAuth/OIDC provider **port** — the structural contract that concrete identity providers (Google, GitHub) implement. Unlike the analogous `PaymentProvider` port in `payments/providers/index.ts`, more than one OAuth provider may be enabled simultaneously, so selection is delegated to the registry in `./index` rather than a single environment switch.
- `src/modules/account/oauth/state.ts` — Manages the per-attempt cookies that an OAuth login round-trip requires: the CSRF `state` token (double-submit pattern, not a server-side session), the PKCE `code_verifier`, and two convenience values (`continue` path, `locale`). It mints tokens, sets/clears the corresponding Express cookies, and provides the validation predicates the callback controller uses to verify a returned request is legitimate before acting on it.
- `src/modules/account/openapi.yaml` — OpenAPI 3.1.0 contract for the **account** module. It defines the module's public HTTP surface — authentication (sign-up, login, refresh, email verification, session teardown) and account management (profile CRUD, password, two-factor, data export, deletion) — and is consumed by the spec bundler, which merges it into the root document under the module's `basePath`.
- `src/modules/account/probes.ts` — Defines four hand-written API requests (probes) that the OpenAPI contract cannot express on its own — e.g. deliberate 401/409/429 responses and a non-admin login. These are emitted alongside the contract-generated collection to fill testing gaps.
- `src/modules/account/rate-limits.ts` — Defines the account module's rate-limit budgets as `RateLimitBudget` data objects and turns them into Express middleware via `buildRateLimiter`. Covers credential-guess protection (per-account, per-address, per-address-block, per-session, per-device-cookie), a password-strength check limiter, signup/reset/MFA budgets (truncated in view), and the `loginChallengeGate` that escalates to a human challenge once a budget is half-spent.
- `src/modules/account/repository.ts` — Plain Mongoose query layer for three account-scoped collections (`accountexports`, `sessions`, and `verificationtokens`). It exposes lean reads and atomic writes (claim-once updates, throttled stamps, scoped deletes) that the account services need but that the shared repository factory does not provide—there is no pagination or general search here, just targeted single-document and small-batch operations.
- `src/modules/account/roles.ts` — Provides a single helper to determine whether a given user holds an unrestricted (admin) role on the deployment's tenant. This value is needed as the `actorRole` field on every login event emission and audit record produced by the account module. Roles are read live from the membership store because the account document itself carries no role.
- `src/modules/account/routes.ts` — Express router that wires every account-related endpoint (auth, profile, password, 2FA, OAuth, sessions, email verification, account deletion) under the `/account` prefix. It centralises cross-cutting middleware (auth parsing, cache suppression, rate-limiting, human-challenge, idempotency, upload) so individual controllers stay thin and a future route cannot accidentally omit a guard.
- `src/modules/account/session-mode.ts` — Defines the shared vocabulary for the two session strategies a deployment can use (`jwt` and `cookie`). It is a dependency-free leaf module so that the schema, configuration, and strategy code can all reference the same literals without importing each other.
- `src/modules/account/session/activity.ts` — Provides a single fire-and-forget stamp of an account's `lastActiveAt` timestamp, written whenever a session is minted or kept alive. It serves as the input clock for the inactivity reaper and is shared by both session modes (cookie and JWT).
- `src/modules/account/session/auth-context.ts` — Resolves a verified session proof (auth time + AMR methods) into the `AuthContext` that downstream guards read. This is the shared "what does the proof mean" step that both cookie and JWT session strategies funnel into, so account validity, epoch expiry, and current role membership are decided in exactly one place.
- `src/modules/account/session/config.ts` — Declares the session policy for the account module: which mode (`jwt` or `cookie`) is active, how long each "remember me" tier lives, the signing key rings, the rotation/reuse windows, and the issuer/audience defaults. It holds no tokens and issues none — downstream modules (`./jwt`, `./cookie-strategy`, `./cookies`) read its values to sign, store, or set `maxAge`. Named `config.ts` (not `tokens.ts`) to make that separation explicit.
- `src/modules/account/session/cookie-strategy.ts` — Implements the `cookie` session mode: a server-side session identified by a random `ses_…` id, stored only as its SHA-256 hash in a `sessions` row. Browsers receive the id as an HttpOnly `__Host-session` cookie; non-browser clients receive it as a Bearer token. There is no JWT signing, no refresh-token rotation, and no race on rotation — logout is a row delete, and the row is read on every request anyway.
- `src/modules/account/session/cookies.ts` — HTTP cookie creation and destruction for the account session layer. Manages two cookies — `__Host-session` (carries the credential: a refresh token in `jwt` mode or a `ses_…` id in `cookie` mode) and `isAuth` (a non-secret, readable-by-JS hint so the client shell can render auth chrome before its first API response arrives). Decoupled from *how* the session is kept; only handles the transport.
- `src/modules/account/session/device-cookie.ts` — Implements the OWASP "familiar-device" cookie: after a fully successful login, the browser stores up to five HMAC-SHA256 tokens (one per account) in an httpOnly cookie. On subsequent logins, a valid token lets the browser skip the **per-account** failure budget, so an attacker who exhausts that budget cannot lock out the legitimate owner. The cookie never bypasses per-address or per-IP budgets.
- `src/modules/account/session/device-label.ts` — Produces a short, privacy-conscious label for a sign-in's origin (e.g. "Firefox on Linux") by parsing the `User-Agent` header at login time. The label is stored on the session so the account owner can distinguish their own devices in a session list. It intentionally omits versions, models, and IPs to avoid singling out a device beyond what the owner already knows.
- `src/modules/account/session/epoch.ts` — Single source of truth for the session-epoch rule: a token or a login's proof is refused when it predates the account's `tokensValidAfter`. Both checks live here as pure functions so the resolver, the refresh path, and the mint path cannot drift apart.
- `src/modules/account/session/family-liveness.ts` — Determines whether a session **family** is still alive: it has a live row in the repository and, for staff-mode sessions, has not idled out. Shared by the JWT bearer path (access token's `sid` field) and by SSE stream rechecks, since a credential rotates under a stable family.
- `src/modules/account/session/idle.ts` — Implements the backend-enforced idle timeout for staff and admin sessions. A session that has not seen a real request within the configured window is considered idled out. Shopper sessions are never idled (NIST AAL1 "MAY"). Lives in the backend so the policy cannot be bypassed by a client timer.
- `src/modules/account/session/jwt-strategy.ts` — Adapter that implements the `SessionStrategy` port for the **JWT session mode**: a short-lived (≈10 min) access token the client keeps in memory, backed by a rotating refresh token in an HttpOnly cookie with one `sessions` row per refresh token. All signing, rotation, and reuse-detection logic lives in `./jwt.ts`; this file only wires that logic into the strategy interface so callers above never see tokens.
- `src/modules/account/session/jwt.ts` — Creates and verifies the application's access and refresh JWTs (HS256, built on `jose`). Policy (secrets, TTLs, audiences, issuer) is owned by `./config`; this file is the signing and verification logic itself. It was app-level middleware until the domain split made it part of the `account` module, since issuing/verifying tokens is what `account` does.
- `src/modules/account/session/key-ring.ts` — Pure helper module that gives each signing secret in the key ring a stable identifier (`kid`) and provides lookup by that identifier. It contains no signing logic — it only derives and matches identifiers so that `./jwt` can stamp and resolve the `kid` header without this file needing to import the signer.
- `src/modules/account/session/listing.ts` — Provides the account's live-session list (the wire `Session` array) shared across both session modes. It fetches live rows, filters out rows invalidated by a ban (epoch) or by an idle-timeout, deduplicates JWT-family rows that can hold two live refreshes simultaneously, and marks the caller's own session as `current`.
- `src/modules/account/session/login-observability.ts` — Fires the metrics, audit, and analytics signals for a completed (successful or failed) login. Extracted from `post-login.ts` so that `post-login-2fa.ts` reuses the same "a login happened" tail without re-implementing it. Lives at the controller/session layer — not in `services/login.ts` — because the success emit is only valid once a session actually exists (cookies, access token), which is a controller-layer fact.
- `src/modules/account/session/mint-guard.ts` — Defines the two invariants a **first** session must satisfy at mint time: the proof must evidence an armed second factor, and it must not predate the account's current session epoch. These checks run inside `issue` (the mint path) rather than in login-branching logic, so a code path that forgets to branch to a challenge or re-validate after an epoch change is still refused at the point of no return.
- `src/modules/account/session/resolver.ts` — Implements the kernel's `AuthResolver` port for the account module. It is a thin delegation layer that forwards every credential-resolution call to whichever session strategy the deployment has activated, and is registered by `module.ts` so the kernel's auth guard can identify callers.
- `src/modules/account/session/session-id.ts` — Generates and classifies opaque session IDs used in `cookie` mode. The ID is 32 random bytes in base64url under the `ses_` prefix; only its SHA-256 is persisted, so a database leak never yields a usable credential. The file also exports cheap shape-checks that let the authentication kernel reject non-matching tokens before any database lookup.
- `src/modules/account/session/session.ts` — Facade module that gives every session-minting controller a single, mode-agnostic API. Controllers call these five functions and never learn whether the system is in `cookie` or token mode — that decision is delegated entirely to `activeStrategy()` in `strategy.ts`.
- `src/modules/account/session/strategy.ts` — Defines the **port** (the `SessionStrategy` interface) through which all higher-level code mints, resolves, and manages user sessions, without needing to know whether the deployment uses JWT or cookie mode. The single entry point is `activeStrategy()`, which returns the concrete adapter selected at process start via `NODE_SESSION_MODE`. Every caller (login, 2FA, reauth, password change, resolver) goes through this one function.
- `src/modules/account/tests/contract/abilities.test.ts` — Contract test for `GET /account/abilities`. It verifies the round-trip invariant: rules the server packs into the response must unpack (via CASL `unpackRules`) into a working `MongoAbility` on the client side. The point is not endpoint shape but that both sides agree on the same policy, preventing silent drift between server enforcement and client-side UI greying-out.
- `src/modules/account/tests/contract/api.contract.test.ts` — Contract tests for the self-service `/account` HTTP surface: login (remember-me tiers), signup, username ceiling, password change, session rotation, single-session logout, sessions listing, and email verification. They cover scenario branches that depend on multi-actor or stateful preconditions (a second account holding the same email, a revoked cookie, a spent token, someone else's session) — situations a generated-payload unit sweep cannot set up. Listing assertions check actual IDs, never just array lengths.
- `src/modules/account/tests/contract/lifecycle.contract.test.ts` — Contract tests for account-lifecycle endpoints that `api.contract.test.ts` does not cover: two-step account deletion, password-reset request, logout-all, and the live breach check. Each token-carrying flow is driven end-to-end by reading the one-time token back out of the mocked mail queue, so the assertions validate the exact payload a real client would receive.
- `src/modules/account/tests/contract/login-paths.contract.test.ts` — Contract test that asserts two invariants shared by every login/session-continuation entry point (password, OAuth, refresh/next-request) in a single pass rather than re-testing them per entry point. Rule 1: no path may mint a session for a deactivated or soft-deleted account. Rule 2: password and OAuth login must each audit the caller's real role and increment the shared `auth_login_total` counter exactly once. Refresh is deliberately excluded from Rule 2 because it audits its own action/counter.

It mints a time-limited code, mails it to the account's verified address, and arms the code's digest on the user record. All channel-agnostic concerns (TTL, cooldown, attempt limits) are delegated to the shared delivered-code module, so every future delivery channel inherits the same constraints.
- `src/modules/account/two-factor/methods/totp.ts` — Registry adapter that exposes TOTP (authenticator-app) as a two-factor method. All cryptographic logic lives in the sibling `../totp.ts`; this file only wires the `setup` and `verify` lifecycle steps to the `TwoFactorMethodHandler` contract, adds per-enrollment secret encryption, and enforces single-use via a conditional step claim.
- `src/modules/account/two-factor/registry.ts` — Central registry of the second-factor methods this deployment supports. It defines the `TwoFactorMethodHandler` contract, registers the concrete handlers (TOTP, email), and provides lookup and ordering utilities so that services and the login flow address a method by wire-name string rather than branching on a specific channel. Adding a new 2FA channel means adding a handler here, not touching the login flow.
- `src/modules/account/two-factor/totp.ts` — Pure crypto layer for TOTP two-factor: encrypts/decrypts the base32 secret for storage and verifies user-supplied 6-digit codes against a known secret. Deliberately free of database or session concerns so it can be unit-tested against fixed clocks; the database-touching adapter lives in `methods/totp.ts`.
