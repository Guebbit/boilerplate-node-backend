# src/modules/returns/

## Purpose

The returns module owns the full lifecycle of customer goods returns and the EU 14-day withdrawal ("cooling-off") flow. It covers every state transition—from a buyer opening a return, through staff approval, physical receipt, refund settlement, and closure—plus the "remainder cancel" path that unwinds unshipped fulfillment lines. All business rules (state machine, quantity arithmetic, statutory deadlines, refund computation) live in a pure domain layer; orchestration and I/O sit in a service and controller layer above it.

## Key parts

- **`domain/`** – Pure, I/O-free business rules: the return state machine (`lifecycle.ts`), quantity math (`quantities.ts`), statutory reason clocks (`reasons.ts`), refund amount and due-date logic (`refund-amount.ts`, `refund-due.ts`), restock rules (`restock.ts`), statement validation (`statement.ts`), order-level status projection (`status-projection.ts`), and accounting for already-settled units (`accounting.ts`). A lint rule enforces that no Express/Mongoose imports leak in.
- **`services/`** – Orchestration that coordinates cross-module effects (delivery, inventory, payments, orders) for each lifecycle action: `cancel-remainder.ts`, `cancel.ts`, `close.ts`, `cancellation-refund.ts`, `cancel-right.ts`, and the options/read flows.
- **`controllers/`** – Thin HTTP handlers that validate requests, delegate to the service layer, and shape JSON responses. One controller per REST endpoint (create, read, list, approve, decline, receive, proof, close, cancel, options).
- **`repository.ts` + `model.ts`** – Persistence layer. `model.ts` declares the Mongoose schema and TypeScript interfaces; `repository.ts` exposes CRUD plus the two concurrency-sensitive primitives (`claimStatus`, `claimProof`) that make parallel approvals/declines a single-writer race at the database level.
- **`routes.ts`, `module.ts`, `module.yaml`** – Module wiring: route table with middleware ordering (auth, rate-limit, idempotency, step-up), the `AppModule` manifest consumed by the kernel, and the declarative YAML for metadata, cross-module dependencies, and the scheduled free-text scrub job.
- **Contracts & declarations** – `openapi.yaml` (REST contract), `asyncapi.webhooks.yaml` (outbound event fragment), `authorization.yaml` (RBAC policy), `events.ts` (domain-event map augmentation), `audit.ts` (audit action vocabulary).
- **Cross-cutting helpers** – `presenter.ts` (document → wire-shape mapping), `emails.ts` (rendered notice copy), `rate-limits.ts` (per-account POST budget), `config.ts` (retention window, read-per-call pattern), `index.ts` (public barrel enforcing module boundaries).

## How it connects

- **orders** – Returns reference an order; the module reads order/fulfillment state to compute eligibility and quotes. It also owns the "remainder cancel" flow that mutates a fulfillment order's unshipped lines.
- **payments** – The module triggers refunds (via the payments service) when a return is received or a remainder is canceled, and listens for `PAYMENT_REFUNDED` to drive `received → closed`.
- **inventory** – On receipt, the module calls inventory to restock units (with per-line overrides for broken goods).
- **delivery** – The last-unit delivery-refund rule (Art. 13(2)) is computed here but applied through the delivery module's refund mechanism.
- **users** – Auth context determines scoping (buyer vs. staff) and provides the locale for email rendering.
- **infrastructure / adapters** – The mailer adapter consumes the rendered `EmailContent` from `emails.ts`; the scheduler picks up the `JobDeclaration` array from `jobs.ts`.
- **shop-tasks** – The free-text scrub job is registered here and executed by the shared task runtime.
- **scenarios** – Integration and end-to-end test scenarios exercise the full return lifecycle against a seeded database.

## Where to start

1. **`domain/lifecycle.ts`** – The state machine table (which status each move starts from and lands in) is the skeleton everything else hangs on; reading it first gives you the vocabulary for every service and controller.
2. **`module.ts`** – The entry-point manifest shows how routes, jobs, events, and cross-module hooks are wired together in one place, giving you the module's shape before diving into any single flow.

## Files
- `src/modules/returns/asyncapi.webhooks.yaml` — AsyncAPI **fragment** (not a standalone document) declaring the three webhook events the returns module publishes: `return.requested`, `return.received`, and `return.closed`. A bundler script merges this fragment into the global `webhooks/asyncapi.yaml` only while the returns module is registered, so deleting the module removes these events from the contract automatically.
- `src/modules/returns/audit.ts` — Declares the set of audit action strings the returns module emits and registers them into the shared `AuditActionMap` type via module augmentation, giving every returns service a single, type-safe vocabulary of audit events.
- `src/modules/returns/authorization.yaml` — Declarative authorization policy for the **returns** module. It defines which actions (read, update, receive) may be performed on the `Return` subject, at `tenant` scope, and groups them into reusable permission sets that roles or scopes can be assigned.
- `src/modules/returns/config.ts` — Defines the retention window (in days) for free-text fields on returns. Follows the read-per-call pattern established by `orders/config.ts` so that tests can override the value case-by-case without mutating module state.
- `src/modules/returns/controllers/get-return-options.ts` — Controller for `GET /returns/options?orderId=`. Given an order ID, it asks the return service what the order can still send back and cancel (with the refund each cancel would owe), then serializes that into a JSON response. The server computes the options; the client only displays them.
- `src/modules/returns/controllers/get-return.ts` — Controller for `GET /returns/:id`. Resolves a single return for the authenticated caller, records a staff-read audit event, and returns the return payload. A return belonging to another buyer is indistinguishable from a missing one (both yield 404).
- `src/modules/returns/controllers/get-returns.ts` — Controller for `GET /returns` that returns a paginated list of returns. Staff callers see every return; all other callers see only returns on their own orders. The scoping decision lives in the service (derived from the caller's auth context), never from a query parameter.
- `src/modules/returns/controllers/post-return-cancel.ts` — Controller handler for `POST /returns/:id/cancel`, which lets staff cancel an approved return whose goods never arrived. It validates the ID and optional body, delegates to the return service, and responds with 200 and the updated return entity (in its `canceled` state).
- `src/modules/returns/controllers/post-return-close.ts` — Handler for `POST /returns/:id/close`, the endpoint a staff member uses to close a received return by hand. It validates the path id and optional note, delegates to the return service, and replies `200` with the updated `Return` (status now `closed`).
- `src/modules/returns/controllers/post-return-decision.ts` — Thin Express handlers for the two staff-facing decision actions on a return request: **approve** (`POST /returns/:id/approve`) and **decline** (`POST /returns/:id/decline`). Each validates the route id (and, for decline, the request body), delegates to `returnService`, and responds with HTTP 200 carrying the updated `Return` object enriched with action metadata.
- `src/modules/returns/controllers/post-return-proof.ts` — HTTP controller for `POST /returns/:id/proof-of-sending`. A staff-facing endpoint that records the carrier's proof of sending against an approved return. Responds `200` with the return object (still in `approved` status), augmented with caller-specific actions.
- `src/modules/returns/controllers/post-return-receive.ts` — HTTP controller for `POST /returns/:id/receive`. Validates the incoming request, delegates to the returns service to put units back on sale and refund the customer, then responds with the updated `Return` entity (status `closed` on successful refund, `received` when a provider-refused refund is pending a sweep retry).
- `src/modules/returns/controllers/post-return.ts` — HTTP handler for `POST /returns`. Opens a return record and responds 201 with a `Location` header. The same endpoint doubles as the EU withdrawal button (distinguished by `reason: withdrawal` in the body). It is a thin controller: it validates/parses the request, delegates to the return service, and formats the HTTP response.
- `src/modules/returns/domain/accounting.ts` — Pure domain logic that answers one question: *what has the order already settled?* It tallies which units are accounted for (canceled before shipping, or physically back) and how much delivery has already been refunded, so that a service settling a new return or cancellation can determine whether it takes the **last** unit and whether a delivery refund is still owed. Keeping the rule here, free of I/O, makes it unit-testable without a database.
- `src/modules/returns/domain/index.ts` — Barrel export for the returns **domain layer**. It re-exports every public symbol (values and types) from the individual domain submodules so that consumers can import from a single path (`returns/domain`) without reaching into each file. The module doc-comment asserts this layer contains pure business rules only — no Express, Mongoose, or other tier dependencies — a constraint enforced by lint.
- `src/modules/returns/domain/lifecycle.ts` — Defines the return-state machine: which status each move may start from and where it lands. The table doubles as the guard for the conditional writes in `repository.ts` (`claimStatus`), making concurrent approvals/declines a database-level race where exactly one wins.
- `src/modules/returns/domain/quantities.ts` — Pure, database-free arithmetic for "how much of an order can still come back." It defines the quantity types, the summation/subtraction helpers, and the validation rule (`checkRequestedLines`) that decides which lines a return actually freezes, so the eligibility logic is unit-testable without a data layer.
- `src/modules/returns/domain/reasons.ts` — Pure domain logic that answers one question: *which return reasons is a buyer still allowed to name right now?* It encodes the two statutory clocks (the 30-day withdrawal window and the 2-year guarantee of conformity) without depending on any service, transport, or storage layer.
- `src/modules/returns/domain/refund-amount.ts` — Pure arithmetic (integer minor units via `Money`) that computes what a customer is owed when a return is received or a fulfillment order is canceled. Keeps the quoted figure and the `payments` figure identical by avoiding any float math. Encodes the shipping-refund rules tied to Art. 13(2): only the entity that takes the last unit of the order refunds delivery, and the amount depends on the reason.
- `src/modules/returns/domain/refund-due.ts` — Pure domain logic that determines when a return's refund is legally due and under which rule. Encodes the deadlines set by EU Directive 2011/83/EU Art. 13 (14-day withdrawal) and Directive 2019/771 Art. 16(3)(b) (defective/wrong item), per Commission guidance 2021/C 525/01 §5.5.3. No I/O, no module access — it receives already-resolved dates and returns a stamp or `undefined`.
- `src/modules/returns/domain/restock.ts` — Pure domain rule that decides how many units of each returned line go back on sale when goods are received. Staff can override the default (full quantity) per line—e.g. set a broken unit to 0. Keeping this as a stateless function makes the "broken unit never reaches the shelf" invariant testable without a database.
- `src/modules/returns/domain/statement.ts` — Defines the "statement" — the date (`requestedAt`) and channel (`statedVia`) recorded when a buyer or staff member makes a return request or withdrawal. Provides a single pure validation function (`checkStatement`) that enforces *who* may supply each field and whether the supplied date is plausible, encoding the rule that timing is judged on the day the message was **sent**, not read (CRD Art. 11(2)).
- `src/modules/returns/domain/status-projection.ts` — Computes the single projected return status displayed beside an order's own status. It is a pure function over a collection of returns, so every status boundary is testable without a database or external state.
- `src/modules/returns/emails.ts` — Resolves the copy for return and withdrawal notice emails into finished, language-specific text. It takes a notice kind, the recipient's locale, and contextual data, then returns a fully-rendered `EmailContent` object ready for the mailer adapter. The file follows the same convention as `@modules/account/emails`: the language is an explicit argument, the output is final text, and downstream rendering resolves nothing further.
- `src/modules/returns/events.ts` — Declares the domain events emitted by the returns module by augmenting the kernel's `DomainEventMap` interface (module augmentation rather than a central list, following the pattern in `modules/orders/events.ts`). It also exports the string-key constants for each event so other modules can reference them without re-typing the literal.
- `src/modules/returns/index.ts` — Public barrel (re-export) for the returns module. It is the **only** import surface a sibling module is allowed to use, enforcing the DDD module-boundary rule described in `docs/theory/strategic-ddd.md` §5. Internal plumbing (`returnRepository`, the model's runtime) is deliberately excluded; consumers interact with returns exclusively through the service layer exposed here.
- `src/modules/returns/jobs.ts` — Declares the scheduled jobs owned by the `returns` module. Currently exposes a single job — the free-text scrub — as a `JobDeclaration` array that the runtime scheduler can pick up.
- `src/modules/returns/model.ts` — Defines the Mongoose schema, compiled model, and TypeScript interfaces for the **Return** document (a request to send goods back) and a **ReturnOrderLock** helper document. This file is purely declarative: it owns the data shape, indexes, and serialization contract, while all queries live in `repository.ts` and business rules in `services/`.
- `src/modules/returns/module.ts` — Entry point (module manifest) for the **returns** module — handling customer goods returns and the EU 14-day withdrawal ("cooling-off") flow. It wires together the module's routes, jobs, config, rate limits, public webhook events, domain-event subscriptions, and personal-data collection into a single `AppModule` object consumed by the kernel.
- `src/modules/returns/module.yaml` — Module manifest for the **returns** subdomain (shop group). Declares the module's metadata, cross-module dependencies, a write-path rate limit, and a scheduled cleanup job. It exists so the platform can wire up cross-cutting concerns (auth flags, delivery state, refunds, etc.) without each handler re-declaring them.
- `src/modules/returns/openapi.yaml` — OpenAPI 3.1.0 contract for the **returns** module: it defines the REST API surface for opening, listing, and managing product returns, EU contract withdrawals, and cancellations, along with the module's error-code vocabulary and its slice of the account data export. It is the single source of truth for the HTTP interface other code (clients, tests, documentation generators) consumes.
- `src/modules/returns/presenter.ts` — Transforms a stored `ReturnDocument` into the wire-contract shapes (`Return`, `ReturnListItem`). It sits between the model layer and the API types, handling the `toJSON()` id/date remap and selecting the field subset each endpoint exposes. The read service (`services/read.ts`) builds on this to append the caller-specific `actions`.
- `src/modules/returns/rate-limits.ts` — Declares the Returns module's rate-limit budget for `POST /returns` and converts it into a ready-to-use Express middleware. It is the module-local "source of truth" for how many return-openings a single authenticated account may perform per window.
- `src/modules/returns/repository.ts` — Persistence layer for the Returns module. It exposes the generic CRUD surface (delegated to `createRepository`) plus the domain-specific operations the service layer needs: atomic status transitions, per-order reads, transactional locking, GDPR text scrubbing, and a stats aggregation. It exists so that services never touch Mongoose directly and so the two concurrency-sensitive primitives (`claimStatus`, `claimProof`) live in one place.
- `src/modules/returns/routes.ts` — Express route table for the returns module. Wires every HTTP endpoint (create, read, approve, decline, receive, proof, close, cancel) to its controller, layers the shared authentication/authorization middleware, and applies route-specific guards (rate limiting, idempotency, conditional step-up, no-cache) in a deliberate order that prevents replay and fail-open edge cases.
- `src/modules/returns/services/cancel-remainder.ts` — Implements the "remainder cancel" flow: canceling the unshipped lines of a specific fulfillment order as a `Return` of `kind: 'cancellation'` that is **closed at creation time**. It exists because a whole-order cancel is impossible once anything has shipped; the remainder must be unwound one fulfillment order at a time, moving money, stock, and the shipping rule atomically. The `returns` module owns this because it is the only module that already reaches all four concerns (delivery, inventory, payments, order).
- `src/modules/returns/services/cancel-right.ts` — Single source of truth for *who may cancel a remainder* (the unshipped portion of an order). Both the enforcement gate (`cancel-remainder.ts`) and the UI-facing options read (`options.ts`) call this one function so the button never promises what the door would refuse.
- `src/modules/returns/services/cancel.ts` — Implements the `approved → canceled` lifecycle transition for an approved return whose goods were never sent. It is a staff-only, bookkeeping-only action (no money movement, no stock adjustment, no outbound event, no mail) that releases the return's held units so the order can progress past `in_progress`.
- `src/modules/returns/services/cancellation-refund.ts` — Computes the refund breakdown owed when cancelling a fulfillment order's remainder. It exists as a single shared computation for the two callers that need the same number: the cancel operation itself (inside its transaction) and `GET /returns/options` (which quotes the refund before anything is written).
- `src/modules/returns/services/close.ts` — Performs the `received → closed` status transition on a return once its refund has settled, or when staff closes one manually without a refund. Two automated paths (same-request refund settlement and the async `PAYMENT_REFUNDED` listener) can race; the atomic status claim ensures only one wins and the other is a no-op.
- `src/modules/returns/services/create.ts` — Opens a return for an order, or a withdrawal when the order has not yet been dispatched. It is the single entry point for both buyer-initiated and staff-initiated openings. The file decides which path to take (withdrawal vs. return + cancellation of unshipped lines), validates requested quantities against what actually shipped and is not already being returned, writes the return document inside a locked transaction, and enqueues the outbox messages that trigger downstream side-effects (mails, status sync).
- `src/modules/returns/services/deadlines.ts` — Converts the two raw deadline dates stored on an order (`withdrawUntil`, `conformityUntil`) into the normalised `FrozenDeadlines` shape that the reason-evaluation logic (`reasonsOpenAt`, `isReasonOpen`) expects. The key transformation: the withdrawal deadline is advanced by one "silent day" via `withdrawalClosesAt` so the returned value is the instant a withdrawal actually stops being accepted, not the last calendar day the buyer was told.
- `src/modules/returns/services/decide.ts` — Implements the two staff actions on a pending return request — **approve** and **decline** — as a single conditional (optimistic-lock) write. Two staff members racing on the same request cannot both succeed; the loser receives a 409. Withdrawals never pass through this file because they open already approved.
- `src/modules/returns/services/digest.ts` — Produces the two headline counts the daily staff digest needs from the returns module: how many requests are still undecided past their allowed waiting period, and how many approved returns are overdue for the buyer's goods. It returns bare numbers, not records.
- `src/modules/returns/services/index.ts` — Barrel/facade for the returns domain. It pulls in every operation a controller might need (create, decide, receive, cancel, close, notify, stats, retention, export) from its sibling modules and bundles them into a single `returnService` object, giving callers one import point instead of a dozen file paths.
- `src/modules/returns/services/notify.ts` — Event listeners that email the customer at each return lifecycle stage—requested, decided, closed. Each listener loads the return, picks the right notice kind and copy, and enqueues a localized email via the buyer lookup in the orders module. All failures are logged and swallowed so that a mail outage never blocks or replays the underlying event.
- `src/modules/returns/services/options.ts` — Computes, in one authoritative pass, what an order can still return and what it can still cancel. By centralising the quantity math, refund calculation, and reason-deadline checks here, no client (or other service) needs to re-derive returnable/cancelable state.
- `src/modules/returns/services/outcome.ts` — Shared outcome builders for the two paths that write a return — `create.ts` (goods coming back) and `cancel-remainder.ts` (canceling an unshipped remainder). Centralizing the 201 success, all 4xx/5xx refusals, outbox-event writes, and the audit row here lets both callers import from one place without importing each other.
- `src/modules/returns/services/ownership.ts` — Answers a single gatekeeping question for the returns module: *who may open a return on a given order?* Both `createReturn` and `getReturn` call into this file before performing any return-specific work, so the authorization logic lives in one place rather than being duplicated across service files.
- `src/modules/returns/services/personal-data.ts` — Provides the `personalData` contribution for the returns module in the `POST /account/export` GDPR data-export flow. It collects every return linked to a user's orders and shapes them into a customer-facing export record. There is intentionally no `erase` function here: a return is keyed by `orderId` (not `userId`), so once `orders` runs its own `detachUserId`, the link is already broken. Returns are legal/accounting records of a consumer-rights act, falling under the Art. 17(3)(b)/(e) retention exemption (same rationale as `invoicing`).
- `src/modules/returns/services/projection.ts` — Keeps the `orders` module's `returnStatus` field in step with the returns attached to an order. Because `orders` cannot import this module, this file acts as the bridge: after any state-changing return operation, it reads the order's returns, computes the correct status word, and reports it back through the orders module's own public API (`orderService.markReturnStatus`).
- `src/modules/returns/services/proof.ts` — Records the buyer's proof of sending (carrier document: date, carrier name, tracking reference) against an approved return. For a withdrawal return it also opens and dispatches the refund within the same flow; for a defective/wrong-item return it only stamps the proof, deferring the remedy to receipt. Implements the one-time, idempotency-guarded write that transitions the return toward completion per Directive 2011/83/EU Art. 13(3).
- `src/modules/returns/services/read.ts` — Read-side service for the returns domain. It answers "what can this caller see?" and "what can this caller do with each row?" by combining ability checks, order-ownership scoping, and the return lifecycle state. It is the single place that projects a `ReturnDocument` into a wire-ready `Return` or `ReturnListItem` with caller-specific actions attached.
- `src/modules/returns/services/receive.ts` — Handles the "goods arriving" step of a return: transitions the status `approved → received`, restocks the units the staff put back on sale, and records the buyer's remedy (refund, replace, or repair) — all inside a single conditional transaction. It intentionally keeps two facts on separate clocks: the parcel receipt (one atomic move + restock) and the money movement (refund record opened in-transaction, provider call deferred to after commit and retried by a payment sweep).
- `src/modules/returns/services/refund-due.ts` — Computes the refund deadline to stamp on a return at the moment it opens. It is a thin service wrapper around the pure domain rule table (`refundDueByOf`) that injects the one piece of context a domain file cannot reach: the shop's timezone, needed to calculate withdrawal deadlines on the shop's calendar.
- `src/modules/returns/services/retention.ts` — Implements the free-text retention sweep for returns: after a return has been quiet (no updates) for longer than a configured number of days, its free-text fields are wiped while the row itself remains as a legal record. Exposes a single function consumed by the `reap:returns` job.
- `src/modules/returns/services/stats.ts` — Aggregation queries that report how many units were received back (returned) within a time window, broken down by currency-bucket, by product, or by bucket for a single product. All three functions delegate to the `sumReceived` repository method with a different MongoDB group-by pipeline.
- `src/modules/returns/services/withdraw.ts` — Implements the buyer's Art. 11a withdrawal before dispatch: cancels the order (full refund, stock release), writes a `Return` document closed at birth as the dated proof of withdrawal, and enqueues the acknowledgement outbox events. When the shop has already started on made-to-order goods, it cancels only the eligible shipment groups instead. A single transaction guarantees the cancel and the record land atomically.
- `src/modules/returns/tests/contract/api.contract.test.ts` — Contract tests for the `/returns` API executed over real HTTP. Every response is automatically validated against the shared spec (`@tests/contract`). The suite exists to pin that each contractual branch is reachable and shaped correctly: the `201 + Location` for new returns, the withdrawal-before-dispatch path that yields a closed return, staff approve/decline decisions, and the specific refusal codes a client can act on (422, 409, 404).
- `src/modules/returns/tests/factories.ts` — Provides a minimal return-document factory for integration tests *outside* the returns module (e.g. shop-tasks tests) that only need to seed rows for a "count by status and age" query. It deliberately bypasses the service layer and validation so tests can insert bare documents without setting up orders, lines, or money.
- `src/modules/returns/tests/integration/cancel-remainder.test.ts` — Integration test for the "cancel remainder" flow: a buyer cancels the unshipped portion of a partially-shipped order (a Return of `kind: 'cancellation'`). Verifies that stock restoration, refund issuance, fulfillment-order closure, and order-status transitions all commit together, and that edge-case rejections (wrong reason, explicit lines, missing fulfillment order) are enforced.
- `src/modules/returns/tests/integration/cancel.test.ts` — Integration tests for the `approved → canceled` return transition. They verify that canceling an approved return is purely bookkeeping: no refunds, no stock movement, no domain events, and no outbound email. They also pin down which states reject cancel, and that post-cancel the return is inert (cannot be received or closed).
- `src/modules/returns/tests/integration/close-by-hand.test.ts` — Integration tests for `returnService.closeReturnByHand`, the manual-close path for a `received` return whose refund was settled outside the app (e.g., cash given at the counter).
