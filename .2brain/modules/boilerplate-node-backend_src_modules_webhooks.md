# src/modules/webhooks/

## Purpose

Outbound webhook delivery. The module manages tenant subscriptions to the platform's event catalogue, signs and POSTs events to subscriber URLs, tracks every delivery attempt (success, retry, exhaustion), enforces a shared retry/backoff policy with auto-disable, and exposes an admin API for subscription CRUD, secret-ring rotation, delivery inspection, and synchronous replay.

## Key parts

- **HTTP surface** — `routes.ts` wires the Express router under `/webhooks`; `controllers/` holds one thin handler per route (subscription CRUD, enable/disable, secret rotation, delivery list/get, replay, event catalogue). `presenters.ts` shapes Mongoose docs into the wire payload.
- **Service layer** — `services/` (behind the `webhooksService` barrel in `services/index.ts`) contains the business logic: `attempt.ts` (sign + POST + record outcome), `publish.ts` (event fan-out), `sweep.ts` (retry re-queue), `enqueue.ts` (single queue-publish helper), `deliveries.ts` (log read + replay), `catalog.ts` (event catalogue built from sibling modules' fragments), `reencrypt.ts` (key-ring migration), `actions.ts` (per-caller permission flags).
- **Domain rules** — `domain/backoff.ts` (retry schedule & auto-disable threshold, generated from `rules.yaml`) and `domain/event-filter.ts` (subscription filter matching). Pure, side-effect-free, shared by the worker, the sweep job, and tests.
- **Data layer** — `model.ts` declares the two Mongoose collections (`webhooksubscriptions`, `webhookdeliveries`) with indexes and `toJSON` transforms. `repository.ts` adds domain-specific queries: atomic lease claims, failure-streak bookkeeping, tenant-scoped lookups.
- **Secrets** — `secrets.ts` implements the encrypted secret-ring lifecycle (mint, encrypt/decrypt, live vs. retiring determination, drop). Plaintext exists only transiently.
- **Configuration & contracts** — `config.ts` (env-derived settings), `rules.yaml` + `rules.schema.ts` (retry policy, codegen for `rules.generated.ts`), `openapi.yaml` (REST contract), `asyncapi.yaml` / `asyncapi.internal.yaml` (event catalogue + private delivery queue).
- **Module wiring** — `module.ts` (manifest: subscribes to sibling events, declares the queue consumer), `index.ts` (public barrel), `events.ts` (internal domain events), `jobs.ts` (retry-sweep job declaration), `metrics.ts` (fleet-level delivery alerts), `audit.ts` (audit-action registration), `authorization.yaml` (permission policy).

## How it connects

- **Sibling modules (`account`, `notifications`, `users`)** — `module.ts` subscribes to their `publicEvents` via the shared domain-event bus. The webhooks module never imports them directly; the edge is reversed (they emit, it consumes). Removing this module removes the subscriber, not the emitter.
- **`shared/` / `src/infrastructure/adapters/`** — Provides the RabbitMQ adapter (queue publish/consume), the metrics registry, the audit-action map, and the repository factory that `repository.ts` extends.
- **`scenarios/` and `scripts/contracts/`** — Exercise the public API surface (subscription lifecycle, delivery replay, event catalogue) in integration tests and contract checks against `openapi.yaml`.
- **`/` (repository root)** — The AsyncAPI bundler reads `asyncapi.yaml` + `asyncapi.internal.yaml` to produce the merged public and backend specs; the codegen step reads `rules.yaml` to emit `rules.generated.ts` consumed by both the Node and PHP runtimes.

## Where to start

1. **`module.ts`** — Short manifest that shows what the module subscribes to, what queue it owns, and the one job it schedules. Reading it first gives you the module's external shape in under a minute.
2. **`services/attempt.ts`** — The heart of the system: signing, the HTTP POST, and the three outcome branches (success / retry / exhausted). Understanding this file makes the sweep, replay, and enqueue helpers fall into place naturally.

## Files
- `src/modules/webhooks/asyncapi.internal.yaml` — Declares the webhooks module's private RabbitMQ delivery queue (`worker.webhook.deliver`) as an AsyncAPI fragment. It exists separately from the module's public event catalogue (`./asyncapi.yaml`) so that the queue is included in the backend-bundled spec but never leaks into the frontend-facing `asyncapi.public.yaml`.
- `src/modules/webhooks/asyncapi.yaml` — The shared (module-agnostic) half of the public webhook event catalogue. It defines the single variable `subscriberEndpoint` server and the cross-event schemas (`WebhookHeaders` plus four copied scalar types) that every webhook delivery carries. The bundler merges this document with per-module channel fragments into the final `asyncapi.yaml` and `asyncapi.public.yaml`. It exists so the catalogue a subscriber reads at `GET /webhooks/events` stays in lockstep with the events that can actually fire.
- `src/modules/webhooks/audit.ts` — Declares the audit-action vocabulary for all webhook subscription and delivery mutations, and registers those actions into the app-wide `AuditActionMap` via TypeScript module augmentation. Every write to a subscription (including non-destructive ones like enabling or rotating a secret) is audited because the stored URL and signing secret are the kind of data a later data-protection question targets.
- `src/modules/webhooks/authorization.yaml` — Declarative authorization policy for the `webhooks` module. It defines which actions a tenant may perform on `WebhookSubscription` resources and groups those actions into reusable permission sets, so that downstream enforcement (middleware, API gates, etc.) can check access without hard-coding rules.
- `src/modules/webhooks/config.ts` — Defines the environment-derived configuration surface for the webhooks module (encryption key ring, per-tenant subscription cap, secret overlap window, delivery retention). Uses the read-per-call `defineConfig` pattern (same as `inventory/config.ts`) so tests can vary values per case without re-imports; a deployment changes a value via env var + restart.
- `src/modules/webhooks/controllers/delete-subscription-secret.ts` — Controller handler for `DELETE /webhooks/subscriptions/:id/secrets/:secretId`. It removes a single secret from a subscription's signing ring (the "other half" of a secret rotation) and returns `204` on success. It exists to give the HTTP layer a thin, tenant-scoped entry point into the webhooks service's ring-management logic.
- `src/modules/webhooks/controllers/delete-subscription.ts` — Controller handler for `DELETE /webhooks/subscriptions/:id`. It permanently removes a webhook subscription (its delivery log remains untouched). It is hand-written rather than generated by `createDeleteController` because the webhooks module defines only a single permanent-delete endpoint, not the soft/hard delete triplet that factory targets.
- `src/modules/webhooks/controllers/get-deliveries.ts` — Thin HTTP controller for `GET /webhooks/deliveries`. It validates query parameters, extracts tenant context from the request, and delegates to `webhooksService.listDeliveries`. Exists to keep route wiring (in `routes.ts`) free of validation and service-call logic.
- `src/modules/webhooks/controllers/get-delivery.ts` — HTTP controller for the `GET /webhooks/deliveries/:id` route. It extracts and validates the delivery ID, delegates the fetch to the webhooks service scoped to the caller's tenant, and shapes the response. It exists to keep the route handler thin and to centralise the "not found / not yours" security contract in one place.
- `src/modules/webhooks/controllers/get-events.ts` — Express controller that serves `GET /webhooks/events`, returning the catalogue of all events a subscription may filter on, annotated with whether the authenticated caller holds the read rule needed to subscribe to each one.
- `src/modules/webhooks/controllers/get-subscription.ts` — Defines the single GET-by-ID handler for webhook subscriptions (`GET /webhooks/subscriptions/:id`). It is a thin wrapper that delegates to the webhooks service while enforcing tenant isolation at the HTTP surface.
- `src/modules/webhooks/controllers/get-subscriptions.ts` — HTTP controller for `GET /webhooks/subscriptions`. It exposes the tenant's webhook subscriptions as a paginated, filterable list (newest-first by default) while guaranteeing that no secret material is returned. It delegates the actual data-fetching to the webhooks service and relies on the shared list-controller factory for pagination, input decoding, and response shaping.
- `src/modules/webhooks/controllers/post-delivery-replay.ts` — HTTP controller for `POST /webhooks/deliveries/:id/replay`. It re-sends a previously stored webhook delivery synchronously, targeting the subscription's *current* URL and secret ring rather than the original. Documented as the most-requested support action in the webhooks module.
- `src/modules/webhooks/controllers/post-subscription-disable.ts` — Controller handler for `POST /webhooks/subscriptions/:id/disable`. Extracts the subscription ID and tenant context from the request, delegates to the webhooks service to pause the subscription, and formats the response as an RFC 9110 §8.8.3 resource (with ETag and Link). Returns 409 Conflict if the subscription is already paused.
- `src/modules/webhooks/controllers/post-subscription-enable.ts` — Controller handler for `POST /webhooks/subscriptions/:id/enable`. Re-enables a previously disabled webhook subscription (from either "off" state). Returns **409** if the subscription is already active.
- `src/modules/webhooks/controllers/post-subscription-secret.ts` — HTTP controller for `POST /webhooks/subscriptions/:id/secrets`. It mints a new ring secret for a webhook subscription and returns the plaintext secret exactly once in the response body. The previous secret remains active until explicitly revoked via `DELETE .../secrets/:secretId`.
- `src/modules/webhooks/controllers/post-subscription.ts` — HTTP controller for `POST /webhooks/subscriptions`. Parses and validates the incoming body, delegates subscription creation to the webhooks service, and emits a `201 Created` response carrying the new subscription plus its one-time secret.
- `src/modules/webhooks/controllers/update-subscription.ts` — Builds the `PUT /webhooks/subscriptions/:id` (full replace) and `PATCH /webhooks/subscriptions/:id` (partial merge) handlers for webhook subscriptions. Both verbs share a single `createUpdateController` factory call; neither touches the secret ring or the enabled/disabled flag (those live on dedicated action routes).
- `src/modules/webhooks/domain/backoff.ts` — Defines the retry backoff schedule and the auto-disable threshold as pure, side-effect-free rules so the sweep job, the delivery worker, and unit tests all share one canonical table of delays and limits. All numeric values are pulled from a generated artifact (`rules.generated`) that is derived from `rules.yaml`; this file adds no hardcoded constants.
- `src/modules/webhooks/domain/event-filter.ts` — Pure decision function that answers a single question for the webhook publish pipeline: does a given event type match a subscription's `eventTypes` filter? It exists to keep the matching rule (exact membership or the `'*'` wildcard) in one place, decoupled from the I/O concerns of actually delivering webhooks.
- `src/modules/webhooks/domain/index.ts` — Barrel file for the webhooks domain layer. It flat-re-exports the pure business rules (retry/backoff logic and event matching) from `backoff.ts` and `event-filter.ts` so that consumers can import domain rules from a single, stable entry point without reaching into individual files.
- `src/modules/webhooks/events.ts` — Declares the webhooks module's domain events by augmenting the kernel's `DomainEventMap` interface. These events represent internal facts emitted to sibling modules (e.g. `notifications`); they are **not** webhook deliveries and never travel over an AsyncAPI channel.
- `src/modules/webhooks/index.ts` — Public barrel (module façade) for the webhooks module. By strategic-DDD convention (`docs/theory/strategic-ddd.md` §5), this file is the **only** import surface available to sibling modules. It re-exports the public API from `services`, `domain`, and `events`, plus the type definitions from `model`, while deliberately keeping `module.ts` (manifest entry) and `secrets.ts` internal.
- `src/modules/webhooks/jobs.ts` — Declares the scheduled jobs owned by the `webhooks` module. Currently owns a single job — the webhook delivery retry sweep — by pairing a generated job descriptor with its handler function and exporting the result as a `JobDeclaration[]` for the kernel to schedule.
- `src/modules/webhooks/metrics.ts` — Defines and registers the webhooks module's domain metrics on the shared `metricsRegistry`. These metrics exist to power two fleet-wide alerts (`WebhookDeliveriesFailingEverywhere`, `WebhookRetriesStalled`) that detect our-side outages in the delivery path, as distinct from per-subscription auto-disable events.
- `src/modules/webhooks/model.ts` — Defines the two Mongoose collections the webhooks module owns — `webhooksubscriptions` (a tenant's standing subscription to a slice of the event catalogue) and `webhookdeliveries` (one row per event × subscription, tracking attempts to success, exhaustion, or a never-notified subscriber). It declares the schemas, indexes, serialization transforms, and the `model()` entrypoints that every other file in the module reads and writes against.
- `src/modules/webhooks/module.ts` — Module manifest for the **outbound webhooks** feature: subscription management, the delivery log, and the admin API. It subscribes to every `publicEvents` entry declared by other modules via the domain-event bus (a reverse edge — this module never imports `orders`/`payments`), and it declares its own queue consumer for webhook delivery so that removing this module is sufficient to stop the queue from mattering.
- `src/modules/webhooks/openapi.yaml` — OpenAPI 3.1.0 contract for the **Webhooks** module. It defines the public REST surface for managing webhook subscriptions (CRUD, enable/disable, secret rotation), the delivery log, replay, and the event catalogue. It is the single source of truth for endpoint shapes, auth scopes, and error semantics that API clients and the bundler consume.
- `src/modules/webhooks/presenters.ts` — Transforms Mongoose documents for the two webhook resources (subscription and delivery) into their wire/API shapes. Each presenter applies the model's `toJSON()` transform (e.g. `_id` → `id`, ring collapse to `secretIds`, derived `enabled` field) and attaches the caller-supplied `actions` object, producing the shape the HTTP layer returns.
- `src/modules/webhooks/repository.ts` — Provides the Mongo data-access layer for both webhook collections (subscriptions and deliveries). Beyond the generic CRUD from the shared `createRepository` factory, it defines the domain-specific queries that have no generic shape: atomic lease-based claims (`claimPending`, `claimForReplay`), failure-streak bookkeeping, tenant-scoped lookups, batch enabled-id checks, and the auto-disable guard.
- `src/modules/webhooks/routes.ts` — Defines the Express router for the `/webhooks` admin surface. It wires every subscription CRUD action, the delivery log, delivery replay, and the public event catalogue to their respective controller handlers, each gated behind a fine-grained `requirePermission` check.
- `src/modules/webhooks/rules.schema.ts` — Defines the Zod schema for the `rules.yaml` webhook configuration file (retry delays and auto-disable thresholds) and declares the `GenerateSpec` that drives `npm run regenerate` to produce `rules.generated.ts`. It is the single source of truth for both validation and codegen of the shared rules data that the PHP twin consumes.
- `src/modules/webhooks/rules.yaml` — Single source of truth for webhook-delivery retry and auto-disable thresholds. It is plain YAML consumed by a build step (`npm run regenerate` → `rules.generated.ts`) and copied into the PHP counterpart, so both runtimes enforce identical delivery policy without hand-syncing numbers.
- `src/modules/webhooks/secrets.ts` — Implements the secret-ring lifecycle for webhook subscriptions: minting, encrypting/decrypting at rest, determining which entries are still live or retiring, and dropping entries. Plaintext secrets exist only transiently (mint response, signing a delivery) and are never persisted in the subscription document.
- `src/modules/webhooks/services/actions.ts` — Computes the per-caller permission flags ("actions") that the API returns alongside each webhook subscription and delivery. By centralising the rules here, controllers and services simply read a boolean off the payload instead of re-deriving capability checks at the edge.
- `src/modules/webhooks/services/attempt.ts` — Core delivery-attempt logic for webhooks: signs the payload, performs the HTTP POST, and records the outcome (success, retry-scheduled failure, or exhausted chain) on the delivery row and the parent subscription's failure streak. Shared by the queued worker path (`processDeliveryJob`) and the admin synchronous replay path (`deliveries.ts`) so that "what recording an outcome means" cannot drift between the two.
- `src/modules/webhooks/services/catalog.ts` — Builds a static, in-memory event catalogue from each registered module's `asyncapi.webhooks.yaml` fragment, then answers three questions: which events exist, which events a given caller may subscribe to, and which requested event names are unknown. Centralising the source so the public endpoint, the subscribe permission check, and the generated contract can never drift.
- `src/modules/webhooks/services/deliveries.ts` — Service layer for the webhook delivery log: paged **list**, single **get**, and synchronous **replay** (re-send). It sits between the HTTP handlers (which supply filters and tenant context) and the repositories/attempt engine, shaping responses with presenters, action hints, and i18n'd error payloads.
- `src/modules/webhooks/services/enqueue.ts` — Single shared helper that publishes a delivery row's next attempt onto the worker queue. It exists so that both the fast-path publisher (`publish.ts`) and the retry sweep (`sweep.ts`) use one identical enqueue call rather than duplicating the payload shape and channel selection. Implements the Claim Check EIP: the message carries only the row's `deliveryId`; the row itself remains the source of truth for attempt details.
- `src/modules/webhooks/services/index.ts` — Barrel export for the webhooks `services/` directory. It aggregates the individual service submodules (subscriptions, deliveries, publish, sweep, reencrypt, attempt, catalog) behind a single `webhooksService` object so that controllers and other module code have one stable import path rather than reaching into seven sibling files directly.
- `src/modules/webhooks/services/publish.ts` — Domain-event subscriber for webhooks. It registers one listener per `PublicEventTarget` declared in each module's manifest (resolved via `kernel/registry.ts`), projects each incoming domain event into a public event, matches it against every enabled subscription's filter, and fans out — creating one delivery row and one queue message per match. It runs once at boot from `../module.ts`'s `onRegistered` hook, after all modules are registered.
- `src/modules/webhooks/services/read-refusal.ts` — Centralised 403 refusal response for the "caller may not read that event" case. Shared by every webhook write that hands an event stream to a receiver (create, update, secret rotation) and by replay, so the error shape, code, and message live in exactly one place.
- `src/modules/webhooks/services/reencrypt.ts` — Service-layer entry point that re-encrypts every webhook subscription's signing secrets onto the newest key in the encryption key ring. It exists so the ops script (defined in `@infrastructure/security/reencrypt`) can drive a bulk rotation without touching domain logic directly.
- `src/modules/webhooks/services/subscriptions.ts` — Implements the tenant-scoped CRUD service for webhook subscriptions: list, get-by-id, create (minting the secret ring's first secret), and the validation/authorization pipeline that guards each write (SSRF check, event-type catalogue check, caller read-permission check, subscription cap enforcement with race-safe rollback).
- `src/modules/webhooks/services/sweep.ts` — Per-minute retry sweep for webhook deliveries. It fetches every delivery due for another attempt plus any stranded `in_flight` row whose lease has expired, then dispatches each one — either by publishing to the broker or by sending inline when no broker is available. This is the "degrade, don't drop" fallback that keeps deliveries moving without tying them to an API request.
- `src/modules/webhooks/tests/contract/schema-drift.contract.test.ts` — Guards against silent drift between the `WebhookSubscription` and `WebhookSubscriptionCreated` schemas in the module's `openapi.yaml`. Because JSON Schema (and the orval-generated Zod judge) cannot compose two `additionalProperties: false` siblings via `allOf`, the field list is restated by hand in the second schema; this test is the sole sync mechanism between the two declarations.
- `src/modules/webhooks/tests/contract/webhooks.contract.test.ts` — Contract tests for the `/webhooks` admin API surface (subscription CRUD, delivery log, replay, public event catalogue) that validate runtime responses against the bundled `openapi.yaml`. Exists to catch drift between the OpenAPI spec and actual controller/serializer behavior.
- `src/modules/webhooks/tests/fuzz/webhook-ssrf.fuzz.test.ts` — Fuzz-style tests for `deliverWebhook`'s own SSRF-adjacent behaviours: that the total timeout budget covers DNS resolution, that 3xx redirects are refused rather than followed, that the exempted demo host is still https-only, that non-443 ports are blocked before any connection, and that `durationMs` uses a monotonic clock. It deliberately does **not** re-test the generic SSRF guard (covered by `ssrf-guard.fuzz.test.ts`) because the guard is infrastructure, not webhook-owned.
- `src/modules/webhooks/tests/integration/delivery-log.test.ts` — Integration tests (run against a real database) that verify the webhook delivery log's `list` and `replay` service functions. They confirm tenant isolation on reads, filtering by subscription and status, and that a replay with nothing to re-send returns 404 without mutating the delivery row.
- `src/modules/webhooks/tests/integration/delivery.test.ts` — End-to-end integration suite for the webhook delivery pipeline, exercising the full path against a **real database** and a **real local HTTPS listener** (started/stopped by the test via `tests/support/https-test-server.ts`). It verifies that a delivery arrives with a valid signature, that a 500 triggers a retry chain, that sustained failure auto-disables the subscription, that replay re-sends, and that the delivery log records every step. The SSRF guard is mocked on purpose because the local test server is inherently on loopback, which the guard correctly always refuses.
- `src/modules/webhooks/tests/integration/event-read-rule.test.ts` — Integration test that enforces the **event-read rule**: a caller may not create, mutate, replay, or process a webhook subscription/delivery for an event type their role cannot read. It exercises every mutation surface (create, update, secret rotation, replay, job processing) to confirm the `WEBHOOK_EVENT_READ_REQUIRED` refusal fires and that no partial state is written.
- `src/modules/webhooks/tests/integration/fan-out.test.ts` — Integration test that verifies the webhook fan-out contract: a single public event produces delivery rows **only** for subscriptions that are both ENABLED and MATCHING the event type, and all rows for one event share the same `eventId` (the dedup key consumers rely on). It exists to guard against leaking data to disabled subscribers and to ensure consistent event identity across recipients.
- `src/modules/webhooks/tests/integration/reencrypt.test.ts` — Integration test for the webhook ring-secret key-rotation flow. It verifies that after a `v1`→`v2` key rotation, the `reencrypt` walk rewrites the stored ciphertext to the new version while the secret still decrypts correctly under its entry id. The test reads the raw collection document (below the repository's own decrypt layer) to inspect the version stamp directly.
- `src/modules/webhooks/tests/integration/subscription-lifecycle.test.ts` — Integration test suite for the webhook subscription service, exercised against a real database via `setupTestDb`. It pins the same outcomes as the HTTP-level contract suite but at the service boundary: listing, single-read, create refusal (bad event types, SSRF, tenant cap), and (per the module doc) update, secret ring, and removal. The SSRF guard is replaced with a deterministic stub so no network lookup occurs.
- `src/modules/webhooks/tests/integration/subscriptions.test.ts` — Integration tests for the `create` function in the webhooks subscriptions service. The suite exists because a mocked repository cannot reproduce two writers landing at the same instant; a real database is required to exercise the post-insertion rank re-check that guards the subscription cap race condition. It also verifies that `ownerUserId` is persisted at creation time but excluded from the wire response.
- `src/modules/webhooks/tests/integration/sweep.test.ts` — Integration test for the retry sweep (`sweepDueWebhookDeliveries`) run against a real database with the queue broker and HTTP delivery mocked. It closes the gap left by `delivery.test.ts`, which always invokes `processDeliveryJob` directly and never exercises the sweep's enqueue path. Covers: what the sweep enqueues, lease-expiry republish, the overdue gauge, and the inline-delivery fallback when the broker is unavailable.
- `src/modules/webhooks/tests/unit/backoff.test.ts` — Unit tests for the pure retry-backoff rules defined in the webhooks domain layer. Validates the tiered delay schedule, the exhausted-signal convention, and the dual-threshold auto-disable logic without any external state or timers.
- `src/modules/webhooks/tests/unit/catalog.test.ts` — Unit tests for the webhook event catalog service (`src/modules/webhooks/services/catalog.ts`). Verifies that the catalog lists only events from registered modules, correctly validates unknown event types, enforces per-caller read rules (subscribe permissions), and rejects modules whose channel fragment lacks a usable `x-read-rule`.
- `src/modules/webhooks/tests/unit/event-filter.test.ts` — Unit tests for the `matchesEventFilter` function, verifying that event-name matching against a filter array behaves correctly for exact matches, non-matches, the `ALL_EVENTS` wildcard, and the empty-filter edge case.
- `src/modules/webhooks/tests/unit/module.test.ts` — Unit tests for the webhooks module's boot-time configuration gate and its registration warning. It verifies that `assertModuleConfig` enforces a valid `NODE_WEBHOOK_SECRET_ENCRYPTION_KEY` (present, non-placeholder, 32-byte hex/base64) and that `onRegistered` warns when no message broker is configured.
- `src/modules/webhooks/tests/unit/schema-contract.test.ts` — Unit test that asserts the **declarative contract** of the two Mongoose schemas (`webhookSubscriptionSchema`, `webhookDeliverySchema`) — required paths, defaults, enums, index specs, and index options — by reading the schema objects directly. It exists because structural drift (a dropped `required`, a flipped default, a TTL index detached from the configured retention window) does not change what a *valid* document looks like, so document-based integration tests cannot detect it.
- `src/modules/webhooks/tests/unit/secrets.test.ts` — Unit tests for the secret-ring operations exported by `secrets.ts` — encryption/decryption of individual entries, minting new secrets, resolving the active signing set under the 24-hour overlap window, listing secrets that are retiring, and removing an entry by id. The file deliberately does **not** re-test the underlying crypto or version-mismatch logic; that belongs to `versioned-secret.test.ts`. Here it verifies the ring-level wiring and timing semantics.
- `src/modules/webhooks/tests/unit/webhook-signing.test.ts` — Unit tests that validate `signWebhookPayload` against the **Standard Webhooks** specification's own reference test vector (copied verbatim from the upstream repo) and confirm that the test-fixture verifier (`verifyWebhookSignatureForTest`) round-trips correctly. A byte-for-byte match here asserts interoperability with any conforming consumer, not just internal consistency.
- `src/modules/webhooks/tests/verify-signature.fixture.ts` — Test-only helper that verifies a Standard Webhooks–signed delivery. It is written independently of the production signer (`webhook-signing.ts`) so that a passing round-trip test proves conformance to the [Standard Webhooks spec](https://www.standardwebhooks.com), not merely that one function inverts itself. The codebase only ever *sends* webhooks; this fixture simulates the receiving side for tests.
- `src/modules/webhooks/transport/webhook-delivery.ts` — Implements a single outbound webhook delivery attempt: SSRF-check, payload signing, HTTPS POST, and timeout — all wrapped so the caller (`attempt.ts` worker) always receives a resolved `WebhookDeliveryResult` and never a rejection. It exists as the one function a worker calls to turn a queued delivery into an HTTP request and a loggable outcome.
- `src/modules/webhooks/transport/webhook-signing.ts` — Implements Standard Webhooks (spec: standardwebhooks.com) **signing only**, hand-rolled over `node:crypto` to avoid a dependency for what is ~12 lines of HMAC. Produces the three outgoing headers (`webhook-id`, `webhook-timestamp`, `webhook-signature`) that `webhook-delivery.ts` attaches to each delivery. There is no production verifier in this codebase — the sender never receives signed webhooks.
