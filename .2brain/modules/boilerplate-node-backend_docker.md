# docker/

## Purpose

The `docker/` module contains every artifact needed to build, run, schedule, and verify the project's containerised deployment: the development and production images, MongoDB bootstrap, the backup pipeline, the deployment/rollback script, the cron job table, and the full local observability stack (Prometheus, Grafana, Loki, Tempo, Alertmanager). It is the operational spine of the system—everything that turns source code into a running, monitored, backed-up service.

## Key parts

- **Image builds** — `Dockerfile` (hermetic dev/test image with `mongod` + Chromium baked in) and `Dockerfile.production` (multi-stage, non-root, Alpine-based runtime image with a type-check gate). Both invoke `install-supercronic.mjs` at build time to vendor the job scheduler.
- **Backup pipeline** (`backup/`) — A set of scripts sharing `common.sh`: `entrypoint.sh` (translates env knobs → crontab, then `exec`s supercronic), `backup.sh` (the actual dump + restic + retention run), `maintenance.sh` (weekly prune/check), `server-maintenance.sh` (client-repo retention on the backup server), `drill.sh` (full end-to-end pipeline proof), and `restore-drill.sh` (restore + integrity verification).
- **Deployment & verification** — `deploy.sh` (single-client bring-up/rollback with health checks and auto-revert), `deploy-drill.sh` (four-scenario test of deploy.sh), and `boot-check.sh` (proves the production image starts fail-closed and the `node` user cannot write under `/app/src/`).
- **MongoDB bootstrap** — `mongo-entrypoint.sh` (generates TLS + keyFile on first boot), `mongo-init.js` (creates scoped app/backup users), `mongo-rs-init.sh` (one-shot service that initiates the single-node replica set).
- **Observability** (`observability/`) — Configs and init scripts for Prometheus (local + production), Grafana (datasource & dashboard provisioning), Loki, Tempo, Alertmanager (template + render script + routing tests), the OTel Collector, Umami init, Gatus local config, and `validate-configs.sh` (runs each tool's built-in config check in its own image). Alert rules are split into app-level and infra-level files, each paired with a `promtool` test suite.
- **Scheduling** — `crontab` (generated, never hand-edited) declares every scheduled job for the `cron` service container.

## How it connects

All of `docker/` is consumed by the repository root: the root's `package.json` scripts (`npm run complete`, `npm run backup:drill`, etc.) invoke the Dockerfile, compose files, and shell scripts defined here; the CI workflow at the root runs `boot-check.sh` and the alert-rule test suites; and the source code's runtime configuration (MongoDB connection strings, metrics endpoints) assumes the containers and services this module defines. In short, the root module *builds and tests* the application, while `docker/` *runs, schedules, monitors, and backs up* it.

## Where to start

1. **`docker/Dockerfile.production`** — Reading this top-to-bottom shows the entire build pipeline (type-check gate → dependency strip → non-root user) and reveals which other files in this module are baked in (supercronic, crontab, backup scripts, mongo init).
2. **`docker/backup/common.sh`** — Once you understand the image, this file's `run_job` wrapper, restic helpers, and heartbeat pattern explain how every other backup/scheduling script in the module is structured.

## Files
- `docker/Dockerfile` — Dev/test Docker image that builds a hermetic environment for running the full test suite (`npm run complete`) without external network access. It bakes in a `mongod` binary, Chromium for Puppeteer, and all build-time dependencies so that `docker-compose.test.yml` can execute tests in isolation.
- `docker/Dockerfile.production` — Multi-stage Dockerfile that produces the production image for the API. Unlike the development `docker/Dockerfile` (which bind-mounts the working tree), this image bakes the source in, strips dev dependencies, enforces a type-check gate before an image can exist, and runs as a non-root `node` user. It targets Alpine to keep the runtime footprint small (no `mongod` dependency here).
- `docker/backup/backup.sh` — Executes a single, ordered backup run: a MongoDB dump streamed into restic, the resulting per-collection counts, the uploads and mail-spool directories, and a retention-pruning pass. Scheduled externally by supercronic via `BACKUP_SCHEDULE`; the script itself runs to completion and exits, updating a heartbeat (green/red) via the `run_job` wrapper.
- `docker/backup/common.sh` — Shared library sourced (never executed) by the per-stack backup scripts. Centralises restic environment setup, repository bootstrap, a Gatus heartbeat, a job wrapper that preserves `set -e`, and a small parser for mongodump/mongorestore output. Design rationale lives in `docs/tools/backups.md`.
- `docker/backup/drill.sh` — A single, self-contained end-to-end proof of the entire backup pipeline. Using only `docker run` (no compose, no published ports), it spins up a production-shaped replica-set Mongo, runs real restic backups into a local repository, verifies deduplication, restores into a throwaway instance, checks the Gatus heartbeat, exercises the scheduler, tests a damaged repository, and validates the rclone append-only "second machine" kit. It leaves nothing behind and exits non-zero on any failure. Invoked via `npm run backup:drill`.
- `docker/backup/entrypoint.sh` — Container entrypoint for the `backup` service. It translates a set of environment-variable "knobs" into a crontab file, validates that crontab, then `exec`s into [supercronic](https://github.com/aptible/supercronic) as the long-running PID 1. The design rationale lives in `docs/tools/backups.md#the-knobs`.
- `docker/backup/maintenance.sh` — Weekly repository upkeep job, scheduled by supercronic via `BACKUP_CHECK_SCHEDULE`. It reclaims freed space with `restic prune` (conditional on append-only repos) and verifies data integrity by reading a rotating slice of stored packs, so corruption surfaces weeks before a restore is needed.
- `docker/backup/restore-drill.sh` — End-to-end restore verification script: restores the latest database and files snapshots into a throwaway environment, validates collection counts and file integrity, runs a partial `restic check`, and reports elapsed time as a proxy for worst-case shop downtime. Exits 0 only if every step succeeds. Never touches the live database.
- `docker/backup/server-maintenance.sh` — Scheduled upkeep for the backup server's own disk. For every client repository it runs `restic forget --prune` (applying retention knobs) and `restic check --read-data-subset`. Because the app side can only append to the repository, this script is the **only** place where old snapshots are actually deleted. Triggered by supercronic via `BACKUP_SERVER_SCHEDULE`.
- `docker/boot-check.sh` — Boots a production Docker image against a real (pinned) MongoDB container and proves two things unit tests cannot: the image starts fail-closed and `/livez` answers, and the runtime `node` user cannot write under `/app/src/`. Run identically by the CI `boot` job and by developers to keep the proof from drifting.
- `docker/crontab` — Generated crontab consumed by the `cron` service container (supercronic). It declares every scheduled job for the deployment—cleanup, backstop sweeps, staff notifications—each routed through a single wrapper script. The file is **not hand-edited**; it is produced from per-module job declarations on every regeneration.
- `docker/deploy-drill.sh` — End-to-end verification of `docker/deploy.sh` against the real production compose file. Spins up a throwaway client with generated secrets, then exercises four scenarios: a successful deploy, auto-rollback of a broken image, a second good deploy, and an explicit `--rollback`. All artifacts are torn down on exit regardless of outcome.
- `docker/deploy.sh` — Single-client production deploy script. It brings up (or rolls back) one client's compose stack via podman or docker, verifies the stack is genuinely healthy (setup exited 0, app and cron are running/healthy, `/readyz` responds), and automatically reverts to the previous good image on failure. The client's `deploys.log` is the sole record of what to roll back to.
- `docker/install-supercronic.mjs` — Build-time script that downloads the supercronic binary, verifies its SHA-256, and installs it to `/usr/local/bin/supercronic`. It exists because supercronic is the job scheduler the `cron` service uses, and it must be present before the container starts. It runs during image builds for both `docker/Dockerfile` and `docker/Dockerfile.production`.
- `docker/mongo-entrypoint.sh` — Wrapper entrypoint for the MongoDB container that generates replica-set keyFile and wire-TLS material (self-signed CA + server certificate) on first boot, with correct ownership, before handing off to the official image's `docker-entrypoint.sh`. Replaces an earlier one-shot service approach that broke podman-compose 1.6/libpod's dependency resolution.
- `docker/mongo-init.js` — A MongoDB first-boot initialization script (executed via `docker-entrypoint-initdb.d`) that creates application-scoped users with minimal privileges, so the app and backup containers never authenticate as the instance root. It runs exactly once against an empty data directory.
- `docker/mongo-rs-init.sh` — One-shot Compose service that initiates the single-node replica set (`rs0`) on the `database` MongoDB container and blocks until that node reaches **PRIMARY** before exiting. It exists because the MongoDB entrypoint's temporary init scripts run *without* `--replSet`, making `rs.initiate()` impossible from `mongo-init.js`; this container connects to the already-running, replSet-enabled `mongod` over the Compose network instead.
- `docker/observability/alertmanager-render.sh` — Renders the Alertmanager YAML configuration from `alertmanager.config.template.yaml` using only POSIX `sh` and `sed` (the image is busybox, so no `envsubst` or `bash`). It conditionally includes receiver sections based on which environment variables are set, extracts secrets into permission-restricted files, and optionally `exec`s Alertmanager as the container entrypoint.
- `docker/observability/alertmanager-routes-test.sh` — End-to-end test script that verifies Alertmanager alert routing, inhibition rules, and config-rendering correctness. It exercises every combination of notification-channel environment knobs (email, webhook, heartbeat), confirms which receiver each alert lands on, and—where `amtool` has no static test—spins up a real Alertmanager daemon to verify inhibit rules actually suppress the expected alerts. Designed to run inside the `prom/alertmanager` image, which ships `amtool`, `alertmanager`, and `busybox`.
- `docker/observability/alertmanager.config.template.yaml` — A Jinja-free, marker-based template for Alertmanager that is rendered into a live config at container startup. It exists because Alertmanager cannot read environment variables natively, so all operator-supplied knobs (SMTP credentials, webhook URLs, receiver names) must be baked in before the daemon reads the file. The routing logic itself is shared by every deployment; only the receiver values differ.
- `docker/observability/gatus.dev.config.yaml` — Local Gatus configuration that stands in as the off-host heartbeat service for the Alertmanager alert-routing chain described in `docs/tools/prometheus.md#alert-routing`. It lets the full ping → detect → email path be drilled on one machine, with Mailpit as the mail sink instead of a production SMTP relay.
- `docker/observability/grafana.dashboard-providers.yaml` — Grafana provisioning file that instructs the Grafana instance to auto-load dashboard JSON definitions from a mounted filesystem path. It eliminates the need to manually import dashboards through the UI—any `.json` file placed under the configured directory is picked up automatically at startup.
- `docker/observability/grafana.datasources.yaml` — Grafana datasource provisioning file. It eliminates manual UI configuration on every container restart by declaring Tempo, Prometheus, and Loki connections declaratively, so Grafana is query-ready the moment it starts.
- `docker/observability/loki.config.yaml` — Loki configuration for a single-node, local Docker observability stack. It sets up filesystem-backed log storage, a one-week retention window, and an in-memory ring so Loki runs as a single process suitable for quick debugging without a distributed backend.
- `docker/observability/otel-collector.config.yaml` — OpenTelemetry Collector configuration that acts as the telemetry gateway for the local Docker stack. It receives OTLP traces from the application, forwards them to Tempo, and derives inter-service metrics (the `traces_service_graph_request_*` family) from those traces so Grafana's Service Graph tab has data to render.
- `docker/observability/prometheus.alert-rules.test.yaml` — Prometheus rule unit tests for `prometheus.alert-rules.yaml`, executed via `promtool test rules`. Each alert gets at least one firing case and one quiet (non-firing) case, with extra quiet cases for expressions that are easy to get wrong (cross-series aggregation, label-mismatched joins, `task`-label reads). Runs in CI under the `alert-rules` job in `.github/workflows/ci.yml`.
- `docker/observability/prometheus.alert-rules.yaml` — Defines the full set of Prometheus alert rules for the local API stack, covering the five SRE signals (availability, errors, latency, load, saturation) plus application-specific concerns: crash-loop detection, dependency health, heap pressure, dead-letter queues, outbox poison events, webhook delivery failures, and scheduled-job staleness.
- `docker/observability/prometheus.config.yaml` — Prometheus server configuration that defines what to scrape, how often to evaluate rules, and where to send alerts. It wires together the API, OTel Collector, and the Prometheus/Alertmanager pair into a single observability loop.
- `docker/observability/prometheus.infra-rules.test.yaml` — Unit-test suite for the alerting rules in `prometheus.infra-rules.yaml`, executed by `promtool test rules`. It provides one firing scenario and (where applicable) one quiet scenario per alert to catch regressions in rule expressions, label/annotation propagation, and threshold logic. Invoked from the `alert-rules` job in `.github/workflows/ci.yml`.
- `docker/observability/prometheus.infra-rules.yaml` — Defines Prometheus alert rules for the infrastructure surrounding the application — the alerting pipeline itself, the host filesystem, and the Traefik proxy. It is kept separate from app-level rules (`prometheus.alert-rules.yaml`) because the cross-cutting test `tests/cross-cutting/alert-rules-metrics.test.ts` rejects any `*_total` metric the app does not register, and these rules read Prometheus, Alertmanager, node_exporter, and Traefik metrics instead.
- `docker/observability/prometheus.production.config.yaml` — Production Prometheus configuration for the `monitoring` profile. It exists as a separate file from the local `prometheus.config.yaml` because the production stack does not run an OTel collector; including those scrape targets (as the local file does) would cause them to report DOWN. It wires up the app's metrics endpoint, Alertmanager, self-monitoring, and node_exporter.
- `docker/observability/prometheus.traefik-scrape.yaml` — A standalone Prometheus scrape-configuration fragment that tells a client stack's Prometheus instance where to find the shared Traefik proxy's metrics endpoint. It exists as a separate file so that only stacks layered with `docker-compose.proxy.yml` (the overlay that actually runs Traefik) pull in this job; without that overlay, no Traefik exists and the scrape config is simply not mounted.
- `docker/observability/tempo.config.yaml` — Configuration for a single-process Tempo instance used in local development. It explicitly defines the HTTP/UI port, OTLP ingest endpoints, in-memory flush cadence, trace retention, and a local-disk storage backend so the tracing pipeline runs with zero external dependencies.
- `docker/observability/umami-init.sh` — One-shot init script that stamps the admin username/password (from `.env`) onto Umami's factory-seeded admin account and inserts a default website row with a known ID. It exists because Umami ships with hardcoded credentials (`admin` / `umami`) and offers no environment-variable override, so the stack needs this bridge step to be log-in-ready without manual DB work.
- `docker/observability/validate-configs.sh` — Validates the Loki and Alloy configs that production actually runs by executing each tool's built-in config check (`loki -verify-config`, `alloy validate`) inside the exact Docker image named in the compose files. This catches the failure mode where an image version bump and a config the new version rejects land in separate commits. Dev-only configs are intentionally out of scope.
