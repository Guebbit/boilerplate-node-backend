# openapi.yaml

## Purpose

This is the **bundled** OpenAPI 3.1.0 contract for the Boilerplate API, generated by `npm run contracts:bundle` from `shared/contracts/openapi.root.yaml` plus every `src/modules/*/openapi.yaml`. It exists as the single, stable, codegen-oriented specification consumed by client/server stub generators, DTO extractors, and SDK tooling across languages. It is **not** an editable source file — all modifications go through the per-module sources and the root contract, then re-bundle.

## Key elements

- **`info.description`** — A long normative paragraph (not just prose) that defines cross-cutting API conventions: `Accept-Language` negotiation rules, RFC 9457 problem-details error shape, list/pagination envelope (`{ items, meta }`), `204`-no-body rule, `201` + `Location` for creates, and the deliberate omission of per-operation header declarations.
- **`info.license`** — AGPL-3.0-or-later.
- **`servers`** — Local (`http://localhost:3000`) and Production (`https://api.example.com`).
- **`tags`** — ~30 tags, each carrying an `x-family` extension (Core, Catalogue, Buying, After the sale, Running the shop, Example) that groups related endpoints for codegen output folder structure.
- **`paths`** — All endpoint operations, each with `operationId`, `security`, `responses`, and `headers` referencing shared `components`. Visible paths include `/` (health), `/config` (public boot config), `/livez`, `/readyz`; the full set is truncated in this view but spans every tagged domain (Products, Orders, Payments, Cart, Auth, Audit, Webhooks, etc.).
- **`components`** (referenced, not shown in full) — Shared `schemas`, `headers`, and `responses` (e.g. `TooManyRequests`, `InternalError`, `ServiceUnavailable`) that all operations `$ref` to avoid duplication.
- **`x-family`** (on tags) — A custom extension used by the codegen pipeline to group output; not standard OpenAPI.

## Relationships

- **`scripts/audit/api-standards.yaml`** — Supplies the set of structural/naming/style rules that the audit tooling checks *against* this bundled spec (e.g. required headers, operationId conventions, tag hygiene).
- **`scripts/audit/compliance-rules.yaml`** — Supplies compliance-specific assertions (likely security, i18n, and error-shape requirements) that the same audit pipeline validates on this file.

Both files are **consumers** of `openapi.yaml`; they do not feed data into it.

## Notes

- **Generated file — do not edit.** Changes must be made in `shared/contracts/openapi.root.yaml` or the relevant `src/modules/<name>/openapi.yaml`, then re-bundled with `npm run contracts:bundle`.
- The `info.description` paragraph is load-bearing: it is the *contract* for the `Accept-Language` header, the error envelope, and the response-shape rules. Codegen and audit tooling rely on these conventions being encoded here, not just in runtime code.
- `x-family` is a non-standard OpenAPI extension; tooling that does not understand it will ignore it, but the codegen pipeline does.
- Tags named `Examples` (family `Example`) are explicitly documented as safe to delete — they are a copy-paste starting point for new domains.
- The spec targets **OpenAPI 3.1.0** (not 3.0.x), which means JSON Schema 2020-12 semantics apply to all `schema` objects.
