# openapi.yaml

## Purpose

The single bundled OpenAPI 3.1.0 contract for the Boilerplate API. It is generated by `npm run contracts:bundle` from `shared/contracts/openapi.root.yaml` and every module's `src/modules/*/openapi.yaml`, producing one stable, codegen-oriented spec consumed by client/server stub generators, DTO builders, and SDK tooling across multiple projects and languages.

## Key elements

- **`info.description`** – Serves as the prose contract for cross-cutting conventions: `Accept-Language` / i18n fallback rules, success-response shape (no wrapper, paged `{ items, meta }`, `204` for empty), and the RFC 9457 `application/problem+json` error format with the `errors[].code` machine key. This paragraph is the binding spec for behaviour that is not repeated per-operation.
- **`tags` (grouped by `x-family`)** – Logical domains: Core, Catalogue, Buying, After the sale, Running the shop, Example. Each tag carries a human-readable description; `x-family` is a custom extension used by tooling or audits to group tags.
- **`paths`** – Concrete operations (e.g. `GET /`, `GET /config`, `GET /livez`, …). Every response references shared `#/components/responses/*` and `#/components/headers/*` definitions, keeping per-operation blocks compact.
- **`components`** (referenced throughout) – Shared schemas (`HealthPing`, `Config`, `PaginationMeta`, …), named responses (`TooManyRequests`, `InternalError`, `ServiceUnavailable`, `NotModified`), and standard headers (`RequestId`, `ContentLanguage`, `Vary`, `RateLimit-Policy`, `RateLimit`, `EntityTag`).
- **`servers`** – Local (`http://localhost:3000`) and Production (`https://api.example.com`) base URLs.
- **`license`** – AGPL-3.0-or-later, declared at the spec level.

## Relationships

- **`scripts/audit/api-standards.yaml`** – Defines the structural/style rules (naming, required fields, header conventions) that this spec is validated against. The audit script reads this file as its input and reports violations.
- **`scripts/audit/compliance-rules.yaml`** – Defines policy-level checks (security, i18n, error-format compliance) applied to this spec. Together with `api-standards.yaml` it forms the CI gate that the generated `openapi.yaml` must pass.

## Notes

- **Do not edit by hand.** The header comment and the `npm run contracts:bundle` pipeline are the source of truth; edit the per-module `openapi.yaml` files or `openapi.root.yaml` instead.
- The i18n / language-selection contract lives entirely in the `info.description` prose, not as per-operation parameters. Generated clients must implement `Accept-Language` handling based on that paragraph.
- `x-family` on tags is a custom extension, not part of the OpenAPI spec; only tooling that understands it will use it.
- The `Examples` tag is explicitly marked "Safe to delete" and exists solely as a copy-paste template for new modules.
- Truncated in this view: the full path list and `components` section extend well beyond what is shown here.
