# src/infrastructure/http/preconditions.ts

## Purpose

The HTTP transport layer for conditional writes (RFC 9110 §13.1.1). It parses `If-Match` from incoming write requests into a `Precondition` that the repository layer can check, and stamps `ETag` / `Content-Location` on outgoing responses. All version semantics and comparison logic live in `persistence/versioning.ts`; this file never inspects a row's shape.

## Key elements

- **`preconditionOf(request, id)`** – Reads the `If-Match` header and returns a `Precondition` (`{ id, etags }`) or `undefined` (unconditional write). Invalid syntax yields an *empty* etag list so the write is refused with 412 rather than silently running.
- **`withIfMatch(request, id, work)`** – Convenience wrapper: calls `runWithPrecondition` with the parsed precondition around an async write.
- **`setEtag(response, row)`** – Monkey-patches `response.json` so that when the body is actually sent, the header is set to `"<version>.<digest>"`. The digest is the first 16 base64url chars of the body's SHA-256 (96 bits). Also calls `keepEtag` to mark the tag as API-owned.
- **`keepEtag(response)`** – Adds the response to an internal `WeakSet` so `dropUnownedValidators` will preserve its `ETag` on write answers. Used by idempotency replay to restore a previously stored tag.
- **`answerAsResource(response, row, uri)`** – Stamps `ETag` and, for non-GET/HEAD responses, sets `Content-Location` (RFC 9110 §8.8.3, §15.3.2). No-op when the row carries no version.
- **`dropUnownedValidators`** – Express middleware. Wraps `response.writeHead` to strip `ETag` from any write response that wasn't marked by `setEtag`/`keepEtag`, and strips both `ETag` and `Last-Modified` from PUT responses unconditionally. Catches Express's auto-generated byte-hash tag.

## Relationships

- **`src/infrastructure/persistence/versioning.ts`** – Direct import of `etagOf`, `runWithPrecondition`, `versionOf`, and the `Precondition` type. This file is the HTTP counterpart; versioning owns the actual check and tag format.
- **`src/infrastructure/http/middlewares/idempotency.ts`** – Referenced in the `keepEtag` JSDoc: an idempotent replay restores the tag the first response stored, relying on the `ownTags` WeakSet.
- **`src/infrastructure/surfaces/create-item-controller.ts`**, **`create-delete-controller.ts`**, **`create-restore-controller.ts`**, **`create-update-controller.ts`** – Surface-level factories that call `withIfMatch` / `answerAsResource` when wiring up write routes.
- **`src/modules/account/controllers/post-email-change.ts`**, **`src/modules/cart/controllers/post-checkout.ts`**, **`src/modules/delivery/controllers/post-process-order.ts`**, **`src/modules/example/controllers/delete-example.ts`**, **`src/modules/example/controllers/post-example-event.ts`** – Module-level write controllers that invoke `withIfMatch` (or `setEtag`/`answerAsResource` directly) around their business logic.
- **`src/modules/account/controllers/get-account.ts`** – Read-side controller that benefits from `setEtag`: the stamped tag lets Express answer `If-None-Match` with a 304.

## Notes

- **Fail-closed on bad `If-Match`:** A syntactically invalid header does *not* mean "skip the check." It produces an empty etag list, guaranteeing a 412. This is intentional: the caller sent the header to *avoid* an unconditional write.
- **`setEtag` defers to `response.json`:** The header is not set until the body is serialised, because the digest covers the exact bytes on the wire. Safe only because nothing in `src` configures Express's `json` `spaces`/`replacer`/`escape` options.
- **Wrapper ordering with Redis cache:** `setEtag`'s `json` wrapper is installed *after* the cache's, so it runs *first* (LIFO). The cache therefore stores the tagged response.
- **`dropUnownedValidators` is hand-written:** It wraps `writeHead` directly because `on-headers` is not a project dependency. It only inspects the *outgoing* response; inbound `If-Match` handling is unaffected.
- **PUT always loses validators:** Regardless of ownership, PUT responses shed `ETag` and `Last-Modified`. The rationale (RFC 9110 §15.3.1) is that a 200 to PUT is "the result of the action," not a cacheable representation.
