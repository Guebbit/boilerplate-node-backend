# src/modules/account/jobs.generated.ts

## Purpose

A generated data file that declares the account module's scheduled jobs (name, cron schedule, human-readable summary) as a frozen constant. It exists so the job *metadata* can be derived from a single YAML source (`module.yaml`) via `npm run regenerate`, keeping the scheduling config in one editable place while `jobs.ts` supplies the actual execution logic.

## Key elements

- **`accountJobData`** (exported `as const`) — the sole export. A plain object keyed by internal job ID, each entry carrying:
  - `name` — the job identifier string (e.g. `'reap:inactive-accounts'`).
  - `schedule` — a standard 5-field cron expression.
  - `summary` — a one-line description of what the job does and which env vars govern its behavior.

  Four jobs are defined:
  - `reapInactiveAccounts` — `5 2 * * *` — minimises / soft-deletes / hard-deletes long-inactive accounts.
  - `reapPreviousEmails` — `7 2 * * *` — clears a previous email once its undo link lapses.
  - `reapAccountExports` — `9 2 * * *` — purges built data exports past their TTL.
  - `reapScheduledDeletions` — `13 * * * *` — cascade-deletes accounts past their grace period and sends a goodbye email.

## Relationships

- **`src/modules/account/jobs.ts`** — the hand-written companion that imports `accountJobData` and attaches the actual function/handler each job executes. This file supplies only the *what and when*; `jobs.ts` supplies the *how*.

## Notes

- **Do not edit this file.** It is regenerated from `src/modules/account/module.yaml` by `npm run regenerate`. Change the YAML and re-run the command instead.
- The `as const` modifier means all strings and numbers are narrowed literal types; any consumer gets autocomplete and exhaustiveness checking for free.
- Schedules are cron strings, not structured objects — a typo or timezone mismatch won't be caught at compile time.
