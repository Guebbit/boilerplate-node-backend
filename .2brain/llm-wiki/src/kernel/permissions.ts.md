# src/kernel/permissions.ts

## Purpose

Defines the application's declared permission vocabulary — rules, sets, and preset roles — by reading and validating two shared YAML artefacts (`shared/authorization-keys.yaml`, `shared/authorization-roles.yaml`) at import time. It exposes the parsed, expanded data as typed constants and schemas so the rest of the kernel and modules can check permissions without ever touching the filesystem at request time. The model is CanCan (Rule → Set → Role), shared byte-for-byte with a PHP twin.

## Key elements

- **`ruleId(action, subject)`** — produces the canonical rule id string `<action>:<subject>`; the single spelling used in roles, credentials, audit rows, and fixtures.
- **`PermissionAction`** — re-exported type for the closed action vocabulary (no `manage`/wildcard).
- **`StepUpTier`** — `'critical' | 'sensitive'`; the step-up authentication tier a rule may demand.
- **`PermissionRule`** — one declared rule: module, subject, action, scope, description, optional `stepUp`, optional ABAC `conditions` (`$caller.<field>` substitution), optional `deniedCode`, optional `credential` flag.
- **`PermissionSet`** — a named bundle of rule ids owned by a module.
- **`PresetRole`** — a named role listing sets, with `permissions` (all rule ids) expanded once at read time; optional `assignable: false` marks roles no request may grant (e.g. `system`).
- **`AUDIENCE_NAMES`** / **`AudienceName`** / **`AudienceRole`** — the three audience roles (`guest`, `unverified`, `customer`); never stored, selected per-request by `audienceOf`.
- **`keysDocumentSchema`** / **`rolesDocumentSchema`** — full Zod schemas for the two YAML files; exported so tests can assert on malformed fixtures without filesystem access.
- **`readShared(file, schema)`** — internal helper: reads the file from `shared/`, parses YAML, safe-parses against the schema, and throws a descriptive error on failure.
- **`DeclaredRule`** — `PermissionRule` plus its computed `id`.
- **`PERMISSION_RULES`** — every declared rule (with id), in file order, available for O(1) lookup by id.

## Relationships

- **`src/kernel/access/tenant.ts`** — provides `DEPLOYMENT_TENANT_ID`, imported here for use in permission evaluation context.
- **`src/kernel/ability.ts`** — consumes the expanded role/audience permissions to build CASL ability objects per request.
- **`src/kernel/middlewares/authorizations.ts`** — calls into the permission data (rules, denied codes, step-up tiers) to enforce authorization on routes.
- **`src/kernel/access/query.ts`** — uses rule `conditions` to scope data-access queries.
- **`src/modules/access/services/grants.ts`** — reads `PresetRole.permissions` when recording or validating a grant.
- **`src/modules/access/services/memberships.ts`** — checks `PresetRole.assignable` before binding a role to an account.
- **`src/modules/account/controllers/get-my-abilities.ts`** — resolves the caller's effective permissions (role + audience) to serialize abilities for the client.
- **`src/modules/account/roles.ts`** — lists assignable preset roles for the account UI, relying on `assignable` and `scope`.
- **`src/modules/account/services/account-deletion.ts`** — triggers a rule whose `deniedCode` and `stepUp` tier govern the "erase account" flow.

- **Test files** (`protection.test.ts`, `grantable-roles.test.ts`, `access.test.ts`) — assert invariants like no duplicate rule ids, credential/stepUp exclusion, and round-trip authorization decisions.

## Notes

- **Boot-time, not per-request.** Both YAML files are read and validated once at `import`. A malformed file throws at process start, not on the first authorization check.
- **No wildcards.** `manage` is intentionally absent from `PERMISSION_ACTIONS`; every permission is an explicit action-on-subject.
- **`deniedCode` is a plain `string`, not a validated enum.** This avoids a circular dependency on `@api/error-codes`, which is generated by a step that itself imports this module transitively. Conformance is checked separately in `tests/cross-cutting/authorization-keys.test.ts`.
- **`credential: false` + `scope: 'platform'` + `stepUp` all independently block API-key minting.** The middleware layer enforces this; the data here merely declares the flags.
- **`conditions` is not an expression language.** The only substitution is `$caller.<field>`; anything else is a literal value.
- **The PHP twin reads the same two YAML files byte-for-byte.** Any change to the shared files must stay compatible with both runtimes.
