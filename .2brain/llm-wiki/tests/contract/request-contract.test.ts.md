# tests/contract/request-contract.test.ts

## Purpose

Contract-derived **request** tests: for every write endpoint the API exposes, this file verifies the API accepts every payload `openapi.yaml` declares legal (`validPayload` → 2xx) and rejects every payload the spec declares illegal (`invalidPayloads` → 422 + `Problem` body). It is the mirror image of the response-side contract tests in `tests/contract/*`—those compare a real response against the spec; this one compares spec-derived requests against the real API. It also sweeps all `in: query` parameters constrained by `enum`, `pattern`, or numeric bounds, asserting 422 for a violating value.

## Key elements

- **`adminQuery(path)`** – returns an async function that sends an admin-authenticated GET to `path?query`.
- **`adminQueryWith(path, base)`** – same, but prepends a `base` query string (used for endpoints requiring additional mandatory params like `from`/`to`).
- **`withRealLocale()`** – seeds a locale via `givenLocale('qp')` so locale-scoped routes pass tag-existence checks before reaching query validation.
- **`QUERY_FIXTURES`** – `Partial<Record<operationKey, QueryFixture>>` mapping each operation that has a constrained query parameter to a ready-to-call request function. The "has a fixture" test enforces 1:1 coverage.
- **`KNOWN_GAPS`** – a `Set` of `"METHOD /path::param"` strings where a spec violation intentionally does **not** return 422 (currently only `GET /locales/{locale}/messages::app`, which returns 404 by design to avoid leaking draft-translation existence).
- **`invalidQueryValues(schema)`** – produces one violating string per constraint: a non-enum member, a pattern-refusing candidate (from a small fixed list), or `maximum + 1` / `minimum − 1`.
- **`isConstrainedQuery(schema)`** – type guard narrowing `schema` to `SchemaNode` when at least one of `enum`, `pattern`, `maximum`, `minimum` is present.
- **`QUERY_CASES`** – flat array of `{ key, paramName, value }` generated by walking `listOperations()` and filtering to constrained query params.
- **`describe('invalid query parameters (contract-derived)')`** – the test suite: a coverage-exhaustiveness check plus one `it.each` per case asserting 422.
- **`validPayload` / `invalidPayloads`** (from `contract-data`) – the body-side generators used in the (truncated) earlier portion of this file.

## Notes

- The file's doc-comment names **four specific mechanisms** that cause validator/spec drift and prescribes the correct fix for each (e.g., fix the spec for `imageUrl` rather than tightening the validator; never `.extend()` a generated schema in a way that replaces a field; coercion must not precede validation; controllers must parse the *whole* generated body, not a `.pick()`).
- `invalidQueryValues` for `pattern` constraints does **not** attempt generic regex negation; it tries a short candidate list and throws if none fails, by design—simpler and avoids pathological patterns.
- This file is explicitly **not** a scenario test. Deterministic scenario tests belong in module-level `tests/factories.ts`; this file answers the broader question "does the API honour its own contract for *any* legal/illegal input?"
- The `QUERY_FIXTURES` coverage test (`has a fixture for every operation…`) will fail if `openapi.yaml` gains a new constrained query param without a matching entry, acting as a guardrail against silent drift.
