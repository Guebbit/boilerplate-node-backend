# scenarios/users.ts

## Purpose

Defines the demo dataset's user accounts and their seeding logic. It builds four role-specific named accounts (`root`, `customer`, `editor`, `moderator`) that e2e and integration tests log in as, plus ten filler customers that give the shop-history flow multiple shoppers to exercise. It exposes two seed entry points so the full `shop` scenario and the minimal `blank` scenario can each pull in exactly the users they need.

## Key elements

- **`SEED_CUSTOMER_IDS`** — Deterministic, hex-prefixed IDs for the ten filler customers, keyed by name (`amelia`…`isla`). Generated by `seedCustomerId` to stay idempotent across `scenario:apply` runs.
- **`namedUsers`** — Four `makeUser` documents (admin, customer, editor, moderator) with verified status, role-appropriate credentials from `@scenarios/accounts`, and image data from `users-images.generated.json`. The `customer` account additionally has `analyticsConsent: true` for the e2e analytics test.
- **`SEED_CUSTOMER_EMAILS`** — Derived email map (`username@example.com`) keyed the same way as `SEED_CUSTOMER_IDS`; exported so the flow runner can sign in without reconstructing addresses.
- **`customerUsers`** — The ten filler customer documents, built from `CUSTOMER_NAMES` in the same order as `SEED_CUSTOMER_IDS`. Alternating `analyticsConsent` and image assignment.
- **`userFixtures`** — `[...namedUsers, ...customerUsers]`; the full set every shop seed writes.
- **`seedUsersCollection`** — Upserts all `userFixtures` via `insertIfAbsent(userRepository, …)`, then assigns the `customer` tenant role to the ten filler customers via `assignRole`. Idempotent on re-run.
- **`seedNamedUsersCollection`** — Upserts only the four `namedUsers`; used by the `blank` scenario which has no shop and therefore no filler base.

## Relationships

- **`scenarios/accounts.ts`** — Source of every `SEED_*_ID`, `SEED_*_EMAIL`, and `SEED_*_PASSWORD` constant for the four named accounts. This file consumes those values; it does not define them.
- **`scenarios/seed.ts`** — Supplies `insertIfAbsent` and the `SeedOutcome` type used by both seed functions.
- **`scenarios/shop-modules.ts`** — Declares `seedUsersCollection` in its module list so the `seedShop` walker calls it.
- **`scenarios/blank.ts`** — Calls `seedNamedUsersCollection` instead of the full seed.
- **`scenarios/flows/shop-history.ts`** — Reads `SEED_CUSTOMER_IDS` and `SEED_CUSTOMER_EMAILS` to sign in and place orders as the filler customers (seven get one order, three get a cart + two orders).
- **`src/modules/users/factories.ts`** — Provides `makeUser`, the document constructor every account in this file goes through.
- **`src/modules/users/repository.ts`** — Provides `userRepository`, passed to `insertIfAbsent` during seeding.
- **`src/modules/access/index.ts`** — Provides `assignRole`, used to grant the `customer` tenant role to the ten filler customers.
- **`src/kernel/access/tenant.ts`** — Provides `DEPLOYMENT_TENANT_ID`, the tenant scope argument to `assignRole`.

## Notes

- **Deterministic IDs, not `new ObjectId()`.** `seedCustomerId` produces a fixed hex string per index so re-running `scenario:apply` upserts the same rows instead of creating new ones.
- **Role assignment is split.** The four named accounts receive their role from `seedAccessModel` in `scenarios/accounts.ts` (run first by `seedShop`). This file assigns the `customer` role only to the ten filler customers, since no other seed does so for them.
- **No pre-banned account.** `marcus` is the banned-user scenario participant, but is seeded ACTIVE; the ban happens at runtime via `PATCH /users/{id}` so the audit log records the action rather than a pre-written state.
- **`blank` excludes the filler base.** `seedNamedUsersCollection` deliberately seeds only the four named accounts — the `blank` scenario has no shop, so the ten shoppers serve no purpose there.
