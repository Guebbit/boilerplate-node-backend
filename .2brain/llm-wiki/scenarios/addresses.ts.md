# scenarios/addresses.ts

## Purpose

Seeds the address-book collection for the demo dataset. Defines three books (admin × 2 entries, ordinary customer × 1, second shopper × 1) and exports a `shopModule` whose `seed` function inserts them idempotently. It exists so scenario flows have concrete, persona-keyed addresses to read, mutate, and freeze onto orders.

## Key elements

- **`addressBookFixtures`** (module-private array) — Three `makeAddressBook` results. Admin gets two entries (one `default: true`, one `false`) to exercise "set-as-default" and "exactly one default" demos. The ordinary customer's single entry deliberately omits the optional `phone` field. Each entry carries a freshly minted `Types.ObjectId()` hex string.
- **`seedAddressBooksCollection`** (module-private) — Maps `addressBookFixtures` through `insertIfAbsentForOwner(addressBookRepository, book)` and returns `Promise<SeedOutcome[]>`.
- **`shopModule`** (export) — `{ seed: seedAddressBooksCollection }`, the single entry point consumed by the generated fixture registry.

## Relationships

- **`scenarios/accounts.ts`** — Supplies `SEED_ADMIN_ID`, `SEED_USER_ID`, `SEED_SECOND_SHOPPER_ID`, the `userId` values that key each fixture and that `insertIfAbsentForOwner` uses as its uniqueness column.
- **`scenarios/seed.ts`** — Provides the `SeedOutcome` type and the `insertIfAbsentForOwner` helper that performs the upsert-or-skip logic.
- **`scenarios/shop-modules.generated.ts`** — Regenerated by `npm run regenerate`; imports `shopModule` from this file and includes it in the aggregated `shopModules` table. Deleting this file removes the entry from the generated file.
- **`src/modules/addresses/factories.ts`** — Source of `makeAddressBook`, the constructor that shapes each fixture object.
- **`src/modules/addresses/repository.ts`** — Source of `addressBookRepository`, passed to `insertIfAbsentForOwner` as the persistence target.

## Notes

- The **book** itself has no pinned `_id`; idempotency relies entirely on `userId` (the unique column). Each **entry** does carry an `_id`, but only to satisfy the contract — no code resolves an entry by that value, so the ids are minted per run rather than hardcoded.
- An order's `shippingAddress` / `billingAddress` is a **snapshot copy** of a book entry, not a reference. The fixtures are intentionally literal values so the live book can diverge from a frozen order without breaking the "an order remembers where it was sent" assertion.
- The admin's second entry (`default: false`) exists specifically as the target a "set as default" demo moves the flag onto.
- Staff / administrator personas have **no** address book entry; the second-shopper persona fills the "second buyer in a two-shopper journey" role.
