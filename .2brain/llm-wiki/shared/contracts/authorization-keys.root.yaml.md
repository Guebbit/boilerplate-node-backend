# shared/contracts/authorization-keys.root.yaml

## Purpose

The single shared authorization vocabulary and rule catalogue for the multi-tenant platform. It defines the action vocabulary, scope separation, step-up tiers, condition conventions, and the full set of permission rules and permission sets. Generated by `npm run regenerate` from per-module fragments (`src/modules/<name>/authorization.yaml`) plus this root residual, it is the one artefact both backend repositories (Node and PHP/Laravel) commit byte-for-byte identical, and the single source that `npm run gen:api` compiles into the frontend permission type.

## Key elements

- **`actions`** — The closed list of verbs (`read`, `create`, `update`, `delete`, `checkout`, `sweep`, `override`, `start`, `receive`, `ban`, `export`, `assign`, `display`, `admin`). No `manage`, no `write`, no wildcard. This list is the sole home of the vocabulary; `gen:api` emits `api/permission-vocabulary.ts` from it.
- **`implies`** — Maps staff actions to the plain actions they also satisfy (`display → read`; `admin → update, delete`), so a single `accessibleBy` call compiles one query filter from both the staff rule and the own-rows rule.
- **`scopes`** — Two mutually exclusive scopes (`tenant`, `platform`). A caller resolves to exactly one; a tenant rule can never be satisfied by a platform caller and vice versa.
- **`stepUp`** — Default re-authentication windows in seconds (`critical: 300`, `sensitive: 900`), overridable by `NODE_REAUTH_TIME_*` env vars. Declared on the rule, not the route. Fed into `src/kernel/step-up.generated.ts` at regenerate time.
- **`credential`** (per-rule flag, documented in comments) — `false` marks a rule as non-mintable via API key. Platform rules and step-up rules are never mintable.
- **`conditions`** (per-rule, ABAC half) — A filter fragment using the `$caller.<field>` placeholder grammar (no expression language). Field names are model-level, not storage-level; each backend maps them to its own columns. Tenancy (`tenantId`) is injected by the resolver, never written in a rule.
- **`# %AUTHORIZATION_RULES%`** — Placeholder where per-module rules are spliced in at generate time. Each rule has a unique `<action>:<subject>` id.
- **`# %AUTHORIZATION_SETS%`** — Placeholder where per-module permission sets are spliced in. A set is the unit a role names; roles never reference rules directly.

## Relationships

- **`shared/contracts/authorization-keys.core.yaml`** — The app-level `core` rules fragment. It is one of the per-owning-module fragments that `npm run regenerate` splices into this bundle alongside this root residual. Drift between the fragment and the bundle fails the build via `--check` (wired into `complete`).
- **`src/modules/<name>/authorization.yaml`** (each) — Per-module rule and set fragments that are spliced into the `# %AUTHORIZATION_RULES%` / `# %AUTHORIZATION_SETS%` slots. A rule or set is introduced in its owning fragment, never edited directly in this bundle.
- **`authorization-roles.yaml`** — References the permission sets declared here; roles are a list of set names only.
- **`api/permission-vocabulary.ts`** — Generated from the `actions` list by `npm run gen:api`; the frontend consumes the same list, avoiding a second type definition.
- **`src/kernel/step-up.generated.ts`** — Generated from the `stepUp` block by `npm run regenerate`.

## Notes

- **Do not edit by hand.** The file is spliced from fragments. `npm run regenerate` rebuilds it; `--check` (part of `complete`) fails the build if the committed bundle has drifted from its fragments.
- **Formatter-excluded in both repos** (`.prettierignore` / `dprint.json`) to prevent a silent byte-level fork between the Node and PHP repositories.
- **No wildcard of any kind exists.** `admin` holds everything by explicitly listing every set in `authorization-roles.yaml`. There is no `manage`, no `*`, no scope-wide grant.
- **`display` vs `read`, `admin` vs `update`/`delete`** — The distinction is scope of rows, not privilege level. `read`/`update`/`delete` are own-rows (filtered by a `conditions` fragment); `display`/`admin` are all-rows. The `implies` block keeps the query compilable as one filter.
- **`deletedAt: null` appears only on narrow (own-rows) reads** of soft-deletable subjects (`Product`, `Order`). Staff-wide reads (`display`) intentionally omit it so soft-deleted rows remain visible for restoration.
- **`manage` is absent by design.** It is explicitly called out in the comments as *not* a declared action; its presence would reintroduce a wildcard.
- **`write` is deliberately not in the vocabulary** — the shop needs `create`, `update`, `delete` as separate grants (e.g., a support agent may update but not delete a user).
- **Modules with no rules are intentional** — `wishlist`, `account`, and `cart` (except `checkout:Cart`) have no entries because access to them follows from being signed in, not from a role.
- **Step-up is declared on the rule, not the route**, so any route that reaches the action inherits the re-auth requirement without per-route bookkeeping. An `amr` list may also be carried for future passkey tiers.
