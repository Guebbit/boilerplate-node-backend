# shared/authorization-keys.yaml

## Purpose

The single canonical declaration of every permission rule, the action vocabulary, scope definitions, step-up tiers, and ABAC condition grammar for the application. It is a **generated bundle**: `npm run regenerate` splices one fragment per owning module (`src/modules/<name>/authorization.yaml`) plus a root residual into this file. The bundle is committed with identical bytes in both `boilerplate-node-backend` and `boilerplate-php-laravel-backend`; `--check` (wired into `complete`) fails the build if the bundle drifts from the fragments.

## Key elements

- **`actions`** — Closed vocabulary of every valid action (`read`, `create`, `update`, `delete`, `checkout`, `sweep`, `override`, `start`, `receive`, `ban`, `export`, `assign`, `display`, `admin`). Single source of truth; `npm run gen:api` compiles it into `api/permission-vocabulary.ts` for both backends. No `manage`, no `write` — intentionally excluded.
- **`implies`** — Maps a staff action to the plain actions it also satisfies (`display → read`, `admin → [update, delete]`). The ability emitter expands these so a single query filter covers both the own-rows rule and the staff rule.
- **`scopes`** — Exactly two: `tenant` and `platform`. A caller resolves to one, never both; no boolean flag derives it.
- **`stepUp`** — Tier names (`critical: 300`, `sensitive: 900`) with default windows in seconds. `npm run regenerate` writes `src/kernel/step-up.generated.ts` from this block. Overridable via `NODE_REAUTH_TIME_CRITICAL` / `NODE_REAUTH_TIME_SENSITIVE`.
- **`rules[]`** — The full rule set. Each entry carries `action`, `subject` (singular CASL type), `module`, `scope`, `description`, and optionally `conditions` (ABAC filter), `stepUp` tier, and `credential` flag. Conditions use **model field names** (e.g. `userId`, `active`), not either backend's column names; each backend maps them into its own query. Tenancy (`tenantId: $caller.tenantId`) is injected by the resolver, never written in a rule.
- **Header comments** — Extensive in-file documentation of design rationale (Solidus/CanCan layering, why `self`/`any` are conditions not names, the tenant/platform invariant, credential-minting rules).

## Relationships

- **`kernel/permissions.ts`** — The runtime enforcement layer. It reads this file's vocabulary and rules to build abilities, compile query filters from `conditions`, and enforce `stepUp` / `credential` gates via `requirePermission`.
- **`shared/authorization-conformance.yaml`** — Declares conformance expectations (e.g. which rules a backend must honour, which conditions it must translate). Both backends are checked against it.
- **`shared/cases/permission-model-version.cases.yaml`** — Test-case fixtures that exercise the rules declared here (especially `implies` expansion, scope separation, and condition compilation) to verify the model version is implemented correctly.
- **`docs/theory/authorization.md`** — Prose reference for the three-layer model (rule → permission set → role), the scope invariant, and the action-vocabulary policy that this file enforces structurally.
- **`docs/demo-ecommerce/`** — Concrete walkthroughs that reference specific rules from this file (e.g. `checkout:Cart`, `display:Product`) to illustrate how the permission model maps to business flows.

## Notes

- **Do not edit this file by hand.** Introduce or change rules in the owning module's `src/modules/<name>/authorization.yaml`, then run `npm run regenerate`. Direct edits will be overwritten and will fail `--check`.
- **Formatter-excluded.** Listed in `.prettierignore` / `dprint.json` in both repos. Two formatters on one shared artefact causes silent byte-level drift; the file must stay byte-identical across the two boilerplates.
- **`subject` is singular** (CASL type, e.g. `Order`); the module folder is plural. `display:Order` is a permission; `Order` is a thing.
- **`wishlist`, `account`, and most of `cart` have zero rules** by design — they are "your own things" gated by sign-in, not by role. The sole cart exception is `checkout:Cart`, which is an account-level fact (address proven?), not a basket-contents rule.
- **`deletedAt: null` appears only on narrow (own-rows) reads** of soft-deletable subjects (`Product`, `Order`). Staff `display` rules intentionally omit it so deleted rows remain visible for restoration. A payment rule carries no such condition because payments are never hidden.
- **`conditions` is the only placeholder grammar** (`$caller.<field>`). There is no expression language. Tenancy is never expressed in a rule — the resolver injects it.
- **A rule with `stepUp` is never credential-mintable**, and neither is a platform-scope rule. `credential: false` makes this explicit per rule.
