# Data Protection

GDPR binds a **controller** — whoever deploys this, decides why data is processed, and answers to
a supervisory authority — not a repository. So this page is not a compliance certificate; it is
the record a controller needs to have, assembled from what the code actually does. Every row below
is derived from a specific file, not aspirational.

Any deployment serving people in the EU/EEA is in scope from its first signup: this processes
email, username, phone, postal addresses with names and phone numbers, IP addresses, user-agents,
order history, and payment metadata.

## Before consent: what the browser stores and sends

The rule: **before the visitor accepts analytics, nothing identifies or measures them.** Only
technical, anonymous data is allowed. The backend half is that `emitAnalyticsEvent` drops every
event without consent (see [Product analytics](../tools/analytics.md#consent)); the browser half is
the table below, swept across both repositories. What the browser adds after consent is Faro's
web-vitals, performance and navigation measurement and Umami's tracker.

| Where                          | What                                                                                              | Why it is allowed without consent                                                           |
| ------------------------------ | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Cookies `isAuth`, `rememberMe` | the signed-in flag and the stay-signed-in choice (the refresh token itself is an httpOnly cookie) | strictly necessary: keeps a login the visitor asked for (ePrivacy Art. 5(3) exemption)      |
| Cookie `analyticsConsent`      | the visitor's own answer                                                                          | strictly necessary: remembers the choice so the banner does not ask again                   |
| Cookie `themePreference`       | light or dark                                                                                     | a preference the visitor set; identifies no one                                             |
| `localStorage`                 | the guest cart                                                                                    | strictly necessary: the cart the visitor is building; stays in their browser                |
| `localStorage`                 | `umami.disabled`                                                                                  | the opt-out switch itself                                                                   |
| `sessionStorage`               | the stale-deploy retry mark, the checkout draft, the checkout attempt                             | strictly necessary for the page or the purchase in progress; cleared with the tab           |
| Request headers                | `Accept-Language`, a per-request `traceparent`, an `Idempotency-Key` on a write                   | none identifies a person: the trace id and the key are random per request                   |
| `X-Analytics-Consent`          | sent only once the guest has granted                                                              | it carries the grant, so it exists only after one                                           |
| Faro                           | errors, console, CSP violations, views, tracing                                                   | crash reports are legitimate interest (see the register); **no session id** is generated    |
| Server logs and audit          | IP and user agent                                                                                 | legitimate interest (6.1.f) in security; see the `auditlogs` register row and its retention |

No third-party font, script or image is loaded by the app shell. The sweep is a table, not a test:
a new `localStorage` key, cookie or header belongs in it in the same change.

## Sub-processor list

Every third party in the data path a controller signs a DPA with, or decides not to because it
stays inside their own infrastructure.

| Sub-processor                                  | Role                | Data it receives                                                               | DPA needed?                                                                                                                                                                                                |
| ---------------------------------------------- | ------------------- | ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Analytics provider (`NODE_ANALYTICS_PROVIDER`) | Product analytics   | `distinctId`, event properties, dropped unless the consent gate below passes   | Self-hosted Umami (the default) stays inside the controller's own infra. Hosted PostHog is a genuine third party — its region (`NODE_POSTHOG_HOST`, EU vs. US) is a real decision, not a default to accept |
| SMTP provider (`NODE_SMTP_HOST`)               | Transactional email | recipient address, message content                                             | Yes                                                                                                                                                                                                        |
| Loki                                           | Log aggregation     | request metadata; personal fields already hashed by `NODE_LOG_PERSONAL_FIELDS` | Only if hosted externally — the shipped `docker-compose` stack runs it in the controller's own infra                                                                                                       |

No object storage sub-processor: uploaded images are written under `NODE_PUBLIC_PATH` on the app
server's own disk, not a third-party bucket. A deployment that adds one (S3, R2, …) adds a row
here.

## Subject-request runbook (Art. 15–21)

| Right                  | Article | Endpoint                                                                                    | Who may call it                       | What it does not cover                                                                                                                                                                                                                                                                                                                                       |
| ---------------------- | ------- | ------------------------------------------------------------------------------------------- | ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Access & portability   | 15, 20  | `POST /account/export`, then `GET /account/export/{id}` (the mailed link)                   | the subject only, fresh-auth guarded  | feedback tickets, opt-in via `NODE_EXPORT_INCLUDE_FEEDBACK` (a shared email is a guess, not a proven match)                                                                                                                                                                                                                                                  |
| Erasure                | 17      | `DELETE /account` (self, emailed confirmation) or admin `DELETE /users/:id?hardDelete=true` | the subject, or an admin              | `orders`/`payments` are anonymised on a delay (`NODE_ORDER_PII_RETENTION_DAYS`), not deleted — invoices are kept for tax law. A **soft** delete (`hardDelete` unset) is reversible and does **not** discharge an erasure request — only `hardDelete=true` does. Honoured even for a shop's last `admin`, leaving the shop with no administrator (`93917986`) |
| Rectification          | 16      | `PUT /account`                                                                              | the subject only                      | —                                                                                                                                                                                                                                                                                                                                                            |
| Objection to profiling | 21      | `analyticsConsent: false` via `PUT /account`, or the `X-Analytics-Consent` header pre-login | the subject, or anonymous per-request | does not retroactively delete events already sent to the provider — that is the provider's own deletion tooling                                                                                                                                                                                                                                              |

The export is a background job that mails a link ([account: data export](../modules/account.md#data-export)),
built one section at a time. Each paged collection it walks (api keys, orders, delivery, feedback)
goes through the shared `readAll(fetchPage, pageSize)` helper until a short page signals done, so
there is no row ceiling and no silently truncated answer. The audit trail reads by cursor instead,
so a long one costs a pass rather than a count and a skip per page.

## Breach runbook (Art. 33 — 72 hours)

```mermaid
flowchart TD
    D["Detection<br/><i>alert, report, or audit review</i>"] --> C["Contain<br/><i>revoke sessions, rotate secrets</i>"]
    C --> S["Scope<br/><i>which records, which subjects, since when</i>"]
    S --> A{"Likely risk<br/>to subjects?"}
    A -->|no| R["Document internally<br/>Art. 33(5) — no notification owed"]
    A -->|yes| N["Notify the supervisory authority<br/>within 72h of becoming aware"]
    N --> H{"High risk?"}
    H -->|yes| U["Also notify affected subjects<br/>Art. 34"]
    H -->|no| R2["Document, no subject notice owed"]

    classDef step fill:#dbeafe,stroke:#2563eb,color:#111827;
    classDef gate fill:#fef3c7,stroke:#d97706,color:#111827;
    classDef out fill:#fee2e2,stroke:#dc2626,color:#111827;
    class D,C,S,U step;
    class A,H gate;
    class R,R2 out;
```

**Scoping the incident** — the queries that establish who and what, both already indexed for
exactly this:

- `GET /observability/audit?actor=<id>` — everything one account did or had done to it.
- `GET /observability/audit?action=<action>` — every occurrence of one action across accounts, for
  the audit vocabulary each module owns (`account/audit.ts`, `users/audit.ts`, …). `auth.login`,
  `admin.user.erased` and `auth.data_export.downloaded` are usually the first three worth checking.
- The Winston log lines in Loki (the actor is `user.id`, the address `client.address`; see
  [Winston](../tools/winston.md#field-names-in-the-log-line)), same actor or time window, once the queryable collection's
  90-day window (`NODE_AUDIT_RETENTION_DAYS`) is not enough — Loki's own retention is longer or
  shorter depending on how the stack is configured, see [ops: Data retention](../reference/ops.md#data-retention).

The clock in Art. 33 starts at **becoming aware**, not at confirming scope — contain and notify in
parallel, don't wait for a complete picture.

## Deployer's checklist

Environment variables this plan introduces or depends on. **Bold** rows must be set to a real,
non-placeholder value before serving EU/EEA traffic; the rest ship safe defaults. Retention
windows are not repeated here — they live in the [processing register](#processing-register-art-30).

| Variable                             | Default | What it governs                                                                                                              |
| ------------------------------------ | ------- | ---------------------------------------------------------------------------------------------------------------------------- |
| **`NODE_TOKEN_ACCESS`**              | —       | Access-token signing secret. The app refuses to boot on the shipped placeholder                                              |
| **`NODE_TOKEN_REFRESH`**             | —       | Refresh-token signing secret. Same boot-time check                                                                           |
| `NODE_TOKEN_ROTATION_GRACE_MS`       | `10000` | Refresh-token rotation grace window                                                                                          |
| `NODE_REAUTH_TIME_CRITICAL`          | `300`   | Step-up freshness window for money/destructive routes                                                                        |
| `NODE_REAUTH_TIME_SENSITIVE`         | `900`   | Step-up freshness window for identity/session/export routes                                                                  |
| `NODE_LOG_PERSONAL_FIELDS`           | `hash`  | How `email`/`ip`/`phone`/etc. are treated on the way into logs                                                               |
| `NODE_EXPORT_INCLUDE_FEEDBACK`       | `false` | Whether `POST /account/export` guesses at feedback tickets by email                                                          |
| **`NODE_ANALYTICS_REQUIRE_CONSENT`** | `true`  | Whether analytics capture is gated on `analyticsConsent`. Turning this off is a decision to document, not a default to relax |

## What this page is not

- Not legal advice. It states what the code does; whether that satisfies a specific controller's
  obligations is a question for that controller's own counsel.
- Not complete forever. A new collection that stores personal data, or a new sub-processor, earns
  a row here in the same commit that adds it — the same habit [the file glossary](../reference/index.md#keeping-this-page-true) asks for.
