# Business logic, money and payments

No parser and no bug involved. The application does exactly what it was told, and what it was told
was wrong. These are the ones scanners never find, because every request is well-formed and every
value is in range — the RULE is the flaw.

What makes this page short is that the arithmetic and the transitions each live in one place:
`orders/domain` owns both, and `cart`, `payments` and `inventory` read them rather than restating
them. A rule stated twice is a rule that will disagree with itself.

## Arithmetic and money

The single decision under every row here: **money is a branded integer count of minor units**, and
the only conversion back to decimals happens on the way out.

| Attack                            | How it works                                                | This boilerplate                                                                                                                                                                                                                                                                            |
| --------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Price manipulation                | price, discount, currency or total trusted from the request | No request ever carries a price. A line's amount is the joined product's `price`; the payment intent freezes `orderTotal(order)`, the same function the order serializer and the confirmation email call — `orders/domain/totals.ts#orderTotal`, `payments/services/intent.ts#createIntent` |
| Negative or zero quantities       | `quantity=-1` credits instead of charging                   | `quantity` is `integer, minimum: 1` in the contract, so the generated schema rejects `0` and `-1` at the controller — `cart/openapi.yaml`, `api/schemas.zod.ts`                                                                                                                             |
| Amount sign / unit tricks         | `-100`, `0.001`                                             | Same answer — the contract's own bounds, checked before a service sees the value.                                                                                                                                                                                                           |
| Integer overflow / precision loss | large totals, floating-point money, rounding per line item  | `addMoney` / `scaleMoney` normalise a non-finite result to zero — `orders/domain/money.ts`                                                                                                                                                                                                  |
| Rounding and precision            | pennies harvested at scale by rounding each line            | There is no per-line rounding to harvest: `toMinorUnits` rounds ONCE per unit price, and everything after it is integer addition — `orders/domain/money.ts#toMinorUnits`                                                                                                                    |
| Currency confusion                | cents vs. units; the currency code changed after pricing    | The currency is `NODE_DEFAULT_CURRENCY`, read server-side and frozen onto the payment document. No endpoint accepts one — `payments/config.ts`, `payments/model.ts`                                                                                                                         |
| Unit / measurement confusion      | weight in kg vs. g on a shipping fee                        | Shipping is priced from the basket's own line total by `priceShipping`, against a method resolved from a server-side table — the request names an ID, never a cost — `delivery/`, `cart/services/checkout.ts`                                                                               |

`tests/cross-cutting/money-reconciliation.property.test.ts` asserts the arithmetic as a property
rather than by example, which is the only way to catch a rounding rule that is wrong only on
certain inputs.

## Who the server derives, and who the client supplies

| Attack                                  | How it works                                        | This boilerplate                                                                                                                                                                                                                                               |
| --------------------------------------- | --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Trusting user-supplied identifiers      | `sellerId` chosen by the buyer                      | The buyer is `authContext.id`; the shipping address is resolved through `addressForCheckout(userId, addressId)`, so naming someone else's entry refuses the checkout before anything is written — `cart/services/checkout.ts`, `account/services/addresses.ts` |
| Trusting client-side validation         | JavaScript rules, HTML `required` and `max`         | Every rule that matters is in the contract and enforced by the generated Zod schema server-side. The frontend's copy is a convenience, never the gate.                                                                                                         |
| Inconsistent validation across channels | the web form validates, the API or import does not  | There is ONE channel: the contract. The frontend, the tests and the fuzzer all generate from the same `openapi.yaml`.                                                                                                                                          |
| Feature-flag / config exposure          | flags evaluated client-side, toggled by a parameter | Module enablement is server-side config read at boot — `kernel/registry.ts`. No request parameter changes which modules are mounted.                                                                                                                           |

## Order of operations

| Attack                     | How it works                                                    | This boilerplate                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| -------------------------- | --------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Workflow step skipping     | the order confirmed without a payment callback                  | `payments` asks the order lifecycle whether `paid` is still REACHABLE rather than comparing against a literal; the order's move to `paid` is the gate, and a charge whose order slipped away is refunded on the spot — `payments/services/settlement.ts#settlePayment`                                                                                                                                                                                                                                     |
| State-machine violations   | cancel after shipped, refund twice                              | Same answer as [State-machine violations](authorization.md#order-and-state) — `ORDER_LIFECYCLE` is a total map, so an illegal move is an absent edge rather than a missing `if`.                                                                                                                                                                                                                                                                                                                           |
| Replay of one-time actions | a resent webhook or a resubmitted form, with no idempotency key | Two layers. DOMAIN idempotence: the conditional `succeeded → refunded` move IS the guard, and both callers come through `performRefund` — `payments/services/refunds.ts#performRefund`. TRANSPORT idempotence: `Idempotency-Key` is mounted on the writes that spend money or send mail, so a client retrying a request the server already committed replays the stored response instead of acting twice — `infrastructure/http/middlewares/idempotency.ts`, and [Idempotency](../../tools/idempotency.md) |

## Concurrency

Two requests pass the same check before either commits. The answer is never "check harder" — it is
to make the WRITE carry the precondition.

| Attack                        | How it works                                            | This boilerplate                                                                                                                                                                                                         |
| ----------------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Race condition / double spend | parallel requests pass one check before any commits     | Checkout empties the cart under the `__v` it read the lines at, so exactly one of two racing checkouts wins; the loser retracts its own order and answers 409 — `cart/repository.ts#clearLinesIfUnchanged`               |
| Checkout race                 | pay once, receive twice, via parallel confirms          | The units are held by a conditional reserve keyed on the order id, and `updateStatusIfIn` re-asserts the precondition inside the write — `inventory/service.ts#reserveForOrder`, `orders/repository.ts#updateStatusIfIn` |
| Coupon / voucher reuse        | a race, missing uniqueness, or case/whitespace variants | No surface: there is no coupon or voucher feature.                                                                                                                                                                       |

## Abuse of a legitimate feature

| Attack                         | How it works                                            | This boilerplate                                                                                                                                                                                                                                                                                                                                                |
| ------------------------------ | ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Inventory reservation abuse    | carts hold stock indefinitely; scalping bots            | A hold carries `expiresAt` (`NODE_RESERVATION_TTL_MINUTES`, 30 by default) and a batched sweep expires stale ones — an abandoned cart returns its units instead of holding them forever. The sweep is a keyed endpoint (`inventory.manage`) an external cron calls, not a timer this process owns — `inventory/config.ts`, `POST /inventory/reservations/sweep` |
| Denial of inventory / wallet   | reserve, then abandon                                   | Same answer — the TTL is what turns a denial into a delay.                                                                                                                                                                                                                                                                                                      |
| Refund / return abuse          | a refund larger than paid, or after a partial cancel    | The conditional `succeeded → refunded` move is the only path, and it is idempotent by construction — `payments/services/refunds.ts#performRefund`                                                                                                                                                                                                               |
| Referral / promo abuse         | self-referral, fake accounts, bonus before verification | No surface: there is no referral or promo feature.                                                                                                                                                                                                                                                                                                              |
| Gift-card / wallet enumeration | short codes, no rate limit on a balance check           | No surface: there are no gift cards or wallets.                                                                                                                                                                                                                                                                                                                 |
| Card testing / carding         | stolen cards validated by many small purchases          | 🚧 Coming soon — `webhookLimiter` bounds the callback route, but nothing bounds how many payment intents one account or card may burn through.                                                                                                                                                                                                                  |
| Insufficient anti-automation   | signups, reviews, votes and polls scripted              | See [Automation and abuse](automation-and-abuse.md).                                                                                                                                                                                                                                                                                                            |

## The payment provider

`POST /payments/webhook` is the one route in this module with no session behind it: its caller is a
machine with no account. That makes it the module's most exposed surface and its most carefully
built one — the three controls below are the whole reason it can be trusted.

| Attack                   | How it works                                                    | This boilerplate                                                                                                                                                                                                                                                                  |
| ------------------------ | --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Stored card data         | PANs in your database — PCI scope and breach impact             | No card number ever reaches this API. `POST /payments/{id}/confirm` takes an opaque provider handle, and the four digits on a payment document come from the provider's own answer — `payments/providers/index.ts`                                                                |
| Payment callback forgery | a fake "paid" notification, unsigned or with a guessable secret | An HMAC over `<timestamp>.<raw body>`, compared with `timingSafeEqual`, plus a 300-second freshness window so a captured body does not stay valid forever. The RAW bytes are preserved for this path alone — `payments/providers/webhook-signature.ts`, `app/security.ts`         |
| Callback replay          | one payment, many orders                                        | An event-id ledger where **the INSERT is the check**: a unique index refuses the second of two concurrent deliveries, so no read-then-write race exists. A settlement that failed gives its claim back, so a redelivery is acted on — `payments/repository.ts#claimWebhookEvent`  |
| 3-D Secure bypass        | a client-reported strong-customer-auth result trusted           | The browser's word is never the authority. `POST /payments/{id}/sync` means "I have finished at the provider", and the server RE-READS the provider's own record rather than believing the claim; the webhook remains the authority — `payments/controllers/post-payment-sync.ts` |
| Chargeback fraud         | goods kept, money returned, weak proof of delivery              | Out of scope: a commercial and logistics control, not an application one.                                                                                                                                                                                                         |

A non-2xx tells a provider the delivery failed and it comes back harder, so only an _unverifiable_
body answers 400 — an authentic event this module simply ignores still answers 200. That is why
the signature check and the ledger are the only two things allowed to refuse.
