# API Standards

This API follows the mature HTTP standards, and writes down where it does not. This page names
each standard, links its source, and lists the differences with their reasons. The two audits under
`scripts/audit/api-*` read it; they report and never change a file.

## Why standards matter here

This is a boilerplate other projects copy. A copied API should be boring and predictable
([API](../build/api-contracts.md#what-matters-most-here)): a client, a proxy or a reader who knows HTTP
should not be surprised. A standard is the cheapest way to be unsurprising.

Most of it is already held mechanically. Spectral lints the contract, the bundler adds `ETag`,
`If-Match`, `412` and `304`, and tests walk the contract. The audits cover what a rule cannot: does
an operation's _meaning_ fit the standard, is a difference written down, does a doc disagree with
the code.

The two IETF drafts move. The page was checked on 2026-11-06 against
`draft-ietf-httpapi-ratelimit-headers-11` (expires 2026-11-24) and
`draft-ietf-httpapi-idempotency-key-header-08` (dated 2026-10-22). Each audit re-checks the latest
draft when it runs, because a draft's number is not a fact that keeps.

The OWASP API Security Top 10 is deliberately not an audit. It is a list of risks, not of rules,
and [Web Attacks & Defences](../understand/defences/index.md) already answers each one.

Compatibility and sunset rules are not covered yet. There is nothing to compare before 1.0; then
the right tool is a deterministic contract diff such as oasdiff, not an AI.

## When standards disagree

The eight web rules do not: they come from the IETF HTTP working groups and are written to fit
together. They only overlap, on a 304 and on a 429, and `api-http` reports each overlap once.

The two style guides do, on purpose:

| Topic          | Zalando               | Google AIP          |
| -------------- | --------------------- | ------------------- |
| Property names | `snake_case`          | `lowerCamelCase`    |
| Errors         | RFC 9457 problem JSON | `google.rpc.Status` |
| Paging         | cursor preferred      | opaque `page_token` |

So an API follows **one**, and the other is never judged. Nobody configures it; the audit looks:

- **Zalando** is the default: REST + JSON first, and it agrees with RFC 9457 on errors.
- **Google AIP** fits a gRPC/protobuf-first API. When the contract shows two or more Google signals
  (Google-shaped errors, `:verb` paths, `page_token` paging, field masks), the audit asks before
  switching. Under Google, `api-http` also asks before it skips its RFC 9457 rules.

The order is fixed: **web rules, then the style guide.** A guide rule a web rule already decides is
listed by `api-style` under "Decided by the web rules", not judged twice.

## Stricter than the standard

A rule in the registry can carry a `house` clause: something this API promises beyond the standard,
and the docs page that promises it. A house clause is stricter but compliant, so it never takes a
row in the table below: a clause that would contradict a standard is a difference, not a house rule.
The audits check house clauses too, and label a miss as ours, not the standard's.
