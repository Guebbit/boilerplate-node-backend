# docs/reference/contracts.md

## Purpose

Reference page for the contract system: it maps every contract-related file (sources, bundled specs, generated code, lint rulesets, client collections) to what it is and which command produces it, so a developer knows what to edit versus what is regenerated.

## Key elements

- **Source files (hand-edited):** `openapi.root.yaml` (REST preamble), `asyncapi.root.yaml` (async preamble), `asyncapi.workers.yaml` (domainless queues), and per-module OpenAPI/AsyncAPI fragments (catalogued in `src-modules.md`).
- **Bundled documents (generated by `npm run contracts:bundle`):** `openapi.yaml`, `asyncapi.yaml`, `asyncapi.public.yaml`. None are hand-edited.
- **Generated code:** `api/schemas.zod.ts` + `api/models/*.ts` (via `npm run gen:api`), `src/types/asyncapi.generated.ts` (via `npm run gen:asyncapi`).
- **Spectral rulesets:** `spectral.yaml` (whole OpenAPI doc), `spectral.modules.yaml` (REST fragments), `spectral.asyncapi.modules.yaml` (async fragments + workers).
- **Client collections (generated from `openapi.yaml`):** Postman, Insomnia, Bruno, Mockoon exports.
- **Guard commands:** `npm run check:contracts-bundle` (byte-identity), `npm run check:spec-identity` (public spec vs. paired repo).

## Relationships

- **`docs/api/contract-fragmentation.md`** — defines ownership rules for which module owns which fragment; this page's source table defers to it.
- **`docs/api/openapi-workflow.md`** / **`docs/api/asyncapi-workflow.md`** — step-by-step workflows for editing and regenerating each spec; this page is the at-a-glance map, those pages are the how-to.
- **`docs/api/regenerating.md`** — lists the exact sequence of commands to run after a contract change; linked from the generated-code rows.
- **`docs/reference/src-modules.md`** — catalogues per-module fragments that feed the bundle.
- **`docs/reference/src-app.md`** — explains how `api/models` is imported via `@types` in the app.
- **`docs/tools/contract-testing.md`** — how the client collections are consumed for response testing.
- **`docs/tools/rabbitmq.md`** — operational context for the workers queues declared in `asyncapi.workers.yaml`.
- **`docs/tools/frontend-observability.md`** — consumes `asyncapi.public.yaml` for browser-observable channels.

## Notes

- **Never edit generated files.** `openapi.yaml`, `asyncapi.yaml`, `asyncapi.public.yaml`, `api/schemas.zod.ts`, `api/models/`, and all four client collections are overwritten on regeneration. Pre-commit hooks (`check:contracts-bundle`, `check:spec-identity`) and postinstall (`asyncapi.generated.ts`) will reject or regenerate hand-changes.
- **Three rulesets, not one.** A fragment lacks `info`, `servers`, etc., so the whole-document rules in `spectral.yaml` would false-positive on fragments. Always run the matching ruleset for the file type you are linting.
- **`api/models/` is deliberately absent from the glossary.** `npm run gen:api` deletes and rewrites the directory wholesale; listing each schema would duplicate the spec, which house rules forbid.
- **`asyncapi.public.yaml` is cross-repo.** `check:spec-identity` asserts it matches a copy in a paired (frontend) repository, so a change here can break that repo's CI.
