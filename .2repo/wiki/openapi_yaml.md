# openapi.yaml

## Purpose

This is the **bundled** OpenAPI 3.0.3 contract for the Ecommerce Demo API (v2.0.0). It is generated by `npm run contracts:bundle` from `shared/contracts/openapi.root.yaml` and per-module `src/modules/*/openapi.yaml` files, then serves as the single source of truth for all downstream code generation, API-client collections, mock servers, and linting. It is **not edited by hand**.

## Key elements

- **`info.description`** – Carries the project-wide i18n contract (how `Accept-Language` is handled, what it may and may not affect, fallback rules, `Content-Language` / `Vary` headers). This paragraph is the *only* place the `Accept-Language` header is specified; it is deliberately omitted from every individual operation.
- **`paths/`** – Endpoint definitions spanning 13 tags (Auth, Account, Users, Products, Cart, Wishlist, Orders, Payments, Delivery, Inventory, Feedback, System, Observability). The visible portion includes:
  - `GET /` – `getHealth` – public liveness ping.
  - `GET /locales` – `getLocales` – lists supported languages with per-tenant capability flags; admin sees inactive rows too.
  - `POST /locales` – `createLocale` – registers a new language (frontend-tenant only until a dictionary is deployed).
  - `GET /locales/tenants` – `getLocaleTenants` – lists configured translation tenants (`backend` vs `frontend`).
  - `GET /locales/{locale}` – `getLocaleDictionary` – the API's own (tier-1) message dictionary for fallback.
  - `PUT /locales/{locale}` – `updateLocale` – edits display names / direction / visibility; locale tag is immutable.
  - `DELETE /locales/{locale}` – `deleteLocale` – removes language + all its entries; refuses while active (409).
  - `GET /locales/{locale}/messages` – `getLocaleMessages` – client-facing dynamic dictionary (one frontend tenant), returned in the same nested shape as tier-1 for a single merge path.
  - `GET /locales/{locale}/entries` – `listLocaleEntries` – paginated, searchable flat entry list for the translation UI.
- **`components/schemas/`** – Referenced throughout (`HealthPingEnvelope`, `LocaleCapabilitiesEnvelope`, `CreateLocaleRequest`, `LanguageEnvelope`, `LocaleDictionaryEnvelope`, `LocaleMessagesEnvelope`, `Locale`, etc.).
- **`components/responses/`** – Shared error/ok responses (`Unauthorized`, `Forbidden`, `NotFound`, `Conflict`, `ValidationError`, `InternalError`, `Success`).
- **`components/parameters/`** – Reusable params (`LocalePathParam`, `MessagesTenantQueryParam`, `PageParam`, `PageSizeParam`, `TextParam`, `EntryTenantQueryParam`).
- **`servers/`** – Two environments: local (`http://localhost:3000`) and production (`https://api.example.com`).

## Relationships

| Neighbor | Interaction |
|---|---|
| `shared/contracts/openapi.root.yaml` | **Input** to the bundle step; provides shared components (schemas, responses, parameters) and any root-level definitions. |
| `src/modules/*/openapi.yaml` | **Inputs** to the bundle step; each module contributes its `paths/` and module-specific components. |

| `docs/reference/contracts.md` | Human-readable reference that documents the contract described here. |
| `github/workflows/fuzz.yml` | CI workflow that likely lints / validates / fuzz-tests this spec as part of the pipeline. |

## Notes

- **Do not edit this file.** It is regenerated from `shared/contracts/openapi.root.yaml` + `src/modules/*/openapi.yaml` via `npm run contracts:bundle`. All changes must be made in those source files.
- **`Accept-Language` is intentionally absent from every operation's `parameters`.** The `info.description` block is its contract. Clients set it once in an interceptor; adding it per-operation would bloat every generated function signature (33+ times).
- **Locale tiering is a core design constraint:** `GET /locales/{locale}` (backend/tier-1, deployed files) and `GET /locales/{locale}/messages` (frontend/tier-2, dynamic DB entries) return the **same nested shape** so clients use a single merge path. The backend tenant is never exposed through the `/messages` endpoint.
- **`DELETE /locales/{locale}` requires a prior deactivation** (otherwise 409). This two-step guard is deliberate to prevent accidental loss of translation work.
- **Inactive locales are invisible to all public routes.** Admin endpoints still surface them with `active: false`.
