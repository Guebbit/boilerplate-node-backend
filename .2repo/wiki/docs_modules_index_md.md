# docs/modules/index.md

## Purpose

Landing page for the modules section. It defines what a module page is (a "decision" owned by one domain, as opposed to a "mechanism" owned by a horizontal page), shows the cross-module dependency graph, lists every module grouped by DDD strategic tier, and records the backend-to-frontend module pairing. It exists so a reader can orient before choosing a specific module page.

## Key elements

- **Navigation tip table** — maps a reader's question ("what does this domain do?", "how does a mechanism work?", etc.) to the correct section of the site.
- **Dependency graph** (`<!-- module-graph:start -->` … `<!-- module-graph:end -->`) — a Mermaid `flowchart TD` and an accompanying reachability table, both generated by `npm run docs:graph` from the `dependency-cruiser` output. Content between the markers must not be hand-edited.
- **"Not every coupling is an arrow" warning** — documents three invisible couplings (shared document columns, string-keyed metrics, DB schema/TTL) that are recorded in `module.ts` docblocks rather than in the import graph.
- **Module list** — every module linked to its page, grouped into **core** (cart, orders, products), **supporting** (delivery, inventory, payments, wishlist), and **generic** (account, audit-logs, feedback, locales, observability, users).
- **Two-repositories table** — maps each backend module to its frontend counterpart in `boilerplate-vue-frontend`, noting the two asymmetries (`audit-logs`→`admin`, `observability`→`admin`+`realtime`) and the frontend-only `demo` module.

## Relationships

- Links to every module page in `docs/modules/` (account, account-sessions, audit-logs, cart, cart-checkout, delivery, feedback, inventory, inventory-reservations, locales, observability, orders, payments, payments-provider-port) as the target of its "every module" list and dependency graph.
- Links to `docs/api/endpoints.md` as the single place listing all application routes.
- References `docs/tools/events-and-logging.md` and `docs/tools/winston.md` to explain the event-bus return path and audit-action semantics, respectively.
- References `docs/theory/strategic-ddd.md` for the core / supporting / generic definitions.
- References `docs/reference/src-modules.md` for the per-file anatomy of a module folder.

## Notes

- The Mermaid diagram and reachability table between `<!-- module-graph:start -->` / `<!-- module-graph:end -->` are **generated**, not hand-drawn. `check:docs-graph` fails `npm run complete` if they drift from the actual import graph.
- `feedback` and `locales` appear isolated in the graph (no inbound or outbound arrows) and are rendered with a dashed style to reflect that.
- The frontend pairing is enforced by `tests/cross-cutting/frontend-pairing.test.ts`: adding a module here without a table entry (or vice-versa) breaks CI; a non-trivial mapping must carry a reason string in the Note column.
- The page intentionally does not define what a module *is*; that belongs to the Theory section. This page only says which pages cover which decisions.
