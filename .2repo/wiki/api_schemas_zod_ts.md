# api/schemas.zod.ts

## Purpose

Zod schema definitions generated by orval v8.22.0 from the `openapi.yaml` contract. It provides runtime validation types for every API endpoint's request body and response envelope (health check, locale manifest, locale CRUD, tenant registry, and per-language message retrieval). The file exists so server-side handlers and test helpers can validate or parse JSON payloads without a separate DTO layer.

## Key elements

- **`GetHealthResponse`** — Zod schema for `GET /health`; asserts the standard `{ success, status, message, data: { status: 'ok' } }` envelope.
- **`GetLocalesResponse`** — Schema for `GET /locales`; validates the full locale manifest including per-locale `tag`, `name`, `nativeName`, `direction`, `active`, `tenants`, `source`, `entryCount`, `revision`, plus top-level `default` and `fallback` BCP 47 tags.
- **`CreateLocaleBody`** — Request-body schema for `POST /locales`; validates `tag`, `name`, `nativeName`, optional `direction`, and `active` (defaults to `true`).
- **`CreateLocaleResponse`** — Schema for the `POST /locales` success envelope; includes derived fields like `baseLanguage` and ISO-8601 timestamps.
- **`GetLocaleTenantsResponse`** — Schema for `GET /locales/tenants`; validates the array of tenant objects (`id`, `label`, `kind`).
- **Regex / numeric constants** — Exported alongside each schema (e.g. `getLocalesResponseDataLocalesItemTagRegExp`, `createLocaleBodyActiveDefault`, `getLocalesResponseDataLocalesItemTenantsItemMax`). These are the building blocks the schemas reference inline.
- **Truncated content** — The file continues past the visible portion with additional schemas (e.g. `GET /locales/{locale}/messages` and likely admin CRUD endpoints for entries).

## Relationships

- **`openapi.yaml`** — Source of truth. orval reads this spec and emits the Zod schemas in this file; the spec version is pinned to 2.0.0 in the generated header.
- **`orval.config.ts`** — The orval pipeline configuration that controls how this file is generated (output path, schema style, etc.).
- **`docs/tools/contract-testing.md` / `docs/tools/contract-request-data.md`** — Documentation that explains how to use these schemas in contract tests and to build request payloads.
- **`tests/support/contract-data.ts`** — Test helpers that likely import or reference these schemas to validate fixtures and responses.
- **`db/demo/assemble.ts`** — Demo data assembly that produces values conforming to these schemas.
- **`src/modules/products/model.ts` / `src/modules/users/model.ts`** — Domain models whose serialized shapes are validated against the endpoint schemas defined here (e.g. product/user error messages flow through the `GetLocalesResponse` envelope pattern).

## Notes

- **Do not edit manually.** The header explicitly states the file is orval-generated; any schema change must go through `openapi.yaml` and a regeneration run.
- **Regexes and numeric bounds are exported separately** so that downstream code (e.g. form validators, test generators) can reuse them without importing the full schema. Their names are mechanically derived from the schema path (e.g. `getLocalesResponseDataLocalesItemTagRegExp`).
- **`Accept-Language` is not modeled per-schema.** The file-level doc block explains that i18n affects only human-readable `message` fields and never the response shape, so no `language` parameter appears in the Zod types.
- **`describe()` strings carry the contract semantics.** Much of the behavioral documentation (tenant capability rules, fallback behavior, `active` flag scope) lives in the schema descriptions rather than in separate docs—read them when reasoning about a field's meaning.
