# asyncapi.yaml

## Purpose

Bundled, read-only AsyncAPI 2.6.0 specification that describes every real-time (SSE) and async-job (RabbitMQ) channel in the boilerplate backend. It is generated by `npm run contracts:bundle` from three source files and serves as the single contract that documents what each channel carries, when, and on which server.

## Key elements

- **Servers** — `sseLocal` (HTTP/SSE on `localhost:3000`) and `rabbitmqLocal` (AMQP on `localhost:5672`).
- **Channels (SSE, subscribe-only):**
  - `observability.metrics.snapshot` — one-shot initial metrics payload on connect.
  - `observability.metrics.updated` — periodic 5 s metrics push.
  - `observability.heartbeat` — 15 s keep-alive with no data.
- **Channels (RabbitMQ, publish + subscribe):**
  - `worker.email.send` — enqueue an email job / worker consumes and sends.
  - `worker.pdf.generate` — enqueue a PDF render job / worker consumes and renders.
- **`components.messages`** — seven message definitions that bind each channel operation to a payload schema.
- **`components.schemas`** — `ObservabilityMetricsPayload`, `EmailJobPayload`, and `PdfJobPayload` define the wire shapes.

## Relationships

- **Generated from** `shared/contracts/asyncapi.root.yaml`, `src/modules/observability/asyncapi.yaml`, and `shared/contracts/asyncapi.workers.yaml` via the `contracts:bundle` script in `package.json`.
- **`asyncapi.public.yaml`** — a sibling spec; both are produced from the same source fragments and are validated together by `spectral.asyncapi.modules.yaml`.
- **`docs/api/contract-fragmentation.md`** — explains how the source YAMLs are split and re-bundled into this file.
- **`docs/api/asyncapi-workflow.md`** — narrative walkthrough of the publish/consume flows described here.
- **`docker-compose.yml` / `docker-compose.production.yml`** — provision the RabbitMQ broker (`localhost:5672`) that the worker channels target.
- **`spectral.asyncapi.modules.yaml`** — the Spectral lint ruleset applied to this file (and its siblings) during contract validation.

## Notes

- **Do not edit by hand.** The header comment marks it as generated output; changes belong in the three source files under `shared/contracts/` and `src/modules/observability/`.
- **Memory units are bytes**, intentionally matching `GET /observability/health`, so dashboards can compare without unit conversion.
- **Email queue is a fallback optimisation, not the system of record.** If the broker is down, the adapter sends inline rather than dropping the message.
- **Rendering failures (email template, PDF) are not retried** — a broken template would starve the queue on every redelivery.
- **`EmailJobPayload.data` / `PdfJobPayload.templateData`** carry already-translated content; locale never travels with the job because the consumer does no i18n resolution.
- The `templateName` / `templatePath` fields use backend-neutral naming (outbox name vs. file path) because the same payload shape is shared with a twin backend that uses a different rendering engine.
